### 1.1 一句话定位

> 牵星是一个 Rust 原生、事件驱动、可确定性回放、插件化扩展的量化交易与回测内核，统一承载多资产、多交易所、多数据源、多账户、多策略、多语言策略和可视化控制；因子、指标和 Alpha 研究能力由 `finkit` 提供，牵星负责把研究结果安全地接入交易生命周期。

## 2. 架构原则

### 2.1 事实唯一性

交易事实只有一个权威来源：按序写入的 `EventLog`。行情、策略决策、订单状态、成交、资金、持仓、费用、风险、对账和控制审计都必须能够追溯到事件、运行和数据版本。

缓存、WebSocket、可视化状态、内存对象、指标结果和数据库投影都不是第二事实源。

### 2.2 事件驱动但不放任事件循环

事件是模块之间的稳定契约，但事件处理必须有：

- 单调序列号和明确排序规则；
- 因果链、来源和幂等键；
- 最大事件数、取消令牌、截止时间和最大因果深度；
- 重复事件、未知事件和非法状态的处理策略；
- 慢消费者、断线、重连和补快照策略。

“事件驱动”不等于“任何模块都可以无限递归地产生事件”。

### 2.3 同一内核覆盖 Backtest / Replay / Paper / Live

四种模式使用同一套领域事件、状态归约、订单生命周期、风险检查和审计模型，仅替换时钟、数据源、撮合/执行适配器、持久化策略和外部副作用策略。

### 2.4 领域内核与适配器隔离

交易领域不依赖具体交易所、数据库、消息中间件、GUI 或 Python 运行时；外部系统通过端口接入，适配器负责协议、重试、限流、认证、映射和故障语义。

### 2.5 研究结果与交易事实隔离

`finkit` 负责因子、指标、特征、Alpha 和研究计算。牵星只接收带有数据版本、时间边界、策略版本和运行上下文的标准化研究结果，不把因子计算逻辑复制进交易内核。

### 2.6 失败必须可解释、可恢复

网络超时、提交结果未知、重复回报、外部状态漂移、部分成交、重启、数据缺口、时钟异常和策略崩溃都必须有明确状态，而不能简单归类为成功或失败。

### 2.7 对开源项目的借鉴边界

牵星借鉴的是成熟项目中经过验证的边界和工程方法，不直接复制其产品定位或代码结构：

| 借鉴方向 | 吸收的设计启发 | 牵星的落地方式 |
|---|---|---|
| Barter | Rust 原生事件驱动、强类型领域模型、统一回测/实盘运行思路、紧凑状态访问 | `EventEngine`、类型化 ID、同一 OMS/风险/账本语义、多模式 EngineNode |
| Lean | 数据、算法生命周期、组合、订单和执行的分层组织 | `StrategyRuntime`、`PortfolioAllocator`、`OMS`、`ExecutionEngine` 的端口边界 |
| NautilusTrader | 事件总线、缓存/组合状态、回测与实盘的同构、可观测运行模型 | EventLog、StateReplica、RunManifest、Replay 和统一运行门禁 |
| Hummingbot | 交易所连接器能力抽象、连接器与策略解耦、连接状态治理 | `VenueAdapter` 能力矩阵、重连、限流、私有回报和对账 |
| 研究型回测框架 | 简洁的策略接口、数据集和报告体验 | `DatasetManifest`、finkit 结果协议、回测报告和可视化投影 |

这些借鉴不改变牵星的核心边界：事实仍由 EventLog 负责，策略不能直接下单，finkit 不被复制进交易内核，可视化不能成为第二事实源。

| 领域 | 牵星负责 |

| 多交易所 | 行情、下单、撤单、查询、私有回报、限流、能力声明和适配器 |
| 多数据源 | 数据源注册、质量、时间边界、优先级、回退、血缘和可重放数据集 |
| 多账户 | 租户、账户、组合、交易所账户、资金、持仓、权限和隔离 |

| 回测 | 时钟、历史数据、撮合、滑点、费用、延迟、保证金、回放和报告 |
| 多语言 | Rust 原生策略、Python/C++ 边界、协议、进程隔离、背压和版本兼容 |
| 插件 | 数据源、交易所、撮合、费用、延迟、风险、分析、持久化和前端扩展点 |
| 可视化 | 查询、快照、增量订阅、回放控制、运行监控和只读投影 |
| 运维 | 健康检查、指标、追踪、审计、配置、恢复、对账和安全门禁 |

### 3.2 不由牵星内核负责的能力

- 因子和指标的完整实现：由 `finkit` 提供。
- 交易所业务规则的最终解释：由交易所适配器和能力声明提供，内核只执行统一契约。
- UI 组件实现：由 Web/Desktop/Notebook 客户端完成，内核只提供查询和订阅模型。
- 大规模数据湖、BI、消息平台和集群编排：属于部署和基础设施层。
- 直接在可视化层修改订单、持仓或 EventLog：禁止绕过控制面。

## 4. 总体分层

### 4.1 分层结构

```text
L0  Interfaces
    qx-api / qx-cli / Rust SDK / Python SDK / C++ SDK / Web / Desktop / Notebook

L1  Control & Application
    Auth / Permission / Command / Audit / Run Management / Scheduler / Config

L2  Engine Runtime
    EventEngine / StrategyRuntime / Clock / Deterministic Queue / Replay / Supervisor

L3  Trading Domain
    qx-core / qx-domain / Portfolio / Ledger / Risk / OMS / Execution / Reconcile

L4  Integration Ports
    MarketDataPort / ExecutionPort / AccountPort / StoragePort / FactorPort / ClockPort

L5  Adapters & Plugins
    CCXT / Binance / A-share / File / Database / NATS / finkit / Python / C++ / GUI

L6  Persistence & Observability
    EventLog / Snapshot / Outbox / StateReplica / Metrics / Tracing / Audit Archive
```

### 4.2 依赖方向

```text
Interface
   ↓
Application / Control
   ↓
Runtime
   ↓
Domain Kernel
   ↓
Ports
   ↓
Adapters / Plugins
   ↓
External Systems
```

依赖只能向下。领域内核不得反向依赖 `qx-api`、GUI、具体数据库、具体交易所或语言运行时。若必须跨层，使用事件、命令或端口接口，不通过隐式全局状态连接。

### 4.4 以最新代码为准的实现判断

1. **事件引擎已经存在，但有两个层次。** `qx-core::Engine` 是确定性测试/回放内核；`qx-runtime::LiveEventPipeline` 是当前实时、Paper 和持久化归约管线。两者都使用 `EventLog` 语义，但还不是一个完全统一的 `EngineNode` 实现。
2. **交易执行引擎已经存在，但执行入口仍需收敛。** `PortExecutionService` 已按应用端口隔离 Venue、订单存储和事件追加；旧 `ExecutionService` 仍直接围绕 `LiveEventPipeline` 编排。目标是让端口化入口成为唯一正式执行入口，再删除或封存旧管线。
3. **运行时事实归约已经较完整。** `LiveEventPipeline` 在追加前刷新共享日志，写入后恢复 OMS/Ledger/去重索引，遇到并发追加冲突会有限重试；这已经形成单节点和多 worker 的基本事实边界，但不是分布式一致性证明。
4. **组合层目前是“可生成调仓计划”，不是完整的多策略组合分配服务。** `qx-portfolio` 的 `RebalancePlan` 已由运行时策略契约调用，但策略预算、跨账户净额、组合级风险聚合和最终 OrderIntent 的统一编排仍需继续收口。
5. **可视化查询链仍未完全接到运行时事实链。** `qx-api::ApiState` 自有 `EventLog`、`ApiEventBus` 和账户快照；CLI 启动 API 时主要从存储加载查询模型，没有发现运行时 `LiveEventPipeline` 自动持续投影到 API 状态的统一桥接。该桥接是 Phase 2 的硬门禁。
6. **当前协议已覆盖账户快照和差量，不等于通用可视化事件协议。** `qx-protocol` 的 `AccountSnapshot`、`SnapshotDiff` 和 `state_hash` 可以作为账户读模型基础，但行情、订单生命周期、运行状态、风险和审计仍需统一投影 envelope。
7. **多语言基础已经落地。** Rust 策略使用 trait，Python/外部策略可用 JSONL、Framed JSON、共享内存 JSON/Columnar，C/C++ 使用 C ABI；运行时还校验策略版本、数据指纹、产物摘要、时间边界和进程超时。发布矩阵、崩溃恢复和生产压力证据仍需完善。
8. **插件体系定位正确但仍是启动期装配。** `qx-plugin` 明确禁止运行期热替换，并具备扩展点、冲突处理、依赖拓扑和签名校验；资源隔离、真实插件实例生命周期和第三方生态仍属于后续产品化工作。
9. **`qx-cli` 仍是当前主要组合根。** 它编排 API、数据、策略、Paper、CCXT、Binance、恢复和 worker；短期可保留，长期应拆成 node/worker、`qxctl` 和研究工具，避免 CLI 成为第二个业务内核。
10. **生产持久化有明确门禁，但高可用仍未完成。** Runtime 对生产配置要求事务型 EventLog/Outbox，并提供 Postgres/NATS 方向；尚未证明多节点写入所有权、故障转移、顺序、幂等和回放一致性。
11. **事件元数据尚未完全统一。** `qx-core::Event` 已有 `seq`、业务/接收/引擎时间、`causation`、`source_seq`、`correlation_id` 和 `EventMetadata`；`run_id`、tenant、portfolio、strategy 等上下文目前主要分散在 `RunManifest`、订单 trace、事件 payload 和运行时 envelope 中，需要形成统一的运行作用域与投影 envelope。
12. **API 服务的连接并发和投影隔离仍需加强。** 当前 `qx-api` 已具备鉴权、mTLS、限流、快照、`/stream` 和读取超时，但服务端接受连接与长连接处理仍需要独立连接任务、有界发送缓冲、心跳和明确的 resync 协议，避免慢客户端影响 API worker。

### 4.5 当前代码证据与验收边界

仓库已提供若干重要测试入口：`qx-xingban/tests/no_lookahead.rs`、`qx-runtime/tests/production_safety.rs`、`qx-cli/tests/process_recovery.rs`、`qx-storage/tests/queue_backend_semantics.rs`、`qx-storage/tests/outbox_backend_semantics.rs`、`qx-zhenlu` 的 Paper/路由/多腿测试，以及 `qx-api` 的查询、权限、mTLS 和 WebSocket 测试。

这些测试证明局部约束和若干链路已经存在，但仍不能替代以下端到端证据：

- `LiveEventPipeline` 产生的事实能自动进入 `StateReplica` 并被 API 查询/订阅；
- 多账户、多策略、多交易所并发时的账户边界和写入所有权；
- 外部下单超时、重复回报、重连和重启后的未知结果闭环；
- Python/C++ 策略崩溃、慢消费者、共享 ring 满载和取消时的副作用安全；
- 分布式 Postgres/NATS 组合下的顺序、重复投递、fencing 和故障转移。

## 5. 端到端主链

### 5.1 市场数据到策略到成交

```text
DataSource
  → DataAdapter
  → DataNormalizer
  → DataQualityGate
  → EventSequencer
  → EventLog
  → EventEngine
  → StrategyRuntime
  → Signal / Target / OrderIntent
  → PortfolioAllocator
  → RiskEngine
  → OMS
  → ExecutionEngine
  → VenueAdapter
  → External Venue
  → ExecutionReport / AccountUpdate
  → EventLog
  → Ledger / Portfolio / StateReplica
  → Query API / WebSocket / Report
```

任何模块都不能跳过 `EventLog` 直接修改另一模块的权威状态。适配器可以产生事实或请求，但不能自行更新组合、账本或可视化状态。

### 5.2 查询与可视化链

```text
EventLog
  → ProjectionReducer
  → StateReplica / AuditStream / Snapshot
  → qx-api Query Service
  → Web / Desktop / Notebook / CLI
```

实时订阅的事件总线只是传输缓存，不是事实来源。客户端断线后必须通过 `snapshot + cursor` 恢复，不能依赖“从断点之后碰巧收到的缓存事件”。

### 5.3 控制命令链

```text
Client Command
  → qx-api Auth / Permission / RateLimit
  → CommandValidator
  → CommandQueue / Idempotency
  → Engine Command Handler
  → Domain Decision
  → EventLog
  → State Projection
  → Command Result / Audit Record
```

例如启动、暂停、停止、撤单、重试、重同步、切换数据源、运行回测等都必须经过控制面，并产生可审计的命令记录和结果事件。

## 6. 统一运行模型

### 6.1 EngineNode

`EngineNode` 是一个可运行的交易内核实例，至少包含：

- `RunManifest`：运行 ID、模式、策略、账户、数据集、配置、版本和能力声明；
- `EventEngine`：事件排序、调度、分发、归约和回放；
- `StrategyRuntime`：策略加载、隔离、生命周期和输出校验；
- `Portfolio/Ledger`：持仓、余额、现金流、费用和权益；
- `RiskEngine`：订单前、持仓后、组合级和账户级风险检查；
- `OMS`：订单意图、订单状态、执行尝试、成交和撤单；
- `ExecutionEngine`：执行算法、拆单、路由、重试、限流和回报归一化；
- `ReconcileService`：外部订单、资金、持仓和本地状态对账；
- `Storage`：EventLog、Snapshot、Outbox、Checkpoint；
- `Supervisor`：启动、恢复、降级、停止和故障隔离。

### 6.2 运行模式

| 模式 | 时钟 | 数据 | 执行/撮合 | 外部副作用 |
|---|---|---|---|---|
| Backtest | 历史事件时钟 | 固化数据集 | 模拟撮合 | 禁止真实下单 |
| Replay | 事件回放时钟 | EventLog/归档 | 可选模拟执行 | 默认禁止 |
| Paper | 实时/模拟时钟 | 实时行情 | 模拟成交 | 不触达真实交易所 |
| Live | 实时单调时钟 | 实时行情和私有回报 | 真实适配器 | 需权限、限额和对账 |
| Sandbox | 实时单调时钟 | 沙盒交易所 | 沙盒适配器 | 仅沙盒账户 |

模式不能通过散落的 `if live` 分支实现。差异必须通过 `ClockPort`、`MarketDataPort`、`ExecutionPort`、`StoragePort` 和 `SideEffectPolicy` 注入。

### 6.3 生命周期状态机

```text
Created
  → ConfigValidated
  → DependenciesReady
  → Recovered
  → Reconciled
  → Running
  → Degraded ───────────────┐
  → Stopping → Stopped       │
       ↑                     │
       └──── Resume / Repair ┘
```

在 `Reconciled` 之前，Live 模式不得放行真实订单。在 `Degraded` 状态下只允许白名单操作，例如撤单、查询、对账和人工恢复；不允许策略继续扩张风险。

## 7. EventEngine 设计

### 7.1 事件分类

```text
MarketEvent       行情、盘口、成交、资金费率、公司行为
TimerEvent        时间驱动、日切、策略定时器
StrategyEvent     信号、目标、订单意图、策略状态
RiskEvent         风险检查、拒绝、限额变更、风控状态
OrderEvent        提交、接受、拒绝、撤单、部分成交、完成
ExecutionEvent    执行尝试、路由、成交回报、未知结果
LedgerEvent       余额、持仓、现金流、费用、权益
ReconcileEvent    外部状态、差异、同步结果、恢复决策
ControlEvent      启动、暂停、停止、重放、重同步、配置变更
AuditEvent        权限、命令、策略、数据和外部副作用审计
```

### 7.2 事件信封

所有跨模块、跨进程或持久化事件都应包含等价字段：

```text
schema_version
event_id
kind
run_id
tenant_id
account_id
portfolio_id
strategy_id
venue_id
instrument_id
occurred_at
received_at
event_seq
causation_id
correlation_id
idempotency_key
source
lineage
payload
```

`event_seq` 是事实流顺序，`cursor` 是客户端消费位置，`state_hash` 是投影状态校验值，三者不可混用。

### 7.3 处理流程

```text
Ingress
  → Validate
  → Normalize
  → Assign Sequence
  → Persist Event
  → Reduce Domain State
  → Emit Derived Events
  → Snapshot / Checkpoint
  → Publish Projection
```

推荐基线为单引擎、单写入者、可确定性队列；扩展到多进程或分布式时，仍必须保留每个 `run/account` 的明确所有权和顺序边界。

### 7.4 防死循环和失控事件

每次 `Engine.run` 或回放任务都必须支持：

- `max_events`：单次运行最大处理事件数；
- `CancellationToken`：用户、系统或超时取消；
- `deadline`：绝对截止时间；
- `max_causal_depth`：派生事件最大因果深度；
- 重复 `idempotency_key` 检测；
- 调度队列大小上限和拒绝策略；
- 单策略、单插件、单事件处理耗时上限；
- 终止原因写入运行结果和审计流。

调度器、插件依赖和事件派生链都必须做环检测。编译期或启动期拓扑检测不能替代运行期预算和取消机制。

## 8. ExecutionEngine 设计

### 8.1 执行边界

```text
Target / Signal
  → OrderIntent
  → Portfolio Allocation
  → PreTrade Risk
  → OrderRequest
  → OMS
  → Execution Algorithm
  → Route Selection
  → Venue Adapter
  → External Request
  → Ack / Reject / Unknown
  → Private Stream / Polling
  → Normalized Execution Fact
  → OMS / Ledger / Portfolio / Reconcile
```

### 8.2 订单生命周期

```text
Created
  → RiskPending
  → RiskApproved / RiskRejected
  → SubmissionPending
  → SubmissionAttempted
  → Accepted / Rejected / Unknown
  → Working
  → PartiallyFilled
  → Filled / Cancelled / Expired
  → Reconciled
```

`Unknown` 是正式状态，不得把网络超时直接当作失败并立即重复下单。恢复策略为查询、私有流确认、幂等键匹配、人工介入或补偿动作，并在 EventLog 中保留所有尝试。

### 8.3 多腿和跨市场执行

多腿订单可以由 `OrderGroup` 管理父子关系、依赖、完成条件和补偿策略，但在不同交易所之间默认不宣称原子成交。必须显式标记：

- `Atomicity = None | VenueScoped | Simulated`；
- 腿之间的最大允许偏差；
- 失败后的撤销、反向、暂停或人工接管策略；
- 每条腿的独立订单和成交事实。

## 9. 领域模块与 Crate 边界

| Crate / 模块 | 责任 | 不负责 |
|---|---|---|
| `qx-core` | 事件、时钟、状态、标识、确定性内核、基础端口 | 具体交易所、HTTP、GUI |
| `qx-domain` | 对外领域类型重导出和兼容边界 | 另建一套事实模型 |
| `qx-application` | 用例编排、运行命令、策略到订单流程 | 具体网络协议 |

| `qx-data` / `qx-provider` | 数据读取、标准化、质量、数据源注册 | 组合和订单状态 |
| `qx-guanxing` | 行情接入、数据转换和市场数据域 | 交易执行 |
| `qx-strategy` | 策略生命周期、上下文、输出契约 | 直接访问交易所 |
| `qx-factor` | finkit 接口、因子结果适配、研究血缘 | 复制 finkit 算法库 |
| `qx-portfolio` | 目标权重、组合分配、再平衡、约束 | 交易所下单 |
| `qx-risk` | 订单前、组合、账户、保证金和限额检查 | 直接写账本 |
| `qx-oms` | 订单、订单组、状态机、幂等和执行事实 | 具体 REST/WebSocket |
| `qx-execution` | 执行算法、拆单、路由、重试和外部执行端口 | 自建第二套 OMS |
| `qx-adapter` | 交易所、经纪商、外部协议适配 | 修改领域权威状态 |
| `qx-xingban` | 回测时钟、撮合、滑点、费用、报告 | 另建实时订单模型 |
| `qx-storage` | EventLog、Snapshot、Outbox、投影存储和恢复 | 业务规则 |
| `qx-protocol` | 跨语言、跨进程、账户/事件/策略线协议 | 绑定某个 UI |
| `qx-control` | 权限、命令、审计、配置、控制面 | 直接持有交易事实 |
| `qx-api` | 查询、控制、快照、订阅、鉴权入口 | 作为第二事实源 |
| `qx-scheduler` | 计划任务、依赖、重试、取消和拓扑检查 | 无限自触发 |
| `qx-plugin` | 插件清单、依赖、能力、加载和版本校验 | 任意运行期热替换 |
| `qx-python` | Python 边界、进程/线程隔离、协议和背压 | 绕过策略契约 |
| `qx-cli` | 启动、诊断、导入导出、管理命令 | 永久承载所有业务服务 |

### 9.1 拆分决策

当前优先进行“职责、文件、端口和测试边界”的逻辑拆分；暂不为了目录数量而拆成多个进程。以下边界必须先稳定：

- `EventEngine` 与 `ExecutionEngine`：逻辑独立、同进程运行；
- `OMS` 与 `ExecutionAdapter`：状态机独立、协议适配独立；
- `Portfolio/Ledger` 与 `RiskEngine`：账本产生事实，风险只做决策；
- `qx-api` 与投影层：API 只读 `StateReplica` 和审计流；
- `qx-runtime` 与 `qx-execution`：收敛重复的旧管线，保留单一执行入口；
- `qx-cli`：逐步拆为节点运行、控制命令和研究工具，但不改变领域 API。

只有在并发隔离、故障域、部署伸缩或语言边界确实需要时，才升级为独立进程或服务。

## 10. 插件化架构

### 10.1 插件平面

```text
Engine Plugin Plane
  DataSource / MarketData / Venue / Matcher / Fee / Slippage / Latency
  RiskRule / ExecutionAlgo / Persistence / Analytics / Notification

Strategy Language Plane
  Rust / Python / C++ / WASM（按安全性和性能需要选择）

Visualization Plane
  Chart / Panel / Report / Dashboard / Notebook renderer（只读）

Research Plane
  finkit Factor / Indicator / Alpha / Dataset operator
```

四个平面必须隔离。可视化插件不能成为交易插件；因子插件不能直接写 OMS；策略插件不能直接改账本。

### 10.2 插件契约

插件清单至少包含：

```text
plugin_id
version
api_version
kind
capabilities
dependencies
conflicts
configuration_schema
required_permissions
determinism
resource_limits
```

启动时进行 API 版本、依赖拓扑、冲突、签名、能力和配置校验。第一阶段采用启动时加载，禁止任意运行期替换核心执行组件；热更新只能作为后续受控能力。

### 10.3 插件失败策略

插件超时、崩溃、产出非法事件、读取越权数据或违反资源预算时，必须隔离该插件并产生 `PluginFault`。交易核心根据插件类型进入拒绝新单、降级、暂停或恢复流程，不能静默吞错。

## 11. 多交易所与多数据源

### 11.1 交易所适配器能力

每个 `VenueAdapter` 必须声明并测试：

- 行情：快照、增量、成交、盘口深度、时间戳和序列号；
- 交易：限价、市价、条件单、撤单、改单、批量操作；
- 私有回报：订单、成交、余额、持仓、手续费；
- 查询：订单、成交、余额、持仓和历史记录；
- 限流、签名、权限、时钟偏差和重连；
- 精度、最小数量、价格步长、保证金和交易日历；
- 沙盒、实盘、区域和账户类型差异。

不能把“支持 CCXT”或“支持某交易所 REST”直接等同于“已完成生产交易能力”。生产门禁必须包含沙盒或小额验证、重启恢复、未知结果、私有流断线和对账测试。

### 11.2 数据源统一入口

```text
ProviderRegistry
  → DatasetManifest
  → Calendar / CorporateAction / InstrumentMaster
  → SourcePriority
  → Normalizer
  → QualityGate
  → Cache / Archive
  → Data Event
```

数据集必须能说明：来源、版本、覆盖区间、时区、复权方式、缺失值处理、更新时间、校验和、权限和血缘。实时数据与研究数据使用同一领域标识体系，不能因为来源不同而形成两套 `Instrument`、`Account` 或 `Timestamp` 语义。

### 11.3 Point-in-Time 原则

回测和研究必须按当时可获得的数据重建，禁止未来数据泄露、事后复权信息倒灌和跨源时间错位。质量门禁至少检查：

- 数据时间与接收时间；
- 交易日历与时区；
- 修订数据版本；
- 盘口/成交顺序；
- 停牌、涨跌停、合约到期和换月；
- 缺失与异常值处理。

## 12. 多账户、多组合、多策略

### 12.1 身份层级

```text
Tenant
  → User / Role
  → Account
  → Portfolio
  → StrategyRun
  → VenueAccount / SubAccount
  → Instrument Position / Order / Ledger
```

所有订单、成交、资金、持仓、策略输出和审计记录都必须带有明确的 `tenant_id/account_id/portfolio_id/strategy_id/run_id`。禁止在多账户场景共享可变的全局余额、持仓或风控状态。

### 12.2 多策略资金分配

策略输出分三层：

1. `Signal`：研究或交易信号，不代表下单。
2. `Target`：目标仓位、目标权重或目标风险暴露。
3. `OrderIntent`：经组合分配和约束后可进入风控的订单意图。

策略不得直接获得交易所客户端。组合分配器负责资金、风险预算、策略冲突、净额合并、最小交易单位和优先级；风险引擎仍对最终订单逐笔和组合级检查。

### 12.3 隔离与公平性

至少支持：策略级预算、账户级限额、组合级净敞口、单品种集中度、优先级、公平调度、熔断和人工禁用。一个策略异常不能覆盖其他策略的订单或账本。

## 13. 多语言策略运行时

### 13.1 策略协议

语言无关的策略协议包括：

```text
on_init(Context)
on_market(MarketEvent)
on_timer(TimerEvent)
on_order(OrderEvent)
on_account(AccountSnapshot)
on_shutdown(ShutdownContext)
```

策略输出只能是 `Signal`、`Target`、`OrderIntent`、`StrategyState` 或诊断事件，不允许直接提交 HTTP 下单请求。

### 13.2 Rust、Python、C++ 边界

| 语言 | 默认方式 | 适用场景 | 必备约束 |
|---|---|---|---|
| Rust | 进程内 trait / 原生插件 | 低延迟、核心策略 | panic 隔离、资源预算、API 版本 |
| Python | 进程外协议或受控嵌入 | 研究、快速迭代、Notebook | 超时、背压、序列化、崩溃恢复 |
| C++ | C ABI/进程外协议 | 既有策略、低延迟库 | ABI 版本、内存边界、线程模型 |
| WASM（后续） | 沙箱 | 不可信或跨平台策略 | 能力限制、燃料预算、无任意 IO |

协议必须支持版本协商、批量事件、心跳、取消、背压、错误码、策略重启和状态恢复。语言绑定不能成为第二套策略语义。

## 14. 回测与研究链

### 14.1 回测主链

```text
DatasetManifest
  → HistoricalDataProvider
  → SimClock
  → EventEngine
  → StrategyRuntime
  → Risk / OMS
  → MatchingEngine
  → Fee / Slippage / Latency / Margin
  → Ledger / Portfolio
  → EventLog / Snapshot
  → Metrics / Report / Visualization
```

回测撮合必须显式声明撮合模型：Bar、Tick、L1、L2、成交量参与率或自定义模型。每次结果必须携带数据集、策略、配置、代码版本、随机种子、成本模型和运行 ID。

### 14.2 finkit 接入边界

```text
finkit
  → FactorFrame / FeatureSet / AlphaResult
  → DatasetVersion + TimeSemantics + Lineage
  → qx-factor Adapter
  → Strategy Context / Target
```

牵星只负责生命周期、时间边界、缓存、协议和交易接入；不在 `qx-factor` 中复制 finkit 的指标实现。若因子计算失败、版本不兼容或血缘缺失，策略输出必须进入拒绝、降级或人工确认流程。

## 15. 可视化、查询与控制面

### 15.1 可视化的定位

可视化是 EventLog 的只读投影和控制面客户端，不是交易领域模块，不建立第二条订单、账本或事件事实链。

可视化能力可以以逻辑模块存在，当前不要求新增 `qx-viz`、`qx-server` 或 `qx-backtest` crate；其能力由 `qx-api`、`qx-control`、`qx-protocol`、`qx-storage` 和客户端组合提供。

### 15.2 查询模型

查询服务至少分为：

- 运行：运行状态、模式、策略、数据集、配置、健康度；
- 市场：行情、盘口、成交、数据质量和数据延迟；
- 交易：订单、订单组、执行尝试、成交、撤单和未知状态；
- 账户：余额、持仓、保证金、权益、费用和账本；
- 风险：限额、暴露、保证金、拒绝原因和熔断；
- 研究：因子版本、数据血缘、回测报告和指标；
- 审计：控制命令、权限、策略版本、外部副作用和恢复操作。

### 15.3 快照、增量和断线恢复

订阅协议必须支持：

```text
Subscribe(filter, from_cursor)
  → Snapshot(snapshot_seq, state_hash)
  → Delta(event_seq, cursor)
  → Heartbeat
  → ResyncRequired(snapshot_seq)
```

服务端采用有界缓冲、慢消费者断开或降级、心跳、鉴权过滤和并发连接处理。HTTP/WebSocket 不能阻塞主事件循环，API 连接不能持有领域可变锁直到网络发送完成。

### 15.4 控制面安全

启动、暂停、停止、撤单、重放、重同步、切换配置和实盘放行都必须：

- 经过身份认证和权限检查；
- 具备幂等键和请求超时；
- 写入审计日志；
- 返回命令接受、执行中、成功、失败或需要人工处理的明确状态；
- 对真实副作用提供二次确认、限额和环境标记。

## 16. 存储、恢复与一致性

### 16.1 核心存储对象

```text
EventLog      事实事件，顺序写入，可回放
Snapshot      领域状态快照，带 event_seq/state_hash
Outbox        需要可靠投递的外部副作用
StateReplica  查询和可视化投影
Checkpoint    策略、投影、数据和运行进度
AuditArchive  权限、命令、配置和外部动作
```

### 16.2 一致性等级

| 等级 | 用途 | 要求 |
|---|---|---|
| Local | 本地开发、快速回放 | 可重建、不可宣称生产持久性 |
| Durable | 单节点实盘基线 | 事务写入、恢复、校验和、备份 |
| Replicated | 多节点或高可用 | 主从/共识、幂等、故障转移和顺序证明 |
| External | 外部交易所最终状态 | 查询、私有流、对账和人工仲裁 |

不能因为使用了 Postgres、NATS 或某个消息队列，就自动宣称已经完成分布式一致性。必须说明写入顺序、重复投递、故障恢复、消息丢失和外部状态漂移的处理。

### 16.3 恢复流程

```text
Load RunManifest
  → Verify Config / Version
  → Load Snapshot
  → Replay EventLog After Snapshot
  → Restore Checkpoints
  → Reconnect Adapters
  → Query External State
  → Reconcile
  → Enable Side Effects
```

恢复前禁止继续产生不可逆外部副作用；恢复结果、差异和人工决策必须形成事件和审计记录。

## 17. 安全、运维与可观测性

### 17.1 安全边界

- 租户、用户、账户、策略和插件权限分层；
- 密钥进入密钥管理系统，不写入 EventLog、日志或策略上下文；
- 外部交易连接支持 TLS、时钟校准、权限最小化和 IP/环境限制；
- Python、C++ 和第三方插件默认按不可信边界处理；
- 所有真实副作用携带 `run_id`、`account_id`、环境和幂等键。

### 17.2 可观测性

指标至少覆盖：

- 数据延迟、缺口、乱序、质量和重连；
- 事件吞吐、队列深度、处理延迟、因果深度和丢弃；
- 策略耗时、错误、重启和输出拒绝；
- 风险拒绝、订单状态、执行延迟、成交率、未知结果；
- EventLog 写入、投影延迟、快照、恢复和对账差异；
- WebSocket 连接数、慢消费者、重同步和错误；
- 插件资源、崩溃、版本和能力冲突。

所有日志、指标、追踪和报告都应能通过适用的 `run_id`、`event_id`、`correlation_id`、`account_id` 和 `strategy_id` 串联；市场级、系统级事件不强制携带不存在的策略或账户身份。

## 18. 当前实现基线与主要缺口

以下结论来自当前仓库审计，必须与“目标架构”区分：

| 能力 | 当前判断 | 主要缺口 |
|---|---|---|
| 确定性内核 | 已有基础 | 运行预算、取消和事件环保护需要补齐 |
| 回测/撮合 | 已有代码链路 | 统一事件、报告和真实边界仍需验收 |
| OMS/Ledger | 已有核心实现 | 多管线重复、跨场景一致性测试不足 |
| Paper | 基本具备 | 产品化恢复、限流和运行控制需完善 |
| CCXT/Binance | 有接入基础 | 沙盒、未知结果、重连和对账需实证 |
| A 股数据 | 有研究链路 | 尚未完全统一到实时/回测数据平面 |
| 多腿 | 有组合/腿/恢复模型 | 不具备跨交易所原子成交语义 |
| 多账户 | 有领域模型基础 | 隔离、权限、资金归属和运维门禁需加强 |
| 多语言 | 有协议和适配方向 | SDK、版本、背压、崩溃恢复和发布矩阵需补齐 |
| 插件 | 有加载和依赖基础 | 能力声明、签名、资源隔离和故障策略需完善 |
| 可视化 | API、控制和协议已有基础 | `EventLog → ProjectionReducer → StateReplica → qx-api` 桥接需落地 |
| 生产 HA | 设计方向存在 | 写入所有权、故障转移和一致性证明未完成 |

当前不能把“存在 crate、路由或适配器”直接等同于“生产能力已完成”。完成度必须以端到端场景、恢复、对账和压力测试为准。

## 19. 分阶段改造计划

### Phase 0：架构基线与证据治理

- 本文作为总架构基线；建立术语、事件、命令、状态和版本规范；
- 为每条主链建立测试入口和完成度证据；
- 标出所有“设计存在但未实现/未验收”的能力；
- 禁止新增重复事实模型和第二套执行管线。

**门禁**：所有目标能力都有责任模块、事实源、入口、恢复策略和验收用例。

### Phase 1：内核边界收敛

- 收敛 `qx-runtime` 与 `qx-execution` 的重复运行管线；
- 固化 `EventEngine`、`OMS`、`Portfolio/Ledger`、`RiskEngine` 和 `ExecutionEngine` 端口；
- 为 `Engine.run` 增加预算、取消、截止时间、因果深度和终止原因；
- 清理领域对 API、GUI 和具体适配器的反向依赖。

**门禁**：Backtest、Paper、Replay 使用同一领域事件和 OMS 生命周期。

### Phase 2：事件与投影闭环

- 打通 `EventLog → ProjectionReducer → StateReplica/AuditStream → qx-api`；
- 统一快照、游标、状态哈希和重同步协议；
- 将 API 内部事件总线降级为传输缓存；
- 增加事件重复、乱序、断线和快照恢复测试。

**门禁**：可视化显示的每个交易状态都能回溯到事件和运行。

### Phase 3：执行与对账可靠性

- 统一订单提交、执行尝试、未知结果、私有回报和查询补偿；
- 增加幂等键、客户端订单号、重试预算和人工接管；
- 统一资金、持仓、费用和成交的账本归约；
- 完成 Paper、Sandbox、Live 的故障注入和恢复测试。

**门禁**：网络超时、重启、断线和重复回报不导致重复下单或账本漂移。

### Phase 4：多资产、多交易所、多账户

- 完善 Instrument/Venue/Account/Portfolio/StrategyRun 身份体系；
- 对每个适配器完成能力矩阵和生产门禁；
- 实现账户隔离、策略预算、组合分配、风险聚合和对账；
- 对多腿明确原子性边界和补偿策略。

**门禁**：两个账户、两个交易所、两个策略并行运行时，状态、权限和风险不串扰。

### Phase 5：数据与研究闭环

- 统一实时、历史、回测和研究数据的标识与时间语义；
- 接入 finkit 的因子结果协议、版本、血缘和 Point-in-Time 校验；
- 固化 DatasetManifest、RunManifest、报告和可复现运行；
- 验证 A 股、加密、期货等不同资产的日历、精度和公司行为语义。

**门禁**：研究结果可以复现，并能安全进入策略目标与交易链。

### Phase 6：控制面与可视化产品化

- 完成查询模型、实时订阅、慢消费者、心跳、断线重同步；
- 完成启动、暂停、停止、撤单、重放、重同步和恢复命令闭环；
- 统一 Web/Desktop/Notebook/CLI 的权限、审计和版本；
- 形成回测报告、实盘监控和事件回放的共同视图。

**门禁**：客户端不能绕过控制面改变交易事实，且所有控制动作可审计。

### Phase 7：插件与多语言产品化

- 固化插件清单、版本、依赖、签名、权限和资源预算；
- 完成 Rust/Python/C++ 协议、SDK、示例、崩溃恢复和发布矩阵；
- 形成数据、交易所、风控、执行、撮合、费用、可视化插件模板；
- 对第三方策略和插件提供沙箱与能力白名单。

**门禁**：插件或策略故障可隔离，不破坏 EventLog、OMS 和账本。

### Phase 8：性能、HA 与生态扩展

- 按 `run/account` 明确单写入者和分片边界；
- 评估多进程、分布式 EventLog、复制投影和故障转移；
- 完成基准测试、容量模型、混沌测试和升级回滚；
- 再考虑热插拔、WASM、集群调度和更多外部生态。

**门禁**：高可用扩展不会改变单节点确定性语义，且能证明顺序、幂等和恢复正确性。

## 20. 验收矩阵

### 20.1 必须打通的主场景

| 场景 | 验收结果 |
|---|---|
| 历史数据 → 策略 → 模拟成交 → 报告 | 可重复、无未来数据、事件可回放 |
| 实时行情 → 策略 → Paper 订单 → 模拟成交 | 与回测使用同一 OMS/风险语义 |
| 实时行情 → Live 订单 → 私有回报 → 账本 | 具备权限、限流、未知结果和对账 |
| 多数据源故障切换 | 数据血缘、优先级和缺口可解释 |
| 多交易所并行 | 适配器隔离、能力声明、状态不串扰 |
| 多账户多策略 | 资金、风险、权限和事件隔离 |
| Python/C++ 策略崩溃 | 策略隔离、取消、恢复、无重复副作用 |
| API/WebSocket 断线 | 快照、游标、重同步、慢消费者安全 |
| 进程重启 | EventLog 重放、外部对账、恢复门禁 |
| 多腿执行失败 | 原子性边界明确，补偿策略可审计 |

### 20.2 三轮架构检查

每次大改前后至少执行三轮：

1. **结构轮**：每个模块是否有唯一责任、唯一事实源和清晰上游/下游。
2. **流程轮**：从数据、策略、风控、订单、成交、账本到 UI 是否存在断链、旁路或孤儿逻辑。
3. **故障轮**：超时、重复、乱序、断线、重启、未知结果、慢消费者、插件崩溃和无限派生是否有终止与恢复路径。

检查结果必须记录为可追踪问题，而不是只在文档中标记“理论支持”。

## 21. 明确禁止的架构退化

- 不为可视化另建一套订单、账本或事件事实源；
- 不让策略直接调用交易所 API 或绕过风险与 OMS；
- 不在 `qx-factor` 中复制 finkit；
- 不为每种运行模式复制一套 Engine；
- 不用字符串到处传递账户、交易所、合约和策略身份；
- 不把网络超时直接当成失败并无条件重下；
- 不把 WebSocket 推送缓存当成可恢复事实流；
- 不把 crate 数量增加当作架构拆分完成；
- 不在没有顺序、幂等和恢复证明前宣称完成分布式 HA；
- 不把“能编译”“有路由”“有适配器”当作生产能力验收。

## 23. 术语表

| 术语 | 含义 |
|---|---|
| EventEngine | 负责事件排序、调度、分发、归约、回放和生命周期的逻辑引擎 |
| ExecutionEngine | 负责订单意图到外部执行及回报归一化的逻辑引擎 |
| EventLog | 交易和运行事实的顺序事件日志 |
| StateReplica | 从事实事件归约出的查询和可视化状态 |
| OMS | 订单与订单组生命周期管理 |
| Ledger | 余额、持仓、现金流、费用和权益的账本归约 |
| RunManifest | 描述一次回测、回放、Paper 或 Live 运行的不可变元数据 |
| DatasetManifest | 描述数据来源、版本、时间、质量和血缘的数据集元数据 |
| OrderIntent | 经策略和组合分配产生、尚未经过风险放行的订单意图 |
| Unknown | 外部副作用结果无法确认的正式状态 |
| Projection | 从事实事件生成查询、监控和报表模型的过程 |
| finkit | 独立的因子、指标、Alpha 和研究计算项目 |

## 24. 最终结论

牵星的核心不是若干交易所连接器、回测脚本或可视化页面的集合，而是一个有明确事实源、确定性事件处理、统一订单生命周期、可恢复外部执行和插件化边界的交易内核。

最终目标可以归纳为：

```text
One Domain Model
+ One Event / Fact Stream
+ One OMS / Risk / Ledger Semantics
+ One Engine for Backtest / Paper / Live
+ Many Data Sources / Venues / Accounts / Strategies / Languages
+ Read-only Projection for Visualization
+ finkit for Factor and Indicator Computation
```

在 `EventLog → Engine → OMS/Risk/Ledger → Projection/API` 主链真正闭合、未知结果和恢复语义完成、插件和多语言边界通过验收之前，牵星应被称为“可扩展的交易内核建设中”，而不是宣称所有生产级能力已经完成。
