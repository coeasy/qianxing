## 1. 项目主要功能梳理（当前代码实际提供什么）

- **内核与账本**：定点数 `Money/Quantity/BasisPoints`、订单与成交域模型、事件日志与多类账本投影（现金、持仓、权利、订阅、公司行为）——`crates/qx-core`（4,591 行 src）。
- **行情与数据**：BarFrame / 深度帧格式与校验、数据集清单与指纹、A 股与 CCXT 事实面——`qx-datastruct` / `qx-data` / `qx-guanxing` / `qx-provider`。
- **回测**：Bar、Tick、订单簿、A 股四套引擎 + 快速回测（多线程复用同一入口）+ 深度档回测——`qx-xingban`（8,216 行 src）。
- **策略**：内置策略、原生 Bar 策略宿主、跨语言（Python/C）策略契约与 worker——`qx-strategy` + `crates/qx-cli/src/strategy_*.rs`。
- **风控**：`qx-risk` 的 `RuleSet` 与 `qx-zhenlu` 的 `RiskGate`（回测 / paper / 实盘共用构造函数）。
- **执行**：`ExecutionGateway` 统一端口、venue 提交契约、回报与对账端口——`qx-execution` + `crates/qx-cli/src/venue_runtime/`（Binance / CCXT / Paper 三条提交链）。
- **运行时**：配置面、worker 策略与监督、事件管线、调度——`qx-runtime`（6,555 行）+ `qx-scheduler` + `qx-orchestrator` + `qx-control`。
- **存储**：文件 / SQLite / Postgres 三态的事件日志、控制面、命令队列、outbox、消费者状态——`qx-storage`（8,672 行）。
- **对外接口**：单一 `qx-cli` binary（18,298 行 src）承载约 40 个命令 + `qx-api` HTTP 服务。
- **Python 侧**：`python/qianxing_bridge` + pyo3 原生扩展 `_qianxing_native`（由 `crates/qx-python` 以 `crate-type=["cdylib"]` 产出，`tools/build_python_wheel.sh:12`）。

## 2. 架构现状与依赖事实

- 27 个 crate 全部在 workspace 成员表内（`Cargo.toml:14-40`），均被 `qx-cli` 直接或间接依赖。
- 分层事实上是"内核 → 领域 → 基础设施 → 编排 → 门面"，但**存在大量薄壳 crate**：`qx-oms` 171 行、`qx-application` 356 行、`qx-portfolio` 283 行、`qx-fenye` 464 行、`qx-genglu` 559 行、`qx-plugin` 583 行、`qx-risk` 645 行——七分之一个 workspace 的 crate 不足 700 行。
- 体量高度集中在 `qx-cli`：18,298 行 src，占全 workspace src 的约 22%；`maturity/line_budgets.yaml` 仍登记 37 个超 500 行文件，首位 `qx-runtime/src/lib.rs` 3,660（V9 §8.3 的"下一轮真拆分目标"两个仍未动）。
- 概念重名多：`qx-zhenlu`(2,210) 与 `qx-genglu`(559)、`qx-guanxing`(783)、`qx-fenye`(464) 等以中文代号命名，职责需读码才能判定（`qx-fenye` 的用途在代码内无自述）。

## 3. 主体链路走查（贯通判定，逐条给证据）

### A. 行情 → 信号 → 风控 → 提交 → 成交 → 账本 → 持久化

- 已接线：stream worker 写 `LiveEventPipeline`（`venue_runtime/binance_stream_worker.rs:38-49,127-136`）；成交经 `apply_fill` 落账（`qx-runtime/src/pipeline.rs:1146,1427`）；策略 worker 构造订单时过 `RiskGate`（`strategy_contract.rs:550-552,669-671`，与回测同一 `strategy_risk_gate` 构造器 `runtime_wiring.rs:99-147`）；提交点带租约 / fencing，先写 EventLog 再调 venue（`venue_runtime/binance_submit.rs:251-332`）。
- **P0 断点（D1）**：`worker_risk_context` 在 `instrument_spec_path` 缺失时 `return Ok(None)`（`venue_runtime/worker_runtime.rs:22-26`），调用方 `execute_submit_order_with_worker_risk` 随即走**不带风控的** `execute_submit_order`（同文件 :214-221）。同一缺口在 paper 侧是显式拒绝：`FAIL_CLOSED: Paper worker 缺少风控配置（instrument_spec_path），拒绝提交订单`（`paper_submit.rs:118-127`）。即：**Binance / CCXT 实盘链存在静默降级的无风控提交路径**。
- 结构性事实：回测从不穿过 gateway，撮合在引擎内部完成（`qx-xingban/src/backtest.rs:724-735`）。所谓"同源"目前只保证**同一规则集构造**，不保证**同一执行代码路径**。

### B. 回测链

- 已接线：`strategy backtest` 与 `fast-backtest` 同一内核（`backtests/fast_backtest.rs:56` → `strategy_backtest.rs:132` → `BacktestEngine`），provider / dataset 指纹校验为真校验（`strategy_backtest.rs:29-54`）；Python worker 的信号在 Rust 侧过风控，跨语言无绕过（契约用例 `src/tests/e2e_and_python_contract.rs:385-407`）。
- **P0 不一致（D2）**：`multi-builtin` 用 `strategy_risk_gate(None, true)`（`backtests/multi_builtin.rs:154`）、depth 用 `strategy_risk_gate(None, false)`（`backtests/depth.rs:65`），两者都**不读** `config.strategy.risk_rules`；只有单策略 / strategy / fast 三条链吃配置（`backtests/single_strategy.rs:86-96,149`）。
- 深度链另用 `TickBacktestEngine` / `OrderBookBacktestEngine` 两套撮合（`depth.rs:69,81`），"同一内核"的表述对深度档不成立。

### C. 多腿 / spread 屏障

- 已接线：策略 worker 在腿数 ≥2 时先落组快照再入队（`workers.rs:618-650` → `spread.rs:12-39`）；**所有** 提交点执行前调用屏障（`binance_submit.rs:120,275`、`ccxt_execution.rs:125`、`paper_submit.rs:93`、`paper_worker.rs:160`），缺快照即拒（`spread.rs:48-73`）；崩溃后按 EventLog 事实做对冲收口（`spread.rs:158-226`）。
- 残留缺口：屏障只作用于携带 `spread_group_id` 的命令（`spread.rs:49-51`）。调用方手工构造两条单腿命令即可组成"事实上的对"而不受组约束；且该约束住在 CLI 层，网关（`qx-execution/src/lib.rs:1223`）自身不设防。

### D. 持久化与恢复

- 已接线：默认文件 EventLog（`runtime_wiring.rs:72-78`），EventLog / 控制面 / 命令队列 / 任务队列按配置切 SQLite / Postgres（`runtime_wiring.rs:25-79`、`configured_backends.rs:57-154,232-274`），特性未编译时显式报错而非静默降级（`configured_backends.rs:64-70`）。
- 覆盖：跨后端语义契约用例存在，CI 里 `service-backends` 作业已定义 postgres:16-alpine + nats:2.10-alpine 服务并跑 `cargo test -p qx-storage --features sqlite,postgres,nats -- --ignored --test-threads=1`（`.github/workflows/ci.yml:113-167`）。**但该作业在 GitHub 上是否真绿灯，本机不可证明**（未 push、无 `gh`）。
- 薄弱：真·进程被杀 + 远端状态未知的恢复只在进程内用例验证，从未对真实 venue 重启演练。

### E. 外部验收

- `maturity/capabilities.yaml` 中 `sandbox_tested: true` 命中数 **0**，且保留待办注记 `testnet_acceptance_has_not_run_with_real_credentials_yet`。
- `tools/binance_testnet_acceptance.py` 无凭据即 exit 3 fail-closed；CI 只跑离线 `--allow-skip` 腿，完整作业依赖仓库外 secret（`ci.yml:304-308`）。
- 结论：**至今没有任何一次真实交易所往返**。

## 4. 不合理清单（按影响分级）

### P0 —— 会导致错误成交或误判能力

1. **实盘无风控静默回落**（§3A）。影响：缺 spec 的部署照样下单，风控等于不存在；与 paper 侧行为不对称，使用者无从察觉。
2. **回测风控不同源**（§3B）。影响：multi-builtin / depth 的回测结果与实盘规则集不一致，策略在回测里"通过"可能实盘被拒，反之更危险。
3. **硬编码假数据被当作能力入口**：`reconcile` 无参数时用手写 `(1,10),(2,5)` 与 `(1,10),(2,4)` 打印差异（`cli.rs:1042-1063`），`all` / `verify` 走合成 BarFrame 与 qx-cli 内置私有 SMA 引擎（`selfcheck.rs:16-54`、`ecosystem_smoke.rs:121,317,318`）。影响：命令名与产物看起来像真对账 / 真回测，容易被当成可用功能。
4. **help 与实际派发不一致**：`run` 的错误文案自称支持 `backtest`（`config_commands.rs:592-596`），而 `run_unified_command` 的 match 无该分支（同文件 :545-597）。影响：按提示操作的到用户会得到"未知入口"。

### P1 —— 架构与边界

5. **风控概念双轨**：`qx-risk::RuleSet`（`qx-risk/src/lib.rs:167-181`）与 `qx-zhenlu::RiskGate` 自带 RuleSet（`qx-zhenlu/src/lib.rs:108-121`），构造点分散三处（`runtime_wiring.rs:126-147`、`ecosystem_smoke.rs:361-364`、`qx-xingban/src/tick_backtest.rs:372-373`）。
   > **勘误（P0 轮实测，2026-09-20）**：类型层面并非双轨——`qx_zhenlu::RiskGate` 已经是 `qx_risk::RuleSet` 的 deprecated 薄包装（`crates/qx-risk/src/rules.rs:132-198` 是唯一 RuleSet 实现）。真正的不合理是**绕过构造**：`RiskGate::new()` 默认值散落在 `qx-xingban/src/backtest.rs:2351,2443,2593`、`tick_backtest.rs:283`、`orderbook_backtest.rs:810,835,885,915` 与 `qx-cli/src/ecosystem_smoke.rs:360`，每一处都等价于"空规则集=不判风控"。P1a 的验收口径据此从"删第二套类型"改为"关掉绕过构造点"。
6. **状态机五套**：`OrderStatus::can_transition_to`（`qx-core/src/order.rs:46-73`）、`SpreadOrderGroupStatus` 九态（`qx-zhenlu/src/lib.rs:344-356`）、gateway 内重新推导的成交态（`qx-execution/src/lib.rs:730-851`）、`CommandStatus`、`JobStatus`。同一"是否可流转"问题没有单一裁决点。
7. **快照类型重复**：`AccountPositionSnapshot` / `AccountBalance`（`qx-core/src/event.rs:148,160`）vs `PositionSnapshot` / `OrderSnapshot`（`qx-protocol/src/lib.rs:102,127`），`qx-cli` 需同时别名导入两套（`main.rs:28,47`）。
8. **`TargetPosition` 定义两次**（`qx-portfolio/src/rebalance.rs:31`、`qx-zhenlu/src/lib.rs:174`）；**对账逻辑四处**（`qx-genglu/src/lib.rs:140`、`qx-adapter`、`qx-execution` 的 EventLogReconcilePort、`venue_runtime/binance_reconcile.rs` + `ccxt_reconcile_worker.rs`）。
9. **存储侧四套 JSON 文件状态存储**（`JsonStateStore` `qx-storage/src/lib.rs:2544-2569,2752`、`FileConsumerStateStore:929`、`FileOutboxStore:1250`、`FileJobQueue:2088`）各自读写序列化；**重试 / 退避三套实现**（`qx-adapter/src/binance.rs:260`、`qx-scheduler/src/lib.rs:145-155,829-842`、`qx-storage/src/lib.rs:1374,1463` + `sqlite.rs:711,883`）。
   > **勘误（P0 轮实测，2026-09-20）**：重复度低于原描述。四个文件状态存储**已经共用** `write_atomic_path`（原子替换）与 `acquire_storage_lock`（互斥），剩下的重复只在各自的 envelope 序列化 / schema 版本 / 损坏判定；退避调度实际只有 **2 套**（`qx-adapter` 指数、`qx-scheduler` 固定），`qx-storage/src/lib.rs:1374,1463` 与 `sqlite.rs:711,883` 是**只计次、不退避**的 attempts 计数器。P1c 的口径据此收敛为"一套 envelope + 一个策略类型覆盖 2 调度 + 2 计数点"。
10. **spread 屏障住在 CLI 而不是网关**（§3C）：网关被绕过时约束消失。
11. **薄壳 crate 与中文代号**（§2）：认知成本高，依赖收益低。

### P2 —— 工程化与体量

12. `qx-cli` 18,298 行、约 40 个命令仍手写字符串派发（`cli.rs:8-1077`），clap `Subcommand` 迁移在 V9 被明确搁置。
13. 37 个超 500 行文件仍在预算表内，`ashare.rs`(1,978) 与 `qx-runtime/src/lib.rs`(3,660) 需职责边界设计才能拆（V9 已列，未做）。
14. 金额类型仍有绕过包装的裸 `i128`（`qx-guanxing/src/lib.rs:24-31` 的 `Bar` 字段）。
15. 平台/环境差异仍靠文档约定：裸 `python` 是坏桩需 `QX_PYTHON`；Windows 文件竞争已修一处（Phase 4t 的追加锁），同形态风险未系统排查。
16. wheel 腿无 CI：`qx-python` 有真实产物（`_qianxing_native`），但没有作业构建它 —— 注意**它是构建目标而非死码**（`crates/qx-python/Cargo.toml` 的 `crate-type=["cdylib"]` + `tools/build_python_wheel.sh:12`），D3 的"清理"不适用于它。

## 5. 核心功能是否全部实现 / 主体链路是否全部贯通

| 能力 | 实现 | 被测 | 真实外部验证 |
|---|---|---|---|
| 内核 / 账本 / 风控规则 | 是 | 是（517+ 用例） | 不适用 |
| 数据帧与数据集指纹 | 是 | 是 | 不适用 |
| Bar / Tick / OB / A 股回测 | 是 | 是（结果哈希确定性） | 不适用 |
| 多腿归因 | 是 | 是 | 否 |
| 跨语言策略 | 是 | 是（本机需 `QX_PYTHON`） | macOS wheel 未跑 |
| Paper 全链 | 是 | 是（`paper-e2e`，CI 有跑） | 注入合成行情，非真实 feed |
| 实盘 Binance / CCXT | 是 | 仅进程内 | **从未** |
| SQLite / Postgres / NATS | 是 | 契约用例存在，CI 作业已定义 | GitHub 绿灯本机不可证明 |
| 崩溃恢复 / 对账 | 是 | 进程内 | **从未**（无真实远端未知态） |
| 运维面（status / config lock / 错误码 / 可复现包） | 是 | 是 | 不适用 |

**判定**：
- **核心功能已实现**——V9 的 P0/P1 目标项都已落地，未发现空壳实现。
- **主体链路在"内核 ↔ 撮合 ↔ 账本 ↔ 持久化 ↔ CLI 产物"范围内贯通**，且 paper 链可端到端跑通并有 CI 覆盖。
- **尚不能称"全链路贯通"**：(a) 实盘链从未跨过真实交易所边界；(b) 实盘存在 §4.1 的静默无风控回落；(c) 回测与实盘的"同源"只到规则集构造，未到执行路径，且 §4.2 两条回测入口根本不读配置；(d) 恢复与对账只在进程内自证。
- 结论口径：**能力齐备、内部闭环、外部未证**。

## 6. 重构方案 V10（按依赖排序，每阶段可独立收口）

| 阶段 | 目标 | 主要改动 | 验收证据 |
|---|---|---|---|
| **P0a 实盘风控 fail-closed**（D1） | 消灭无风控提交路径 | `worker_risk_context` 缺 spec 时返回 `Err(FAIL_CLOSED: …)`；`execute_submit_order_with_worker_risk` 删除无风控分支；三条链（Binance / CCXT / Paper）共用同一个缺配置判定函数 | 新用例：缺 spec 的 Binance / CCXT 提交命令 → 命令被判 Failed 且原因含 FAIL_CLOSED，EventLog 无成交事实；反向验证：把回落分支改回来该用例必须红 |
| **P0b 回测风控吃配置**（D2） | 四个回测入口同规则集 | `multi_builtin.rs:154`、`depth.rs:65` 改为读 `config.strategy.risk_rules`；深度链在产物清单里显式声明所用撮合内核（不谎称同一内核） | 扩展 `src/tests/backtest_entries.rs` 的规则集等价用例：同一份 risk_rules 在四条链产出同一 `rule_set_version`；改回 `None` 时用例红 |
| **P0c 命令面诚实化**（D3/D4） | help 与能力一致 | `reconcile` 无参演示删除，改为必须给本地与远端来源（或明确 `--demo` 且输出打 DEMO 标记）；`run` 的错误文案与实际 match 对齐（补 `backtest` 派发或删提示）；`all` / `verify` 的内置 SMA 引擎改调 qx-xingban 内核 | 用例：`reconcile` 无参退出码 2；`run backtest` 要么真跑要么文案不再宣称；`cli_surface` 用例把 help 命令表与 match 分支做集合相等校验（新增架构不变量） |

**写入侧同源缺口**一起收口——后者比前者严重得多：`apply_fill` 的现金账簿取自
`LiveEventPipeline::open(name, currency)` 传入的币种，而这个值随 `LedgerApplied` 事实**永久落盘**
（`ReplayVerifier::rebuild_ledger` 只重放 entry，不再回读配置）。于是任何一条用 `"USDT"` 打开账户日志的
链路，都会把该账户的成交扣减与手续费记进 USDT 账簿，而播种的初始资金和 `paper_available_margin` 读的是
worker 声明的 USDC 账簿——**风控永远看到满额保证金，扣减落在另一本账上**，且落盘的事实已经错了。
修复前实测：

```
[("Adjustment", "USDC"), ("TradeCash", "USDT"), ("TradePosition", "USDT")]
```

15 处字面量按调用方持有的身份分两类处理：

| 类别 | 站点 | 形状 |
|------|------|------|
| 持有 worker 句柄（写入侧） | `paper_worker.rs` 6 处、`worker_entry.rs` Binance 多腿恢复 1 处 | 直接用 `worker_settlement_currency(&worker)`。Binance 这条与同文件的 CCXT 分支自相矛盾：同一个 worker 的两条恢复链路把同一条日志开成两本账 |
| 只持有日志身份（读取侧） | `api_service.rs` 4 处、`strategy_contract.rs` 2 处、`strategy_binding.rs` 1 处、`market_bridges.rs` 1 处 | 新增 `open_account_pipeline()` + `settlement_currency_for_log()`：账户级日志名由 `(account_id, venue_id)` 唯一确定，按日志身份反查 worker；打开后经 `LiveEventPipeline::settlement_currency()` 回读，使"打开的账簿"与"查询的账簿"是同一个值 |

两个配套形状决策：

- getter 而不是再传一次币种：`settlement_currency()` 挂在 `LiveEventPipeline` 上，读侧权益/现金查询直接
  取管线自己的记账币种，"开一本账、查另一本账"从签名上就不可能出现。
- `owns_account_event_log()`：只有 UserStream/Execution/SpreadRecovery/Reconciler 拥有账户日志的写入权，
  Strategy/Scheduler 只提交意图，它们声明的币种不能替账户定口径。此前 `api_service.rs` 内联了 3 份、
  `market_bridges.rs` 内联了 1 份同一个过滤器，合并后 `api_service.rs` 净减 16 行、`market_bridges.rs` 净减
  14 行。禁用 worker 不参与反查，否则一个下线了的 worker 能给在线账簿改记账币种。
