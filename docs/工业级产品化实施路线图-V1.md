# 牵星工业级产品化实施路线图 V1

更新时间：2026-09-11

本文是当前代码之后的工业化收口清单。工业级不等于“模块数量多”，而是必须同时满足：交易事实可恢复、订单结果可证明、故障可隔离、策略可替换、性能可度量、发布可回滚。

## 1. 当前结论

### 已经形成主体闭环

```text
Rust / C++ / Python Strategy
        → StrategyContract / OrderIntent
        → RiskGate / InstrumentSpec / Margin
        → OMS / client_order_id 幂等
        → Paper / CCXT / Binance Execution
        → Accepted / Fill / Cancel / Unknown
        → EventLog
        → Ledger / Position / Cash / Margin
        → Snapshot / Reconcile / Query API
```

- Rust 策略可使用 `Strategy` trait；Python 使用持久 JSONL Worker；C++ 可使用稳定 C ABI 或独立 JSONL/framed/shared-memory Worker。
- Bar、Tick、L1/L2 订单簿回测共用策略决策、Risk、OMS 和账簿语义；当前 Bar 因果回测和 Paper 主链路已具备可运行验收证据。
- Paper、公共 Python CCXT、Binance 的执行事实均通过统一 `LiveEventPipeline` 归约，未知下单结果进入对账边界，不自动补单。
- 文件、SQLite 和可选 PostgreSQL 已实现主要控制面、队列、审计、快照、EventLog 以及 Outbox 端口；PostgreSQL 当前是可配置单进程连接池，不应宣称跨节点高可用。

### 不能宣称已经工业级完成

1. 没有经过真实 Binance/OKX 等沙盒网络的签名、UserStream 重连、订单账单和未知结果验收，不能称为实盘验收完成。
2. PostgreSQL 已具备可配置单进程连接池；仍无读写分离、跨节点 leader/fencing 编排，当前连接池实现适合功能和单进程生产化，不等同于最终 HA 方案。
3. NATS JetStream Publisher/Pull Consumer、跨服务消费位点、重试、死信状态、DLQ 重放和 Relay/Consumer worker 已落地；worker 心跳、批次计数、失败和 DLQ 指标已通过 API `/metrics` 聚合暴露，Prometheus 告警模板也已提供。stream/consumer 自动治理、真实 MQ 集群验收、告警送达/SLO 和领域业务 reducer 的事务级验收仍未完成。多节点扩展不能仅依赖共享文件或单数据库连接。
4. QXCB 是固定宽度列式传输，不等同于完整 Arrow C Data Interface 零拷贝行情热路径；缺少策略端到端 P50/P95/P99/P999 基准。
5. C++ ABI 的签名校验和动态库大小限制已具备，但不受信任插件仍未完成沙箱、崩溃隔离、信任根轮换和回滚。
6. L3 队列、撤单竞态校准、逐笔强平和交易所差异化保证金规则仍需要真实数据验收。

## 2. 工业级目标架构

```text
                         ┌──────────────┐
Market / UserStream ────→│  Event Ingest │───┐
                         └──────────────┘   │
                                            ▼
Strategy Worker ─→ Signal/Intent ─→ Risk ─→ OMS ─→ Execution Gateway
     Rust/C++/Python                         │             │
                                            │             ▼
                                            └──────→ Venue Adapter
                                                          │
                         ┌────────────────────────────────┘
                         ▼
                  Event Bus / EventStore
                         │
              ┌──────────┼───────────┐
              ▼          ▼           ▼
          Reducer      Ledger      Reconcile
              │          │           │
              └──────→ Snapshot / Query / Audit
```

职责边界必须保持：

- Strategy 只读输入、只产生 `Signal/PortfolioTarget/OrderIntent`，不得读取凭证、交易所客户端、Ledger 或控制面。
- Risk/OMS 是唯一订单准入和生命周期入口；任何 Worker 不得直接修改订单状态或账簿。
- Venue Adapter 只负责协议翻译和外部事实采集；交易所差异必须通过 `VenueCapability`、`TradingInstrumentSpec` 和标准化账单事实表达。
- EventStore 是事实来源，Ledger、持仓、余额和查询视图必须可由事实重放得到。
- Event Bus 负责跨进程/跨节点传输，EventStore 负责可恢复事实，两者不能互相替代。

## 3. 必须优先补齐的 P0

### P0-1：交易安全和未知结果

- 所有下单请求必须绑定 `strategy_id/signal_id/intent_id/request_id/client_order_id`。
- 超时、连接断开、进程崩溃后的下单必须进入 `Unknown`，只能由 Reconcile 依据 remote order/trade/bill 事实决策。
- 增加重复 Submit、重复 Fill、旧租约 Ack、远端订单已成交但本地未知、撤单与成交竞态的故障矩阵。
- 生产默认拒绝裸 `target_qty`、未绑定 `data_fingerprint`、未冻结产品规格和未配置风险限额的实盘策略。

### P0-2：凭证和插件安全

- CCXT、API、策略子进程只接收声明过的凭证变量；日志、配置摘要、EventLog 禁止出现秘密值。
- C++ 动态库默认采用签名白名单；不受信任代码必须通过独立进程或操作系统沙箱运行，不能直接加载进交易进程。
- 凭证轮换要支持新会话、新下单、新对账轮次重新加载，并记录 `credential_version`，不记录秘密本身。

### P0-3：可观测性

至少提供以下指标和结构化日志字段：

- 行情延迟、策略耗时、Risk/OMS 拒绝数、下单请求数、Unknown 数、成交延迟、对账差异数。
- EventLog ingest、去重、重试、失败、恢复耗时和当前事件游标。
- `request_id/client_order_id/venue_order_id/correlation_id/worker_id` 全链路关联。
- `/health` 只表示进程存活；`/ready` 已检查控制面、已声明研究快照、生产凭据/冻结规格文件和已有 Relay/Consumer 指标中的 down/stale 状态；仍需继续纳入 Venue 用户流、对账和完整交易安全状态，不能用一个 `ok` 覆盖所有状态。
- Relay/Consumer worker 的 `up`、心跳时间、扫描/发布/重试、消费/重复/死信和发布/确认失败计数；API 通过 `storage.data_dir/worker-metrics/*.prom` 聚合这些跨进程指标。
- API `/ready` 独立于 `/health`：运行时会检查控制面、已声明研究快照、生产交易凭据/冻结规格和已有跨进程 worker 指标，依赖不可用时返回 503；生产部署还应把 MQ、Venue 用户流、对账状态和完整交易安全状态接入同一 readiness provider。

## 4. P1：性能和多节点能力

### P1-1：数据面分层

| 场景 | 传输 | 事实边界 |
|---|---|---|
| 研究/分钟级 | Python + Arrow/Parquet | 允许批处理和列式扫描 |
| 通用实时 | JSONL/framed/shared memory | 控制面可审计、数据面可替换 |
| 低延迟 | Rust/C++ + Arrow C Data Interface/QXRB | 热路径不得写 DB、不得同步写日志 |

QXCB 先保留为兼容协议，再补 Arrow C Data Interface 的生命周期、释放、跨语言所有权和回放一致性测试。性能验收必须同时报告传输、策略、Risk、OMS、Venue 和端到端 P50/P95/P99/P999，不能只报告 ring 吞吐。

### P1-2：PostgreSQL 生产化

- 已落地基础固定大小连接池：运行时通过 storage.postgres_pool_size 配置，控制面、命令队列、JobQueue、EventLog 和 Paper 执行路径均可复用该配置。
- write pool 已配置 statement/lock/idle-in-transaction timeout，并提供 `health_check`；连接失效后的自动重建和读写分离仍需补齐。
- `read pool`：查询、审计和报表走只读连接；读模型不得参与写事务。
- 迁移版本、兼容窗口和回滚策略必须显式记录；生产启动只允许向前兼容迁移。
- leader lease 必须绑定 fencing token；旧 leader 即使网络恢复也不能继续追加事实或确认任务。
- Postgres 只保存交易事实和控制面；高频行情原始数据应进入 Parquet/对象存储或专用列式库。

### P1-3：MQ 事件流

Outbox 端口和通用 relay 骨架已经落地，文件、SQLite、PostgreSQL 共用 `OutboxStore` 契约，`OutboxRelay` 只要求注入一个 Publisher，至少保证：

- `event_id` 幂等；相同 id 不允许覆盖不同 payload。
- relay claim/ack/retry 使用租约和 fencing token；旧 relay 不能确认新 relay 的事件。
- retry 只递增 attempts 并释放租约，不删除未确认事件；进程崩溃后可过期接管。
- relay 按 claim → publish → ack 执行；发布失败走 retry，发布成功后才确认删除。

真实 NATS JetStream Publisher、Pull Consumer 已作为可选 `qx-storage/nats` feature 接入，并提供 `qx-cli outbox-relay` 单批 relay、`outbox-relay-worker` 持续 relay 和 `event-consumer-worker` 持续消费入口；消费者端已具备 ACK/NAK、位点、event_id 幂等、重试、死信终态和 DLQ 重放语义。`ConsumerEngine::consume_with_projection` 为文件/SQLite/PostgreSQL 提供 projection、processed marker 和 checkpoint 的原子提交路径；外部 JSON handler 仍是 at-least-once。worker 指标已通过原子 Prometheus 文件写入并由 API 聚合，失联窗口由 `messaging.worker_stale_after_ms` 控制。生产部署仍需预创建 stream/consumer、配置复制/保留/max-deliver 策略，并补齐告警送达/SLO、真实 NATS 集群故障矩阵和业务 reducer 的领域表事务适配：

- topic、partition、offset、event_id、schema_version、producer_epoch、trace_id。
- at-least-once 投递、消费者位点、幂等归约、重试退避和死信队列。
- 事件顺序以账户/订单/标的键保证，不假设全局顺序。
- EventStore 追加成功后再发布，或使用 Outbox；禁止“先发 MQ、后写事实”造成幽灵成交。当前 PostgreSQL EventLog 已支持与 Outbox 同一事务提交，文件/分段后端仍采用恢复友好的顺序写入；文件/SQLite/PostgreSQL consumer state store 与 NATS Pull Consumer、外部 JSON handler worker 已接通，但业务 reducer 与消费位点的同库事务、stream/consumer 治理和真实集群验收仍未完成。

NATS JetStream 已作为真实 Publisher/Pull Consumer 实现接入；Redpanda 仍保留为可替换后端，
需要复用同一 Outbox/Consumer 契约完成适配和真实集群故障验收。

## 5. P1：回测和衍生品真实性

- 产品规格冻结版本必须进入 RunManifest：tick、lot、contract size、settlement、margin mode、leverage tier、funding、fee、价差和时区。
- L2 回测增加队列位置随撤单/成交动态变化、撮合延迟分布、市场冲击校准和盘口缺失处理。
- 衍生品增加逐事件维持保证金、跨币种抵押、资金费账单、交割、部分强平、保险基金和 ADL 的可重放模型。
- 回测输出必须包含净值、费用、滑点、换手、最大回撤、杠杆、保证金占用、强平次数、成交覆盖率和数据质量摘要。
- 同一 `RunManifest + seed + strategy artifact digest` 必须可重放；策略代码、配置、数据指纹和依赖锁文件都要纳入摘要。

## 6. P1：多语言策略产品化

### Rust

- 同进程 SDK 用于低延迟和核心策略；提供版本化 `StrategyContext/MarketEvent/StrategyDecision`。
- 对策略 panic、超时、非法 intent 和资源超限做边界隔离；策略不能污染 Runtime 状态。

### C++

- 稳定 C ABI 只暴露固定宽度类型和显式释放函数；C++ 包装器不得把 STL/异常/RTTI 跨 ABI 边界传递。
- 发布 CMake toolchain、Windows/Linux/macOS 预编译包、ABI 版本矩阵、符号白名单和回滚策略。
- 默认采用独立进程 JSONL/shared memory；只有受信任、已签名插件才允许进程内加载。

### Python

- 保留 JSONL 作为调试/控制面；Arrow/shared memory 用于批量数据面。
- Worker 必须是持久进程，有请求超时、最大内存/CPU、崩溃重启和状态恢复边界。
- Python 策略只能返回统一 OrderIntent，必须经 Rust Risk/OMS；CCXT 客户端不注入策略进程。

三种语言必须通过同一组 golden vectors 验证：相同输入、版本、seed、数据指纹下，决策摘要和订单意图摘要一致。

## 7. P2：拆分、运维和生态

- 将 `qx-cli` 中的具体 Worker 编排继续拆成 `qx-strategy-worker`、`qx-paper-worker`、`qx-ccxt-worker`，CLI 只做参数、配置和进程拓扑。
- 增加 OpenTelemetry trace、告警送达/SLO、指标保留治理和完整值班手册；基础 Prometheus 指标与告警模板已落地。
- 建立 Binance/OKX 沙盒矩阵：现货、杠杆、永续、交割合约、单向/双向持仓、isolated/cross、手续费、资金费和断线恢复。
- 建立数据质量门禁：缺失、重复、乱序、未来数据、时钟漂移、盘口交叉和异常成交必须产生可查询报告。
- 增加备份、恢复、跨区域灾备和定期演练；演练结果要包含事件数、digest、订单状态、Ledger 和审计链一致性。
- 策略包、模型、研究快照、配置和二进制发布统一签名，支持灰度、暂停、回滚和人工审批。

## 8. 工业级完成定义

只有以下证据全部具备，才能把项目标记为工业级生产候选：

1. Rust/Python/C++ golden vectors 一致，并通过崩溃、超时、非法输出和资源超限测试。
2. Paper 完成跨进程重启恢复；至少两个真实交易所沙盒完成下单、成交、撤单、对账和未知结果恢复。
3. EventStore、MQ、Ledger、Snapshot、Reconcile 的恢复顺序和幂等语义有契约测试。
4. PostgreSQL 连接池、leader/fencing、备份恢复和故障切换通过演练；旧 leader 无法继续写入。
5. 端到端延迟、可用性、数据延迟和对账延迟有基线、阈值和告警，而不是只有单元测试耗时。
6. 所有策略、数据、配置、依赖和运行结果可通过 RunManifest 复现；上线和回滚均可审计。

当前版本达到“核心链路可运行、单机可恢复、多语言策略协议可用、PostgreSQL 基础端口已落地”的阶段，距离上述工业级完成定义主要差在真实外部验收、MQ/HA、性能基准、安全隔离和运维演练。
