# 牵星 Qianxing 重构方案 V9

- 更新时间：2026-09-19
- 审计基线：`main@296e56e`（本轮实测）
- 审计方法：3 组并行代码探查（领域/执行层、CLI/API/存储/运行时、Python/C++/数据/CI）+ 关键结论逐条 `文件:行` 复核；本机无 Rust 工具链，所有"通过"类历史数字均视为 CI 侧旧证据，不作为本轮结论。
- 取代文档：`docs/自研量化框架架构审计与重构方案-V8.md` 的"计划"部分；V8 仍是有效的能力台账，但本审计发现其中若干状态判定偏乐观（见 §5）。
- 已确认的决策前提（本轮用户决策）：
  1. 方案范围 = 架构收敛 + 正确性修复 + 补链路 + 外部沙盒验收，不新增交易所/策略；
  2. 项目未发布正式版，**允许破坏性清理**（重复命令、兼容门面、死代码可直接删除）；
  3. `qx-cli` **保持单 binary**，只做内部模块化，不拆 qx-node/qxctl/qx-lab；
  4. 本机安装 Rust 工具链，每阶段门禁在本地可复现。

## 1. 结论摘要

> **牵星是一个内核真实、外围许诺超前于证据的项目。** 确定性内核（定点数/EventLog/Ledger/Replay/Bar 回测）是全仓最可靠的部分；但应用层以 15,497 行单文件 CLI 的形式存在，端口化重构做到一半就停住了，风控存在会静默放行订单的 fail-open 缺口，README/V8 宣称的多项能力（L1/L2 回测、多交易所、SQLite 单机持久、A 股 PIT）与代码现实有可验证的差距。

一句话判定（对应 V8 的四档）：

| 维度 | 判定 |
|---|---|
| 交易内核 | A：保留，禁止重写 |
| 回测（Bar 档） | A-：链路闭合 |
| 回测（Tick/L1/L2 档） | **C：引擎存在但零消费者，不可触达**（V8 判 A- 不成立） |
| Paper 主链 | **B-：代码贯通但含 fail-open 与伪造行情分支**（V8 判 B+ 偏高） |
| Live/CCXT 链 | C+：Rust 原生只有 Binance，其余靠 Python 子进程 |
| 应用层/入口 | **D 级架构债：qx-cli 是事实上的应用层** |
| 外部验收 | D：maturity 台账 `sandbox_tested`/`production_approved` 命中数为 0 |

## 2. 项目主要功能（当前真实状态）

### 2.1 确定性内核 `qx-core`（5,551 行）—— 最稳定资产
- 128-bit 定点金额/价格/数量；`InstrumentId`/账户/Venue 身份（`src/identity.rs`）；
- TestClock、因果事件队列、事件优先级；
- 唯一权威订单模型：`src/order.rs:91 Order`、`:156 Fill`（全仓无第二套 Order/Fill —— 本轮证实）；
- EventLog、digest、Replay、RunManifest；
- `src/ledger.rs` **2,876 行、单 `impl Ledger` 42 个 pub fn**，混装成交/资金费/利息/交割/强平/分红/配股/可转债转股/A 股结算/FX —— 职责过载，是内核里唯一的重灾区（§3.2-5）。

### 2.2 回测撮合 `qx-xingban`（7,076 行）
- Bar 回测真实闭合：`backtest.rs:85 on_bar_orders_checked → :729 Risk → :741 Oms → :399 BarMatchingEngine → :787 apply_fill → :789 ledger → :797 EventLog → :930 validate → :951 report`，含 `:213 result_hash`/`:216 replay_hash` 重放自校验；
- `TickBacktestEngine`（265 行）与 `OrderBookBacktestEngine`（651 行）**在 qx-xingban 之外零引用**（本轮 grep 实测），CLI 无入口触达；
- A 股规则（`ashare.rs`）：日历/停牌/T+1/整手/涨跌停/公司行为，但为手写适配器（见 §4 P2-3）。

### 2.3 策略
- `qx-strategy/src/builtin.rs:19-79`：17 类内置策略属实，Rust `trait Strategy`（`lib.rs:309`）；
- 跨语言协议同源实证：QXSF/QXRB/QXCB 帧格式 Python 端（`qianxing_strategy/frame.py:14-18`）与 Rust 端（`qx-strategy/src/frame.rs:10-13`、`ring.rs:15-23`、`qx-runtime/src/lib.rs:133-135`）magic/version 一致；
- C ABI：`cpp/` 896 行 ↔ `qx-strategy/src/c_api.rs` 1,106 行，CI 仅 Ubuntu。

### 2.4 风控 / OMS / 执行
- 三套语义并存且**都还在生产路径上**（详见 §3.1，这是本轮最重要的新发现）；
- `qx-oms`（171 行）独立订单生命周期成立；
- `qx-application`（343 行）是**有效契约层**：7 端口 + 提交/撤单/行情校验函数，但只有 OrderStore/EventAppender/MarketDataPort 三个端口有实现，`ReconcilePort` 全仓零实现；
- `qx-execution`（3,191 行）：`PortExecutionService`(:387)、`SpreadExecutionService`(:918)、`MultiVenueSpreadExecutionService`(:1055) **在生产代码中零调用，仅被自己的单测触达**（本轮实测）；生产流量全部走旧函数 `ingest_venue_events`(:1782/:1840)。

### 2.5 Paper / CCXT / Binance
- Paper：Queue→Fill→Ledger 闭环存在，但含 §3.1 的 fail-open 分支；
- `qx-adapter/binance.rs` 2,283 行（HMAC 签名/REST/WSS 用户流/对账），是**唯一的 Rust 原生 venue**；
- "多交易所"实为：`ccxt.rs:29 CcxtProcessClient` 用 `Command::new(python) -m qianxing_ccxt.worker`（:44-46）起 Python 子进程 JSON-RPC；CLI 有 5 处以上各自 fork python 进程的重复实现（`main.rs:4432/8075/9738/12872/…`）。

### 2.6 存储 / 运行时 / API
- 四后端矩阵（本轮实测）：EventLog 只有 Files 和 PostgreSQL 有实现，**SQLite 缺 EventLog，运行时回落到文件**（`main.rs:633-657`），与"sqlite = single-node durable"的定位声明不符；
- `storage.consistency` 三级门禁已真实落地（`qx-runtime/src/lib.rs:600/:1771-1795`，runtime-check/status 输出）——V8 该条属实；
- `qx-api` 是真接线非演示壳：17 条路由（`lib.rs:1377-1514`）、mTLS+证书→operator 映射（`:185/:205/:332`）、`serve` 装载 control store/command queue/Ledger 投影（`main.rs:1367-1430`）；
- `RuntimeConfig`：`WorkerConfig` 12 字段 9 个 Option、`StrategyRuntimeConfig` 约 40 字段、`strategy`/`strategies` 双轨兼容（`qx-runtime/src/lib.rs:741/:936/:1165`）——tagged enum 重构未开始；
- production 示例 fail-closed 属实且被 CI 断言（`ci.yml:96-101`）。

### 2.7 A 股数据链
- Python 侧 5,733 行（ashare 1,574 / ccxt 1,296 / bridge 670 / strategy 471），重依赖懒加载、import 不触网——工程习惯好；
- 链路字段错配（本轮实测）：BarFrame JSON 无 `schema_version`；Rust `qx-data/src/provider.rs:125-134` 静默忽略 `source` 且无 `deny_unknown_fields`；公司行为的 `published_at`/`raw_payload` 在 Rust 适配器（`qx-xingban/src/ashare.rs:306-418`）未读取 → **Python 侧 `--as-of` PIT 可见性进入回测后丢失**；CI 只用 6 行合成 bars，真实 fetch→回测只通 happy path。

### 2.8 周边空壳与残骸（本轮实测）
- `crates/qx-kernel/`：无 Cargo.toml、不是 workspace 成员、全仓零引用 —— V5 遗弃脚手架；
- `qx-domain`（131 行）：9 文件 7 个纯 re-export，`.rs` 中零引用，却被 `qx-data/Cargo.toml:10`、`qx-runtime/Cargo.toml:15` 依赖 —— 空挂边；
- workspace 实际 28 个成员、29 个目录（"30 crate" 说法不成立）；
- `tests/e2e/` 与 `benchmarks/` 只有 README 占位，无任何脚本/测试；
- Python 测试本轮实测 42 个 test 方法（V8 记载的 39 为旧数）；README:182 承诺的"Linux/macOS/Windows wheel CI 矩阵"在 CI 中**不存在**（`ci.yml` 仅 4 job，无 wheel 构建，`tools/build_python_wheel.*` 未被 CI 引用）。

### 3.2 P1：架构不合理

1. **qx-cli 是事实上的应用层**（用户决策：保持单 binary，内部模块化）：
   - `main.rs` 15,497 行、44 个顶层子命令、无 clap、`main()`（:12106 起）45 处 `if mode ==` 字符串分派；
   - 回测入口 8 个：`backtest`/`strategy-backtest`/`run backtest` 是同义壳（收敛到 `run_unified_backtest:3248`），而 `builtin-backtest:10904`/`multi-builtin-backtest:11071`/`ccxt-builtin-backtest:11263`/`ccxt-backtest:10840` 各自内联 `BacktestEngine::new`，未复用装配；

   - CCXT（:9678）与 Binance（:9994）两张平行的 `WorkerRole` 分派表；
   - 5 个生产函数因测试需要被 `#[cfg(test)]` 标注（`main.rs:1592/4237/5556/10035/31`）；
   - "跑 CLI 自校验演示 = 主要验收手段"（`ci.yml:66-104`）。
2. **端口迁移半途而废**：`qx-execution/Cargo.toml:18` 仍依赖 qx-runtime、feature 转发 `postgres = ["qx-runtime/postgres"]`(:10)、`lib.rs:14 use qx_runtime::LiveEventPipeline`；端口化新服务零生产调用、旧 `ingest_venue_events` 仍是主干（CLI :6185/:6676/:8425/:8434 调用）→ **多腿执行存在 CLI 内联与 qx-execution 两套并行编排**。
3. **qx-zhenlu 2,703 行单文件、约半数是死出口**：`Router/Candidate/VenueQuote/AccountRouter/allocate_target/AccountCommandQueue/VenueReconcileIssue/TradingAccount` 零外部引用（`qx-zhenlu/src/lib.rs:313/:289/:298/:1574-1770/:1471/:843 区段`）。

5. **内核 `Ledger` 单文件 2,876 行 / 42 个 pub fn 混装所有资产类别账本语义**——应拆为 fill/funding/settlement/corporate-action/derivatives 子模块（只拆文件，不改语义）。
6. **概念多套定义**：Position 4 份（`qx-core/ledger.rs:55` 权威、`qx-zhenlu:20`、`qx-genglu:199`、`qx-protocol:102`）、Bar 2 份（`qx-guanxing:24` vs `qx-data/src/schema.rs:21`）、Intent 4 份（`qx-zhenlu:368`、`qx-strategy/lib.rs:211`、`c_api.rs:123`、`qx-runtime/lib.rs:197`）。
7. **SQLite 后端 EventLog 回落文件**（§2.6），一致性分级掩盖了这一实现事实。

## 5. 重构方案（分阶段，含验收门禁）

总原则：
- **不动内核语义**：`qx-core` 的 Order/Fill/Ledger/EventLog/定点数是资产，只拆文件不改行为；
- **每阶段独立可回滚**：一个阶段一个可合入分支，golden 结果哈希（`backtest.rs:213 result_hash` 同款思路）证明移动前后语义一致；
- **验证一律本地 + CI 双跑**（决策 4）；
- **文档诚实性作为交付物的一部分**：每阶段结束同步修订 README 状态表与 `maturity/capabilities.yaml`。

### Phase 0：可复现基线（0.5 周）

1. 本机安装 rustup stable + Python 依赖（用户已批准）；
2. 本地跑 `cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`、`pytest python/tests`，把**当前真实通过数**记录进本文件附录（替换 V8 的旧数字）；
3. 生成基线 golden：`qx-cli` 无参自校验、`strategy-backtest`、`paper-e2e` 三组输出哈希入库（`tests/golden/`，替换空占位的 `tests/e2e`）。

门禁：四连全绿 + golden 入库。这是后续每阶段的回归底座。

### Phase 1：P0 正确性修复（1 周）—— 最高优先

1. **Fail-closed 化**：
   - `load_worker_instrument_spec` 缺 spec/position 时返回 `ReconcileRequired`/拒绝执行，禁止 `(None,None)→execute()` 直通（`qx-execution/src/lib.rs:2142`）；
   - 删除生产路径 `unwrap_or_else` 伪造盘口分支（:2147），Paper 无行情时拒绝撮合——与 V8 §1.3 已声明的"无行情事实拒绝撮合"对齐；
2. **统一风控入口**（V8 Phase 3 收尾）：
   - `qx-risk::RiskEngine::evaluate_order` 为唯一判定实现；删除 `decision.rs/exposure.rs/volatility.rs` 死代码与重复 `RiskAction`；
   - `RiskGate` 规则链迁移进 `RuleSet`（保留类型名一个版本的 re-export 由决策 2 改为直接删除，调用点全部显式改）；
   - CLI 回测入口的空 `RiskGate::new()` 改为从 runtime/strategy 配置加载 RuleSet，缺省用文档化的保守默认并写进 RunManifest；
   - worker 硬编码 `MaxQtyRule{1000}` 移入配置；
   - 新增一致性测试：同一订单快照 × 同一 RuleSet，回测/Paper/Live 三条路径的 `RiskDecision` 序列化结果必须 bit 级一致。
3. README"设计底线"补充第 8 条：**任何风控上下文缺失必须 fail-closed**。

门禁：golden 哈希在允许差异清单内（风控结果差异需逐条人工确认为"修复的预期差异"）+ 新增三路径一致性测试绿。

### Phase 2：破坏性清理（0.5 周，可与 Phase 1 并行分支）

按决策 2 直接删除（均经本轮零引用实测）：

| 删除项 | 依据 |
|---|---|
| `crates/qx-kernel/` 整目录 | 无 Cargo.toml、零引用 |

## 6. 里程碑与顺序

```text
P0 环境基线 ─┐
             ├─ Phase 1 风控正确性（独立分支，最高优先合入）
             ├─ Phase 2 破坏性清理（并行分支，先合 1 再合 2）
             └─ Phase 3 端口单轨化 ─→ Phase 4 CLI 模块化 ─→ Phase 6 外部验收
                                        Phase 5 补链路（与 4 并行） ↗
```

- 关键路径：Phase 1 → 3 → 4。Phase 1 修的是"钱会不会错"，其余修的是"代码会不会烂"；
- 人力假设：单人全職约 9-11 周；若并行双人（架构线 3+4 / 数据线 5+6）约 7 周；
- 每阶段合入后冻结一次 tag，golden 集随阶段演进，差异必须逐条书面评审。

(async )?(unsafe )?(extern )?(fn|struct|enum|trait|impl|type|const|static|union)` 的行，缩进在模块内的项、宏生成的项都不计入，因此"根不再长大"是形状判定不是归属判定；链路入口唯一性那六项认的是**十个写死的标识符**（四个冒烟入口加本轮六个分派入口），加前缀改名、或把入口拆成 `run_runtime_check_v2` 之类的转发函数都不会红，KK 实验只证明"在根里再定义一份同名项"会红，而它的红因同时命中条目上限（两条门禁重叠，不代表各自独立生效）；"crate 根 `main.rs` 已退出行数登记集"读的是 `maturity/line_budgets.yaml` 里 `crates/qx-cli/src/main.rs:` 这个**字面前缀**还在不在，判据是"行数 < 500 且 不在预算表内"的合取，故写回 500 行以上或被人重新登记都会红，但把根改名（如 `qx.rs`）会让前缀检查读不到任何行而假绿；模块清单从 5 个扩到 11 个仍靠脚本里那张写死的元组，新拆第十二个簇必须同步登记，否则该项对新材料完全不设防（这是脚本与代码的同步义务，不是自动发现）。本轮还额外暴露出门禁脚本自身的一层可信度边界：反向验证的"还原基准"若取在 `--snapshot` 之前，MM 类实验会把上一轮的棘轮表写回工作树，同时令末尾的残留检查假绿（因为它比对的就是那份陈旧备份）——本轮首次整跑即因此废弃、修脚本后重跑，说明**变异实验的可信度也依赖脚本自身的备份时序**，这条不在 `check_architecture.py` 的判定面上，只能靠日志里的 `RESTORED_*_ARCH_EXIT=0` 与逐字节 `RESTORE[*]=identical` 两行同时成立来人工核对。Phase 4r 把 Phase 4o 那四项从"写死 qx-cli"参数化成 `TEST_MODULES` 表之后，边界随之新增三条，须一并记清：其一，元组里每项的**目录名、被拆单文件名、挂载文件名、用例下限、夹具名单都是写死的**，因此第三个 crate 再拆用例文件不会自动被约束，得有人往表里加一行（同表两行共用同一份判定逻辑，这是复用而非放宽）；其二，挂载判定读的仍是 `src/<挂载文件名>` 里 `#[cfg(test)]` + 换行 + `mod tests;` 这段精确文本与 `#[path = "<被拆文件名>"]` 的不存在，所以 4o 那两条误报/漏报开口原样继承——把挂载并成一行会误报缺失，而把目录整体改名（`src/cases/`）会让"目录内 0 个文件 + 用例数 0"两条同时报红（宁误报不漏报，但红因不是它声称的那件事）；其三，用例计数只认行首 `^#\[test\]$`，`#[ignore]` 与空断言同样计数（本轮 KK 实验用等行数的 `#[cfg(any())]` 把属性行改掉才会红，说明"禁用一条用例"这种退化确实被条数拦住，但"把断言掏空留着属性"仍然拦不住）。本轮额外把夹具判定从 `f"fn {name}("` 子串换成行首 `(pub(...))? (fn|struct|enum|trait|type) <名>\b` 正则：旧写法对结构体夹具恒不匹配，若不换，六条 qx-execution 夹具里的五条会长期假绿（LL 实验正是复制 `struct PortState` 才证明新判定有效）。变异实验的还原基准这一次也已按 4q 的教训改在 `--snapshot` 之后重取，日志里 `RESTORE[MM]=identical` 与 `RESTORED_MM_ARCH_EXIT=0` 同时成立。它只拦到目前为止已想清楚的不变量，不等于覆盖所有架构约束——注入实验只能证明对应项会红，不能证明门禁完备；Phase 4s 暴露了同一类盲区的第二个实例，且这次后果更直接：`backtest_assembly_check()`（第 6 项「Bar 回测引擎装配只有一份」）原先把路径写死成 `src/backtests.rs`，拆分后该文件不存在，门禁不是「判定变弱」而是**直接抛 FileNotFoundError 让整支自检崩掉** —— 崩在脚本里比假绿好（不可能被误当成通过），但同样说明「以文件路径为键的检查」对搬家零容忍。本轮把它改成按 `src/backtests/*.rs` 目录聚合读，并专门用反向验证 SS 在**子文件**里注入第二处 `BacktestConfig {` 字面量，证明新口径确实会红。另记一条与门禁可信度同类、但属被测代码的遗留：`qx-storage` 的 `file_token_bucket_is_persistent_and_serializes_concurrent_consumers` 在全量并发跑时偶发 `Io(拒绝访问 os error 5)`（Windows 文件共享冲突；隔离连跑 8/8 全绿），因此「本轮 workspace 用例数」这类数字必须成对记录首轮失败与隔离复跑，不能只挑绿的那次写进文档。
