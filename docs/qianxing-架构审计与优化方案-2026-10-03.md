## 1. 结论摘要

牵星当前已经形成一条相对完整的本地闭环：

```text
数据/配置
  -> 数据质量与 PIT
  -> 策略/信号/目标
  -> 风控与 OMS
  -> 回测撮合或 Paper Venue
  -> 统一执行事实
  -> EventLog / Ledger / Outbox
  -> 快照、报告、API、Prometheus
```

当前最准确的产品定位是：

- 本地确定性回测内核：已贯通，且 Bar、L1、L2、多腿、A 股规则均有代码级测试。
- Paper 闭环：已贯通，包含调度、策略、风控、队列、成交、Ledger、审计和读模型。
- 真实交易：适配器、提交、回报和对账契约已实现，但能力矩阵中的 `sandbox_tested` 与 `production_approved` 仍为 `false`，不能宣称已完成真实账户闭环。
- 多语言策略：Python JSONL/framed/shared-memory 和 C++ C ABI/ring 均有契约，但跨语言协议仍是仓内手工维护的 v1 边界，不是完整的 schema registry 或插件平台。
- 插件：`qx-plugin` 是启动期 manifest、依赖拓扑和静态装配校验，不是运行时热插拔；C ABI 动态加载是另一条独立边界。
- finkit：只有 provider/version/schema/digest 的研究工件绑定与校验；finkit 不在仓库内运行，因子物化写侧未进入 CLI 生产装配，因子值本身也不会直接改变订单决策。

总体判断：

| 维度 | 当前判断 | 说明 |
| --- | --- | --- |
| 主体流程完整性 | 良好 | 本地回测、Paper、API 读面和故障恢复均有真实链路测试 |
| 领域模型一致性 | 中上 | `qx-core`、统一执行端口和市场规格已建立，但公共模型仍有重复族 |
| 运行时成熟度 | 中等 | 生命周期、幂等、租约、停机和观测已有基础；实时重试、调度形状、生产信号仍有边界 |
| 性能可扩展性 | 偏弱 | EventLog 写侧仍按日志长度线性重读、重放和序列化，且 `ingest_once` 会 clone 整个管线 |
| API 稳定性 | 中等 | JSON/ABI/快照契约有版本和门禁，但版本发布、兼容策略和 schema 注册仍偏手工 |
| 真实交易就绪度 | 未达标 | 没有已证明的 sandbox/production evidence；PostgreSQL/NATS 依赖服务也需持续验收 |

## 3. Workspace 与主体架构

### 3.1 Crate 分层

| 层 | crate/目录 | 主要职责 | 当前边界 |
| --- | --- | --- | --- |
| 确定性内核 | `qx-core` | 定点数、身份、时间戳、事件、订单状态、Ledger、重放、产品规格 | 领域基础较稳定；公共导出面较宽 |
| 数据与研究输入 | `qx-guanxing`、`qx-data`、`qx-provider`、`qx-datastruct`、`qx-factor` | 数据源、质量门、PIT、数据集清单、列式帧、因子定义/工件/候选绑定 | `DataProvider`、`Bar` 等同名模型仍有多个主人；因子物化未进入生产运行时 |
| 交易领域 | `qx-risk`、`qx-zhenlu`、`qx-xingban`、`qx-genglu` | 风控规则、OMS、信号合并、Venue/Paper、Bar/L1/L2 撮合、费用/保证金、对账与归因 | 规则复用较好；权益、对账、风险投影仍有重复读模型 |

| 运行时与持久化 | `qx-runtime`、`qx-storage`、`qx-orchestrator` | RuntimeConfig、LiveEventPipeline、监督、健康、EventLog、Outbox、队列、文件/SQLite/PostgreSQL/NATS | `qx-runtime` 职责密集；文件/PG EventLog 写侧仍存在全量内容成本 |
| 传输与适配器 | `qx-adapter`、`qx-api` | Binance、CCXT、HTTP/TLS/WebSocket、API 读写面 | 真实供应商验收未完成；API 是自研 HTTP/WS 最小实现 |
| 策略与绑定 | `qx-strategy`、`qx-python`、`python/`、`cpp/` | Rust Strategy、C ABI、共享 ring、Python worker、PyO3/Arrow、C++ SDK | 多语言契约已版本化，但加载/注册/发布治理未统一 |
| 产品壳 | `qx-cli`、`deploy/`、`build.*`、`.github/` | 单一 CLI、worker 装配、模板、构建、CI、运行入口 | `qx-cli` 是 21 个内部 crate 的装配中枢，耦合度最高 |

直接依赖图没有发现正常生产依赖环，但存在两个仅在测试边上的环：

1. `qx-risk -> qx-zhenlu` 为正常依赖，`qx-risk --dev -> qx-zhenlu` 用于一致性测试。
2. `qx-runtime -> qx-execution` 为正常依赖，`qx-execution --dev -> qx-runtime` 用于执行契约测试。

这两个环不会破坏默认构建，但说明测试仍通过反向拉应用层，长期会增加拆分和独立发布成本。

### 3.2 依赖热点

- `qx-core` 是最广泛共享的基础契约，承载身份、数值、订单、事件、账簿、交易规格等多种语义。
- `qx-cli` 同时负责命令分派、配置解释、回测装配、worker 启动、API 启动、Paper、CCXT/Binance 接线、产物读写和大部分端到端验证。
- `qx-runtime` 同时负责配置 schema、worker policy、监督/停机、策略契约、事件管线、后端切换和数据绑定。
- `qx-storage` 同时实现 EventLog、Outbox、控制面、作业队列、快照、审计、消费者状态和多个后端。

这不是立即需要“按文件拆分”的问题，而是应用边界已经成为未来演进的瓶颈。

## 4. 核心领域模型与详细实现

### 4.1 身份、数值与产品规格

`qx-core` 使用 `Fixed`/`Money`/`Price`/`Quantity` 的 `i128` 定点数，统一 `SCALE`，热路径避免浮点。身份分成：

- `CanonicalProduct`：产品层语义。
- `InstrumentId`：交易标的身份。
- `MarketId`：市场/交易场所组合身份。
- `VenueId`/`VenueFamily`：执行场所类别。
- `DataSourceId`：行情/研究数据来源，位于 `qx-guanxing`，不覆盖交易身份。
- `TradingInstrumentSpec`：价格 tick、数量 step、最小量、乘数、结算币种、产品/保证金/持仓模式等执行规格。

这是项目最重要的正确性设计之一：数据源身份、产品身份、执行场所身份和结算账户身份没有被压成一个字符串。

仍需改善的是构造方式。部分调用点仍需组合 `InstrumentId`、产品、规格、账户和 venue 才能完成一次风控/记账；如果继续以散落的参数组合扩展产品，会形成“规格/乘数/结算币种/保证金模式”的组合爆炸。

### 4.2 订单与状态机

`OrderStatus` 主要状态为：

```text
PendingSubmit -> Submitted -> Accepted -> Working
                                  |          |
                                  |          +-> PartiallyFilled -> Filled
                                  |          +-> CancelPending -> Cancelled/Filled
                                  +-> Unknown -> reconcile -> known state
```

关键安全语义：

- `Submitted` 表示本地提交意图已经离开本地，不代表交易所接受。
- 网络错误、空回包或不确定回报进入 `Unknown`/待对账，禁止自动补单。
- 终态不能回退。
- `OrderTrace` 将 strategy/signal/intent/rule version 传入成交事实。
- `client_id` 需要跨策略轮次稳定唯一；最新代码已把 `round_scope` 纳入策略订单身份，修复了每轮从 1 重新计数造成的幂等误杀。

当前风险是 `OrderStatus`、Venue 回报、对账问题、执行事件和多腿组状态分布在多个 crate，状态迁移合法性虽然由测试保护，但外部适配器新增状态时仍需要同时修改多个表。

### 4.3 事件与 Ledger

`EventKind` 是事实词汇表，事件带有：

- `(ts, prio, seq)` 因果全序。
- `receive_time`、`engine_time`、`source_seq`。
- `correlation_id`、`EventMetadata`、`EventContext`。
- `source_id`、`source_kind`、`dedup_key`、`rule_version`。
- `run/account/portfolio/strategy/signal/intent` 等作用域。

`Priority` 将 timer、feedback、market、command、match、apply、post 排出因果顺序，防止策略先看到尚未到达的行情或成交结果。

`EventLog` 的 `append_checked`、`validate`、`ReplayVerifier::replay` 构成单一重放内核：逐条接受事件、重新应用 `LedgerApplied`、最后校验整本日志。回测产物不是只保存一个“看起来一致”的 hash，而是同时声明日志摘要、事件数量和 Ledger 条数。

这是目前最完整的正确性闭环；建议保持“一个事实流、一个重放内核、多个投影”的原则，不再给 API、回测、Paper 或语言绑定增加第二个账本。

## 5. Runtime / Engine 与执行链路

### 5.1 LiveEventPipeline

`qx-runtime::LiveEventPipeline` 在进程内持有：

- `EventLog`。
- `Ledger`。
- `Oms`。
- 最新 mark/quote。
- 账户余额/持仓/资金费观察值。
- 成交去重集合。
- `RuntimeEventStore` 与 Outbox 投影游标。
- 管线指标计数器。

`ingest()` 采取以下策略：

1. 刷新最新 EventLog。
2. clone 当前管线形成 staged 状态。
3. 根据外部事件映射成核心事实和优先级。
4. 做 correlation/dedup/fill 去重。
5. 将事实写入 EventLog，更新 Ledger/OMS/观察读模型。
6. 写 Outbox 或推进投影。
7. 共享写冲突最多重试三次。

读面和写面已经分开：读模型走 `ReadOnly`，写 worker/提交路径走 `ReprojectOnOpen`。这修复了“每个 GET 都重投整本 Outbox”的严重副作用。

### 5.2 回测链路

```text
runtime.json / CLI 参数
  -> Dataset/BarFrame/DepthFrame 读取
  -> 数据质量、时间严格递增、输入 fingerprint
  -> Strategy / BuiltinStrategy / Python / C++ contract
  -> Signal / TargetPosition / OrderIntent
  -> RiskGate + ExecutionCostRules + TradingInstrumentSpec
  -> Bar / L1 Tick / L2 OrderBook MatchingEngine
  -> Fill / LedgerApplied / EventLog
  -> ReplayVerifier
  -> summary/equity/fills/run manifest
```

三档撮合不会伪造数据能力：

- Bar 只接受 `next_bar_open`、`best_price`、`one_tick_slippage` 这类 OHLCV 可诚实支持的模型。
- L1 使用一档报价与概率/容量模型。
- L2 直接消耗深度帧，不从 Bar 猜盘口。
- A 股规则链单独处理 T+1、整手、停牌、涨跌停、公司行为和费用。

### 5.3 Paper 链路

```text
Scheduler
  -> Strategy worker
  -> ControlPlane submit/audit
  -> persistent command queue
  -> Paper execution worker
  -> ExecutionGateway
  -> PaperVenue::on_quote
  -> Accepted / Filled / Rejected / ReconcileRequired
  -> EventLog + Ledger + Outbox
  -> snapshot/report/API
```

Paper 和回测共享风控、费用、延迟、保证金和事件归约规则，但不是同一台撮合器：Paper 以真实 L1 quote 的首档 touch 产生成交，回测按数据档位使用不同撮合内核。README 已明确这一点，后续文档不应再使用“完全同一撮合机”的表述。

### 5.4 Live/Adapter 链路

- `qx-adapter::BinanceSpotVenue`：REST 签名、用户流、余额、订单、成交、对账。
- `qx-adapter::CcxtProcessVenue`：通过 Python `qianxing_ccxt.worker` 运行公共 CCXT REST/交易边界。
- `qx-execution`：统一订单登记、风险、Venue 副作用、执行事实归约、回报精度闸门、未知结果保护。
- `qx-genglu`：订单/余额/远端未知订单等对账报告。

最新代码已经补上若干无预算等待：PostgreSQL 建池握手 5 秒预算，策略 worker 和事件 consumer 的 stdin 写入也受 timeout 保护，CCXT 用户流/行情通道有重连预算。但真实交易仍未达到 sandbox/production evidence 等级。

## 6. 资产、市场与交易规则抽象

### 6.1 多资产数据抽象

`qx-data` 提供 `Bar`、DatasetBundle、组件 manifest、Provider、Registry、Storage、Validation；`qx-guanxing` 提供 `DataView`、`QualityGate`、金融记录的 `as_of()` PIT 视图和 `DataSourceId`。

已有正确性设计：

- 输入帧不自动排序后悄悄继续，乱序/非严格递增会被拒绝。
- 数据指纹覆盖真正读到的输入，而不是只覆盖配置声明。
- 数据组件可用 bundle manifest 绑定，防止 bars 与策略研究工件错配。
- A 股公司行为和交易日历有跨语言夹具与 PIT 取证。

主要问题：`qx-data::DataProvider` 与 `qx-provider::DataProvider` 同名但语义不同；`qx-data::Bar`、`qx-guanxing::Bar`、`qx-datastruct` 的帧形状也存在相邻模型。建议保留“输入帧”和“运行时可见行情”两个概念，但使用明确的 `DatasetBar`、`MarketBar`、`QuoteTick` 名称和显式转换接口。

### 6.2 交易规格与产品

`TradingProduct`、`MarginMode`、`PositionMode`、`PositionSide`、`OrderPolicy`、`MarginState` 和 `TradingInstrumentSpec` 位于 `qx-core`，回测、Paper、CCXT、Binance 都应该以规格为唯一来源。

当前规则门禁已经覆盖：

- 价格、数量、最小量精度。
- 现货/永续/期货的乘数和结算币种。
- leverage、margin mode、position mode。
- 现货禁空和衍生品做空。
- 费用、资金费、保证金和 funding 事实。

仍存在三把“权益尺子”：Ledger `equity_for`、Paper margin valuation、StrategyContext 的 available margin。下一阶段应定义 `ValuationContext`/`AccountValuation`，统一标的价格、汇率、乘数、保证金与缺价诊断。

## 7. 插件、扩展与多语言绑定

### 7.1 `qx-plugin`

当前真实能力：

- `Manifest`：id/version/kind/provides/requires/replaces/capabilities/permissions/schema。
- FNV manifest hash、可选 Ed25519 签名。
- 独占扩展点冲突检查。
- 依赖缺失和环检测。
- `Registry::resolve_order` 计算启动顺序。
- 扩展点当前只保留真正被内核装配的 `Matcher`、`FeeModel` 两类。

当前不具备：

- 运行期动态发现。
- 热插拔和热升级。
- WASM sandbox。
- 统一把 C ABI 动态库、Python worker、finkit provider 注册进同一个 Registry。

`qx-strategy::DynamicCAbiStrategy` 另有 `libloading` loader、SHA-256、可选 Ed25519 校验和 vtable ABI 校验。它解决的是“受信任 native library 的应用侧加载”，不是 `qx-plugin` 的运行时插件系统；两套机制需要明确区分，否则调用者会误以为 manifest 签名覆盖了动态库加载安全。

### 7.2 Python

两类边界并存：

- `qianxing_strategy`：Jsonl、framed JSON、shared-memory JSON、shared-memory columnar worker。
- `qianxing_ccxt`：CCXT REST/交易子进程。
- `qianxing_bridge` 与 `qx-python`：PyO3 原生扩展、Arrow C Data Interface、BarFrame digest 和 Python wheel。
- `qianxing_ashare`：A 股数据/标准化/公司行为工具链，部分能力由 Rust 读取其导出的 JSON，而不是在 Rust 内直接调用 Python 模块。

优点是跨进程故障隔离、版本化 JSON、超时和 stderr 诊断已较完善。缺点是 Python worker 的协议、schema、超时、身份、父进程监督分散在 `qx-runtime`、`qx-cli`、`python/` 和 `schemas/` 多处，尚无独立协议包或自动生成代码。

### 7.3 C++

`cpp/include/qianxing_strategy.h` 与 `qx-strategy/src/c_api.rs` 通过静态门禁逐字段比对 `repr(C)` 结构、枚举值、vtable 顺序和 ABI 版本。C++ ring、JSONL 和 shared-memory worker 有 CI smoke。

但 CI 目前不把构建出的 C++ 动态库真正交给 Rust `DynamicCAbiStrategy::load_verified` 进行 host-side load。这留下了“SDK 自己能工作”和“Rust host 能安全加载 SDK”之间的证据缺口。

## 8. finkit 集成边界

当前 `qx-factor` 的边界是有意的“研究工件消费协议”，不是把 finkit 拉进交易内核：

1. `FactorProviderBinding::finkit` 写入 provider/version/schema/digest。
2. `validate_finkit_artifact` 校验工件摘要与 binding 一致。
3. `ResearchSnapshot`/CandidateBinding 带策略版本、数据 fingerprint、PIT、事件回测证据和候选暴露。
4. `readiness`、Strategy binding 和 StrategyContext 会校验研究快照血缘。
5. 具体 finkit 计算、物化、增量物化和运行计划编译在仓库外完成。

当前明确缺口：

- `FactorMaterializer::materialize`、`materialize_incremental`、`compile_execution_plan`、`compute_momentum`、`validate_finkit_artifact` 没有进入 CLI 的生产装配。
- `artifacts[].values` 主要用于 PIT/指纹校验，策略下单数量取自 `candidate.intended_exposure`；因子值修正不会自动改变订单决策。
- 没有 finkit connector、任务队列、工件注册中心、缓存、失败重试和版本兼容矩阵。

因此应明确二选一：

- 继续保持“外部研究平台 + Qianxing 只验收工件”，就删除/隐藏未接线的物化生产暗示，并把接口契约写得更清楚。
- 立项做真正桥接，就新增 `qx-factor-runtime`/外部 finkit adapter，定义工件输入、计划、输出、缓存 key、PIT 证据和策略消费的端到端验收，不要只把 `materialize()` 调进 CLI 就算接通。

## 9. 配置、存储、错误与可观测性

### 9.1 配置

`RuntimeConfig` 使用 `schema_version`、`deny_unknown_fields`、环境闭合词表、worker role、storage、messaging、scheduler、strategy 和多策略配置。配置校验覆盖：

- feature 与 backend 一致性。
- production 需要事务性存储与完整凭据/规格。
- 明文 API 只能绑定回环地址。
- credential env/file 不进入日志和摘要。
- path 相对 runtime 配置解析并有模板查找/内置模板兜底。
- runtime fingerprint 可锁定配置。

配置面已经较成熟，但 `RuntimeConfig` 仍是一个巨型 schema。建议下一版本将其拆成 `TopologyConfig`、`StorageConfig`、`SecurityConfig`、`StrategyConfig`、`MarketConfig`、`ObservabilityConfig`，外部 JSON 继续提供 envelope，内部用模块化校验器。

### 9.2 存储

当前后端：

- 文件 JSON/分段 EventLog、文件 Outbox、控制面、作业队列、审计、消费者状态。
- SQLite 事务 EventLog/Outbox/队列/审计/快照。
- PostgreSQL 事务接口、连接池、advisory lock、租约/fencing、审计/Outbox/消费者状态。
- NATS JetStream publisher/consumer，带 connect/request/pull wait budget。

正确性方面，至少一次投递、幂等 event_id、lease/fencing、原子写、审计 hash chain、backend switch fail-closed 都已有测试。

性能方面有明确结构性问题：

- 文件后端写 EventLog 会读取旧日志、比较前缀、重新序列化整本日志并原子替换。
- 分段后端虽然让满段不可变，但每次 `write()` 仍遍历全部 chunk，并重新读取/校验整本日志。
- PostgreSQL EventLog 当前仍把整本日志放在 `qx_event_logs.content` 中更新，不是按事件增量行写入。
- `LiveEventPipeline::ingest_once` 先 clone 整个 pipeline；刷新和多 worker 之间还会重复重放。
- 当前没有 retention、compaction、snapshot + tail、冷热归档或按账户/租户分区策略。

已有仓库量具表明，日志从约 1000 增长到 8000 时，写侧 tick 和一次追加大致按线性比例放大；分段后端没有消除该成本，反而有约两成稳态写入开销。

### 9.3 错误模型

`QxError`、`StorageError`、`ControlError`、`ProtocolError` 和 CLI 字符串错误共同存在。当前实践是：

- 业务拒绝、未知交易结果、存储冲突、供应商错误和内部不变量尽量分开。
- CLI/API 对失败路径 fail closed。
- 不再把缺失金额伪造成 0。
- API 状态码已区分 400/403/404/409/429/500/503。

问题是跨 crate 的错误仍需经字符串包装，调用方难以稳定按机器码处理。建议建立共享 `qx-error`/`qx-contract` 错误码层：错误码、重试性、是否可安全重放、是否需要对账、用户消息和内部上下文分离。

### 9.4 可观测性

已有：

- worker health/heartbeat/overall readiness。
- API `/health`、`/ready`、`/metrics`。
- Prometheus 文本指标、worker metrics 文件聚合、stale/down 语义。
- EventLog/Outbox/queue/reconcile/report/run manifest 产物。
- Python worker stderr tail、退出码、来源和 broken pipe 诊断。

限制：

- `qx_pipeline_*` 当前主要在 Paper worker 侧按进程累计，API 读路径和 live venue worker 仍未完整纳入同一量纲。
- 目前没有统一 trace/span ID 跨 CLI → worker → EventLog → API → provider 传播的可查询实现。
- 没有标准化 JSON structured log、日志级别、敏感字段 redaction policy 和 incident correlation 规范。
- readiness 能识别许多“不具备条件”的情况，但没有统一 capability/feature 状态 API。

## 10. 三轮架构与链路审计

### 第一轮：主体流程和核心链路是否完整贯通

| 链路 | 结论 | 证据与缺口 |
| --- | --- | --- |
| 配置 → 校验 → 路径解析 → 装配 | 已贯通 | `RuntimeConfig`、deploy lookup、fingerprint、runtime-check、模板覆盖测试；配置 schema 仍偏大 |
| Bar 回测 | 已贯通 | 输入 fingerprint、策略、风控、撮合、Ledger、ReplayVerifier、四类产物；两条 Bar 链元数据/结果区分仍需长期保持一致 |
| L1/L2 深度回测 | 已贯通 | `DepthFrame`、L1/L2 规则、容量、因果和产物；缺少更高阶真实市场数据验收 |
| A 股规则 | Rust 侧已贯通 | 公司行为、PIT、交易日历、涨跌停、T+1/整手等有测试；Paper A 股提交因缺完整结算状态而主动拒绝 |
| Paper | 已贯通 | process-boundary E2E、重复运行、缺行情终态、风控/队列/账簿/审计均有用例 |
| API/API projection | 已贯通 | 17 HTTP routes + WebSocket upgrade，读模型与实际落盘链路已接通；自研 HTTP 解析器能力有限 |
| CCXT/Binance | 代码链贯通，外部证据不足 | 适配器、submit、回报、重连预算、对账、未知结果保护存在；`sandbox_tested=false` |
| 调度 | 基础 Cron/Any 已贯通 | 生产 tick 支持的形状有限，calendar/event/manual 形状被拒；自动重试链无生产装配 |
| finkit/研究 | 读侧贯通，写侧未贯通 | 研究快照可校验并绑定策略；因子物化和因子值消费未进入生产决策 |
| 发布 | 工程门禁贯通，发布供应链未完整 | build scripts、CI、wheel/C++ smoke 存在；没有完整 tag/release/sign/SBOM/deploy workflow |

第一轮结论：核心“本地可复核交易循环”完整；真实外部系统和研究生产平台是明确的边界，不应被错误宣传为已贯通。

### 第二轮：孤儿逻辑、重复抽象、循环依赖、状态机/并发/生命周期风险

#### 孤儿或半接线逻辑

1. `qx-factor` 的物化/计划编译/finkit 校验多数只有库内测试和 ecosystem smoke 读者。
2. Python A 股大部分能力是仓外运行/导出边界，Rust 没有全量调用路径；需要保持“外部工具”定位或增加漂移验收。
3. `qx-plugin` 的 manifest registry 与 `DynamicCAbiStrategy` 动态库 loader 没有统一装配关系。
4. `qx-scheduler` 的 calendar/event/manual/retry 能力有类型和测试，但生产 tick 不消费全部形状。
5. 五类 ControlCommand 已被“提交即拒绝”收口，避免假装受理；长期应删除未支持的外部入口或真正实现执行者。
6. 账户级 margin/frozen/realized/unrealized/funding 等字段目前诚实地输出 null，但下游如果把快照当完整账务会误解。

#### 重复抽象

- `DataProvider` 至少两个公共 trait。
- `Bar`、`CorporateAction`、`StrategyContext`、`RetryPolicy` 等存在跨 crate 同名类型。
- 对账类型族分散在 adapter/genglu/api/runtime/execution。
- `RiskDecision`、`OrderRiskDecision` 与执行侧风险结果各自承担相邻语义。
- 权益/保证金存在多套 ruler。
- 文件、SQLite、PostgreSQL 后端仍有大量相似读改写/幂等/队列逻辑，契约测试共用但实现没有完全模板化。
- `qx-runtime` 与 `qx-cli` 都承担运行时装配；`qx-orchestrator` 和 runtime supervisor 的生命周期边界需要进一步单一化。

#### 循环与耦合

- 正常生产依赖图没有环。
- 两个 dev-only 环允许 Cargo 构建，但测试依赖应用层反向拉核心领域，阻碍独立编译和发布。
- `qx-cli` 是显著的依赖汇聚点，任何领域模型改动都可能触发 CLI、产物、门禁和文档联动。

#### 状态、并发与生命周期

- 订单 `Unknown`、多腿 `ReconcileRequired/HedgeRequired` 的 fail-closed 逻辑较好，但每个新 Venue 都必须正确接入相同回报门禁和规格冻结。
- Outbox 是至少一次；写面启动补投影可能重放已 ack 事件，消费端必须严格按 event_id 幂等。
- file/segmented/PG EventLog 的追加在大日志下会线性变慢。
- `LiveEventPipeline` clone + refresh + 最多三次重试能保护一致性，但不是高并发写优化方案。
- worker 监督、Python 子进程、API 连接线程、WebSocket 会话和停止令牌已建立边界；真实 OS signal → shutdown 的生产演练仍缺。
- `run_paper_submit_order` 仍登记了 Accepted 到终态回写之间的队列失败窗口，不能贸然覆盖常驻 worker 的裁决。
- 动态 C ABI 是 native code in-process；签名/摘要只能认证文件，不能提供内存安全或 sandbox。

第二轮结论：未发现“默认路径立即会错误下单”的新断裂，但发现了“概念已经出现、生产消费者不完整”和“日志规模增长后会拖慢 worker”的结构性风险。

### 第三轮：扩展性、性能、API 稳定性和工程化成熟度

#### 扩展性

- 新增一个 Venue 需要实现 adapter、回报映射、规格、worker role/入口、对账、配置模板、能力矩阵和契约测试多个点。
- 新增一种数据组件已有 `dataset_component_paths` 扩展机制，方向正确；但组件 schema、读模型和 provider registry 仍分散。
- 新增一种策略语言要同时接 Strategy trait、strategy contract、worker transport、订单身份、超时、stderr、CI 和 schema。
- 新增插件目前只能静态装配，无法作为独立分发单元动态升级。

#### 性能

主要瓶颈按优先级：

1. EventLog 全量读/校验/序列化/重放。
2. `LiveEventPipeline` 全状态 clone。
3. 多 worker 共享同一账户日志时的重复 refresh/replay。
4. 文件 Outbox 每事件文件和读改写锁。
5. PostgreSQL EventLog 的整本 JSON content 更新。
6. API 读模型每请求重新构造部分投影，虽已移除读面写副作用，但仍需缓存/版本化 snapshot。

#### API 稳定性

已有 schema v1、`deny_unknown_fields`、快照 hash、C ABI 字段比对、strategy contract v1 和错误状态码门禁，这是优点。

仍缺：

- 公共 Rust crate 都是 `0.1.0`，没有 SemVer policy、deprecation window、migration guide。
- API 路由、JSON Schema、事件类型、CLI 参数、C ABI、Python contract 没有统一生成的兼容性报告。
- 自研 HTTP parser 只处理单请求连接和有限 HTTP 形状，URL query 解析也不是完整 RFC 解析。
- 事件和 projection envelope 没有独立 schema registry、兼容矩阵和跨版本回放测试。

#### 工程化成熟度

已有 CI 维度很丰富：Rust fmt/clippy/test、架构门禁、Python wheel 3 OS × 3 Python、feature matrix、Postgres/NATS service container、Paper E2E、C++ SDK smoke、可选 Binance testnet acceptance。

缺口：

- 没有独立 release workflow，CI 更像验证流水线而不是发布供应链。
- 没有 lockfile 策略、依赖漏洞扫描、SBOM、可复现构建证明、签名发布物和 provenance attestations。
- 没有 Docker/Kubernetes/迁移回滚/容量压测/长期 soak/故障注入作业。
- Postgres/NATS contract 需要真实 service container；本地缺 Docker 时不能把“未跑”解释成“已验证”。

第三轮结论：项目的测试工程化明显领先于运行时性能和发布供应链；下一阶段应减少源码形状门禁的边际投入，把资源转移到可量化的性能、兼容、故障和外部环境证据。

## 12. 建议目标架构

目标不是继续堆 crate，而是把“稳定事实契约”“应用编排”“外部适配器”“启动壳”分开。

```text
                    +------------------------------+
                    | qx-cli / deploy / operators  |
                    +---------------+--------------+
                                    |
                    +---------------v--------------+
                    | Application services         |
                    | backtest / paper / live / API|
                    +---+-------------+-------------+
                        |             |
              +---------v--+   +------v---------------+
              | Runtime    |   | Ports / contracts    |
              | engine     |   | execution, store,    |
              | supervision|   | scheduler, research  |
              +------+-----+   +----+-----------+-----+
                     |               |           |
       +-------------v--+    +-------v--+   +----v-------------+
       | Domain kernel   |    | Storage  |   | External adapters|
       | core/risk/OMS/  |    | EventLog |   | Venue/Data/Python |
       | ledger/matching |    | Outbox   |   | C++/finkit       |
       +-----------------+    +----------+   +------------------+
```

### 12.1 稳定核心

建议收敛一组稳定类型：

- `AccountScope { tenant, account, portfolio, venue, settlement_currency }`。
- `InstrumentRef { instrument, product, market, venue }`。
- `MarketSpec`，统一价格/数量/乘数/保证金/结算/fee/position 规格。
- `EventId`、`CorrelationId`、`SourceOffset`、`OrderId`。
- `ExecutionFact`：Accepted、Fill、Cancelled、Rejected、Unknown、ReconcileRequired。
- `ProjectionVersion`/`SchemaVersion`。
- `ValuationContext`/`ValuationResult`。

`qx-core` 保持纯确定性，不依赖 runtime、storage、网络、Python、C ABI。

### 12.2 事件存储与投影

推荐的持久化形状：

```text
event_log(log_name, seq, event_id, ts, prio, kind, payload, dedup_key, source_seq, digest)
outbox(event_id, topic, partition_key, payload, attempts, lease, status)
projection_checkpoint(projection, log_name, seq, state_hash)
snapshot(log_name, seq, state_hash, compressed_state)
```

一个 `append_batch()` 事务同时完成 EventLog、Outbox、checkpoint 前移；消费者以 event_id 幂等，以 fencing token 更新 checkpoint。文件后端可以实现同一语义的 WAL + immutable segments；不能再以全量 JSON overwrite 作为长期主路径。

### 12.3 Runtime

`runtime-engine` 只负责：

- 事件输入、事实归约、投影更新。
- worker command/job 的生命周期。
- 统一时钟、停机、健康和重试策略。

`runtime-config` 只负责 schema、默认值、路径、能力校验和 fingerprint。

`runtime-supervision` 只负责 worker/process/thread、timeout、graceful shutdown、exit classification 和 restart policy。

### 12.4 扩展策略

分成三类，不再统称“插件”：

1. **编译期组件**：Rust 内置策略、撮合器、费用模型。
2. **受信任 native extension**：C ABI，必须显式签名、版本、信任根和运行 profile。
3. **隔离外部 worker**：Python/CCXT/finkit，走 versioned IPC、资源预算、stderr、父子进程监督和独立 artifact digest。

如果未来需要热插拔，优先引入 WASM/独立进程沙箱，而不是继续扩大 in-process `libloading`。

## 13. 迁移路线

### M0：基线冻结，1 个迭代

- 冻结 EventLog、snapshot、strategy contract、C ABI、account snapshot、CLI JSON 的当前 schema。
- 将 `maturity/capabilities.yaml` 拆成机器可读事实和人工限制说明两部分。
- 保留当前 555 项门禁，但新增“代码测试 / 本地 E2E / 沙盒 / 生产”四级证据导入格式。
- 建立性能基线：N=1k/8k/32k 事件的 append、refresh、replay、read model、recovery p50/p95。

### M1：契约去重，1–2 个迭代

- 新增 `qx-contract` 或在 `qx-core` 中建立稳定 contract 子模块。
- 先迁移 `EventId`、`AccountScope`、`MarketSpec`、`ExecutionFact`、`ReconcileReport`。
- 为 `DataProvider`、`Bar`、`StrategyContext`、`RiskDecision`、对账类型建立命名/转换矩阵。
- 把错误码从字符串中抽出，保留原有中文 message 作为展示层。
- 把两个 dev-only 依赖环迁移到 contract-tests。

### M2：EventLog 增量化，2–3 个迭代

- 先实现 SQLite `append_batch` + Outbox 同事务，作为正确性参考后端。
- 再实现 PostgreSQL 行式 EventLog/Outbox，保留现有 advisory lock/fencing 语义。
- 文件后端新增 WAL/immutable segment + snapshot，旧 JSON 只做导入/迁移。
- `LiveEventPipeline` 改为 cursor 增量 refresh，减少全量 clone。
- 增加 kill -9、磁盘满、重复 relay、半提交、并发 append 的故障注入。

### M3：运行时拆边界，2 个迭代

- 把 RuntimeConfig、Engine、Supervisor、StrategyContract 分模块/独立 crate。
- 把 `qx-cli` 中 backtest/paper/live/api 的装配抽为 application service。
- `qx-orchestrator` 只保留进程规划/管理，`qx-runtime` 只保留 worker contract/supervision，不再重复管理。
- 统一 worker lifecycle 状态：Starting、Ready、Degraded、Stopping、Stopped、Failed、Unknown。
- 接入真实 OS signal、Windows stop 语义和 join 超时的长驻测试。

### M4：研究与 finkit，按产品选择推进

如果选择“外部研究平台”模式：

- 保留 `FactorProviderBinding` 和 snapshot reader。
- 删除或标记所有未被生产装配的 materializer 入口。
- 明确 Candidate 的 intended exposure 是唯一交易输入，artifact values 只做证据和 PIT 校验。

如果选择“内置研究生产”模式：

- 新增 finkit adapter/worker 和 artifact registry。
- 让 `compile_execution_plan -> materialize -> candidate -> strategy` 有真实生产消费者。
- 用“修改 artifact value 必须改变策略输入或明确被过滤”的行为测试钉住语义。

### M5：外部 Venue 与发布证据，持续迭代

- 每个 Venue 按统一 acceptance matrix 运行 sandbox。
- 生产 profile 只允许通过 evidence gate 的 adapter/spec/credential/environment 组合。
- 发布物同时输出 binary/wheel/C++ SDK、SBOM、签名、hash、source commit、schema registry version。
- 把 CI 的可选 Binance testnet 变成按环境受控、定时、脱敏、可审计的 acceptance workflow。

## 14. 验收标准

### 14.1 主链路

- 同一输入在 debug/release、Rust/Python/C++ strategy 下，`result_hash` 相同；构建身份变化只改变 manifest digest。
- 回测完成前必须通过输入 fingerprint、market spec、risk/cost binding、ReplayVerifier。
- Paper 同日重跑只显示新增事实；零新增不得宣称重新完成端到端交易。
- 缺行情、缺规格、未知 Venue 回报、重复回报、过期 lease、非法精度、未知订单均 fail closed。

### 14.2 事件与存储

- EventLog/Outbox append 是增量写，不随历史长度做全量序列化。
- N=1k、8k、32k 事件的单次追加 p95 不应呈线性翻倍；目标是固定上限内的近似常数增量，恢复时间按 snapshot tail 长度可预测。
- EventLog、Outbox、snapshot、projection checkpoint 在崩溃后满足：不丢事实、不重复记账、重复投递可去重、旧 fencing token 不能 ack。
- 迁移旧 JSON/旧 segment/旧数据库必须有显式版本和回滚/拒绝策略。

### 14.3 状态与生命周期

- 所有 Venue 都通过同一 `ExecutionFact` reducer 和同一精度/终态门禁。
- 每个 worker 能报告启动、就绪、降级、停机、退出原因和最后 heartbeat。
- 每个阻塞 I/O 都有 timeout：DB connect、HTTP、WS、stdin/stdout、queue claim、handler、shutdown join。
- `SIGINT/SIGTERM`、Windows stop、kill -9、子进程不读 stdin、子进程无响应均有自动化用例。

### 14.4 API 与跨语言

- API、snapshot、strategy contract、C ABI、Python SDK 使用同一 schema 版本矩阵。
- 新字段默认兼容、未知字段按契约拒绝；删除字段至少有一个 deprecation cycle。
- Rust/C++ vtable、Python worker、shared-memory header、JSONL/framed payload 均由 golden corpus 交叉验证。
- API 不再手工解释不完整 HTTP；若继续自研，必须有 framing、URL、header、keep-alive、WebSocket control frame 的覆盖表。

### 14.5 finkit

- 若只消费外部工件：文档、capability、readiness 和代码均明确“Qianxing 不生成因子值”。
- 若内置：工件 digest、PIT、execution plan、materialization cache、candidate、strategy decision、order trace 形成一条可复核血缘；修改任一输入都能证明哪些订单变化。

### 14.6 发布与运维

- 一个 tag 生成可复现 Rust binary、Python wheel、C++ SDK artifact，并带 commit、target、profile、schema、SBOM、签名和 hash。
- feature matrix：sqlite、postgres、nats、postgres+nats 全部 check/test/clippy。
- service-backend contract 在真实 Postgres/NATS service container 中执行，而不是仅编译 ignored tests。
- venue acceptance 无凭据时明确输出 `skipped`，有凭据时输出受控 evidence；二者不能都显示为绿色“production ready”。

## 15. 最终建议

当前不建议再优先增加更多策略、更多 Venue 或更多配置模板。下一阶段优先级应为：

1. 先把真实交易的 sandbox evidence、EventLog/Outbox 事务语义和凭据/权限边界做成可审计的 P0。
2. 再做 EventLog 增量写、snapshot + tail、Pipeline cursor，解决规模增长后的确定性性能问题。
3. 同步收敛公共模型、错误码、权益尺子和运行时职责，降低 `qx-cli`/`qx-runtime` 的装配耦合。
4. 明确 finkit 是“外部工件边界”还是“内置研究生产链”，不要长期保持半接线状态。
5. 最后完善插件命名、API 兼容、发布供应链和运维故障注入。

在这个顺序下，牵星会从“测试和门禁非常扎实的单机研究/Paper 框架”，逐步成为“有清晰生产边界、可扩展、可观测、可证明恢复的交易运行时”。
