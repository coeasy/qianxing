> 日期：2026-11-22（复核更新）
> 评审范围：Cargo workspace、Rust 核心与应用层、CLI/Rust SDK、Python/C++/HTTP/Web 接入、回测/Paper/Live 主链路、构建与分发。
> 评审基线：2026-11-22 工作树的 `cargo metadata --no-deps`、`docs/module-map.md`、`docs/first-run.md`、`docs/installation.md`、`docs/release-scope-0.4.0.md`、`maturity/` 登记及相关源代码。工作树含未提交修改，本文的数量是该检查快照，不等于已发布版本；竞品只按其公开仓库/官方文档可见的工作流和边界比较，不推导未经同条件测量的性能结论。

## 2026-11-22 代码复核补记

本节把较早方案中的概括性判断落实到本轮能复核的仓库事实，并区分**已证实的结构性成本**和**需要门禁持续审计的风险**。计数来自 `cargo metadata --no-deps`；源码行数只用于定位审阅热点，不作为单独拆模块的理由。

### 本轮确认的架构事实

| 观察点 | 本轮工作树事实 | 结论与处理方向 |
|---|---|---|
| Workspace 边界 | 30 个成员：29 个 `qx-*` 包加 `contract-tests` | 规模本身不构成坏架构；需要区分可发布 SDK、应用二进制、内部实现和测试宿主，避免把 workspace 成员误当成公开产品。 |
| 内部依赖扇出 | 按不同 `qx-*` 包名计，`qx-sdk` 直接依赖 4 个内部包；`qx-app` 11 个；`qx-api` 14 个；`qx-cli` 24 个；`qx-service` 20 个 | SDK 与 CLI 的 registry 闭包是现实发布成本；API/service 是装配边界，依赖多不自动代表错误，但应由 crate DAG 检查禁止反向依赖和不必要传递依赖。 |
| 应用与入口职责 | `qx-app` 已按 cases、report_read、artifact_store 等目录拆分；`qx-api` 也有分域 adapter 子模块；Python `app.py` 仍保留稳定兼容导出和大量模型/入口 | 保留模块化单体和兼容 facade；逐步把 Python 模型按领域拆到内部模块，通过原路径重导出，避免一次性破坏公共导入。 |
| 高审阅优先级文件 | `qx-runtime/src/pipeline.rs`、`qx-api/src/app_surface/research_artifacts.rs`、`qx-api/src/lib.rs`、`qx-adapter/src/binance.rs`、`qx-zhenlu/src/lib.rs`、`python/qianxing/app.py` 均为较大源文件 | 这些是职责/状态机审阅热点；下一步要按函数调用图、事实 owner、错误路径和测试边界检查。禁止仅按行数机械拆分或新建同义 facade。 |
| 多语言契约 | 已有 `maturity/language_api_contract.yaml`、应用用例登记、Python/C++ HTTP 路由清单和架构门禁 | 当前已有防漂移基础。改进重点是让新增用例从登记、路由、SDK 到独立消费者形成闭环；检查失败要明确指出缺失语言、路由或生产消费者。 |
| 分发边界 | `qx-sdk` 的直接内部依赖包含 `qx-app`、`qx-execution`、`qx-provider`、`qx-strategy`；CLI 直接依赖 24 个内部包 | 单独发布一个门面 crate 不能自动消除传递闭包问题。先明确 crate 发布策略与 clean consumer 目标，再选择拓扑发布闭包或减少暴露/收拢实现；不要为过 crates.io 而把所有内部包无差别公开。 |
| 交易所证据 | README 与 `maturity/capabilities.yaml` 把代码能力和 sandbox/production 证据分开；没有实测证据的 scope 不应升级成熟度 | 连接器评审必须细到 venue × 产品 × 账户/持仓模式 × 操作/订单形状；统一 API 不能替代逐 scope 外部验收。 |

### 对标后更具体的差距

RQAlpha 的公开仓库把策略生命周期、数据入口、事件扩展和 analyser 拆成用户可理解的模块，并突出单命令运行和 Mod 扩展；Freqtrade 的回测文档给出直接的策略命令、多策略比较、费用、日期范围和交易导出参数；LEAN 把数据源、交易处理、实时事件、初始化和结果处理列为可替换 handler；Qlib 把原始数据、Loader、Handler、Dataset 和 Cache 串成可单独使用的数据工作流。牵星已经有更多显式身份、事件重放、数据质量与多语言边界，差距主要在**高层流程和稳定发布体验是否同样直接**，不应以增加 crate 数、策略数或抽象层来追赶。

因此，产品架构应保留“双层入口”：新用户走稳定高层命令/API，专家通过低层策略、端口和运行合同扩展。简单任务不应先要求用户理解 `BacktestSpec`、manifest、artifact reader 或运行时拓扑；高级接口则应通过类型化的能力/profile 选择暴露明确前置条件。

### 复核结论：已证实问题与待审计风险

**已证实并应优先处理：**

1. **Rust registry 发布被内部包闭包放大。** `qx-sdk` 目前直接连接多个 workspace 包，CLI 的依赖范围更大；发布前必须由 `cargo tree`/package dry-run 给出完整闭包及拓扑顺序。当前不能把“仓内可编译”当作“外部消费者可安装”。
2. **外部协议有多处人工维护点。** 用例登记、Rust export、Python/C++ route table、HTTP dispatch、语言映射和文档同时描述同一能力。已有静态门禁降低了风险，但新增入口仍可能只接通部分语言；每次新增用例必须有一张闭环变更清单与跨语言独立消费者验证。
3. **复杂度主要集中在运行/服务主路径和兼容门面。** 较大的 pipeline、API、adapter、execution 和 Python façade 应开展状态机/所有权审计；拆分时保留原有公共入口，先抽纯逻辑和合同测试，再移动装配代码。
4. **“代码支持”与“交易所可用”之间仍需按证据等级隔离。** 没有真实 sandbox/test 证据的订单类型、账户模式和恢复场景继续保持未验证状态；本地 mock、回放和 paper 只能证明其各自边界。
5. **性能对比缺少一致基准口径。** 不从语言、README 或局部微基准推断胜负；要对齐数据字节、费用/成交语义、线程数、硬件、缓存状态、输出和结果复核后才比较吞吐/内存。

**目前不应直接判为缺陷、但需持续审计：** crate 数量多、某文件行数高、模块化单体、基础设施依赖较多、模拟与 live 内核不完全相同。这些只有在造成不允许的依赖边、重复领域事实、不可独立测试、安装负担或可观察的运行断链时，才应进入重构任务。

## 1. 结论摘要

牵星当前最合适的方向仍然是**Rust 模块化单体 + 少量受控 worker 进程 + `qx-app` 用例边界 + 多语言薄客户端**。当前已经具备领域类型、确定性事件和回放、数据质量与 PIT、撮合、订单执行、应用用例、SDK、CLI、API、Paper 运行及报告产物等多层设计。主要架构风险不是缺少模块，而是模块和公共入口的复杂度已很高：一个 workspace 横跨几十个 crate 和多个语言/运行表面；内部 crate 之间大量使用同版本路径依赖；CLI 负责大量产品流程；各层还需要维护能力声明、schema、DTO、文档和发布状态的一致性。

建议保留核心领域设计，暂不改成微服务、不重写撮合/OMS、不做机械拆 crate。改进集中在五件事：

1. **固定领域事实所有权和依赖规则**，精简交叉依赖，减少“同一个事实多处归约”。
2. **收敛应用用例和运行主路径**，让 CLI、Python、HTTP 都调用相同的 `qx-app` 用例合同。
3. **把 Rust 可复用库与 CLI 产品的发布边界拆清楚**，解决 crates.io 发布必须发布整条内部依赖闭包的问题。
4. **把能力声明、版本化协议、兼容性和验收证据做成可检查的发布合同**。
5. **以用户可完成任务和可复现证据验收**：首次回测、Paper 恢复、报告复核、跨语言一致、外部连接器验证分别计量。

## 2. 当前架构地图

### 2.1 仓库产品面

当前是一个 Rust workspace，覆盖领域与基础设施 crate、`qx-app` 应用用例、`qx-sdk` 面向 Rust 使用者的门面、`qx-cli` 可执行产品及合同测试宿主。仓库还包含 Python 包及策略/CCXT 扩展、PyO3、C/C++ 接口、HTTP/WebSocket API、Web Console 和部署配置。它实际是一个**多入口、多运行形态的模块化单体仓库**，不只是 Rust library。

从现有 `docs/module-map.md` 和 crate 职责可归纳为以下逻辑分层：

```text
用户入口：CLI / Python SDK / Rust SDK / C-C++ / HTTP-WebSocket / Web Console
                         │
适配装配：qx-api / qx-cli / qx-python / qx-service / qx-orchestrator
                         │
应用用例：qx-app（研究、回测、实验、报告核验、Run 产物）
                         │
领域能力：qx-core / qx-strategy / qx-xingban / qx-zhenlu / qx-risk / qx-genglu
                         │
端口与基础设施：qx-data / qx-guanxing / qx-provider / qx-adapter /
                qx-execution / qx-storage / qx-runtime / qx-scheduler
```

图示表达的是建议的逻辑依赖，不意味着现有每条边都已完全符合，也不应把所有基础设施 crate 放在同一个运行时边界。

### 2.2 重要领域主链

**离线研究/回测：**

```text
输入与策略 → 数据/规则/PIT 预检 → Strategy 事件 → 撮合与费用/保证金
→ 确定性事件/账簿 → Run 与产物 → 回放/身份核验 → CLI/API/Python 报告投影
```

主要 owner 应是 `qx-app` 用例负责流程，领域 crate 负责业务事实，`qx-core` 负责确定性事件和身份合同，展示入口只做请求转换和结果呈现。

**Paper/Live 执行：**

```text
行情/账户事实 → OrderIntent → capability/精度预检 → 风控与预留
→ OMS/执行端口 → Venue adapter → 权威回报/用户流
→ EventLog 与账簿 → 对账/恢复 → 策略状态更新
```

该链路必须将“请求已发送”“交易所已接受”“成交/拒绝已确认”“响应未知需对账”作为不同状态。任何 connector 的接口统一都不等于交易语义一致。

### 2.3 当前设计值得保留

- Rust 持有确定性撮合、风险、执行和账务事实，Python/C++/CLI/API 作为接入与表达层。
- `qx-app` 被定位为跨 CLI/API/SDK 共用的用例和报告事实 owner，`qx-sdk` 是面向第三方的稳定 Rust 门面。
- EventLog、Run identity、报告核验、PIT 数据语义和能力/证据登记为可复现研究与恢复提供基础。
- Backtest/Paper/Live 能共享必要的策略和订单合同，同时允许时钟、数据源、撮合、网络和授权有明确差异。
- 已有 crate 依赖检查、跨 crate 合同测试、CLI 架构检查、发布范围文档等治理基础；后续应收敛为一套清晰的门禁，而不是再增加重复静态规则。

### 3.1 对标结论

竞品共同强项集中在清楚的产品主路径、共享核心语义、组合式扩展点、具体的撮合假设、可复用公开包和较短的真实示例。牵星的潜在差异化在于确定性重放、数据质量/PIT、多语言入口、连接器能力范围以及订单恢复证据。要形成优势，必须把这些能力变成少而稳定的默认流程；不能只增加代码模块、配置项和文档数量。

## 4. 架构与开发细节的不合理项

下表分为**结构性风险**与**需由依赖/调用审计确认的风险**。前者可从仓库结构和模块职责直接观察；后者需实施依赖图和调用图门禁，不能凭文件大小或 crate 数量断言已经发生循环依赖或运行时断链。

| 优先级 | 观察 / 风险 | 影响 | 优化决策 |
|---|---|---|---|
| P0 | workspace 内部包统一 `0.4.0`，内部依赖同时设置 `version` 与 `path`；例如 `qx-sdk` 仍依赖 `qx-app`、`qx-execution`、`qx-provider`、`qx-strategy`，CLI 依赖大量内部 crate。 | 源码 checkout 构建可正常，但 registry 消费者看不到这些 path crate；任一库发布就要求其完整内部依赖闭包先上 registry 并版本兼容。`cargo install` CLI 的发布面也会被所有这些 crate 放大。 | 明确 crates.io 产品边界和包白名单；第一阶段只发布稳定 SDK 及最小依赖闭包，CLI 使用 GitHub 预编译包/独立分发；只有 CLI 确实有 cargo 安装需求时再纳入发布闭包。 |
| P0 | 多个入口和语言暴露大量能力，capability、wire schema、SDK DTO、CLI 命令、HTTP 路由、前端消费和文档容易重复维护。 | 新能力出现“内核可用但入口缺失”或不同入口的字段/默认值/错误语义不一致；发布说明容易超出已验证范围。 | 建立单一能力登记源及 consumer 映射，生成或校验公开能力矩阵、CLI/HTTP/API schema 索引和发布说明；所有能力都有 scope、状态和证据链接。 |
| P1 | `qx-app` 既拥有大量研究用例与产物合同，又承担多种报告事实核验和实验恢复。 | 应用层可能成为新的“万能 crate”；每增加一种报告/实验类型都扩大内部耦合和编译/评审成本。 | 保持 `qx-app` 为唯一用例入口，但按领域用例拆内部模块（data preparation、run lifecycle、experiment、artifact reader、report verification）；新 crate 只有在独立 API/依赖/发布边界收益明确后创建。 |
| P1 | `qx-cli` 是产品门面，也承载多种回测、实验、报告生成、HTML/XLSX 渲染和运行装配流程。 | CLI 可能绕过或重复应用层规则；大量功能令新手 `--help` 与包依赖都偏重；作为 crates.io 包时依赖闭包尤其大。 | CLI 只保留命令解析、路径/环境适配、调用用例和格式输出。报告领域事实留在 `qx-app`，共享 renderer 若需拆分，先检查被 CLI 与 API/Python 实际复用的边界。将默认新手命令收敛到 init/doctor/backtest/report。 |
| P1 | 应用、domain、protocol、storage 和 transport 多处都出现版本化 DTO/序列化边界。 | DTO 迁移可能与领域重构耦合；schema 兼容矩阵不易审查，旧产物升级规则可能分散。 | 划分三个明确合同：核心领域类型、持久化/事件 schema、外部 API DTO；每一个仅有一个 owner。定义读兼容和写版本策略、迁移责任与弃用周期。禁止以“共用一个 Rust struct”替代协议版本策略。 |
| P1 | Backtest/Paper/Live 需要共享订单状态和策略合同，但各自有不同时间、撮合、外部副作用、行情与恢复条件。 | 抽象若过度共享，会把模拟假设泄漏给实盘；若重复，则 OMS/账本在入口间漂移。 | 共享订单意图、状态归约、风控与事件合同；环境差异由 `ExecutionContext` / execution port / market-data port 明确表达。Paper 的模拟撮合结果和真实 Venue 回报使用同一归约模型，但 source/evidence 标签必须不同。 |

## 5. 建议的目标架构

### 5.1 逻辑分层与硬性依赖方向

```text
CLI / Python / Rust SDK / C ABI / HTTP / Web
                 ↓ 只做协议转换、授权、装配和呈现
应用用例（qx-app；若后续拆 use-case crate，仍保留单一 owner）
                 ↓ 依赖领域模型及端口，不依赖入口/具体 adapter
领域核心（身份、事件、策略、风险、撮合、OMS、账簿、对账）
                 ↑ 由 adapter/infra 实现端口
基础设施（数据源、交易所、文件/DB、网络、worker、进程运行时）
```

硬约束：

1. `qx-core` 和纯领域 crate 不依赖 CLI、HTTP、Python binding、Web 或具体 venue。
2. `qx-app` 不依赖具体 HTTP/CLI/Python 类型；输入输出是稳定用例合同。
3. adapter 实现领域端口，不反向定义领域状态；应用层不得通过 `Any`/动态字符串绕过类型合同。
4. SDK 公开类型不泄漏内部 crate 的偶然实现细节；用户只需依赖 SDK 才能构造公开的常见请求。必要的可扩展端口应作为有意公开的包/API 管理。
5. Web UI 不直接写交易所、不推算订单终态；写命令统一经授权的控制边界，所有副作用都带幂等身份和审计事实。
6. 每个订单/账务/报告事实指定唯一 owner；其它层只能消费、校验或投影，不重新解释。

### 5.2 稳定产品包策略

建议将 Rust 发行分成三个清楚类别：

| 类别 | 例子 | 分发策略 | 稳定性承诺 |
|---|---|---|---|
| 用户应用 | `qx-cli` | GitHub Release 预编译二进制、Python wheel 捆绑 CLI；短期不以 crates.io 为安装前提 | 命令/配置/产物合同按产品版本管理 |
| 用户库 | `qx-sdk` | crates.io 的首选稳定入口；公开必需类型通过 SDK re-export 或稳定 facade 提供 | 明确 semver、MSRV、feature 和弃用周期 |
| 内部实现/开发包 | `qx-*` 的领域/infra 子集、测试宿主 | 默认 `publish = false`；只有独立复用需求清晰才逐个提升为公开 crate | 内部重构允许跟随 workspace 版本，不承诺外部兼容 |

发布 SDK 前先验证依赖闭包：`cargo package --list`、`cargo package --no-verify` 只用于审包内容检查，随后使用真实 registry dry-run/临时 registry 和 clean consumer 做验证。不得通过一次性地把所有内部 crate 公开来“解决”依赖闭包；那会将内部类型、特性和版本关系永久暴露给下游。`qx-cli` 若要支持 `cargo install`，应以明确成本评估拆分最小运行时/CLI 包或继续 GitHub 二进制安装，不让低频安装方式决定所有内部库的公开 API。

### 5.3 核心合同与状态模型

- **领域合同：** `OrderIntent`、订单状态事件、成交/账簿、风险决定、Instrument/Venue 规格、策略生命周期、Run 身份。
- **持久化合同：** EventLog、RunManifest、数据集快照、报告产物索引和迁移规则。新版本必须能读既有稳定产物；不可读时应准确指出 schema/version，不静默猜测。
- **外部合同：** SDK、HTTP API、CLI 命令配置、Python/C++ 边界。分别注明兼容承诺和 owner，不把内部 serde 类型自动当成公共协议。
- **错误合同：** 分类稳定错误码/字段路径/是否可重试/是否状态未知/建议动作。CLI/Python/UI 可翻译，但不得将未知外部提交结果改写成普通失败或自动重发。
- **能力合同：** 明确实现范围和证据等级。unsupported 和 unverified 均不能当作可执行能力。

### 5.4 Backtest 与 Paper/Live 的共享边界

共用策略输出合同、数量/价格精度、订单意图、订单状态 reducer、风险决定、账户账簿事件、run/trace identity 和报告事实模型。环境实现分别提供：

- Backtest：可控时钟、历史数据、确定性排序、仿真撮合、明确的 bar/tick/depth 成交假设。
- Paper：实时或历史行情、虚拟成交策略、延迟/拒绝/部分成交等模型、运行中订单状态和重启恢复；应明确哪些事件是假设生成。
- Live：真实连接、异步/乱序回报、幂等副作用、未知提交、用户流丢失、权威查询、重启对账、人工介入状态。

不得为了“同一接口”隐藏行情时间、事件源或成交真实性；报告和 UI 要能追溯每个 fill 是模拟生成还是交易所确认。

## 6. 详细重构实施路线

### 阶段 0：建立可验证基线和架构台账（P0）

1. 从 Cargo metadata 生成 crate 依赖 DAG，检查循环依赖、层级禁边和每个 crate 的直接依赖；附上 public/internal/test-only 分类与 owner。
2. 对每条主要用户路径做调用链清单：入口 → use case → domain/port → adapter/storage → artifact/report；标记是否有并行实现和测试证明。对外露出的 route、CLI 命令、SDK 方法做反向消费者检查，找出只有声明无调用方的孤儿入口和有服务端实现却无客户端消费的端点。
3. 盘点外部可见合同：crates.io crate、Python exports、C ABI、HTTP 路由、CLI 命令、EventLog/report schema、capability 注册。
4. 输出一份“事实 owner × consumer × 版本 × 验收”矩阵，并将已有 `docs/module-map.md` 降为结构索引，不再重复撰写全量模块说明。
5. 对工作区每个 crate 加入发布分类及 `publish = false` 策略；明确哪些真实支持用户消费。
6. 为 worker、订单组、run 和异步 HTTP 启动/取消路径画状态图；每条等待/重试/分页循环必须有 deadline 或次数上限、取消传播和明确终态。检查 Unknown/部分成交/超时是否进入可查询的恢复状态，失败路径是否仍能写出相关 ID 和诊断。

**完成标准：** 依赖图可生成；所有禁止依赖有静态门禁；每个公开入口/协议有 owner；未登记入口、孤儿路由、无主事实、无上限重试或缺少取消/终态的状态路径会让 CI 失败。架构图来自 Cargo metadata 和显式登记，不手工猜依赖关系。

### 阶段 1：解决 SDK/crates.io 闭包与公共 API（P0）

1. 确认 Rust 用户最需要的消费模式：策略开发库（SDK）与 CLI 安装分别评估，不绑定成一个发行物。
2. 选定 `qx-sdk` 做第一个外部稳定库，检查其对 `qx-app`/execution/provider/strategy 的暴露是否完整；公开函数的参数/返回类型必须通过 qx-sdk re-export 可用，避免用户被迫直接依赖一组内部 crate。
3. 逐层收窄 SDK 闭包；纯实现依赖默认内部化。不能内部化时先做 `publish = false` 隔离验证，提出明确的必要公开理由和 semver 计划。
4. 先发布 alpha 或 0.x 库做 clean-consumer 验收：新建空目录，只从 crates.io 拉包，编译最小回测例子；再验证 MSRV、默认 features、无默认 features、Windows/Linux 构建矩阵。
5. 单独设计 CLI 的分发方式：继续 GitHub Release/安装脚本，或将应用运行时拆为最小稳定依赖闭包后再提供 `cargo install`。不得把 `qx-cli` 直接改名/假设一个 crate 就可完整发布。
6. 发布 workflow 采用 lockstep 或独立版本策略二选一并写清。若内部 crates 一律同版本，应以自动拓扑发布、验证 registry index 可见性和回滚处理支撑；若采用独立版本，应自动计算升级边界和兼容范围。

**完成标准：** crates.io 上的 SDK 可以由不在仓库内的 clean consumer 安装并编译；用户示例不依赖本地 path；发布失败可从日志定位是包内容、依赖未发布、版本冲突还是认证问题。

### 阶段 2：收敛 `qx-app` 与入口适配（P1）

1. 将 `qx-cli` 的业务流程调用逐项迁移/核对到 `qx-app` 用例；CLI 只负责参数、路径、输出格式和错误呈现。
2. HTTP 与 Python 的创建 Run、回测、获取结果和报告复核都调用同一应用合同；共享 request/response 使用稳定的 `qx-app` DTO 或专门的 protocol crate，入口各自映射。
3. 对 `qx-app` 按内部模块划分明确边界：运行创建/生命周期、数据准备、实验搜索、产物读写、报告核验。每个模块有单一 facade，避免多个子模块互相读取私有实现。
4. 报告 renderer 与报告事实拆开：应用层产出已核验的语义 DTO；HTML/XLSX/JSON/CSV 展示层转换数据但不得重算事实。renderer 复用的实际需要必须有依赖证据再抽成包。
5. 建立一致的 RunHandle 生命周期和终态定义；CLI/Python/Web 展示相同的 run id、输入/数据指纹、状态、产物清单和失败分类。

**完成标准：** 对同一输入，CLI/Python/HTTP 返回相同领域结果摘要和相同产物身份；只有展示字段可以不同。每个用例有成功、输入拒绝、运行失败和恢复路径的合同覆盖。

### 阶段 3：拆清协议、schema 和能力登记（P1）

1. 制定 `contracts/` 或等价目录：外部 API、持久化 schema、C ABI、Python 导出和 CLI config 分开版本化；不要将多个协议塞进一个巨型 schema。
2. 每个字段记录：owner、单位/精度、默认值、空值语义、向后兼容规则、写入版本和读取迁移规则。
3. 构建 machine-readable capability registry，内容至少包含 venue/product/account/position mode/order kind/operation、错误降级、代码状态、外部证据链接和最近验证版本。
4. 生成帮助页、连接器矩阵、发布 scope 和 docs 索引。文档中已过期的“支持/已验证”声明由 CI 找出，而非人工到处搜索。
5. 为错误合同建立统一的公开分类：invalid input、unsupported capability、permission/config、transient/retryable、rate limit、unknown outcome/reconcile required、internal invariant。不同语言只做本地化显示。

**完成标准：** 对任一外部能力可追踪到实现、owner、协议版本、使用入口和证据；同一操作不会在 registry、API 与 CLI 文档中给出相互矛盾的支持状态。

### 阶段 4：降低新用户操作和维护成本（P1/P2）

1. 新手路径维持一条主线：安装 → init → doctor → quickstart/backtest → report → compare/evidence。高级运行、连接器、分布式 worker 和实验搜索从默认帮助中分层展示。
2. 每个模板包含数据范围、参数解释、warmup、费用/滑点/撮合假设、风险说明和可执行验证命令。
3. CLI 错误输出包括字段路径、实际/期望类型、失败分类和修复示例；`--json` 输出稳定 error code，便于 CI 和 UI 消费。
4. Python 高层用法提供最短可运行流程，SDK 低层对象继续开放给专家；避免让新用户首先了解内部 RunSpec/manifest/port 实现。
5. 使用相同应用用例为 CLI、Python 和 Web 的首跑体验做录屏/脚本化验收，统计首次成功时间、命令数、失败后恢复率。

**完成标准：** 干净环境从安装到离线示例回测并读取图表仅需少量有序命令；首次失败能定位到输入或环境；所有入口都能拿到相同 report identity。

### 阶段 5：运行可靠性、连接器和可观测验收（持续 P0/P1）

1. 为 Paper/Live 定义状态机和故障矩阵：断网、超时未知、部分成交、重复回报、订单流漏消息、重启、权限不足、限流、Venue 维护。
2. 以订单 intent × 交易所产品/账户模式建立连接器合同测试；测试回报归约、幂等、撤改单、保护单触发、对账和恢复，不以 mock 调用成功代替外部行为验证。
3. 将模拟与外部来源的 market/fill/account 事实打上 source/evidence 标签；报告明确标示 Paper 和 Live 差异。
4. 统一 trace/correlation id，从策略事件关联到命令、Venue request、回报、EventLog、报告行；metrics 控制 cardinality，不记录密钥和敏感 payload。
5. 建立可复现工作负载档案：半年 15 分钟 K 线、百万级 Bar、L2 replay、并发参数搜索、冷启动、峰值 RSS、报告生成；保留源码/数据/配置哈希和输出摘要。

**完成标准：** 未知提交结果不盲目重发；重启后能通过权威事实恢复或明确转人工；每个宣传中的连接器能力都附有精确范围和证据等级。

### 阶段 6：收敛 CI、发版及架构债务（持续 P2）

1. CI 分为快速静态层、领域/合同层、平台构建层、外部验收层、性能基准层；PR 不重复运行昂贵且无差别的整仓步骤。
2. Rust、Python、C/C++、Web 的发布版本和能力矩阵统一从 release manifest 读取，禁止手工复制版本号和 feature 状态。
3. Rust 检查包括 fmt/clippy、层级依赖、公开 API diff、MSRV、package dry-run 和 clean consumer；Python 检查 wheel import/CLI entrypoint；跨语言检查关键 DTO roundtrip。
4. 接入 SBOM、许可证清单、artifact checksum/provenance；正式发布流程只对批准的 tag 和 release manifest 产生资产。
5. 对每个新 crate 做架构 ADR：为什么需要独立编译/API/复用/版本边界，为什么不能是 crate 内模块。以依赖收益为准，不以文件行数作为拆分门槛。

### 6.2 重构执行顺序和变更控制

按 **A → D → B/C → E/F → G/H** 推进。A/D 先建立包和接口准入；B/C 将研究主链路收敛为可重复调用的应用用例；E/F 在订单生命周期与数值合同稳定后逐个补 connector scope；G/H 用相同 run identity 验证体验、恢复和效率。能并行的文档、fixture 和可观测字段盘点可提前进行，但不得并行发布未对齐的协议版本。

## 7. 方案排序与资源建议

建议先解决能解除后续开发阻塞的结构，再增加策略/图表/交易所能力：

| 顺序 | 交付 | 价值 | 不应并行扩张的工作 |
|---|---|---|---|
| 1 | 依赖 DAG、公开/内部包分类、事实 owner/consumer 清单 | 找出层级边界和 crates.io 阻塞的真实闭包 | 暂停为了“完整”再拆新 crate |
| 2 | qx-sdk 最小外部依赖闭包和 clean consumer 发版 | 建立可复用 Rust 包的发布可信度 | 暂不将整个 CLI/runtime 仓库都公开 |
| 3 | CLI/Python/API 共享应用用例与 Run 结果身份 | 降低多入口行为漂移 | 不新增平行的 report/backtest API |
| 4 | schema/capability registry 自动化 | 提升连接器声明、文档和 release scope 一致性 | 不扩展没有验收入口的能力表面 |
| 5 | Paper 故障恢复与 Venue 外部验收 | 让“可执行”从代码声明变成证据 | 不把模拟测试叫作真实交易验收 |
| 6 | 体验/性能基准和可观测闭环 | 以用户任务和真实负载比较竞品 | 不用单个微基准或宣传词代表整体优越 |

## 8. 发布准入指标

每次正式发布至少应同时具备以下证据；无法提供的项目标为未验收，不用总分掩盖：

1. **架构完整性：** 依赖 DAG 无禁止环/边；所有公开 API 有 owner、版本与弃用约定。
2. **安装闭环：** PyPI wheel、GitHub 二进制、crate 包各自有 clean environment install evidence；没有发布的渠道清楚标注。
3. **回测可信度：** 策略假设、数据覆盖、费用、撮合顺序、预热、PIT 与结果哈希明确可复核。
4. **Paper 可靠性：** 用户流/控制命令/运行状态/重启恢复状态贯通；不依赖模拟返回掩盖真实执行路径。
5. **连接器精度：** 能力按产品/账户/订单形态列举；执行未知、部分成交、撤改单和恢复有合同与外部证据分级。
6. **跨入口一致性：** 同一 Run 的 CLI/Python/API 领域结果与产物身份一致。
7. **可观测性：** Run/订单/控制命令可关联；关键 worker 心跳、队列年龄、外部错误和 reconcile 状态可查询。
8. **分发完整性：** 版本、changelog、checksums、SBOM/provenance 与发布资产匹配。

## 9. 非目标和决策约束

- 不整体改写现有 Rust 核心，不因竞品有微服务就把模块化单体拆成网络服务。
- 不为增加 crates.io 包数量而公开内部 crate；稳定的高层 Rust SDK 优先于全面暴露低层模块。
- 不把单一回调策略接口当作所有研究、Paper 和 Live 能力的唯一接口。
- 不扩张连接器数量以替代已有 connector 的订单状态、恢复、权限和账户模式验收。
- 不把 mock、回放、Paper、测试网、生产小额验证混为同一证据等级。
- 不以“超过所有竞品”作为不可检验目标；使用首次成功时长、端到端完成率、复现一致性、恢复成功率、包安装成功率、资源画像和报告交互能力逐项比较。
