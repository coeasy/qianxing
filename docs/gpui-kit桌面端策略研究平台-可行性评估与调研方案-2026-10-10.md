## 0. 结论摘要

### 0.1 一句话结论

**「接入 gpui-kit」在 UI 层可行，但它不是当前的瓶颈——瓶颈在后端接入面；而 gpui-kit 自身的成熟度（5 周龄、pre-1.0、第三方 GPUI 快照、Windows/中文 IME 未证）使它在现阶段是一个高风险选项。**

### 0.2 三层判定

| 层 | 需求 | 判定 | 关键依据 |
|---|---|---|---|
| **UI 壳** | 桌面窗口、布局、编辑器、图表、表格 | ⚠️ **技术可行，风险高** | gpui-kit 声称 75+ 组件、tree-sitter 代码编辑器、自绘 Candlestick 图表、虚拟滚动表格、Dock 布局（来源：lib.rs/crates/gpui-kit，2026-10-10）；但首版 0.1.0 = 2026-09-03、8 个版本/1 个月、依赖第三方快照 `gpui-pre-*` 0.3.8、Windows 渲染与中文 IME 未证 |
| **后端接入** | 提交策略、跑回测、取结果 | 🔴 **当前不可行，必须先做前置工程** | `qx-cli` 是**纯 bin crate**（无 `src/lib.rs`，`Cargo.toml` 无 `[lib]`/`[[bin]]`，回测编排模块为 `pub(crate)`）→ 编排逻辑不可库化复用；`qx-api` **18 条路由中 0 条与 backtest 相关**（全目录 `backtest` 关键字 0 命中）→ 薄客户端无法提交回测 |
| **本地运行用户策略** | 用户自定义策略在本地执行 | ⚠️ **受"策略开放阶梯"约束** | 本仓已定阶梯：P0 内置+声明式（无任意代码执行）→ P1 独立进程 worker（沙箱）→ P2 Rust/C++ 编译包。路径依赖 Python ≥3.10 + Windows `tzdata`（`python/pyproject.toml:9,18`；`crates/qx-cli/src/main.rs:311-325`），桌面分发负担重 |

### 0.3 推荐路线（详见 §7–§8）

> **不要先选 UI 框架，先做后端前置工程（抽 `qx-backtest` 库 + `qianxing-agent`），再用两个 spike 并行验证 gpui-kit 与 Tauri 两个 UI 壳。**

理由：无论最终选 gpui-kit 还是 Tauri/React，**后端前置工程的产出是同一份**（社区已归档的 Tauron 方案 §12–§13 P0 恰好就是这个）。先做 UI 壳选型会把 80% 的工作量押在 20% 的不确定性上。

### 0.4 最需要正视的两件事

1. **本仓已两次决策"不做 GUI"**：`docs/archive/竞品对比与易用性改进优化计划-V1.md` §7「明确不做：自研 Web GUI / 交易面板」，理由写得很清楚——「GUI 是持续维护承诺（freqUI、Jesse GUI 背后是专职前端与长期 issue 流）」；`docs/qianxing-项目结构与GitHub竞品对比及优化方案-2026-10-06.md` §8 亦列「暂缓：完整桌面 GUI」。**引入 gpui-kit 等于推翻这两条决策**，而这个决策的代价在原生 GUI 上比 Web GUI **更高**（gpui-kit 比 React 生态更不稳定）。
2. **已有一份完整的桌面方案并已归档**：`docs/archive/qianxing与tauron一体化桌面客户端终版方案-2026-10-03.md`（Tauri 2 + React + 本机 `qianxing-agent`），归档说明是「本仓代码里没有 Tauron/Tauri 集成的任何实现面（全仓 `tauron`/`tauri` 关键字 0 命中），桌面 Host 属 M4' 未关闭项」。本报告**不重复造轮子**，而是把 gpui-kit 作为该方案的**UI 壳替代候选**来评估。

## 2. 需求拆解：三个能力各自的真实难度

用户需求原文：「支持用户自定义编辑策略，策略在本地运行，策略回测结果展示」。

| 需求 | 表面难度 | 真实难度 | 真实难点在哪 |
|---|---|---|---|
| **① 自定义编辑策略** | 低 | 🟡 中 | 「编辑器组件」不是难点（gpui-kit/CodeMirror 都能给）。难点是**策略的契约**：参数 schema、输入数据层级声明、输出只允许 Signal/OrderIntent、依赖锁定、签名与撤销状态——本仓已归档方案 §7.3 已给出 manifest 必需字段 |
| **② 策略在本地运行** | 中 | 🔴 **高** | 三条路径各有硬成本：<br>• 内置/声明式策略 → 无任意代码执行，最易复现（**推荐起点**）<br>• Python/C++ worker → 需随包分发 Python ≥3.10（Windows 还需 `tzdata`）或 C++ worker，且要处理 `python_module_search_path`、超时、资源配额<br>• 用户自己写 Rust 编译 → 需要编译隔离、ABI 兼容、签名（本仓列为 P2，未开放） |
| **③ 回测结果展示** | 中 | 🟡 中 | 难点不是画图，而是**画什么**：本仓的核心承诺是「产物自己说得出结论压在哪些输入上」。UI 必须显示 `result_hash` / `log_digest` / `input.fingerprint` / 数据档位声明 / 已未验证清单，**且不得自行计算任何数值**（只读投影原则）。这些字段今天的 CLI 产物里有，但**没有面向 UI 的 API** |

**关键洞察**：三个需求里，**「编辑器」是最容易的，「能跑」和「能看到可信结果」才是难的**——而后者与 UI 框架**完全无关**。

## 3. 可行性判定：后端接入面是真正的阻塞点

### 3.1 `qx-cli` 是纯 bin crate → 编排逻辑不可复用（🔴 最大阻塞）

| 证据 | 内容 |
|---|---|
| `crates/qx-cli/Cargo.toml` | **无 `[lib]` / `[[bin]]` 声明** |
| `crates/qx-cli/src/lib.rs` | **不存在**（实测确认） |
| `crates/qx-cli/src/main.rs:105-137` | 所有编排模块以私有 `mod` 挂在根上（`mod api_service; mod backtests; …`），无 `pub mod` |
| `crates/qx-cli/src/backtests/mod.rs:12` | `pub(crate) struct BarBacktestAssembly`；该目录 `pub fn` 计数 = **0** |

**后果**：`qx-cli` 里那套「风控门同源注入 + market-spec 解析 + 费用/滑点/延迟模型装配 + 产物落盘 + RunManifest/RunRecord 生成」**无法作为库被桌面端调用**。桌面端若想进程内直连，只能重写这套装配（`qx-cli` 约 4.5 万行编排逻辑），或先把它改成 lib+bin（要动全仓最大 crate + 940 条门禁 + README 计数断言）。

### 3.2 引擎层**是**可复用的（好消息）

| 证据 | 内容 |
|---|---|
| `crates/qx-xingban/src/lib.rs:1-60` | `pub use BacktestEngine / BacktestConfig / BacktestReport` 等 |
| `crates/qx-xingban/src/backtest.rs:313` | `BacktestEngine::run(self, bars: &[Bar], strategy: &mut dyn BarStrategy) -> Result<BacktestReport, QxError>` —— **纯返回值，本身不写文件、无副作用** |
| `tick_backtest.rs:175` | `TickBacktestEngine::run(self, ticks: &[QuoteTick], strategy: &mut dyn TickStrategy) -> Result<TickBacktestReport, …>` |
| `orderbook_backtest.rs:266` | `OrderBookBacktestEngine::run(self, snapshots: &[OrderBookSnapshot], strategy: &mut dyn OrderBookStrategy) -> Result<OrderBookBacktestReport, …>` |
| `qx-core` / `qx-data` / `qx-storage` | 均导出完整公开面（`qx-core/src/lib.rs:33-66`；`qx-data/src/lib.rs:21-43`），足以在进程内拼出「读数据 → 跑回测 → 拿结果」 |

**进程内最小链路（真实类型，可编译级参考）**：

```rust
// 依赖：qx-core / qx-data / qx-datastruct / qx-xingban / qx-risk / qx-strategy（全部是 lib crate）
let provider = JsonBarFrameProvider::new(data_path)?;        // qx-data/src/provider.rs:38
let bars = provider.load_bars_with_manifest()?;               // qx-data/src/provider.rs:61
let frame = BarFrame::from_json(&raw)?;                       // qx-datastruct/src/lib.rs:304

let engine = BacktestEngine::new(BacktestConfig {
    instrument, account_id, currency, initial_cash, multiplier,
    fill: Box::new(FifoModel), fee, data_tier, latency, margin, seed,
    risk: RiskGate::default(), virtual_trading: false,
});                                                          // backtest.rs:162
let report: BacktestReport = engine.run(&bars, &mut strategy)?; // backtest.rs:313
// report.final_equity() / report.run_manifest() ...
```

> ⚠️ 这条链路**绕过了 `qx-cli` 的装配**，因此**必须自行补齐**风控门、market-spec、费用模型、产物落盘与 RunManifest——否则会产出一份「跑得出来但不可复算」的结果，直接违反本仓核心承诺。

### 3.3 `qx-api` 不支持回测（🔴 薄客户端路线不成立）

| 项 | 事实 |
|---|---|
| 路由总数 | **18 = 17 条只读 GET + 1 条写面 `POST /control/commands`**（`crates/qx-api/src/lib.rs:1533-1716`） |
| 写面能力 | 仅交易控制面命令（SubmitOrder / PauseStrategy / ResumeStrategy 等，`crates/qx-control/src/lib.rs:19-27`） |
| 回测能力 | `qx-api` 全目录 **`backtest` 关键字 0 命中** → **不能提交策略、不能跑回测、不能查回测进度/净值/成交/回撤** |
| WebSocket | 1 条事件流（`ws.rs`），消息类型 `connected`/`snapshot`/`events`/`event`/`resync_required`/`idle_timeout`/`server_shutdown` |
| 既有 UI 资产 | `web/console/`（`index.html` 144 行 + `app.js` 937 行纯原生 fetch/WS + `styles.css` 204 行，**无第三方 JS 库**）只消费 `/account/*`、`/control/audit`、`/scheduler/runs`、`/events(/live)`、`POST /control/commands` |

**结论**：桌面端**不能**通过现有 API 提交或读取回测结果。要么补 `/research` 命名空间（已归档方案 §8.1 已给出 14 条路由设计），要么走 `qx-cli` 子进程 + 解析产物文件。

### 3.4 三条集成路线可行性汇总

| 路线 | 描述 | 可行性 | 为什么不选/选 |
|---|---|---|---|
| **A. 进程内直连内核** | 桌面 app 直接依赖 `qx-xingban` 等，进程内跑回测 | ⚠️ 引擎可行、**编排不可行** | 需重写或抽离 `qx-cli` 编排逻辑；且与「CLI/桌面/Web 结果必须同源」的承诺冲突（两套装配 = 两份 `result_hash` 风险） |
| **B. 纯 HTTP/WS 薄客户端** | 只吃现有 18 路由 | ❌ **不可行** | 无回测提交/查询面（§3.3） |
| **C. 桌面壳 + 本机 agent 进程** | 桌面 UI 只做展示；spawn `qx-cli` 子命令跑回测；实时面走 HTTP/WS | ✅ **推荐** | 保住「写面只有控制面那一条」「只读投影不做第二事实源」的确定性边界；不必 fork 内核装配；与已归档 Tauron 方案 §3.2 方向一致 |

**路线 C 的代价**：需管理子进程生命周期（启动/停止/重启/崩溃恢复/端口与 token），且需解析 CLI 的 JSON 产物——**这里会直接踩到本仓产物版本治理的已知漏洞**（见 §4 D-11）。

## 4. 缺点清单：引入 gpui-kit 的具体代价

> 分级：🔴 可能否决 ｜ 🟠 重要成本 ｜ 🟡 需管理

### D-1 🔴 成熟度：5 周龄、pre-1.0、1 个月 8 个版本

首版 0.1.0 = 2026-09-03，当前 0.7.1 = 2026-10-05。README 明示「1.0 前常有 breaking change」。**5 周龄的框架要承担一个持续维护承诺**——这恰好是本仓 §7「明确不做 Web GUI」的核心理由（「GUI 是持续维护承诺」）。选 gpui-kit 等于把维护承诺押在一个比 React 年轻 10 年、比 Tauri 年轻 5 年的框架上。

### D-2 🔴 第三方 GPUI 快照 + 精确锁版

gpui-kit 依赖 `gpui-pre-* = 0.3.8`（第三方快照，Jason Lee 发布），而非 Zed 官方发布（官方 `gpui` 停在 v0.2.2/2025-11）。含义：
- 上游 Zed 持续演进，快照按 7 天一版跟进 → **gpui-kit 与 Zed 之间是人工同步，非官方契约**；
- Zed 官方版本与快照的差异长期存在 → 迁移回官方成本未知；
- 生态已碎片化：`gpui-ce`、`bite-gpui-ce`、`gpui-box`、`gpui-alloy`、`fc-gpui`、`gpui-fast`、`gpui-cn`、`wgpui` 等多个 fork/快照并存。

### D-3 🔴 Windows 渲染与中文 IME 未证（对本项目最致命）

- 开发机与目标用户都是 **Windows x64**；文档对三平台都只称「Ship one codebase」，**未见 Windows 成熟度背书**；渲染后端多源冲突（DirectX 11 / WGPU / D3D12 **未核实**）。
- **像素级/视觉验证明显 macOS 中心**：gpui-kit 集成测试文档称不检查像素；旁证显示无窗口 PNG 快照与 GPU 截图测试主要在 macOS（部分来源称 macOS+Windows），**"其他平台显式跳过"的原文未定位**。
- **中文 IME 是实打实风险**：Zed GPUI 侧有约 15 个 open IME issue（含组字被 keybinding 抢占、候选窗闪烁）。对一个**中文主场**的产品（本仓明言「中文主场是有意的产品选择」），策略编辑器里的中文注释/字符串输入是高频操作。

### D-4 🟠 需要 GPU：与「本机可审计 / CI 可跑」哲学冲突

GPUI 需要 Metal/Vulkan/D3D。**虚拟机、远程桌面、无独显机器、CI 无头环境**存在风险（Linux 曾有 `NoSupportedDeviceFound` 报告）。而本仓的定位是「在一台没有交易所账号、没有网络凭据的机器上跑出可复算结论」——如果 UI 在普通办公本/虚拟机上起不来，这条定位就被削弱。

### D-5 🟠 依赖规模与「零强制依赖 / 离线可装」哲学张力明显

约 72 个新依赖、~3.5M SLoC、72–170MB 依赖树。而本仓的既有哲学是：
- Python wheel **强制依赖清单为空**，且门禁 `wheel_optional_dependency_check`（`tools/check_architecture.py:10855`）**明文断言**「`dependencies` 里不许再有 ccxt 这类『要到调用点才需要』的第三方运行时包」；
- README 强调 `uv pip install --offline`、仓库 venv 离线重建。

**注意**：该门禁只约束 **Python wheel**，不约束 Rust 依赖——引入 gpui-kit **不会直接踩门禁**（已核实：`tools/check_architecture.py` 中无外部 crate 依赖白名单/禁止新增依赖判据；`layer_dependency_check`/`dev_dependency_cycle_check` 只管内部 `qx-*` 依赖边）。但**哲学张力是真的**：一个「单 binary、零依赖、离线可跑」的项目引入 3.5M SLoC UI 框架，需要正面回答「这还算不算单 binary 哲学」。

### D-6 🟠 构建成本未测，且与 `lto = true` 叠加

根 `Cargo.toml:47-49` 是 `opt-level = 3` + `lto = true`。在 25 crate 之上叠加 3.5M SLoC 依赖，**release 构建时间与增量编译时间的增量未测**。已知旁证：docs.rs 单 crate 构建约 50s（整 app 更久），官方对比表称二进制约 12MB（非同方法基准，**未核实**）。

### D-7 🟠 前端资产完全重写，零复用

| 既有资产 | gpui-kit 路线 | Tauri/React 路线 |
|---|---|---|
| `web/console/`（1,285 行，含 937 行 app.js） | ❌ 全部重写为 Rust | ✅ 直接复用/演进 |
| `qx-cli report --html` + `report_svg.rs` 自绘 SVG | ❌ 无法复用（自绘 SVG 逻辑与 GPUI 渲染树不同） | ✅ 可内联复用 |
| 生态图表/表格库（ECharts、AG-Grid、uPlot） | ❌ 不可用，必须用 gpui-kit 自绘图表 | ✅ 可用 |
| 参数热力图 / Pareto 前沿 / 多 run 对比（研究层） | ❌ 需自绘 | ✅ 生态现成 |

### D-8 🟠 组件缺口与细节成本

- **无内置终端组件**（需引入 `gpui-libghostty` 等）
- **系统托盘不在 gpui-core**（仅 fork 提供）
- 多光标、括号匹配、查找替换等编辑器细节**未核实**
- CJK 字体回退、a11y（AccessKit 有但覆盖度未证）、国际化细节

### D-9 🟡 许可证歧义

`gpui-pre` 标 Apache-2.0，但 Zed 主仓为 GPL-3.0-or-later。虽牵星本身是 Apache-2.0、分发 GPUI 派生二进制通常可行，但**法务边界需要在正式立项前书面确认**（本报告未能核实 `gpui-pre` 的 LICENSE 实文件）。

### D-10 🟡 Bus factor 与治理

单一公司（Longbridge）+ 单 Lead 主导；除 Longbridge Pro 外**无独立生产背书**；生态多 fork 并存 → 治理碎片化风险。

### D-11 🔴 桌面端会踩上本仓已知的产物版本治理漏洞

这是**独立于 UI 框架**的风险，但对路线 C 尤其致命：本仓 16 份 git 跟踪的 `summary.json` **仍停在 `schema_version: 1`，而代码已写到 5**（`crates/qx-cli/src/backtests/artifacts.rs:345`），且**无用例守护**；多腿链**无 RunManifest**。桌面端要解析这些产物来画图 → **会静默走错分支或显示错误结论**。这是必须先修的前置项。

### D-12 🟡 「纯 Rust 单栈」的收益真实但被高估

收益：无 Node/pnpm 工具链、无 WebView 版本碎片、与后端同语言、单一二进制分发、与「单 binary 哲学」一致。
被高估之处：UI 迭代速度（热重载、样式调试、图表库生态）**远低于 Web**；Rust 编译-运行循环比 Vite HMR 慢一个数量级；出错时可用的人才池远小于 React。

## 6. 三条候选路线对比

| 维度 | A. gpui-kit（纯 Rust 原生） | B. Tauri 2 + React（已归档 Tauron 方案） | C. 增强 web console（不做桌面） |
|---|---|---|---|
| UI 语言 | Rust（GPUI DSL） | TypeScript + React | 原生 HTML/JS |
| 成熟度 | 0.7.1 / 5 周龄 / pre-1.0 | Tauri 2.11 稳定；React 生态成熟 | 已有 1,285 行可演进 |
| Windows 成熟度 | ⚠️ 未证 | ✅ 成熟（WebView2） | ✅ 浏览器即可 |
| 中文 IME | ⚠️ 有 open issue | ✅ WebView 原生支持 | ✅ 浏览器原生 |
| 代码编辑器 | 内置（tree-sitter + LSP），细节未证 | CodeMirror 6 / Monaco（成熟） | CodeMirror 6 |
| 图表（净值/回撤/热力图） | 自绘 Candlestick/Line/Area（够用，大数据未证） | ECharts / uPlot（成熟） | ECharts |
| 复用 `web/console` | ❌ 0% | ✅ 高 | ✅ 100% |
| 与现有哲学（单 binary/零依赖） | ✅ 最一致 | ⚠️ 引入 Node 工具链 + WebView | ✅ 最一致（无新依赖） |
| 后端接入工作 | 相同（都需路线 C 的 agent） | 相同 | 相同 |
| 分发 | 单 exe（+ Python worker） | 安装包 + sidecar | 浏览器/本地服务 |
| 主要风险 | 框架年轻 + Windows/IME + GPU 依赖 | 重前端工程 + WebView 碎片 | 交互上限低，做不出编辑器体验 |
| 适合「内部小团队自用」 | ✅ 好 | ⚠️ 偏重 | ✅ 够用 |
| 适合「对外产品化」 | 🔴 风险高 | ✅ | ❌ 不适用 |

**关键结论**：三者的**后端接入成本完全相同**。差异只在 UI 壳。因此「先做 UI 框架决策」是错的顺序。

## 8. 详细调研方案（核心交付）

### 8.1 待验证假设与通过判据

每条假设必须给出**验证方法**与**可判定的通过/否决阈值**。S2 的全部工作就是把这些假设变成可复现的实验。

| # | 假设 | 验证方法 | 通过判据 | 否决门槛（fail-fast） |
|---|---|---|---|---|
| **H1** | gpui-kit 能在目标 Windows x64 机器上启动窗口并稳定渲染 | 跑 `gpui-kit` 官方 `hello_world` + `story` gallery 示例，在一台**配置最低的目标机器**（含 VM/RDP 场景）上运行 30 分钟 | 窗口正常、连续 30 分钟无崩溃/白屏；`MTL_HUD` 等价手段测 FPS ≥ 60；记录渲染后端实际名称 | 目标机器无独显或 RDP 下无法启动 → **直接否决路线 A** |
| **H2** | **中文 IME 在策略编辑器中可用**（最高优先级） | 在编辑器组件中：连续输入中文注释 500 字、切换输入法、组字期间打字、光标移动、撤销重做、复制粘贴中文 | 组字不丢、候选窗不闪烁、光标位置正确、撤销粒度合理；无字符错乱 | 组字被 keybinding 抢占或候选窗闪烁导致无法正常输入 → **否决**（中文主场产品不可接受） |
| **H3** | 代码编辑器满足策略编写需要 | 加载 Rust / Python / C++ 三种 tree-sitter 语法；测试括号匹配、查找替换、多光标、行号/gutter、大文件（10 万行）打开与滚动 | 三种语言高亮正确；查找替换可用；10 万行打开 < 3s、滚动无卡顿 | 缺少括号匹配或多光标 → 降级为「够用但需自研补齐」 |
| **H4** | 图表能渲染真实规模的净值/回撤曲线 | 用真实 `equity.csv`（10 万点）与回撤序列渲染 Line/Area；叠加 fills 标注点（1 万个） | 首帧 < 2s；交互缩放/平移 ≥ 30 FPS；内存增量 < 500MB | 10 万点卡顿不可用 → 需自研降采样（增加成本） |
| **H5** | 表格能承载 fills 明细 | 虚拟滚动 100 万行 fills；排序 + 固定列 + 单元格选择 | 滚动 ≥ 30 FPS；排序 < 5s | 排序卡死 → 需分页方案 |
| **H6** | gpui-kit 能与 qx-* crate 同进程共存 | 在探针 crate 里同时依赖 `gpui-kit` 与 `qx-core`/`qx-xingban`/`qx-data` | 编译通过；无 `tokio`/`tracing`/`serde` 版本冲突（注意 `qx-storage` 的 `nats` feature 是唯一 tokio 使用者，探针不应启用） | 出现不可调和的依赖冲突 → 必须走子进程隔离 |
| **H7** | 构建成本可接受 | 在探针 crate 里测量：clean release 构建时间、增量构建时间、二进制体积 | clean release ≤ 基线（现有 `qx-cli`）的 2.5×；增量 ≤ 60s；二进制增量 ≤ +40MB | 增量构建 > 3 分钟 → 开发体验不可接受 |
| **H8** | 离线构建可行 | 在有网机器 `cargo vendor`，在断网机器构建 | 断网可完整构建并可运行 | vendor 失败或体积失控 → 与「离线」哲学冲突，需正面决策 |
| **H9** | 版本漂移成本可承受 | 记录 4 周内 gpui-kit 的版本数与 breaking change 次数；做一次「从 0.6.x 升到 0.7.1」的迁移演练 | 单次迁移 ≤ 8 小时；4 周 ≤ 3 次 breaking | 单次迁移 > 3 人日 → 长期维护成本不可接受 |
| **H10** | 许可证可用 | 获取 `gpui-pre` 的 LICENSE 实文件、gpui-kit/gpui-component 的 LICENSE；必要时咨询法务 | 明确为 Apache-2.0 且可分发派生二进制 | 若为 GPL 系 → **直接否决**（本仓 Apache-2.0） |
| **H11** | 子进程路线的产物解析稳定 | 用 `qx-cli` 子进程跑回测，解析 `summary.json`/`equity.csv`/`fills.csv`/`record.json`；对多腿链（当前无 RunManifest）做容错 | 所有产物可解析；版本漂移有显式错误（S0 修复后） | 多腿链产物无法解析 → 桌面端必须限制为单腿策略 |
| **H12** | 用户策略执行的沙箱与分发可行 | 在干净 Windows 机器上分发并运行 Python 策略 worker（无 Python 环境） | 能给出明确可执行的安装引导或随包分发方案 | 无法解决 Python ≥3.10 + `tzdata` 分发 → 「用户自定义策略」降级为**声明式策略**（无任意代码执行） |

### 8.5 决策门（Go / No-Go）标准

**S3 评审时，gpui-kit（路线 A）只有在以下条件同时成立时才 Go**：

| 必过条件 | 阈值 |
|---|---|
| G1 中文 IME 可用 | H2 全部用例通过，无阻断级缺陷 |
| G2 目标机器可渲染 | H1 在三类环境（物理机 / VM / RDP）至少两类通过，且物理机必过 |
| G3 许可证 | H10 确认为 Apache-2.0 且可分发 |
| G4 构建成本 | H7 clean release ≤ 2.5× 基线 且 增量 ≤ 60s |
| G5 图表可用 | H4 10 万点首帧 < 2s、交互 ≥ 30 FPS |
| G6 结果同源 | H11 进程内或子进程路线的 `result_hash` 与 CLI **逐字符相同** |
| G7 维护成本 | H9 单次版本迁移 ≤ 8 小时 |

**任一必过条件不成立 → 转为路线 B（Tauri/React）或路线 C（增强 web console）。**

## 9. 风险与放弃条件

| 风险 | 概率 | 影响 | 缓解 | 放弃条件 |
|---|---|---|---|---|
| 中文 IME 不可用 | 中 | 致命 | S2-G 第一优先验证 | H2 失败 → 放弃路线 A |
| 目标机器无法渲染（VM/RDP/无独显） | 中 | 致命 | 三类环境矩阵测试 | H1 物理机失败 → 放弃路线 A |
| 框架 pre-1.0 breaking 频繁 | 高 | 高 | 锁精确小版本 + vendor；每季度迁移演练 | H9 单次迁移 > 3 人日 → 放弃 |
| 构建/体积成本过高 | 中 | 中 | 用 feature 裁剪（关 inspector/JS 运行时） | H7 增量 > 3 分钟 → 放弃 |
| 进程内结果与 CLI 不同源 | 中 | 高 | S0-2 先抽共享库；P5 探针验证 | H11 不同源且无法收敛 → 只走子进程路线 |
| Python 分发负担 | 高 | 中 | 降级为声明式策略起步 | H12 失败 → 桌面端首版只支持内置+声明式策略 |
| 推翻项目既有决策的治理成本 | 高 | 中 | S0-3 显式决策会 + ADR | 决策会否决 → 不立项 |
| 前端资产重写超出预算 | 高 | 中 | 路线 B 可复用 `web/console` | 预算超支 → 转路线 C |

**建议的总体节奏**：**先花 3 人日做 S2-G 的 H1+H2 两个最小探针（只驗证渲染与中文 IME），不通过就立即停止 gpui-kit 评估**——这是成本最低的 fail-fast 点，避免在 45 人日前置工程之后才发现 UI 壳不可用。

## 11. 最终裁定

| 问题 | 回答 |
|---|---|
| **是否可行？** | **技术上可行**（UI 层与引擎层都验证了通路），但**当前状态下不建议直接立项**——真正的阻塞点是后端接入面（`qx-cli` 不可库化 + `qx-api` 无回测面），不是 UI 框架。 |
| **有哪些缺点？** | 见 §4 共 12 条，其中三条可能否决：**D-1 框架 5 周龄 pre-1.0**、**D-3 Windows 渲染与中文 IME 未证**、**D-2 第三方 GPUI 快照**；另有一条独立于框架的致命前置：**D-11 产物版本治理漏洞会让桌面端静默显示错误结果**。 |
| **推荐怎么做？** | **先做 3 人日的 H1+H2 最小探针（渲染 + 中文 IME）做 fail-fast**；通过后再做 S0/S1 前置工程（45 人日，与 UI 壳解耦）；最后双壳 Spike 后决策门。 |
| **如果不通过？** | 转 Tauri 2 + React（复用已归档 Tauron 方案 + 现有 `web/console` 资产），或增强 web console 不做桌面。 |
