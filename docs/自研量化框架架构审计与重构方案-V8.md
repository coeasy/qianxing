## 1. 审计口径与结论

### 1.1 状态分级

| 状态 | 定义 |
|---|---|
| A | 代码链路闭合，核心逻辑存在，已有稳定测试或本地端到端证据 |
| B | 主要代码已接线，但缺外部环境、故障恢复、性能或发布级证据 |
| C | 有模型、接口、兼容路径或局部实现，但不能称为完整产品能力 |
| D | 尚未形成可交付能力 |

### 1.2 总体结论

牵星已经具备真实的确定性交易内核、回测撮合、OMS/Ledger、Paper、CCXT/Binance 适配、策略协议、存储和运行时配置能力，不是概念工程。

但当前仍不能宣称“核心功能全部完成”或“工业级实盘链路全部贯通”。主要原因不是缺少更多策略，而是：

1. `qx-cli` 仍承载大量应用编排，形成 God Binary；
2. 风控存在 `qx-risk`、`RiskContext`、`RiskGate` 多套语义；
3. `qx-execution` 的核心 `ExecutionService` 已改为依赖 `qx-application` 端口，但兼容性的
   `ingest_venue_events`、Paper helper 和 CLI 仍保留对 `qx-runtime` 的边界依赖，完整拆分尚未结束；
4. A 股 Python 数据层现在已有版本化 JSON BarFrame、公司行为和交易日历到 Rust 回测规则的适配入口，Rust 侧新增了可绑定 Bars、公司行为、日历、停牌和涨跌停规则的 `DatasetBundleManifest`；目前支持公司行为/日历、显式 JSON 组件和带 schema/行数/指纹的 Arrow manifest 组件校验，并写入逐组件 RunManifest；Arrow IPC 解码仍保持在外部数据提供方边界；
5. Paper、CCXT、Binance 代码级流程存在，但真实外部沙盒、断线、未知结果和账单闭环未完成验收；
6. 多腿套利已经形成顺序腿状态、部分成交补偿、未知结果、单机恢复快照和幂等 `HedgeRecoveryWorker`；Paper/Binance/公共 CCXT 既可由 Execution worker 兼容扫描，也可由独立 `SpreadRecovery` worker 持续扫描和触发；仍不具备跨 Venue 原子提交和生产级实时故障矩阵；
7. PostgreSQL/NATS/多语言 SDK/生产部署有实现，但 CI 和真实环境验收仍不完整；
8. A 股公司行为已增加显式账户级账本语义：配股登记/部分认购/剩余权利失效、现金分红登记/支付、增发认购、回购要约、可转债发行认购、利息登记/支付、回售/赎回/强赎和转股均采用追加事实并可重放；配股支持登记日授予权利、认购开始日扣减权利和截止日自动失效，现金分红与可转债利息按登记日锁定权益并在支付日到账，强赎在提供发行人明确结算价格及可选数量时按账户当前持仓结算；发行人层面的股本变更、债券供给、强赎触发条件与回售规则仍需外部事实明确。

结论：**核心内核基本成型，主体链路在代码级大部分贯通；生产级应用链路和外部边界尚未全部完成。**

### 1.3 本轮单机工业化落地增量

本轮按照“PostgreSQL/NATS 暂缓，其余优先完成”的决策继续改造，已落地并通过本地测试：

- 新增 `RuntimeProfile`：默认 `single_node`，在配置校验阶段拒绝 PostgreSQL、NATS、OutboxRelay 和 EventConsumer；分布式示例显式声明 `distributed`，避免可选 feature 被误启用。
- 统一运行时相对路径解析，兼容 `foo.json` 与 `deploy/foo.json`，并让 `runtime-check` 真正检查调度任务、CCXT endpoint、交易规格、策略快照、DatasetBundle、A 股规则和策略发布物引用。
- qx-cli 默认启用 SQLite feature；Files 继续作为研究/回测和兼容 smoke 的本地后端。CI 增加 Python 测试、非 production 配置全量扫描和 production 占位配置 fail-closed 断言。
- 订单级规格、杠杆、保证金、减仓、投影持仓风控下沉到 `qx-risk::OrderRiskContext`；`qx-zhenlu::RiskContext` 保留兼容门面并转调唯一实现。
- 新增可序列化 `SpreadOrderGroup` 状态机和部分成交反向补偿目标，并由 `SpreadExecutionService` 接入顺序单腿执行；新增 `venue_id`、`VenueRouterPort` 和 `MultiVenueSpreadExecutionService`，可按腿路由多个 Venue 并持久化恢复，但仍不宣称跨 Venue 原子提交。
- `qx-execution::SpreadExecutionService` 和 `MultiVenueSpreadExecutionService` 已把多腿组接入统一执行事实边界：按腿路由/提交、归约 Accepted/Fill/Cancelled，在未知结果时保留组状态和补偿目标，并可通过 `FileSpreadOrderGroupStore` 持久化/恢复未完成组；`HedgeRecoveryWorker` 已由 Paper/Binance/公共 CCXT Execution worker 的兼容恢复扫描调用，也已提供独立 `SpreadRecovery` worker 角色，以确定性 client_order_id、reduce-only 订单、按订单组可过期 claim lease + fencing token 和状态快照执行幂等补偿，并在补偿提交前支持复用当前账户 `RiskContext`、产品规格和持仓快照，对 `ReconcileRequired` fail-closed；跨 Venue 原子性和生产级实时恢复编排仍未完成。
- `qx-data` 新增 `JsonBarFrameProvider`，可直接消费 Python/AkShare/Baostock/easy_tdx 输出的定点 BarFrame JSON，并进入统一 Provider/校验/范围查询接口。
- `JsonBarFrameProvider` 现在同时实现 `qx-provider::DataProvider`，可通过 `ProviderRegistry` 执行能力匹配、failover、source hash 和 `as_of` 门禁；`load_bars_with_manifest` 将数据范围、来源、版本和 fingerprint 绑定到 DatasetManifest。
- `strategy-backtest` 已在启动回测前通过 `qx-data` 重读并比对 BarFrame，注册并验证 DatasetManifest；列式输入与 Provider 输入不一致时 fail-closed。回测完成后会原子保存 RunManifest，Bundle 配置存在时将聚合指纹及 bars/corporate_actions/calendar 逐组件指纹写入清单。
- 新增 `qx-data::ingest_bars`：Provider 数据通过统一 `DataStorage::upsert_bars` 增量合并，再注册不可静默覆盖的 DatasetManifest，完成本地缓存/增量摄取的公共语义。
- 新增 `JsonFileDataStorage`：单机数据集采用安全 dataset key、临时文件写入和原子替换；它只承担研究/回测缓存，不与运行时 EventLog 或未来 PostgreSQL 事实存储混淆。
- 新增 `JsonDatasetRegistry`、`JsonDatasetBundleStore` 与 `DatasetRegistrar`：DatasetManifest 以版本化 JSON 持久化到单机数据目录，采用锁内重读、冲突拒绝和原子替换，跨 CLI 进程重启仍可验证 fingerprint；策略回测也复用该持久化 Registry。`dataset-bundle` CLI 已能校验并保存行情、公司行为、日历等组件清单。
- qx-cli 新增 `dataset-ingest <bar-frame> <dataset-id> <version> <data-dir>`，可直接把 Python/A 股标准化输出摄取到单机数据集缓存，作为快速回测前的统一入口。
- `AshareRuleConfig::apply_corporate_actions_json` 和 `apply_calendar_json` 已接入 Python 标准化 JSON：现金分红登记/支付、送股、转增进入现有 Ledger 语义；配股登记/部分认购/剩余权利失效、增发认购、回购要约、可转债发行认购、利息登记/支付、回售/赎回/强赎和转股在显式事实齐全时进入多腿 Ledger 并可重放；`CapitalChange` 已保存绝对总股本和可选流通股本快照；强赎数量缺省时按支付日账户当前持仓全量结算；发行人增发过程、债券供给变化和缺少强赎价格/回售价格等触发事实仍 fail-closed。
- `RuntimeConfig` 对 `live_enabled` 策略增加主体拓扑门禁：主标的/对冲腿必须有匹配的 MarketData worker，账户与 Venue 必须有匹配的 Execution worker；配置不会再出现“Strategy 已启动但没有行情输入或执行消费者”的静默失效。
- 实时 Bar 驱动增加新鲜度门禁：MarketData 写快照和 Strategy 读取快照都会拒绝未来 Bar 及超过 `live_max_staleness_ms` 的旧 Bar；省略该字段时按 3 个周期计算，行情停滞不会继续产生新订单。
- 实时 Job 在领取前和订单落队前重新比对 `manifest_digest` 与当前 Bar 快照；旧 Job 或评估期间行情切换会被幂等确认并跳过，避免 Job 身份与实际策略输入不一致。
- Paper Execution worker 改为读取同一 EventLog 的最近 L1 行情；无行情事实拒绝撮合。固定价格仅保留在明确的离线 smoke fixture，Paper E2E 会先注入可审计行情事实再执行。
- CCXT/Binance MarketData worker 现在会把真实轮询/流式 L1 行情按 source worker + source sequence 幂等镜像到匹配的 Paper 账户 EventLog；同一账户多个标的 worker 会合并过滤条件，Paper execution 不再依赖另一个 market worker 的内存状态。
- `JsonBarFrameProvider` 在范围裁剪前校验全量时间序列单调性，避免把范围外的乱序数据隐藏在回测输入之外；CI 的可选 feature 矩阵改为 `--no-default-features`，真实验证 SQLite 默认路径与 PostgreSQL/NATS 可选编译路径的边界。
- 新增 `qx-application` 端口层：定义执行事实、订单存储、风控、行情、对账和 Venue 契约；`LiveEventPipeline` 已实现订单注册与执行事实适配，`ExecutionService`/`SpreadExecutionService` 已可对任意 `ExecutionEventPort` 编排，保留旧 Runtime helper 作为兼容入口。
- 新增 `qx-execution::PortExecutionService`：提交、取消、重复订单、空回报和异常回报全部通过 `VenuePort`/`ExecutionEventPort` 完成；空回报和异常统一进入 `ReconcileRequired`，并有独立端口测试，后续 CLI 拆分可直接迁移到该服务。`qx-application` 进一步提供统一的提交/撤单事实契约，校验 `client_order_id`、`venue_order_id`、成交数量/价格和事件类型；非法回报不会写入 EventLog，而是 fail-closed 进入待对账。`qx-execution` 现已用同一 PortExecutionService contract test 实际覆盖 Paper、公共 CCXT Venue 和 Binance Spot Venue 的提交/撤单路径。
- `qx-application::QuoteBook` 已提供经过 L1 质量校验的单机行情端口实现；它只作为 Paper/回测的可替换内存视图，生产事实仍必须先进入 EventLog。
- 标准 `MarketQuote` 事实现在持久化 bid/ask 数量，并参与 EventLog digest、重放和 Paper 恢复；Paper worker 不再从固定 `1000` 伪造盘口容量。
- `qx-data::DatasetBundleManifest` 已提供带类型的多组件数据快照绑定、稳定 bundle fingerprint 和单机持久化；CLI 与 `qianxing_ashare bundle` 已能生成/保存组件清单，并可在提供 BarFrame 时复现 Rust bars fingerprint。策略回测配置了 `dataset_bundle_path` 后，会在启动前强制校验 Bundle、bars fingerprint、公司行为/日历内容指纹和行数；新增组件可通过 `strategy.dataset_component_paths` 显式绑定，通用 JSON 会递归规范化，Arrow 组件会校验独立 manifest 的 schema/行数/指纹，所有组件指纹写入 RunManifest；实际 Arrow IPC reader 由外部数据提供方负责。
- 事件事实元数据已贯通 `RuntimeEventEnvelope` → `EventLog` → Replay：每个事实带 schema version、source、observed/effective 时间语义、dedup key 和 rule version；显式 dedup key 对跨重试 source sequence 生效，派生 Ledger 事实使用派生去重键，旧日志缺少 metadata 字段时按默认值兼容恢复。
- A 股配股时间语义已贯通 Python JSON → `AshareCorporateActionEvent` → Backtest/Ledger：保留公告、登记、除权、认购起止和支付日期；登记日按当时持仓授予独立权利，认购按权利余额原子扣减，截止日自动失效，旧版仅有 `ex_date` 的 JSON 继续走兼容路径。
- A 股现金分红时间语义已贯通登记日权益、除权日拆分/送转和支付日现金到账；支付日不再按支付日当前持仓重新计算，旧版没有登记/支付日期的事件继续兼容即时账本语义。
- CLI 易用性已补齐项目初始化闭包：`qx-cli init` 会把运行时配置引用的调度样例、BarFrame、DatasetBundle、品种规格和 Paper 目标复制到同一目录；`init --strategy <name>` 可直接生成内置策略回测项目，`config fingerprint/lock` 用于稳定计算和验证发布配置锁，`run backtest/paper/doctor/live-check` 提供统一安全入口。

因此，本轮已把单机运行和关键安全边界从“代码存在”推进到“配置/测试可验证”。仍不能据此宣称真实交易所、券商柜台、PostgreSQL/NATS 集群和多腿跨 Venue 原子执行已完成。

## 2. 当前项目主要功能

### 2.1 确定性交易内核

`qx-core` 当前负责：

- 128 位定点金额、价格和数量；
- `InstrumentId`、账户、Venue 和产品身份；
- Clock、因果队列、事件优先级；
- Order、Fill、订单状态迁移和未知状态；
- EventLog、事件摘要、Replay 和 RunManifest；
- Ledger、现金、持仓、费用、资金费、利息、结算、清算；
- 现货、保证金、永续、期货的 `TradingInstrumentSpec`；
- Hedge/OneWay、杠杆、保证金和合约乘数。

这是当前最稳定、最应保留的内核。后续重构不得重新实现一套订单、持仓或账簿模型。

### 2.2 数据与研究

当前数据相关模块包括：

- `qx-provider`：Provider 能力、查询、质量结果和错误分类；
- `qx-guanxing`：行情、质量门、PIT 可见性和数据视图；
- `qx-data`：数据目录、缓存、增量合并、存储和公司行为模型；
- `qx-datastruct`：BarFrame、列式数据和 Arrow 边界；
- `qx-factor`：因子定义、因子报告、候选标的、研究快照和数据指纹；
- `python/qianxing_ashare`：AkShare、Baostock、easy_tdx 的 A 股行情和公司行为适配；
- `python/qianxing_ccxt`：公共 CCXT REST、可选 CCXT Pro、行情、订单、持仓、资金费和账单归一化。

当前 A 股 Python 层已经可以获取和标准化行情、公司行为、PIT 字段、交易日历并输出 JSON/BarFrame；BarFrame 已可通过 Rust `qx-provider` Registry adapter、`qx-data` DatasetManifest 和 `dataset-ingest` 进入单机缓存与回测入口，策略回测还可加载公司行为和交易日历 JSON。策略回测已支持通过 `dataset_bundle_path` 强制绑定 Bars Bundle，并校验公司行为/日历、显式通用非 Bars 组件和 Arrow manifest 组件的内容指纹；配股登记日/认购期/截止日、现金分红登记/支付及显式可转债强赎结算已进入规则与账本，发行人级公司行为仍未完成。

### 2.3 回测与撮合

`qx-xingban` 当前提供：

- Bar 级回测；
- Tick/L1 回测；
- L2 订单簿回测；
- 成交模型、滑点、延迟、排队和市场冲击；
- 费用模型、保证金和资金费；
- 确定性随机数和结果重放；
- A 股交易日历、停牌、T+1、整手、涨跌停、印花税和公司行为门禁；
- 现货、保证金、永续、期货的虚拟交易。

`qx-xingban` 的撮合和回测主体逻辑是真实实现，但不同数据档位的真实性不同：Bar 只能进行有限路径重构，不能等同于 L2/L3 实盘微观结构。

### 2.4 策略

当前支持：

- Rust 原生 Strategy；
- Python JSONL、framed、共享内存 JSON、共享内存列式协议；
- C ABI 和 C++ Worker；
- 内置 17 类策略，包括 SMA、EMA、MACD、RSI、布林、Donchian、动量、均值回归、网格、ATR/Keltner 趋势、VWAP、波动突破、配对套利、基差套利、跨交易所套利和期现套利；
- 多订单意图、信号、目标仓位、策略版本和数据指纹。

这些策略已经能生成统一意图并进入 Risk/OMS，但“策略存在”不等于“策略已经经过参数稳定性、跨标的、成本、滑点、极端行情和真实成交验收”。套利策略还缺少完整的双腿执行状态机。

### 2.5 风控、组合与 OMS

当前存在三层相关能力：

1. `qx-risk::RiskEngine`：较轻量的组合暴露和回撤判断；
2. `qx-zhenlu::RiskGate/RiskRule`：数量、名义额、禁止卖空和规则链；
3. `qx-zhenlu::RiskContext`：产品规格、保证金、参考价、持仓和账户限额的订单级预检。

`qx-oms` 已有独立订单生命周期模型，`qx-zhenlu` 仍保留兼容 re-export。当前订单、风控、路由和 Venue trait 仍主要集中在 `qx-zhenlu`。

### 2.6 Paper、CCXT 和 Binance

当前执行边界包括：

- `PaperVenue`：内存 Venue 和订单生命周期；
- Paper worker：队列领取、订单执行、Ledger、EventLog 和恢复；
- 公共 CCXT REST：多交易所行情、下单、撤单、订单查询、余额、持仓、资金费、账单、杠杆和精度；
- 可选 CCXT Pro：`watch_*` 流接口和重连封装；
- Binance Direct：REST、TLS、签名、市场行情、用户流和对账；
- `LiveEventPipeline`：外部事实去重、归约、Ledger/OMS 更新和 EventLog；
- Reconcile：本地订单、远端订单、持仓、余额、资金费和账单差异。

当前生产实时策略默认通过公共 CCXT REST 轮询 ticker/OHLCV，并以闭合 Bar 快照和 digest 触发策略 Job；这不是低延迟 WebSocket 主链。CCXT Pro 虽有可选接口，但尚未作为本期默认生产链路验收。

### 2.7 存储、控制面和运行时

当前支持：

- 文件 EventLog、分段 EventLog、快照、控制命令和 JobQueue；
- SQLite 后端；
- PostgreSQL 后端和连接池；
- Outbox、Relay、Consumer、Checkpoint、Projection、DLQ；
- NATS JetStream Publisher/Pull Consumer；
- API、mTLS、权限、审计、健康和 readiness；
- RuntimeConfig、Supervisor、Worker、健康状态和停机信号；
- Scheduler、Strategy、Execution、MarketData、UserStream、Reconciler、OutboxRelay、EventConsumer worker。

这些模块代码量较大，但文件、SQLite、PostgreSQL 和 NATS 并不具备相同事务与可用性语义，必须在产品层明确分级。

### 3.1 架构合理的部分

- `qx-core` 基本保持外部依赖隔离；
- EventLog、Ledger、OMS 和 Replay 的事实优先方向正确；
- Strategy 不直接访问凭证、Venue、Ledger 和控制面；
- 外部 Venue 事实通过统一 `RuntimeExternalEvent` 归约；
- `TradingInstrumentSpec` 是多资产和衍生品的正确抽象；
- 未知下单结果进入 Reconcile，不自动补单；
- 生产配置已有 mTLS、凭据、研究快照、产品规格和风险限额门禁；
- A 股数据源已保存原始字段、来源和 PIT 信息，不把复权行情直接当成成交事实。

### 3.2 架构不合理的部分

#### 3.2.1 应用服务和运行时反向耦合

`qx-execution` 直接依赖 `qx-runtime::LiveEventPipeline`。这使执行服务无法独立测试和复用，也让运行时承担了本应由应用层定义的事实写入职责。

目标依赖应为：

```text
qx-application / qx-execution
       ↓ ports
EventAppender / OrderStore / RiskPort / VenuePort / ReconcilePort
       ↑ adapters
qx-runtime / qx-storage / qx-adapter
```

#### 3.2.2 风控有三套语义

`qx-risk::RiskEngine`、`RiskGate` 和 `RiskContext` 的输入、输出和责任不同，容易造成回测、Paper、Live 走不同判定路径。必须收敛为一个 `RiskEngine.evaluate()`，返回可审计的 `RiskDecision`。

#### 3.2.3 `qx-zhenlu` 职责过宽

它同时承担 Risk、Signal、Target、Intent、Router、Venue、PaperVenue、Strategy lifecycle 和 OMS 兼容，变化原因过多。后续应拆出 Portfolio、Risk、Execution Contract 和 Paper Adapter，而不是继续向该 crate 加功能。

#### 3.2.4 `qx-cli` 是 God Binary

当前 `crates/qx-cli/src/main.rs` 超过 10,000 行，包含回测、研究、API、Supervisor、Scheduler、Strategy、Paper、CCXT、Binance、Reconcile、Outbox、Consumer、DLQ 和测试。它已经成为实际应用层，导致业务编排、配置解析、CLI 参数和测试全部耦合。

目标拆为：

```text
qx-node   # 运行时节点、worker、supervisor
qxctl     # 控制、诊断、对账、DLQ、配置检查
qx-lab    # 数据、研究、回测、基准和策略实验
```

第一步只移动代码，不改变业务语义。

#### 3.2.5 A 股数据层与 Rust 数据平面断开

`python/qianxing_ashare` 现在直接输出 BarFrame 和公司行为 JSON，当前已完成：

- `JsonBarFrameProvider` 到 `ProviderRegistry` 的注册适配；
- `qx-data` DatasetManifest 生成和 fingerprint 校验；
- Rust 侧 BarFrame 质量门和策略回测前的输入一致性校验；

统一缓存/增量更新和持久化 DatasetManifest 已完成；Bars Bundle 到策略回测的启动绑定、公司行为/交易日历 JSON 到 `AshareRuleConfig` 的转换、配股登记日/认购期/截止日和现金分红登记/支付账本生命周期、增发/回购/可转债发行认购/利息登记支付/回售赎回/显式强赎结算/转股账本及 Bundle 逐组件 RunManifest 绑定已完成，新增非 Bars 组件可通过显式路径映射完成通用 JSON 内容校验；发行人级股本变化、债券供给变化和强赎触发规则仍未完成。

因此当前可以称为“具备 Rust Provider/Manifest 门禁的 A 股数据接入链”，但不能称为“统一 A 股数据平面全部完成”。

#### 3.2.6 多腿套利已贯通组身份和单机恢复快照，但不是原子交易

17 类内置策略和多交易所示例已经存在。策略 worker 现在会在多条 `OrderIntent` 进入命令队列前创建幂等 `SpreadOrderGroup`，把 `spread_group_id` 随每条命令传递到执行 worker；Paper、Binance 和公共 CCXT 执行路径在 EventLog 写入后回写对应腿的 Accepted/Cancelled/Rejected/Unknown 和已确认成交数量。因此重启后可以按组快照继续对账，而不是只看到彼此无关的单腿命令。

当前仍不具备：

- 跨 Venue 原子提交或可证明的跨进程提交屏障；
- Supervisor 自动调度 `HedgeRecoveryWorker` 和补偿命令；
- 每腿费用、保证金、资金费和跨账户归因的统一组级汇总；
- 生产级故障矩阵、时钟/行情新鲜度门禁和人工恢复工作流。

所以现在可以定义为“多腿信号、命令、单腿事实、组快照和独立恢复编排已贯通”，不能把它定义成“生产级自动套利交易已完成”。

#### 3.2.7 存储后端一致性等级被一个枚举隐藏

文件后端通常是 EventLog 写入后再逐条生成 Outbox；PostgreSQL 可以实现事件和 Outbox 同事务；NATS 只负责投递，不应成为事实来源。三者必须在配置和报告中明确标出：

```text
files      = local/replay/smoke
sqlite     = single-node durable
postgres   = production transactional baseline
postgres+nats = distributed delivery baseline
```

#### 3.2.8 配置仍是大量 optional 字段和 role 分支

`WorkerConfig` 同时承载 API、Scheduler、Strategy、Execution、MarketData、UserStream、Reconciler、Consumer 等角色，非法组合主要靠运行时 `validate()` 和 CLI 分支发现。应逐步改为 tagged configuration，令非法拓扑在反序列化和启动前失败。

#### 3.2.9 Paper Smoke 行情和真实 Paper 行情边界不清

`paper-e2e` 使用合成报价推动订单成交，适合作为确定性 smoke，但不等同于持续行情驱动的 Paper 产品。该 helper 应独立命名为 `SyntheticQuoteFixture/PaperSmokeExecutor`，真实 Paper Venue 必须只消费 `MarketDataPort`。

#### 3.2.10 生成物仍被版本控制（本轮已修复）

本轮已将 `python/build` 和 `python/qianxing_bridge.egg-info` 从版本控制中移除，并加入 `.gitignore`；后续只保留源码、锁文件和可重复构建脚本。

### 5.1 回测链路：代码级贯通

```text
BarFrame / Tick / OrderBook
        ↓
Strategy
        ↓
StrategyDecision / Signal / Target / Intent
        ↓
Risk / OMS
        ↓
Xingban Matcher
        ↓
Fill
        ↓
Ledger / EventLog
        ↓
Report / Replay / RunManifest
```

结论：**已贯通，A-/B+。**

主要限制：多腿套利的跨 Venue 自动对冲、A 股权利生命周期/发行人事件、真实 L3 盘口、真实强平和交易所差异化费用还不能视为完整仿真。

### 5.2 Paper 链路：代码级贯通，行情来源和执行语义已分层

```text
Scheduler
  → JobQueue
  → Strategy Worker
  → Signal / Intent
  → Control / CommandQueue
  → Paper Execution Worker
  → Paper Venue / Synthetic Quote
  → Accepted / Fill
  → LiveEventPipeline
  → EventLog / OMS / Ledger
  → Query / Reconcile
```

`paper-e2e` 已真实运行 Scheduler、Strategy、Execution 和 Ledger；合成报价只用于明确的
smoke fixture，持续 Paper worker 消费同一账户 EventLog 中由 CCXT/Binance MarketData
镜像的 L1 价格和数量，重启后也能恢复盘口容量。真实断线、延迟和外部沙盒仍需验收。

结论：**代码级 B+，产品级 B-。**

### 5.3 CCXT 实时链路：代码已接线，外部闭环未证明

```text
CCXT REST MarketData
  → ticker / OHLCV
  → EventLog + closed BarFrame snapshot
  → digest 触发 Strategy Job
  → OrderIntent / ControlCommand
  → CCXT Execution
  → Accepted / Fill / Cancel / Unknown
  → EventLog / OMS / Ledger
  → REST Reconcile / optional CCXT Pro UserStream
```

结论：**代码链路 B-，真实沙盒 C+。**

当前没有真实交易所凭证、订单、成交、UserStream 断线、未知提交结果和账单恢复证据，不能称为实盘链路完成。

### 5.4 A 股研究链路：快速回测已通，统一数据平面未通

```text
AkShare / Baostock / easy_tdx
  → Python 标准化
  → BarFrame / CorporateAction JSON
  → screen
  → fast-backtest
```

这条链路已经能快速选股和回测。但还缺：

- Rust ProviderRegistry 接入；
- 数据目录和增量缓存；
- 公司行为快照自动绑定回测；
- 股票池、财务、公告 PIT 的统一管理；
- 权利生命周期、发行人级事件和可转债完整生命周期；
- A 股真实券商执行。

结论：**研究工具链 B，完整 A 股产品链 C+。**

### 5.5 多腿套利链路：组身份、单腿事实和单机自动补偿已贯通

```text
多标的行情
  → spread / basis signal
  → 多个 OrderIntent
```

当前已有策略侧 `spread_group_id`、执行侧单腿 EventLog 事实、`SpreadOrderGroup` 恢复快照、多腿生命周期、部分成交补偿目标和多 Venue 顺序路由；Paper/Binance/公共 CCXT Execution worker 保留兼容自动扫描，同时提供独立 `SpreadRecovery` worker 扫描 `HedgeRequired` 并执行确定性补偿；同账户同 Venue 配置独立恢复角色后，Execution 会自动停止兼容扫描，避免并发补偿竞态；仍缺少跨账户归因、跨 Venue 原子提交和生产级故障演练，因此不能把它判定为完整生产套利交易链路。

```text
│ StrategyService / PortfolioService / RiskService           │
│ OrderService / ExecutionService / ReconcileService         │
│ DataIngestionService / BacktestService                     │
└────────────────────────┬───────────────────────────────────┘
                         │ Ports
┌────────────────────────▼───────────────────────────────────┐
│ Domain Kernel                                              │
│ qx-core / qx-oms / qx-risk / qx-portfolio                  │
│ Event / Order / Ledger / Position / TradingSpec / Replay    │
└────────────────────────┬───────────────────────────────────┘
                         │ Ports
┌────────────────────────▼───────────────────────────────────┐
│ Adapters                                                   │
│ Paper / CCXT / Binance / Broker / A-share / Storage / NATS  │
│ Python / C++ / Arrow / Shared Memory                       │
└────────────────────────┬───────────────────────────────────┘
                         │
┌────────────────────────▼───────────────────────────────────┐
│ Runtime                                                   │
│ typed config / worker lifecycle / supervisor / health       │
└────────────────────────────────────────────────────────────┘
```

依赖规则：

1. `qx-core` 不依赖 runtime、storage、API 或具体适配器；
2. Domain 只定义事实、状态和端口，不依赖具体数据库；
3. Application 只依赖 Port，不依赖 `LiveEventPipeline` 具体类型；
4. Adapter 只负责协议转换和外部事实采集；
5. Runtime 只负责装配、进程生命周期和健康状态；
6. API/CLI 只负责输入解析、鉴权、调用 Application；
7. Strategy 只产生 Signal/Target/Intent，不访问 Venue、凭据、Ledger 或控制面；
8. Paper、CCXT、Binance、券商适配器必须通过同一组 contract tests。

## 8. 分阶段重构方案

### Phase 0：可信基线和仓库治理

目标：先把“能验证”建立起来，不改变业务语义。

交付：

- 增加 maturity/capabilities.yaml，区分 implementation、test、sandbox、production；
- 修复所有 runtime 示例中的相对路径规范；
- runtime-check 递归检查引用文件，不只检查字段存在；
- 清理 Python 构建生成物；
- 修 README 本地绝对路径；
- CI 增加 Python、全部 runtime 配置和 all-features；
- 以当前 `57cb62a` 生成基线回测结果和事件摘要。

验收：

```text
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test -p qx-cli --all-features
python -m unittest discover -s python/tests

```

### Phase 1：拆分应用入口

目标：不改变业务结果，只移动职责。

顺序：

1. `qx-cli/src/main.rs` 拆为 command、worker、backtest、connector、operator、research；
2. 引入 typed command parser；
3. 保留旧命令别名，输出相同结果摘要；
4. 形成 `qx-node`、`qxctl`、`qx-lab` 三个产品入口；
5. 用 golden result hash 证明移动前后语义一致。

### Phase 2：Application Ports 和依赖反转（本轮已完成核心迁移）

新增最小端口：

```text

LedgerRepository

```

重构 `qx-execution`：

```text

  → OrderService

```

`LiveEventPipeline` 变成 runtime adapter，而不是 ExecutionService 的直接依赖。

当前进度：`qx-application` 已建立 `ExecutionEventPort`、`OrderStore`、`RiskPort`、
`MarketDataPort`、`ReconcilePort` 和 `VenuePort` 契约；`qx-runtime` 已将
`LiveEventPipeline` 适配为订单/执行事实/最新 L1 行情端口；`qx-execution` 的
`ExecutionService`、`PortExecutionService` 与 `SpreadExecutionService` 已可对端口泛化。
运行配置已增加 `storage.consistency`，并由 RuntimeConfig、runtime-check、status
和配置指纹共同约束 `local_durable`、`transactional`、`distributed_outbox` 三种等级；
示例配置已按 Files/SQLite、PostgreSQL、NATS Outbox 拓扑更新。剩余工作是将 CLI
中的 Paper helper、兼容性事件函数和 worker 装配继续迁移到端口，完成 `qx-cli` 拆分
后再删除旧 Runtime 兼容入口。

### Phase 3：统一 RiskEngine

统一输入：

- AccountSnapshot；
- PositionSnapshot；
- TradingInstrumentSpec；

- RiskRuleSet；
- OrderIntent。

统一输出：

```text
RiskDecision {
  allowed,
  violations[],
  projected_position,
  projected_margin,
  snapshot_id,

  reference_price_ts

```

回测、Paper、CCXT、Binance、未来券商统一只调用该入口。旧 `RiskGate` 和 `RiskContext` 在两个版本周期内转为兼容包装，之后删除。

本轮已新增 `qx-risk::RiskEngine::evaluate_order` 和可序列化的
`OrderRiskDecision`（allowed、violations、投影持仓、投影保证金、参考价和
rule_set_version），并由 `qx-execution::CanonicalRiskPort` 直接注入应用层；
`qx-zhenlu::RiskContext` 仍作为兼容快照门面并转调同一基础校验。`RiskGate` 的
策略规则链尚未删除，后续需要把规则集本身迁移到该统一决策输出。

### Phase 4：统一 Paper/CCXT/Binance 执行契约

为所有 Venue 运行同一套 contract tests：

- submit accepted；
- partial/full fill；
- cancel；
- duplicate client id；
- timeout/unknown；
- reconcile required；
- restart recovery；
- late/duplicate/out-of-order event；
- precision/lot/margin rejection；
- risk rejection before side effect。

Paper 增加真正的 MarketDataPort 驱动模式，SyntheticQuoteFixture 只能被测试或明确的 smoke profile 使用。

### Phase 5：A 股数据平面和公司行为

统一数据流：

```text
AkShare / Baostock / easy_tdx / Exchange Notice
  → RawRecord
  → Canonical Dataset
  → Data Quality Gate
  → DatasetManifest
  → PIT / CorporateActionFrame
  → Rust Backtest / Research Snapshot
```

公司行为分层：

1. 现金分红、送股、转增：进入现有 Ledger；
2. 配股：权利登记、显式认购资金、参与数量、剩余权利失效和目标标的已进入 Ledger 并支持重放；登记日授予、认购起止和截止日失效已按时间事实执行；发行人层面的除权价和完整结算周期仍需扩展；
3. 增发：显式认购资金、数量和上市标的已进入 Ledger；`CapitalChange` 已支持显式绝对总股本和可选流通股本快照，并纳入回测报告结果；发行过程和上市时间仍需扩展；
4. 可转债：独立 Instrument 与显式发行认购、利息登记/支付、回售、赎回、强赎、转股已进入 Ledger；强赎支持明确价格下按当前持仓全量或显式数量结算；发行人债券供给、条款触发和自动强赎规则仍需扩展；
5. 所有事件必须带 `source/published_at/effective_at/record_date/ex_date/raw_payload`。

账户级复杂事件已按显式事实接入，但以下场景仍保持 fail-closed，禁止把它们当普通拆股：缺少显式权利登记/失效数量的事件、发行人增发过程、债券供给变化、缺少价格的可转债回售赎回/强赎、自动强赎条款、未明确参与数量的回购或认购；`CapitalChange` 不允许从账户持仓或变更差额反推，必须提供绝对总股本，流通股本缺失时保持未知；强赎数量缺省仅表示“支付日当前持仓全量”，不代表系统自行推断触发条件。

生产环境的绑定策略已禁止非零裸 `target_qty`，必须通过 ResearchSnapshot、CandidateBinding
和数据指纹提供目标；`target_qty=0` 仅作为兼容字段的空值保留。

### Phase 6：多腿套利执行

新增：

```text
├── hedge_policy
├── max_leg_skew
```

当前已落地组身份、组快照和单腿事实归约；后续必须继续支持：

- 双腿同步提交或明确先后策略；
- 部分成交和剩余腿补偿；
- 价差失效撤单；
- 对冲失败进入人工/自动恢复；
- 每腿事件重放和归因；
- 重启后恢复未完成套利组。

### Phase 7：存储、消息和发布工业化

- PostgreSQL：事件、Outbox、命令队列、JobQueue、消费位点的事务边界；
- NATS：只承担 at-least-once delivery、重试、DLQ 和指标；
- Files：限制为 local/replay/smoke profile；
- SQLite：限制为 single-node profile；
- 增加 schema migration、backup/restore、fencing 和 crash recovery；
- CI 运行 PostgreSQL/NATS service container；
- 发布物包含版本、锁文件、SBOM、checksum、策略 ABI 和配置 schema。

### Phase 8：多语言 SDK 和策略运行时

- Rust Strategy API semver；
- Python wheel 多平台和 Python 版本矩阵；
- C++ ABI symbol/version/ownership/error contract；
- JSONL、framed、shared-memory JSON、QXCB 使用同一 golden vectors；
- Worker 超时、内存、CPU、崩溃重启和状态恢复；
- 不受信任 C/C++ 策略默认独立进程，禁止直接加载进交易进程。

## 9. 验收门禁

### G0 代码质量

- fmt、Clippy、依赖审计；
- 禁止非法层依赖；
- warning-as-error feature matrix；
- 源码和生成物分离。

### G1 确定性

- 相同输入、策略、配置、seed、数据指纹得到相同 EventLog digest；
- 数据、策略或规则变化必须改变 RunManifest；
- no-lookahead；
- 重启恢复前后结果一致。

### G2 领域正确性

- 订单状态迁移；
- Ledger 现金/持仓守恒；
- 衍生品乘数、保证金、资金费、交割和清算；
- Risk reject-before-side-effect；
- 公司行为账本和复权价格一致性。

```text
Scheduler
 → Strategy
 → JobQueue
 → Risk

 → Paper Venue

 → EventLog
 → Ledger
```

必须同时提供 synthetic smoke 和 market-driven paper 两套结果，不能混为一个“Paper 已完成”。

### G4 外部连接器

真实交易所和券商验收需要真实账户、权限、网络、凭据和模拟环境，不能由 mock 或协议单测替代。

## 10. 已确认的产品边界和执行决策

本轮已确认：PostgreSQL/NATS 暂不作为默认运行依赖，也不阻塞单机主体功能收口；后续只保留可选 feature、适配接口和独立配置，不把未连接的外部服务写成已验收能力。

当前执行顺序固定为：

1. 先完成单机 `CCXT REST → EventLog → MarketDataPort → Strategy → Risk → Paper/Execution → Ledger` 主链和恢复/对账门禁；
2. 同时把 A 股 BarFrame、公司行为、交易日历、停牌和涨跌停规则绑定为可验证的数据快照，再接快速选股回测；
3. 将 `qx-cli` 拆分为应用服务和入口层，逐步删除 Runtime 兼容 helper；
4. 真实交易所沙盒、券商协议和模拟账户具备后，单独执行外部 contract/sandbox 验收；
5. PostgreSQL/NATS、多节点 HA、分布式 outbox 和生产灾备另立阶段，不混入本次单机完成度。

兼容路径（`target_snapshot/target_qty`、旧 RiskGate、`qx-zhenlu` OMS re-export）本阶段继续保留，但新代码不得新增依赖；待 CLI 拆分和新端口迁移完成后再设删除版本。

## 11. 最终判断

当前项目的正确定位是：

> **确定性量化交易内核和单机研究/回测/Paper 平台已经形成，公共 CCXT 和多语言策略协议已经具备可扩展基础；但统一应用层、A 股完整数据平面、多腿执行、真实外部验收、生产存储和发布体系仍需重构收口。**

下一阶段不建议继续横向增加更多交易所或策略。最优顺序是：

```text
可信基线
  → 拆应用入口
  → 反转依赖
  → 统一 RiskEngine
  → 统一 Venue/Execution contract
  → 完成 A 股数据平面和公司行为账本
  → 完成多腿执行
  → PostgreSQL/NATS/发布工业化
  → 最后扩展券商、HA 和更多插件能力
```
