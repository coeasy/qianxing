## 1. 项目定位分析

| 维度 | 特点 |
|---|---|
| **核心价值主张** | 「分级校准，量天定位」——一台**确定性**的量化回测与纸面交易内核：同样输入必然得到同样结果，产物自己说得出结论压在哪些输入上；数据档位不足即**拒绝运行**，绝不从 K 线读出不存在的盘口 |
| **目标用户** | 需要**可复算、可审计**结论的量化研究者 / 策略团队 / 合规敏感场景（当前主用法：本机无凭据的回测与 Paper 闭环） |
| **核心功能** | 三档回测（Bar / L1 Tick / L2 订单簿）＋ Paper 闭环（Scheduler→Strategy→Risk→OMS→Queue→Fill→Ledger）＋ 多交易所/多数据源/多账户/多策略治理 ＋ 多语言策略（Rust / Python / C++） |
| **技术架构** | Rust workspace（25 成员）＋ PyO3 Python 扩展 ＋ C++ C-ABI worker ＋ CCXT worker；自研 HTTP/WS；SQLite/PostgreSQL/文件/分段文件四后端 |
| **商业模式** | 开源（Apache-2.0），无商业化路径声明；能力矩阵分四档证据（implementation / code_tested / sandbox_tested / production_approved） |
| **差异化优势** | ①事件流重放确定性（`log_digest` / `result_hash`）；②数据档位与撮合模型绑定；③「没算过 ≠ 是零」（`Option<i128>` money）；④`fail-closed` 凭据策略；⑤文档即门禁（940 条架构不变量） |
| **明确边界（非缺陷）** | 不是已对接真实账户的系统（`sandbox_tested`/`production_approved` 全为 false，50 条能力项 `true=0`）；不是热插拔插件平台；不是统一撮合机（回测三内核 ≠ Paper 首档 touch 撮合）；不含跨节点 HA、WASM、券商柜台协议 |

### 2.4 三条主链路（关键函数）

| 链路 | 入口 | 调用链 | 产物 |
|---|---|---|---|
| Bar 档回测 | `qx-cli backtest` | `QualityGate::check` → `DataView::try_new` → `BarMatchingEngine` → `Ledger`/`Oms`/`EventLog`（`qx-xingban/src/backtest.rs:305-420`） | `*.summary.json`/`equity.csv`/`fills.csv`/`run.json` + `*.record.json` |
| 深度档回测 | `backtest book --fill-tier l1\|l2` | `TickBacktestEngine::run`（`tick_backtest.rs:175`）／`OrderBookBacktestEngine::run`（`orderbook_backtest.rs:266`）；l1 帧多一档盘口即拒 | 同上，落点名的 `--root` |
| Paper 闭环 | `qx-cli paper-e2e` | Scheduler → Strategy → Paper Execution → Ledger；成交由 `PaperVenue::on_quote` 首档 touch 产生（`qx-zhenlu/src/lib.rs:1306`） | 订单、Ledger、审计事实、队列终态 |

**回测与 Paper 同源的是「规则」（风控/费用/延迟/保证金四模型 + 事件归约），不是「撮合」**——这是 README 反复声明的边界，也是与 Nautilus/LEAN「同一撮合机」叙事的根本差异。

### 2.5 数据模型与存储

- **四级存储 = `EventLogStore` 四后端**：文件 / `SegmentedEventLogStore` 分段文件 / SQLite（rusqlite bundled）/ PostgreSQL（`qx-storage/src/lib.rs:352`）。
- **另一个「四级」是质量门**：`Verdict::{Ok,Warn,Quarantine,Fail}`，fail/quarantine 直接拒跑（`qx-guanxing/src/lib.rs:368-407`）——两个「四级」概念同名不同物，文档中需区分。
- feature 开关：`sqlite` / `postgres` / `nats`（`async-nats` JetStream，**全仓唯一 tokio 使用者**）。
- **schema 版本机制**：每契约一个 `*_SCHEMA_VERSION: u32` 常量 + `maturity/schema-registry.json`（producer/consumers/compatibility/golden_fixtures）+ 11 份 `schemas/*.json`；版本判定**排在字段解析之前**；契约正文用 `include_str!` 单一文本源（`qx-protocol/src/lib.rs:33-39`）。
- 列式：`qx-datastruct` 提供固定列名 BarFrame + Arrow C Data Interface **借用视图**（不引入内核热路径）。

### 2.7 门禁与测试体系

- **九步门禁**（`build.bat` / `build.sh`，两者同序同条由 `build_script_parity_check` 断言）：[0/9] 解释器探测 → [1/9] **架构不变量（940 条）** → [2/9] fmt → [3/9] release 构建 → [4/9] Rust 测试 → [5/9] clippy → [6/9] Python/JSON 边界 → [7/9] 核心语义自校验 → [8/9] CLI 全链路生态冒烟 → [9/9] 运行时拓扑校验。
- **不变量类别**：契约单点、死码/零读者公共面、CLI 分派一致性（`help ≡ clap 命令表 ≡ cli.rs 派发分支`）、单测地板、能力矩阵证据存在性、「诚实牙齿」（无外部证据不许标高等级）、行数棘轮。
- 168 个测试文件，17 个 crate 带 `tests/`；`contract-tests` 承载跨 crate 契约（paper_accounting / reconcile_port_contract / recovery_and_replay / risk_parity / venue_report_contract）。
- CI 7 作业：rust-core / python-wheel / feature-matrix / service-backends / runtime-contracts / cpp-sdk / venue-acceptance（`.github/workflows/ci.yml`）。

### 2.8 多语言策略与插件

- `qx-plugin`（卯眼/榫头）：**仅启动期静态装配**（manifest schema/hash + Ed25519 签名、`replaces` 独占冲突、`requires` 拓扑、`resolve_order`），**无运行时热加载**；只保留 `Matcher` / `FeeModel` 两个真分派扩展点（`qx-plugin/src/lib.rs:10,23-24`，核验确认无 dlopen/libloading）。
- Worker 生命周期：`worker_entry.rs` 的 `WorkerRole` 分派表（api / market-data / user-stream / execution / spread-recovery / scheduler / reconciler / strategy / outbox-relay / event-consumer）+ `VenueEntry`（CCXT / Binance）登记表；跨语言解释器统一 `QX_PYTHON`。
- 策略传输四档：JSONL / `framed_json`(QXSF, 含版本+序号+长度上限+CRC32) / `shared_memory_json` / `shared_memory_columnar`(QXCB 定宽列)，同一份 `schemas/strategy_api_v1.schema.json` 描述。
- **硬边界**：策略进程不得绕过 Risk/OMS 直接调 Venue。

### 2.9 风控、账户与多策略治理

- **双树风控**：账户级 `RiskPort` 与订单级 `RuleSet` 两条不同通道（账户拒绝 ≠ 端口给不出裁决），`qx-risk/src/lib.rs:62-325`。
- **净额**：`TargetPosition` 为组合层净额唯一目标表示（定义在 core）；多腿按 `priority` 排序。
- **Ledger**：`qx_core::ledger::{Ledger, LedgerEntry}`，钱字段 `null` 表未算、`0` 表算过且为零。

### 2.10 部署与运维

- `deploy/` 53 份顶层模板 + `grafana/` + `prometheus/` + 跨平台启动脚本。
- **自研 HTTP 服务器**（未用成熟框架），覆盖/缺口逐格登记在 `maturity/http_surface.yaml`（如 chunked=gap）。
- `web/console/`：M1' 快照 / M2' 实时事件 / M3' 控制面，写面仅 1 条，**不直接下单**。`qx-cli console` 提供同源 BFF：仅绑回环、CSRF 双提交、身份服务端注入、引导令牌只从环境变量读。

### 4.2 深挖要点（文档级，非本地克隆）

#### NautilusTrader —— 最像的对手
- **crate 划分**：`nautilus-core` / `model` / `common` / `system` / `backtest` / `execution` / `risk` / `portfolio` / `infrastructure`。比牵星的 25 crate 更粗、边界按「引擎」组织而非按「领域名词」。
- **核心抽象**：`Cache` / `MessageBus` / `DataEngine` / `ExecutionEngine` / `Portfolio`；`MessageBus` 是类型化 pub/sub，把数据、命令、事件统一成消息——牵星目前是「事件日志 + 命令队列」双通道，无统一 typed bus。
- **回测-实盘同源**：同一 event model / clock / cache / execution flow，只换 venue 与 data client。牵星是「同规则不同撮合」，**确定性与诚实性更强，但代价是两套路径需要各自维护**。
- **许可风险**：LGPL-3.0。牵星 Apache-2.0 是**企业友好度上的真实优势**。
- **可借鉴**：typed MessageBus、统一节点生命周期、adapter 分层与 crash-only 设计。

#### barter-rs —— Rust 同构对手，MIT
- **6 crate**：`barter` / `barter-data` / `barter-execution` / `barter-integration` / `barter-instrument` / `barter-macro`。crate 数远少，`barter-macro` 提供声明式策略宏。
- **关键设计**：`EngineFeedMode::Iterator`（回测）与 `Async`（实盘）**同一个 `Engine`**，`Strategy` / `RiskManager` / `ClosePositionsStrategy` / `OnDisconnectStrategy` 四个 trait 组合；`AuditTick` 用于状态复制（对齐牵星的 Ledger，但粒度是 tick 级）。
- **诚实声明**：README 明示「仅教育用途、不适合生产」——**牵星在「敢不敢用于生产」的表述上反而更自信**（尽管外部证据为 0）。
- **可借鉴**：`barter-macro` 式的极简策略书写；单 Engine 双 FeedMode 的心智模型；crate 数量克制。

#### hftbacktest —— 深度档必须正视的对手
- **模块**：`backtest/evs.rs` / `order/mod.rs` / `proc/{local, exch, nopartialfillexchange, partialfillexchange, l3_*}`。把**撮合模型做成可组合的 processor**——比牵星的三套硬编码内核更灵活。
- **亮点**：
  1. **队列位置模型**（queue position modeling）——L2 成交的行业标准做法，牵星 L2 是「按帧带的全部深度吃单」，**没有队列位置估计**；
  2. `OrderBus` 注入 entry/response 延迟；
  3. 确定性 sharding-time 事件流；
  4. **同一份 algo 代码跑 live bot（Binance/Bybit）**，比牵星「回测/Paper/实盘三套装配」更一体。
- **可借鉴**：processor 可组合化、队列位置模型、延迟注入的显式化。
- 注：hftbacktest 是 MIT，牵星在同样强调 L2/L3 时，**队列位置建模缺失会直接影响深度档回测的可信度**。

#### 多语言/插件的行业做法
- **pyo3 范式**（Nautilus v1→v2 用 PyO3 重写控制面、ruff/polars 同路）：牵星已用 PyO3，方向正确。
- **WASM 沙箱**：extism + wasmtime 的 deny-by-default Manifest、fuel/epoch 计量是「不受信策略」的标准做法——牵星当前策略 worker 是**独立进程 + 明文协议**，无资源计量与沙箱（README 已将 WASM 列为未接入）。
- ⚠️ 安全参照：wasmtime/cap-std 曾有沙箱逃逸 CVE（GHSA-vqjp-4c8c-hfgg）——说明 WASM 不是银弹，牵星的「进程隔离 + 签名 manifest」路线本身并不落后。

## 6. 优缺点分析

### 6.1 牵星的相对优势（应守住）

1. **信任层是真实护城河**：定点数 + 注入时钟 + 事件全序 + 重放验证 + `input.fingerprint` 按实读帧重算——**在全部对照竞品中，没有第二家把「可复算」做到这个粒度**（hftbacktest 的确定性偏「同机同参可复现」，Nautilus 偏「同模型」，都没有 `log_digest`/账本比对这种双向校验）。
2. **数据诚实性**：档位不足即拒绝运行，是**行业内罕见的「宁可不跑」**姿态；backtrader/vectorbt/Qlib 都默认从 K 线推出隐含假设。
3. **`null ≠ 0` 的钱字段契约**：`Option<i128>` 贯穿线格式——这是**没有任何对照竞品实现**的资产（Nautilus/LEAN 都用 0 或 NaN）。
4. **许可证**：Apache-2.0，对比 Nautilus（LGPL-3.0）、backtrader/freqtrade（GPL-3.0）、vectorbt（+Commons Clause）、rqalpha（非商业）——**商用友好度第一梯队**。
5. **单个自包含 binary + 内置模板**：`qx-cli.exe` 不依赖仓库、模板打进二进制，部署摩擦低于 Nautilus/LEAN 的 Python/C# 运行时。
6. **文档即门禁**：940 条不变量把「文档承诺」和「代码事实」强行对齐，长期重构回归风险显著低于同业。

### 6.2 牵星的相对劣势（应补足）

| # | 劣势 | 对比竞品依据 | 严重等级 |
|---|---|---|---|
| L1 | **队列位置/延迟模型缺失** | hftbacktest 的 `partialfillexchange`/queue model 是 L2 回测行业标准；牵星 L2 按帧全深度吃单，会系统性高估成交 | 🔴 致命（对深档可信度） |
| L2 | **研究层几乎空白**：无统一实验规格、参数网格/walk-forward/OOS 报告 | LEAN optimize、Qlib Workflow、vectorbt 参数扫描、freqtrade hyperopt | 🔴 致命（对研究者） |
| L3 | **结果可视化为静态 HTML/SVG**，无交互图表、无回撤归因、无交易点标注 | LEAN/vnpy/vectorbt/freqtrade WebUI | 🟠 重要 |
| L4 | **上手门槛高**：25 crate、多 worker、53 模板、角色术语（观星/星板/针路/更路）对新人构成认知负担 | freqtrade/Jesse/quantdigger 的十分钟首跑 | 🟠 重要 |
| L5 | **连接器生态起步**：无 capability matrix / 官方-社区-实验性分级 / conformance suite | Hummingbot connector conformance、vnpy gateway 生态 | 🟠 重要 |
| L6 | **零真实外部证据**（`sandbox_tested`/`production_approved` 全 false） | Nautilus/LEAN/vnpy 有实盘生态记录 | 🟠 重要（营销与信任双面） |
| L7 | **插件只有启动期装配**，无运行时扩展 | Nautilus adapter 分层、LEAN 可插拔模型、freqtrade 插件 | 🟡 次要（且是刻意取舍） |
| L8 | **无 WASM/资源计量**，策略进程无沙箱与 fuel/epoch 计量 | extism+wasmtime 的 deny-by-default | 🟡 次要（已列非目标） |
| L9 | **无跨节点 HA、无连接池/读写分离** | LEAN/Nautilus 的分布式部署形态 | 🟡 次要（已列非目标） |
| L10 | **社区规模极小**（单团队 352 commits，无外部贡献者生态） | 全部竞品 | 🟠 重要（长期可持续性） |

### 6.3 最大威胁

1. **hftbacktest 在深度档的专业度**：若目标用户是高频/L2 研究者，牵星「档位不足即拒」的姿态会被 hftbacktest「队列位置 + 延迟 + live 同源」直接比下去——**牵星拒跑的那部分，hftbacktest 是能跑的**。
2. **Nautilus + Python 生态的复利**：LGPL 只在闭源分发时是硬约束；如果用户是内部研究（不分发），Nautilus 的生态、文档、连接器会持续拉开差距。
3. **「正确但没人用」**：真正会让项目失败的不是架构，而是**研究者的工作流走不通**（无寻优、无交互图、无 OOS），他们会在第一天就回到 vectorbt。

### 6.4 市场空白机会（牵星可以独占的生态位）

| 空白 | 说明 | 谁能抢 |
|---|---|---|
| **可审计回测（Auditable Backtest）** | 「结论能被第三方复算，且产物自带输入 provenance 与档位声明」——面向合规、投资尽调、策略外包验收、量化教学评分 | 目前**无人占据**；Nautilus/LEAN 只有「可复现」，没有「可审计凭证」 |
| **档位诚实声明（Data Fidelity Disclosure）** | 把「这份回测用了什么档位、隐含哪些假设、哪些指标因此不可信」做成**机器可读报告** | 无人占据；竞品都靠用户自觉 |
| **多语言策略同内核** | Rust（性能）/ Python（研究）/ C++（低延迟）三种策略同一条风控-OMS-Ledger | 只有牵星三语齐备 |
| **零凭据安全回测** | fail-closed 到「无凭据即退出码 3」的程度 | 无人占据 |

**定位建议**：不要去和 freqtrade/vnpy 比连接器数量、不要和 vectorbt 比参数扫描速度、不要和 hftbacktest 比 L3 撮合精度。**把「可审计」做成产品**：`ExperimentSpec → 回测 → EvidenceBundle（档位声明 + 输入指纹 + 可复算指令 + 已/未验证清单）`，这是唯一没人抢、且与现有内核强匹配的位置。
