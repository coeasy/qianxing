# 牵星（Qianxing）自研量化框架重构与全量落地方案 V6

更新时间：2026-09-11

## 0. 文档定位

本文是当前工程的重构、实现和验收基线。目标不是继续扩展概念，而是把已有 V5 设计收敛成可运行、可恢复、可验收的主体系统。

工业级生产化的连接池、MQ、HA、真实交易所、策略沙箱、性能和灾备验收，统一见[工业级产品化实施路线图 V1](工业级产品化实施路线图-V1.md)。

本阶段遵循以下边界：

- 优先完成 `Signal → Portfolio → Risk → OrderIntent → OMS → Venue → EventLog → Ledger → Reconcile` 主链路。
- 优先支持单机、多进程、文件/SQLite 持久化；PostgreSQL 事务后端已作为可选生产路径落地，保持后续连接池/MQ/HA 的接口边界。
- PaperVenue 作为无网络的完整验收 Venue。
- 公共 Python CCXT 作为默认多交易所连接层，优先覆盖现货、杠杆、永续和交割合约；内部 Rust 仅保留无交易所业务逻辑的 JSONL/事实翻译边界，不重复实现交易所签名与 REST 协议。
- Binance Spot 直连实现仅保留兼容、协议对照和故障注入测试用途；真实账户网络验收单独进行。PostgreSQL 基础事务端口已落地，但连接池、MQ、跨节点高可用、WASM、DEX 和第二个真实交易所仍不作为本阶段完成条件。

## 1. 现状结论

### 1.1 已有基础能力

当前工程已经具备较完整的底层能力：

- `qx-core`：定点数、身份、时间、因果事件、订单状态机、Ledger、事件重放。
- `qx-core`：新增 `TradingInstrumentSpec`、`OrderPolicy`、`MarginMode`、`PositionMode`、杠杆/线性反向合约 PnL、资金费和 `MarginState` 契约。
- 订单规格门禁：`TradingInstrumentSpec::validate_order` 与 `OrderIntent::validate_against` 统一拒绝低于最小数量、未对齐 lot step 或 price tick 的订单，不在核心层静默截断数量/价格。
- `qx-xingban`：回测循环、NextBarOpen/L1 撮合、费用、延迟、容量和确定性随机。
- `qx-zhenlu`：PaperVenue、策略生命周期、信号合并、账户路由、风险门禁和账户命令队列。
- `qx-oms`：独立的本地订单状态/成交归约和 client id 幂等边界；`qx-zhenlu` 只做兼容 re-export。
- `qx-orchestrator`：Worker 拓扑规划、Paper/CCXT/Binance 入口选择、子进程日志隔离和退出传播。
- `qx-scheduler`：Cron/Event/Manual、Calendar、JobRun、重试、超时和依赖。
- `qx-control`：权限、命令幂等、Accepted→终态、审计和订阅游标。
- `qx-storage`：文件 EventLog、控制面、命令队列、JobQueue、快照、审计、限流以及 SQLite/PostgreSQL 事务后端。
- `qx-runtime`：RuntimeConfig、Worker 监督、健康、停止、LiveEventPipeline、订单和账簿恢复。
- `qx-adapter`：Binance Spot REST、L1、用户流、签名、凭据重载和对账协议。
- `qx-api`：HTTP/WebSocket、API 权限、事件游标、mTLS、证书和 Operator 映射热重载。
- `qx-python` / `qx-datastruct`：Python/Arrow 数据交换和 wheel 构建基础。

### 1.2 尚未形成完整产品能力的部分

以下能力不能只以“接口存在”视为完成：

1. 研究/因子产物已可以通过 `StrategyResearchSnapshot` 成为 Strategy 的真实输入（CandidateBinding + FeatureArtifact + FactorReport 会做 PIT/策略版本/数据指纹校验）；旧版配置化目标仓位仍保留兼容路径，但 production 中已绑定交易对象的策略现在强制声明 `research_snapshot_required`、`research_snapshot_path` 和发布时锁定的 `research_data_fingerprint`，回测/纸面兼容配置仍可渐进迁移。
2. `qx-cli` 仍承担适配器逻辑、Paper 逻辑和命令入口，但监督器以及 Scheduler/Strategy worker 已拆出模块，剩余适配器/执行 worker 继续按域拆分。
3. Paper 主链路虽已可运行，但 Scheduler、Strategy、Execution 主要通过多个 CLI 模式拼接，缺少统一的 Pipeline/Worker 抽象和正式端到端验收器。
4. Paper、Binance 执行流程中仍有重复的“取命令、写控制面、开事件管线、执行、回写终态、确认队列”代码。
5. 运行时配置以字符串和角色分支为主，账户、Venue、Instrument、Worker、Execution Route 的绑定约束仍不够集中。
6. 文件后端具备单机恢复语义；文件、SQLite 与可选 PostgreSQL 后端已共享命令/任务队列语义，PostgreSQL 已落地事务队列、控制面、审计、快照、EventLog 和可配置单进程连接池；跨节点 HA、读写分离和 MQ 仍未实现。
7. Paper/CCXT/Binance 已共享 `ExecutionService` 的提交与事实归约边界；`RiskExecutionContext` 可在拥有账户快照/规格的 worker 中执行下单前资金预检，并增加了跨进程租约接管、旧 fencing token 拒绝和重启后队列恢复验收；真实网络未知结果和完整启动拓扑仍需外部环境验收。
8. 真实 Binance 沙盒/实盘闭环、秘密管理、证书签发、跨节点 HA 尚未完成，不能在文档中宣称为已完成。
9. CCXT REST 主链路已打通公共 MarketData/Execution/Reconcile；持仓（含强平价）、负债余额、订单/成交手续费、资金费率观察和带外部 ID 的资金流水已进入可恢复 EventLog/Ledger，但 CCXT Pro 用户流、各交易所账单字段、跨币种保证金和分层规则仍未完成真实交易所验收。

10. 工业级多语言策略第一阶段已落地：`qx-strategy` 提供 Rust `Strategy` trait 和多订单 `StrategyDecision`；Python 契约支持 `intents[]` 与持久 worker；`cpp/include/qianxing_strategy.h` 提供稳定 C ABI；旧 `target_qty` 路径继续兼容。协议和后续性能分层见 [工业级多语言策略与高性能交易方案](工业级多语言策略与高性能交易方案-V1.md)。
11. Paper worker 已支持幂等 `paper_initial_cash_raw`；`qx-xingban` 已新增 L1/L2 `OrderBookMatchingEngine`，并由 `TickBacktestEngine` 接入 L1 Tick 因果回测，支持盘口校验、逐档成交、部分成交、手续费，以及可配置的快照延迟、队列前置量和固定市场冲击；真实 L3 队列、撤单竞态和完整强平逐笔过程仍属于后续增强。

### 1.3 本轮主体流程审计结论

截至本轮代码审计，单机代码链路已形成以下闭环：回测 `BarFrame→Strategy→Risk→Xingban→Ledger/Report`；Paper `Scheduler→Strategy→Control/Queue→Execution→VenueEvent→EventLog/Ledger`；CCXT 实盘 `Strategy/Control→公共 CCXT Execution→订单/成交事实→EventLog/Ledger`，并由 UserStream 唤醒、REST Reconcile 做订单、余额、持仓、资金费率和资金流水补偿。Paper、CCXT 和 Binance 的规格化成交均已按现货/保证金/永续/期货产品归约，不再默认按现货现金交易记账。

本轮还补齐了三项部署级约束：运行时配置中的相对路径统一按配置文件目录解析；CCXT UserStream/Reconcile 使用同一份产品规格进行衍生品成交归约；CCXT worker 启动前强制校验 `worker.venue_id == exchange_id`，避免错接交易所配置。对应回归测试和 Clippy 检查已通过。

以下内容仍不能标记为“全部完成”：研究快照尚未强制替代旧目标仓位兼容路径；C++ ABI 尚未形成跨平台预编译 SDK；Python/C++ Worker 已接入 `shared_memory_json` 和 `shared_memory_columnar` 双向 SPSC mmap ring，QXCB 已承载 Bar 固定宽度列，但完整 Arrow 零拷贝行情热路径和端到端性能基准仍待接入；订单簿模型已有可复现的延迟/队列/冲击假设，但真实 L3 队列、撤单竞态和完整强平逐笔过程仍待补齐；CCXT Pro 重连、交易所账单/精度/杠杆档位、真实沙盒与实盘凭证尚未验收；PostgreSQL 已具备可配置单进程连接池，但读写分离、跨节点 HA、MQ、CLI worker 完全拆分和统一 Paper/Live Pipeline 仍属于后续产品化工作。

## 2. V6 目标架构

### 2.1 分层结构

```text
研究层 Research
  DataProvider → QualityGate → PIT DataView → Feature/Factor → Candidate
                                                        │
                                                        ▼
策略层 Strategy
  StrategyRuntime → Signal → SignalMerger → PortfolioTarget → RiskGate
                                                        │
                                                        ▼
交易内核 Trading Kernel
  OrderIntent → OMS/OrderState → Command/Audit → ExecutionPort
                                                        │
                                                        ▼
连接层 Venue
  PaperVenue / Public CCXT (多交易所) / Binance direct compatibility
       REST / WS / UserStream / Reconcile / RateLimit
                                                        │
                                                        ▼
事实层 Event & Ledger
  EventStore → Reducer → EventLog → Ledger → Snapshot/Diff/Reconcile
                                                        │
                                                        ▼
运行层 Runtime & Operations
  Scheduler → JobQueue → Workers → Health → API → Supervisor
```

### 2.2 依赖规则

- `qx-core` 不依赖任何 Venue、Storage、API、Runtime 或具体策略。
- `qx-zhenlu` 只依赖核心契约、`qx-oms` 和必要市场数据类型，不直接依赖 CLI、Storage 或具体交易所。
- `qx-runtime` 负责运行时契约、事件归约、OMS/Ledger Worker 抽象和恢复，不内嵌 Binance 协议细节。
- `qx-adapter` 只实现 Venue/Market/UserStream/Reconcile Port，不决定策略和账簿业务。
- `qx-storage` 实现 EventStore、CommandStore、JobQueue、SnapshotStore 等端口，不包含交易策略。
- `qx-orchestrator` 负责 Worker 拓扑和进程生命周期；`qx-cli` 负责命令解析、配置装配和具体 worker 入口，具体业务流程继续按 worker 域拆分。
- `qx-api` 通过 ControlPort/QueryPort 访问运行时，不直接修改 Ledger 或调用 Venue。

### 2.3 推荐目标模块

在保留现有 crate 兼容性的前提下，逐步拆分为以下模块：

| 模块 | 责任 | 主要产物 |
|---|---|---|
| `qx-core` | 不可变领域契约和确定性内核 | Order、Fill、Event、Ledger、Identity、Clock |
| `qx-domain` | 交易应用服务契约 | OrderIntent、PortfolioTarget、ExecutionReport、ReconcileReport |
| `qx-strategy` | 策略运行时和信号管线 | StrategyContext、Signal、Portfolio、RiskPipeline |
| `qx-oms` | 订单注册、状态机、幂等和生命周期 | OrderManager、OrderCommand、OrderTransition |
| `qx-runtime` | 事件管线、Worker、健康和恢复 | EventReducer、WorkerRuntime、RuntimeSupervisor |
| `qx-execution` | Venue 无关的执行编排 | ExecutionService、CommandDispatcher、ExecutionRecovery |
| `qx-orchestrator` | Worker 拓扑和进程生命周期 | WorkerLaunch、Supervisor、日志隔离、退出传播 |
| `qx-adapter` | Binance/Paper 及未来 Venue 适配器 | VenuePort、MarketDataPort、UserStreamPort |
| `qx-storage` | 存储端口和文件/SQLite/PostgreSQL 实现 | EventStore、CommandStore、JobQueue、AuditStore |
| `qx-scheduler` | JobSpec、触发、重试和 JobRun | Scheduler、JobDispatcher |
| `qx-api` | 查询和控制接口 | QueryPort、ControlPort、HTTP/WebSocket |
| `qx-cli` | 启动、配置和诊断入口 | CLI、Supervisor、Smoke Runner |

如果当前阶段不新增 crate，则至少在 `qx-cli`、`qx-runtime`、`qx-adapter` 内按上述模块拆分文件和 trait，禁止继续把功能追加到单一 `main.rs`。

## 3. 核心领域契约

### 3.1 订单主链路

唯一允许的交易主链路：

```text
Signal
  → SignalMerger
  → PortfolioTarget
  → RiskGate
  → OrderIntent
  → OMS register
  → ControlCommand Accepted
  → ExecutionPort submit
  → VenueEvent Accepted/Fill/Cancel/Unknown
  → EventStore append
  → Reducer
  → LedgerApplied
  → Snapshot/Reconcile
```

所有 Paper、Binance 和未来 Venue 必须复用这条链路。任何 worker 不得绕过 OMS、EventStore 或 Ledger 直接改变订单状态。

### 3.2 关键 ID

- `strategy_id`：策略实例身份。
- `signal_id`：信号事实身份，重复信号必须幂等。
- `order_intent_id`：策略意图身份。
- `client_order_id`：账户级订单身份，必须全局唯一且不可复用。
- `command_id` / `request_id`：控制命令身份和请求幂等身份。
- `venue_order_id`：交易所订单身份，只能由 Venue 回报绑定。
- `event_seq` / `source_seq` / `correlation_id`：事实序列、来源序列和关联身份。

### 3.3 时间和事实规则

- 事件使用 `event_ts`、`receive_ts`、`engine_ts` 三种时间。
- 同一事实以 `correlation_id + source_seq` 去重。
- 成交事实先于 LedgerApplied 派生事实。
- 未知下单结果不能自动补单，必须进入 `Unknown/ReconcileRequired`。
- 账簿只能由成交事实和明确余额/结算事实驱动，不能由订单状态猜测。

## 5. 重构实施顺序

### Phase 0：契约冻结和基线

1. 建立 `docs` 方案、能力矩阵和证据矩阵。
2. 给现有主链路增加统一的 domain 类型和端口，不改变已有 Paper 行为。
3. 把 `qx-cli/main.rs` 中的业务函数迁移到独立模块。
4. 固定错误分类：Validation、Permission、Conflict、Transient、UnknownOutcome、ReconcileRequired、Invariant。

验收：workspace 测试、clippy、release 构建和现有 Paper 集成测试全部通过。

### Phase 1：ExecutionService 与 OMS

1. 抽取 `ExecutionPort`、`VenueEvent`、`OrderTracker`。
2. 抽取统一 `ExecutionService::execute(command)`。
3. Paper 和 Binance 都接入同一执行编排。
4. 把未知结果、重复执行、终态队列清理和重启恢复纳入统一测试。

验收：Paper 与 Binance 注入式测试共享同一执行测试矩阵。

### Phase 2：策略到交易真实贯通

1. 抽取 `StrategyContext`、`PortfolioTarget`、`OrderIntent`。
2. 将当前固定目标仓位策略改造成标准策略实现。
3. 将现有 Factor/Candidate 产物转换成可加载的 StrategyConfig。
4. 增加持仓、资金、风险和归因输入。

验收：同一策略输入可以在回测、Paper 和模拟实时模式生成相同的信号/意图摘要；Paper 成交后下一轮不重复发单。

### Phase 3：Worker 和 API 收敛

1. 抽取 SchedulerWorker、StrategyWorker、ExecutionWorker、ReconcileWorker。
2. CLI 只保留参数解析和装配。
3. API 接入 QueryPort/ControlPort，补齐订单/持仓/JobRun/审计查询。
4. 增加跨进程启动验收器和故障注入器。

验收：使用临时 data_dir 启动完整 Paper 拓扑，按进程逐个终止和重启，最终账簿、订单、审计和队列状态一致。

### Phase 4：单机生产化

1. 文件/SQLite 实现同一端口测试矩阵。
2. 凭据、证书、日志、指标和对账报告统一运行目录。

## 6. 当前实现中的不合理点与处理方式

| 问题 | 当前表现 | 重构处理 |
|---|---|---|
| CLI 过重 | `main.rs` 同时包含 CLI、Worker、Paper、Binance 和测试 | 按 Runtime/Worker/Execution/Paper/Binance/Diagnostics 拆分 |
| 业务流程重复 | Paper/Binance 各自维护命令执行与终态回写 | 统一 ExecutionService |
| 研究与交易断开 | Factor/Candidate 可运行，但 Strategy 读取不到真实产物 | 增加 CandidateBinding→StrategyConfig→StrategyContext |
| 运行时字符串分支 | Venue、角色和日志名通过字符串判断 | 引入 VenueId、Capability、RouteBinding 和集中校验 |
| 事件与账簿耦合 | LiveEventPipeline 同时负责持久化、归约、订单和 Ledger | 拆 EventStore、Reducer、OrderTracker、LedgerApplier |
| 存储后端边界不统一 | 文件和 SQLite 能力分散在不同调用路径 | 统一 StoragePort 和语义测试矩阵 |
| 测试偏进程内 | 难以证明真实重启、旧租约和跨进程一致性 | 增加 ProcessHarness、CrashPoint、RecoveryScenario |
| 生产状态容易被高估 | 协议测试被误读成实盘闭环 | 审计按代码证据、模拟证据、真实外部证据分级 |

## 7. 验收矩阵

### 7.1 核心功能验收

| 场景 | 必须证明 |
|---|---|
| 回测 | 同输入同摘要、改变参数摘要变化、无前视、下一 Bar 成交 |
| Paper | Signal→OrderIntent→Accepted→Fill→Ledger→Snapshot |
| Paper 重启 | 任意阶段重启不重复发单、不重复成交、不丢审计 |
| Paper 故障 | 队列租约过期、控制面终态未确认、重复回报、事件写冲突 |
| Binance 模拟 | 签名、限频、Accepted/Fill/Cancel/Unknown、对账恢复 |
| API | 权限、幂等、游标缺口、快照恢复、审计 |
| 调度 | Cron/Manual/Event、依赖、重试、超时和人工介入 |
| 多账户 | 账户隔离、资金分配、命令路由和归因 |
| Python | Arrow/JSON 契约、版本、错误边界和释放生命周期 |

### 7.2 完成定义

只有同时满足以下条件，才能宣称“主体链路已贯通”：

1. Strategy 产生的 OrderIntent 不是测试函数直接构造，而是经过正式 StrategyContext、Portfolio 和 RiskGate。
2. Paper 与 Binance 共享 ExecutionService、OrderTracker 和事件归约语义。
3. 订单、命令、队列、EventLog、Ledger、审计在进程重启后可恢复且摘要一致。
4. 至少有一个跨进程 Paper 端到端场景和一个注入式 Binance 端到端场景。
5. API 查询能看到订单、持仓、账簿、JobRun、结构化对账报告、事件游标和审计结果。
6. 所有未完成的真实外部边界仍明确标注，不能用 mock 或协议单测替代真实验收。

## 8. 执行规则

- 每完成一个模块，必须同时补代码、单元测试、集成测试、文档和审计证据。
- 不在 Rust 核心模块中引入 CCXT、PostgreSQL 或 MQ 的具体依赖；CCXT 只存在于 Python 连接边界。
- 不为了追求模块数量进行无收益重命名；优先消除重复流程和错误边界。
- 不删除用户已有实现；重构采用兼容迁移，旧入口在新入口验收通过后再废弃。
- 所有新功能必须有确定性 ID、事件关联、错误分类和恢复行为。
