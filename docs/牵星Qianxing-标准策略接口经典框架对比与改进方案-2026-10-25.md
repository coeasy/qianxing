# 牵星 Qianxing：标准策略接口与经典框架对比方案

> 日期：2026-10-26（在 2026-10-25 方案上完成源码复核）
> 范围：Rust `qx-strategy`、Python callback SDK、仓库内 Python 文件策略入口；对照 Freqtrade、Backtrader、VeighNa、RQAlpha、Qlib 的公开文档和接口。
> 状态：对比结论与接口状态已复核；下文明确区分已实现能力与后续建议，不表示所有目标 API 已上线。

## 1. 结论

牵星的策略 API 应分为三个层次，而不是把所有函数都做成一个巨大 `BaseStrategy`：

1. **稳定核心协议**：策略接收有时间边界的上下文和市场/执行事件，只返回版本化 `StrategyDecision` / 订单意图；风险、订单、撮合、账本和交易所访问仍由 Rust 引擎负责。
2. **易用型事件策略 helper**：提供可选 `BaseStrategy` 或语言适配器，把 `Bar/Tick/OrderBook/Timer` 分派给更易读的钩子，并提供 warmup、ready、订单/成交更新的便利接口。
3. **向量化研究适配器**：独立支持 `populate_indicators / populate_entry_trend / populate_exit_trend` 一类整表计算。它服务于批量研究，不取代逐事件撮合，也不直接承载 live 回调。

吸收重点是竞品的清晰生命周期、warmup 语义、typed 事件和用户体验；不照搬其策略可以直接操作 broker/gateway 的副作用模型。牵星必须继续让所有策略订单经过同一风险、OMS、执行和账本链路。

### 1.1 标准策略类的基础函数速览

**普通策略只需要实现一个市场决策入口。** Rust/跨语言协议使用 `on_event(context, event)`；Python `BaseStrategy` 用户可以只覆盖实际使用的 `on_bar`、`on_tick`、`on_order_book` 或 `on_timer`，由基类负责分派。`create_strategy(spec)` / 构造函数负责生成每次运行隔离的新实例，不是行情回调。

| 函数 | 用途 | 牵星当前 Python callback 基类 |
|---|---|---|
| `on_init(context)` | 每次运行初始化策略本地状态 | 已有，可选覆盖 |
| `history_requirements()` / `on_warmup_complete(...)` | 声明历史需求；按标的确认预热完成 | Bar 预热已接通；非 Bar host 对不支持的预热拒绝启动 |
| `history(context, length=...)` / `current(context, field=...)` | 查询当前决策时间之前可见的历史 Bar / 当前 Bar | 只读 PIT 数据门面；回测 callback 与 Python Runtime class worker 均按 `as_of` 截断，单次历史请求最多 10,000 根 |
| `history_decimal(...)` / `current_decimal(...)` / `bar_decimal(...)` | 以 Python `Decimal` 计算 OHLCV，兼容低于 1e-9 的小币种价格 | 优先解码 `exact_ohlcv` coefficient/scale；raw-only 数据精确按 1e-9 还原，不经过 float |
| `on_start(context)` | 配置和宿主准备完成、首个市场事件前启动 | 已有，可选覆盖 |
| 一个市场决策入口 | 消费当前可见事件并返回 decision/intents | `on_event` 自动分派到 Bar/Tick/OrderBook/Timer hooks |
| `on_order_status_update(...)` / `on_order(...)` | 接收 OMS 已提交的订单状态变化 | DTO 与 callback 已接通；覆盖范围按宿主而异 |
| `on_order_update(...)` / `on_trade(...)` | 接收账本已提交的 fill | 已有兼容分派；`on_trade` 对应单笔 fill |
| `on_account(...)` | 接收绑定账户的完整余额快照 | Runtime Python class worker 已接 input v7，空快照也会送达 |
| `on_positions_snapshot(...)` / `on_position(...)` | 接收完整持仓集合及逐行记录 | 快照先调用一次，再逐行调用；空集合可清理策略缓存 |
| `on_stop(context=None, reason="host_stop")` | 结束时释放本地资源 | Python helper 支持可选上下文/原因；Rust 新增版本化 `StrategyStopContextV1`，C ABI v2 保持旧回调兼容；Bar 与 Tick/L2 回测区分完成/取消/失败，Runtime worker 按干净 EOF/输入协议故障区分 shutdown/failed；单次运行的 completed/cancelled 尚未传给 Runtime worker |
| `diagnostic_state()` | 提供有限、只读的偏差诊断状态 | 已有，不能当作重启 checkpoint |
| `snapshot_state()` / `restore_state()` / `on_restore(context)` | 在策略进程重启后恢复用户状态并重接本地资源 | Python Runtime class worker 已有可选持久 checkpoint；只支持版本化 JSON 对象，64 KiB 上限，与执行事实游标原子提交 |

`on_account` 和 `on_positions_snapshot/on_position` 已在 Python Runtime class worker 开放：输入来自绑定账户 EventLog 的完整快照，使用 v7 合同、按 `(account_id, venue)` 游标去重；快照只用于观察，不更新账本。账户更新回调 context 隐去请求内较新的余额、仓位、保证金、风险和研究目标，策略应读取当前 `update`。这些 hook 尚未扩展到 Rust/C ABI/C++ 的所有 host。`on_error`、session hooks 和目标仓位/退出策略便捷函数仍可按需要逐项增加。snapshot/restore 只在 Python Runtime class worker 首版可用，不能推断为其他宿主和供应商 worker 都支持恢复。查询或下单 helper 只能读取受 PIT/as-of 约束的数据、构造精确 intent/policy，不能把交易所客户端、Broker 或 Gateway 直接交给策略。

## 3. 牵星当前策略接口事实

### 3.1 Rust 核心 callback

`crates/qx-strategy/src/lib.rs` 目前定义：

- `StrategyContext`：策略/版本、账户和 venue、数据 fingerprint、`as_of`、持仓、现金、可用保证金与风险状态。
- `MarketEvent`：`Bar`、`Tick`、`OrderBook`、`Timer`。
- `StrategyDecision` / `StrategyOrderIntent`：版本化的策略决策、精确数量/价格/预算和订单约束。
- `Strategy` trait：`on_init`、`history_requirements`、`on_start`、`on_warmup_complete`、必须实现的 `on_event`、可选 `on_order_update` / typed `on_strategy_update`、`on_stop`、只读 `diagnostic_state`。

当前设计有重要优点：策略只能表达 intent；事件和上下文带时间/来源身份；精确十进制数量可承载小币种；Rust 负责风控、OMS、执行和账本。策略不应该直接调用具体交易所 API。

当前需要补齐的 API 体验与合同：

1. `on_event` 把所有市场输入压成一个入口，作者需要自行解包；内核可保留该形式，但 helper 应提供按事件类型分发的钩子。
2. 成交事实在 Rust 策略、Bar/Depth 回测和 Python callback 中已增加 `StrategyFillUpdateV2`：携带 EventLog `event_seq` 与成交 `ts`，策略可据序号去重；未实现 v2 的 Rust 策略默认投影为旧 fill update，Python bridge 也保留 v1 回退。C ABI/C++ 动态策略现可导出可选 `qx_strategy_on_fill_update_v2` JSON callback；旧插件没有该符号时回退旧 vtable fill callback。Python Runtime class worker 的用户策略快照和 adapter 更新游标现由 input v4 checkpoint 跨进程恢复，并按 `(account_id, venue)` 隔离；checkpoint 与 EventLog cursor 同一原子快照提交，但交付仍是 at-least-once。独立的 `StrategyOrderStatusUpdate` 已接入 Bar/Depth 回测、Python callback、Python/外部策略文件 worker 与支持可选状态符号的 C ABI 插件。worker 从 OMS/EventLog 以固定范围重放已提交的订单状态，持久化游标并用作业幂等键保证重投；它不等于所有宿主/供应商状态都已覆盖。独立 position、account、lifecycle facts 仍未构成统一更新流。
3. Rust 原生 Bar adapter 与 Python callback host 现都按每个 instrument 分别执行 `warmup_bars` 和 `on_warmup_complete`；DepthBar adapter 也执行同类 Bar 门控。Native Tick 与原生 OrderBook 暂不支持 Bar 计数预热，遇到非零声明会 fail closed，避免把 Tick/深度快照误当 Bar。
4. Python callback adapter 已转发 init/start/stop，并提供可选 `BaseStrategy` 与事件类型分派。Python Runtime Strategy worker 现也有显式 class adapter：仅设置 `python_strategy_spec` 时启用，复用 `create_strategy(spec)`/`STRATEGY_CLASS`、完整 manifest 默认值与校验，并将 StrategyInput 映射为生命周期、Bar warmup、市场 hook、订单状态和 fill 回调；旧模块级 `on_event(request)` 默认路径保持不变。它仍是独立进程协议，不是 callback SDK 的同一宿主。
5. `diagnostic_state` 明确是只读诊断快照，不应误用成 crash restart 的持久 checkpoint。Python Runtime class worker 已另有带 schema/version、策略身份绑定和大小上限的 snapshot/restore checkpoint；其它宿主没有因此自动获得恢复能力。

### 3.2 Python API 要分清两条路径

- **SDK callback 策略**：`create_strategy(spec)` 返回对象，常见接口为 `on_event(context, event)` / `on_order_update(context, update)`；由 `python/qianxing_bridge/app.py` 适配到 Rust 策略 callback。可选 `BaseStrategy` 将 `on_event` 分派到行情事件钩子。继承者若只重写 `on_trade(context, trade)`，默认 `on_order_update` 会把已提交 fill 传入该钩子；显式重写 `on_order_update` 时仍由子类完全接管。
- **策略文件进程协议**：`python/qianxing_bridge/strategy.py` 的 `StrategyInput/StrategyOutput/StrategyIntent` 是独立的版本化 JSON 进程边界。它不是同一个 `StrategyContext/MarketEvent` callback，也不应在不做 schema 升级的情况下混用同名方法。

Bar 型 `BaseStrategy` callback 和 Runtime class worker 现在都通过 context 中的 `data` 门面提供 `history/current`。查询只返回 `ts <= context["as_of"]` 的 Bar，避免同步加载完整快照后让早期事件回调看到未来数据。OHLCV 的 `*_raw` 字段保留核心 1e-9 刻度；有来源精度时同时提供 `exact_ohlcv`。预热声明仍是独立的下单门控，不会由查询长度自动推断。

Python `BaseStrategy.diagnostic_state()` 是可选的只读诊断钩子；策略偏差 worker 在可见 Bar 重放后读取它，要求有限、可序列化的 JSON 对象并限制为 64 KiB。它不参与执行策略。`snapshot_state()/restore_state()` 是另一条持久化合同，Runtime class worker 通过 Strategy Input v4 使用它；两种快照不能互相替代。

Runtime Tick class worker 使用 Strategy input v6，将 L1 quote EventLog 中冻结的 `MarketQuote` 事件与 exact bid/ask、挂单量送入 `on_tick`；`strategy_checkpoint` 和 EventLog cursor 一起原子提交。首次启动从当前行情日志最近最多 10,000 条报价开始建立策略状态，之后按游标续接。配置需显式声明 `python_strategy_spec.data_level="tick"`，策略 manifest 也声明 `data_level="tick"`、`warmup_bars=0`；运行时需启用 `live_enabled`，并配置唯一匹配的行情 EventLog 和 Execution worker。Runtime Timer 以 `live_timeframe` 划分时间桶并进入同一幂等策略队列，每桶一次派发 `on_timer`；OrderBook 持久 Runtime 输入尚未接通。

两条 Python 路径最后都应归约为相同的 Rust 决策/订单/风险链；共享的是语义与 schema 版本，不是强行共享 Python 方法签名。

### 3.3 执行反馈在不同宿主中的真实覆盖

| 宿主 | 当前可见执行事实 | 当前缺口 |
|---|---|---|
| Rust `Strategy` + Bar/DepthBar 回测 adapter | fill `StrategyFillUpdateV2` 携带 EventLog `event_seq`/`ts`，并有 v1 projection fallback；独立 `StrategyOrderStatusUpdate` 也可用。 | 订单簿实时 worker、position/account 快照及所有执行状态的统一时序仍未覆盖。 |
| Python callback SDK `BaseStrategy` | fill v2 可由 `on_fill_update(context, update)` 接收；基类默认投影到旧 `on_order_update`/`on_trade`，订单状态由 `on_order_status_update`/`on_order` 单独分发。 | callback adapter 与 Python 策略文件协议是两条宿主路径；文件协议尚未接入 fill v2，也不代表所有 venue 状态已接通。 |
| C ABI 动态策略 | 可选 `qx_strategy_on_fill_update_v2` 收到含 EventLog `event_seq`/`ts` 的 fill JSON；没有该符号时投影到旧 vtable fill callback。可选 typed `qx_strategy_on_order_status_v2` 优先消费订单状态，没有 v2 时回退旧 JSON 状态 callback；`qx_strategy_get_order_policy_v1` 按 intent_id 返回订单政策，旧 vtable/intent 布局不变。 | fill v2 是版本化 JSON callback，目前不是独立 C struct；position/account/lifecycle DTO 和全宿主 golden matrix 仍未齐备。旧插件仍可只消费行情事件并沿用运行时默认订单政策；状态范围受实际 EventLog reducer 与宿主合同约束。 |
| Python/外部策略文件实时 worker | `StrategyContractInput` v2 增加 `execution_updates`；worker 按 EventLog 固定范围重放订单提交、接受、拒绝、撤销、成交（部分/全部由 OMS 当前状态表示）和 reconcile unknown，成功处理后推进耐久游标。旧 v1 市场输入形状保持兼容。 | 此路径交付的是版本化订单状态，不是独立 fill stream，也没有权威 position/account/lifecycle 通知；过期、cancel-pending 等未由当前 EventLog reducer 产生的状态不可宣称已全覆盖。真实供应商沙盒仍需按 venue/product/account scope 验收。 |

这一区分是发布能力判断的依据：**订单状态反馈的离线代码链已贯通到策略文件 worker 和新版 C ABI callback，但不等于完整交易所回报覆盖或实盘验收**。生产状态事实由 EventLog/OMS/Execution worker 掌握；策略宿主读取固定事件范围并维护可恢复投递游标，不能靠策略根据仓位变化猜测订单状态。

## 4. 建议标准函数

### 4.1 核心生命周期

经典框架的最小共同集合不是几十个交易回调，而是 **初始化、就绪、市场决策、执行反馈、停止** 五段。`on_event` 是牵星当前统一协议里唯一必须由策略实现的决策入口；其余入口应保持可选，并有默认 no-op。

| 函数 | 调用语义 | 是否必须 |
|---|---|---|
| `__init__()` / `create_strategy(spec)` | 每次运行、参数候选或策略槽创建新实例；只解析和校验参数、初始化本地状态，不加载未声明数据、不连接交易所、不发单。 | 工厂入口必须返回新实例；它不是行情回调 |
| `on_init(context)` | 策略实例创建后由 host 调用一次；参数在 factory/构造阶段注入并校验，初始化纯内存状态；不得提前交易。 | 可选 override；默认 no-op |
| `history_requirements()` | 声明预热长度；未来可扩展到数据种类/周期，由数据层按 PIT 截止准备历史。 | 可选；当前只支持 `warmup_bars`，缺省为 0，manifest 与方法值冲突时拒绝运行 |
| `on_warmup_complete(context, instrument, observed_bars)` | N>0 时，每个标的的第 N 根 Bar 可见后、该 Bar 的策略事件 hook 前调用一次；前 N−1 根用于更新状态且订单意图被抑制，第 N 根决策可以入场。零预热在 `on_start` 后以 `instrument=None, observed_bars=0` 调用。 | 可选；Python callback、Rust Bar 与 DepthBar host 已实现，Tick/OrderBook 对非零 Bar 预热拒绝启动 |
| `on_start(context)` | host 完成配置后、第一条市场事件前调用一次；它不表示每个标的的预热都已完成。 | 可选；当前标准名称。每标的 readiness 由 `on_warmup_complete` 表达，不再额外加同义 `on_ready` |
| `on_event(context, event)` | 消费 Bar、Tick、OrderBook 或 Timer，返回版本化 `StrategyDecision`；不直接提交订单。 | **必须** |
| `on_strategy_fill_update_v2(context, update)` / Python `on_fill_update(context, update)` | 接收已提交 fill、事件时间和 EventLog 序号；可以用 `event_seq` 做幂等去重。旧策略由默认 adapter 投影到 v1 `on_strategy_update` / `on_order_update`；Python `on_trade(context, fill)` 仍是便捷分派。订单生命周期状态继续走独立 `on_strategy_order_status` / `on_order_status_update`。 | 可选；Rust Bar/Depth、Python callback 和 C ABI optional JSON symbol 已接入；策略文件 worker 仍为旧合同 |
| `on_stop(context, reason)` | 目标签名：正常结束、取消、失败或 shutdown 时调用一次；用于释放策略本地资源/记审计。 | Rust `StrategyStopContextV1` 与 C ABI v2 JSON 回调已提供兼容合同；Bar 和 Tick/L2 回测将完成/取消/失败映射到具体 reason，Runtime worker 与 shutdown 仍传通用 `host_stop` |
| `on_error(context, error)` | 策略回调/数据错误发生后接收可序列化错误事实；错误处理策略由宿主决定。 | 可选；不能吞掉 fatal 错误继续发单 |
| `diagnostic_state()` | 返回只读、确定性、受大小限制的诊断快照，用于报告与偏差定位。 | 可选；Python callback 诊断限制为 64 KiB；不是恢复 checkpoint |

上表给出标准语义；Python `BaseStrategy` 可选择接收 `on_stop(context, reason)`，旧无参策略仍兼容。Rust trait 已新增版本化 `StrategyStopContextV1`，可选 C ABI `qx_strategy_on_stop_v2` 接收 JSON 上下文/原因并回退旧回调；Bar 和 Tick/L2 回测引擎现把 `completed/cancelled/failed` 经策略槽、适配器和组合路径传到策略；Runtime worker 正常 EOF 发送 `shutdown`、输入/帧协议错误发送 `failed`，直接 adapter close 默认仍为 `host_stop`，单次运行的 completed/cancelled 还没有传给 Runtime worker。其他 service wrapper 仍需梳理。`on_error`、跨 host 完整一致的订单/成交/持仓/账户事实和广义持久投递恢复故障矩阵尚未全部加入。Python Runtime class worker 已实现首版版本化策略 checkpoint，不能据此宣称所有 host、存储故障或供应商回报已统一。订单状态 DTO 已在部分 Rust/Python/C ABI/策略文件路径接入。牵星用每标的 `on_warmup_complete` 表达 readiness，不另设同义 `on_ready`。

`history_requirements` 是声明，不应由策略通过回看未来数据自行加载任意 DataFrame。引擎必须在 `as_of` / 可见性边界内提供 warmup 输入，warmup 期间返回的意图必须被抑制或明确标为非交易观测。`ready` 不能只靠策略自行数 bar 后猜测。

### 4.2 市场和时钟事件

建议 helper 分派为：

```text
on_bar(context, bar)              # OHLCV / 指定周期
on_tick(context, tick)            # L1 逐笔/快照
on_order_book(context, book)      # L2 深度，带 sequence
on_timer(context, timer)          # 仿真时间驱动的定时回调
on_trading_day_start(context)     # 仅交易日历/产品提供时
on_session_start(context, session)
on_session_end(context, session)
```

`MarketEvent` 仍是跨语言统一 wire union；上面这些是易用层的 typed dispatch，不是每种语言各自定义一套事件。跨周期/跨标的的输入必须包含周期、标的、数据 source、事件时间和有效截止，不能因方便合并就突破 PIT。

### 4.3 执行结果通知

建议统一一个版本化 `StrategyUpdate` tagged union，至少覆盖：

- order：created/accepted/rejected/partially-filled/filled/cancel-pending/cancelled/expired/unknown/reconciled；
- trade/fill：成交 ID、订单/intent ID、成交时间、价格、精确数量、手续费及币种、maker/taker、流动性/来源；
- position：账户、标的、long/short/net、数量和更新时间/ledger sequence；
- account：现金/保证金/权益变化的权威快照或可归因变动；
- lifecycle：开始、暂停、恢复、终止和错误。

策略可提供 `on_order_update(update)`、`on_trade(trade)`、`on_position(position)`、`on_account(account)` 的方便入口；宿主必须规定去重键、更新顺序、时间边界和 stale/duplicate 行为。多个 hook 同时由同一 fill 触发时，不得重复记账；通知只是事实输入，不是授权策略直接修改 ledger。

当前实现进度：fill v2 与 `StrategyOrderStatusUpdate` 是两个独立合同。`StrategyFillUpdateV2` 与订单状态 DTO 均包含 `schema_version` 和 EventLog `event_seq`；fill v2 另带成交事件时间。Bar/Depth 回测、Python callback 和 C ABI/C++ optional symbol 已接入 fill v2，未升级的 Rust、Python 和 C ABI 策略可经 v1 投影兼容；订单状态则由 Bar/Depth、Python callback、Python/外部策略文件 worker 和具备可选新符号的 C ABI host 分别接入。文件 worker 的 v2 输入由持久化 EventLog 游标驱动，但那是订单状态输入，不是 fill v2。独立 position、account 或 lifecycle updates 未启用；状态覆盖取决于实际 EventLog reducer 和宿主能力。新增事件需明确事实源、去重键和时间顺序，不能从一个 fill 推断所有账户事件。

策略文件实时路径通过 `StrategyContractInput` v2 接收 `execution_updates`，而非复用 callback SDK 的 Python `BaseStrategy` 对象或方法签名。worker 将固定序列范围附在作业上，成功处理后才推进持久游标；策略文件消费到的是可验证的订单状态 DTO。完整的独立 fill、position、account 和 lifecycle 流仍需分别定义事实源与语义。

Python `BaseStrategy.on_fill_update(context, update)` 是 fill v2 入口，包含 `event_seq` 和 `ts`；基类默认把它投影回原有 fill-only `on_order_update` 与 `on_trade(context, fill)`，旧策略无需修改。`on_trade` 仍不代表独立的交易所 trade stream，每次调用对应一个宿主已提交的 fill。版本化订单状态通过 `on_order_status_update` 分发到 `on_order`；position/account 仍没有统一、权威的策略更新合同，不能用本地推算伪造这些通知。

### 4.4 信号与交易管理

常用买入/卖出/开空/平仓、目标仓位、杠杆、止损/止盈、ROI、仓位调整、订单价格和超时等可以提供高级 helper，但需分成两类：

- **纯策略决策**：返回 `StrategyDecision`、目标仓位或 policy；无网络 I/O、无 broker 副作用，可回放，可做 lookahead 检查。
- **执行请求**：转换为精确、具单位的 `StrategyOrderIntent` 或取消请求；再交给账户/能力校验、风控、OMS 和 `OrderExecutionPort`。

Python `BaseStrategy` 提供 `order_intent(...)` 和 `buy/sell/short/cover/close_position` 构造器：接受显式 side、旧 raw 或精确十进制数量、限价/报价币预算、policy 与 reduce/post-only 标志，只返回 Rust 决策需要的 mapping，不提交订单。`short()` 表达卖出开空意图，现货卖出仍受可用库存约束；`cover()` 固定为 reduce-only 买入。Hedge 模式必须在 policy 显式指定 `position_mode="hedge"` 与 `position_side="short"`，产品能力、杠杆和风险仍由 Rust 运行时校验。仍建议后续在稳定的目标仓位协议上提供 callback `target_position`，并评估 `exit_policy`（止损/止盈/超时/ROI）等 intent/policy helper。所有便利函数都只能返回意图，不能向策略传入可直接绕过 OMS 的 Gateway；频繁被调的 custom callback 还要定义预算、调用时点和失败关闭语义。

`short()` 与 `cover()` 的策略文件 worker 合同已定向验收：exact 数量、Hedge `position_side=short`、margin mode、leverage 均保留到 Rust `StrategyOutput`，cover 的 `reduce_only` 固定为 true。它们只产生意图，不代表所有 venue/product 都允许开空或已经通过实盘验收。

### 4.5 向量化信号 API 是另一种策略形式

对 Bar 历史研究，可增加可选 `VectorizedStrategy` 适配器：

```python
populate_indicators(frame, metadata) -> frame
populate_entry_trend(frame, metadata) -> frame
populate_exit_trend(frame, metadata) -> frame
```

它适合快速指标/信号计算、参数筛选和可视化；需显式输入 warmup candle 数、数据可见性、时区和 informative 数据的合并规则。对外产物仍转换成牵星的信号/intent，再经 Rust 撮合、风险与账本重算。Tick/L2、部分成交、资金费、持仓路径依赖和 live 事件不应由整表向量结果代替。

## 5. 推荐的可选 BaseStrategy 形态

```python
from qianxing_strategy import BaseStrategy

class MyStrategy(BaseStrategy):
    def history_requirements(self):
        return {"warmup_bars": 60}

    def on_bar(self, context, bar):
        # 只构造 intent；不调用交易所客户端。qty 使用核心旧 raw 单位。
        intents = []
        if bar["close_raw"] > bar["open_raw"]:
            intents.append(self.order_intent(
                intent_id=1,
                instrument=bar["instrument"],
                side="buy",
                qty_raw=1_000_000_000,
            ))
        return self.decision(context, "Bar", bar, intents=intents)

    def on_trade(self, context, trade):
        # 更新策略本地统计；不得在这里再次记账或直连交易所。
        self.last_fill_ts = trade["ts"]
```

示例中的 `on_trade` 接收已经提交的 fill；`order_intent(qty_raw=...)` 使用旧接口的 `1e-9` raw 定点数量，exact quantity/price 和 quote budget 则编码为 `coefficient/scale`；浮点输入被拒绝，不做隐式舍入。Bar 回测当前账本和撮合器仍使用 `1e-9` 数值：策略 exact quantity/price 只有在可无损映射到该精度时才转成 Bar 订单，更细精度和 quote-budget 单会显式报错；不能把可编码为 exact DTO 误解为每种执行适配器均支持该精度。最终标的 lot/minimum/market capability 检查仍由 Rust 执行。独立 Python 文件策略 API 继续使用十进制字符串。当前 SDK 已提供可直接继承的 `BaseStrategy`，并保留 duck-typed `on_event` 兼容。市场 hook 返回 `None` 会转换为空 decision，订单更新 hook 返回 `None` 表示不追加 intent；最终 DTO 仍由 Rust 校验。`BaseStrategy` 只作为 Python callback 易用层，不是 C ABI、Rust trait 或远端 HTTP 的必要基类。

### 5.2 Python Runtime class worker 持久 checkpoint（2026-10-26）

Python `BaseStrategy` 默认 `snapshot_state()` 返回 JSON 兼容实例属性；策略可重写 `snapshot_state()/restore_state()` 处理自定义状态结构，并用 `on_restore(context)` 重建非持久资源。策略状态与 adapter warmup/bar/update cursors 由 `StrategyCheckpointV1` 封装，input v4 绑定 `strategy_id/strategy_version`，最大 64 KiB。Rust worker 将 checkpoint、执行事实 cursor、策略 binding digest 和已提交 run marker 写入同一原子快照；checkpoint 恢复时验证身份，不匹配或旧游标缺 checkpoint 则 fail closed。已提交的 run 在重启时完成 Scheduler 并 ack，避免重复调用 Python。

验收：checkpoint+cursor 同一快照与身份绑定 1/1；原子写中断 backup 恢复 1/1；Rust→Python class worker 四种 transport/checkpoint 端到端 1/1；input v4 schema 9/9；Python BaseStrategy 与 process adapter 32/32。语义为 at-least-once：策略回调副作用与宿主 checkpoint 不是跨外部交易所的分布式事务；订单效果已提交而 checkpoint 未提交的故障窗需稳定 intent id 或 OMS 对账处理。当前只覆盖 Python Runtime class worker，不覆盖 SDK callback、Rust/C++ 策略恢复、第三方沙盒或持久介质损坏。

### 5.3 本地直跑与远程沙箱的执行边界（2026-10-26）

本地 `run-strategy`、`search-strategy` 和 Python callback 研究默认直接执行用户本机策略，不要求沙箱；这是可信代码的开发路径。策略文件继承本地用户权限，不能把普通 worker 子进程当作安全隔离。部署隔离策略由服务端宿主配置控制，策略参数不能覆盖服务端执行策略；多租户或用户上传代码必须隔离，并且沙箱失败时 fail closed。

Rust Python `strategy-worker` 默认 `local`，并有显式 E2B、Microsandbox、OpenSandbox 持久 worker provider。多租户或不可信策略的服务器部署建议由宿主显式选择 E2B；Microsandbox local microVM 可部署在自有服务器，worker 与 microVM 位于同一主机。其 Python SDK 当前列明 Linux/KVM、macOS/Apple Silicon 与 Windows 11/WHP（preview）；OpenSandbox 适合已有自建生命周期控制面的场景。远程传输限 JSONL/framed JSON；provider/worker 失败不会退回本机执行。远程 class manifest 支持 Bar、显式 `data_level=tick`、持久 L2 `data_level=orderbook` 和 scheduler `data_level=timer`；Tick 使用 input v6，账户/持仓快照使用 v7，盘口事实使用 v8 并从 Runtime EventLog 重放。远程批量研究 CLI 默认 E2B，并可显式选择 OpenSandbox；当前没有 Microsandbox 批量研究命令。`llm-sandbox`（包括 `vndee/llm-sandbox`）尚未作为牵星 provider 集成。Provider 选择由宿主显式设置，策略 worker unset 时仍是 `local`，因此服务器必须配置 `QX_PYTHON_STRATEGY_EXECUTION_MODE=e2b` 或明确选择其他隔离 provider。以上是代码集成状态，不代表真实供应商账户、隔离策略、远程容量/成本、长时间运行和故障恢复已经验收。

本地接入仍走 Python 包与 `run-strategy`/`search-strategy` 研究命令，无需配置沙箱。服务器运行不可信或多租户策略时，E2B 是建议的默认 provider，由宿主配置 `QX_PYTHON_STRATEGY_EXECUTION_MODE=e2b`；Microsandbox local microVM 是自有服务器备选，目标主机需满足 SDK 当前要求（Linux/KVM、macOS/Apple Silicon 或 Windows 11/WHP preview）；OpenSandbox 是自建服务备选。部署侧统一管理 CPU/内存、网络、worker 并发和策略输入，策略 spec 不得改变隔离模式。provider 由宿主显式选择；失败关闭，不自动换 provider 或退回本机。`llm-sandbox` 尚未集成。独立的 `remote-research` 批量研究命令当前仍默认 E2B。Tick 单次输入最多 10,000 条；首次启动从行情日志尾部回放最近批次，后续恢复使用 durable cursor。代码集成不代表沙箱供应商验收或发布包验证已经完成。

1. 诊断快照 `diagnostic_state()` 与可持久化 `snapshot_state()/restore_state()` 分开；恢复格式需 schema 版本、策略版本、参数/source digest 和确定性检查。

## 9. 面向策略作者的标准函数清单与采用决策（2026-10-25）

### 9.1 建议作者先实现哪些函数

对于普通事件策略，用户只需要写“策略实例 + 一个市场决策函数”；其它能力按需覆盖。避免把十几个 no-op 函数当成入门门槛。

| 层次 | 推荐函数 | 用途 | 是否作为最小策略要求 |
|---|---|---|---|
| 参数与实例 | `create_strategy(spec)` / `__init__(params)` | 校验参数，创建一次运行专属的状态。不得连交易所、读隐含未来数据或提交订单。 | 工厂需能创建新实例；用户无需实现独立 `create_strategy` 方法 |
| 生命周期 | `on_init(context)`、`on_start(context)`、`on_stop()` | 初始化本地状态、运行启动和清理。实例新建后初始化一次，首个行情事件前 start 一次，终态 stop 一次。 | 全部可选 |
| 预热 | `history_requirements()`、`on_warmup_complete(context, instrument, observed_bars)` | 声明历史长度并接收每个标的的 readiness 通知；宿主负责 PIT-safe 输入、计数和屏蔽未 ready 期间的订单。 | 可选；无需求默认为 0 |
| 市场决策 | `on_event(context, event)`，或 helper 的 `on_bar/on_tick/on_order_book/on_timer` | 消费带时间戳的已知输入并返回 intents；Python `BaseStrategy` 将具体事件分发到对应 hook。 | **必须有一个决策入口**；统一 wire 协议是 `on_event` |
| 执行事实 | `on_order_status_update(context, update)`、fill 专用 `on_order_update(context, update)` / `on_fill_update(context, update)`，易用层 `on_order(context, status)` / `on_trade(context, fill)` | 分别接收 OMS 已提交的订单状态和账本已提交的成交事实，更新策略本地状态或排入后续决策；不能重复记账。 | 可选；订单状态已接入 Rust/Python/策略文件/C ABI 的部分宿主；带事件序号的 fill v2 已接入 Rust Bar/Depth、Python callback 和 C ABI/C++，策略文件 worker 尚无独立 fill stream |
| 会话 | `on_trading_day_start`、`on_session_start/end` | 市场日历明确提供时处理开盘前/盘中/收盘阶段。 | 可选；按交易所日历或 session 能力触发 |
| 交易管理策略 | `StrategyOutput.for_target_position`、`for_intents`；后续可评估 `exit_policy`、`stop_loss/take_profit` 等 intent/policy helper | 文件策略 API 可直接表达目标仓位或多订单意图；运行时完成差额、规则、能力、风险与 OMS 校验。 | 目标仓位/多意图构造器已落地于 Python 文件协议；后续 helper 仍须是纯 DTO/policy，不是直接下单 API |
| 研究型向量化 | `populate_indicators`、`populate_entry_trend`、`populate_exit_trend` | 对已封存的 Bar 矩阵批量计算指标和信号，服务参数搜索和快速研究。 | 与事件策略分开的可选 adapter |

用户最常见的实现可简化为：

```python
class SmaCross(BaseStrategy):
    def history_requirements(self):
        return {"warmup_bars": 30}

    def on_bar(self, context, bar):
        # 根据截至 bar.ts 的可见数据计算信号，只返回 decision/intents。
        return self.decision(context, "Bar", bar, intents=[])
```

`BaseStrategy` 是 Python callback SDK 的可选易用层。Rust trait、策略文件 JSONL 协议和 C++ ABI 仍可通过各自语言形态实现同一语义，不应被强制绑定到 Python 继承结构。普通用户不需要同时实现 `on_event` 和 `on_bar`；在统一协议边界上保留 `on_event`，在 Python helper 内由它完成事件分派。

### 9.2 调用顺序与边界

```text
创建独立实例并验证参数
  → on_init
  → 准备受 PIT 限制的历史输入
  → on_start
  → 每标的 warmup 进度；达到声明值时 on_warmup_complete
  → 逐事件市场决策 → Rust 决策校验 / 能力门 / RiskGate / OMS / 执行 / Ledger
  → 已提交的订单/成交/账户事实通知（只读事实；策略可返回下一时点 intent）
  → 正常结束、取消或失败时 on_stop
```

关键规则：

- `on_start` 只代表 host 即将开始推送输入，不代表 warmup 已完成。Ready 通过 `on_warmup_complete` 表达，避免额外 `on_ready` 重复表达同一状态。
- 市场数据 callback 必须携带 event time 与 instrument；跨周期/跨标的输入还要保留数据源、周期和 as-of 可见性。回测和实盘不能以系统墙钟推断市场 session。
- 策略产生的是意图，不是订单执行结果。撤单、改单和目标仓位也要成为通过同一 Rust 执行链路的受约束请求。
- `on_trade` 当前对应单笔已提交 fill，并非完整交易所 trade stream；订单状态有独立版本化合同。Python Runtime class worker 的 `on_account` 和 `on_positions_snapshot/on_position` 消费完整权威快照；Rust/C ABI/C++ 跨宿主合同仍待扩展。
- 搜索的每个参数候选必须创建隔离实例；候选状态不能泄漏。诊断快照不是重启恢复快照。

### 9.4 对牵星的收敛建议

**标准核心保持少而稳定：** `on_init`、`history_requirements`、`on_start`、`on_warmup_complete`、单一市场事件入口、typed 执行事实更新、`on_stop`。其中只有一个决策入口是策略必须实现的；生命周期、warmup 和执行反馈均可选。

**helper 按场景扩展：** Python callback `BaseStrategy` 提供 `on_bar/on_tick/on_order_book/on_timer`、decision/order-intent builder；Python 文件策略另有身份绑定的 `StrategyOutput.for_target_position/for_intents`。A 股 session、crypto leverage/hedge-mode、止损退出、订单超时继续按明确市场能力逐项提供。所有 helper 只生成 DTO/policy，不直接连接交易所。

**向量化与事件型策略并存但分开：** 为 Freqtrade 风格研究增加独立 Bar 矩阵 adapter，输出信号后交给已有 Rust 撮合、费用、保证金、风险和账本重算；不要通过“整表填 signal 列”代替 Tick/L2、部分成交、资金费和实时恢复测试。

下一批按此顺序落地：① 将 Rust/Python/C++ host 收敛到一致的 lifecycle/readiness 与 golden 合同；② 将带事件序号的独立 fill stream 扩展到策略文件 worker，再完善 position/account 和更完整订单状态事实；③ 为 A 股 session 与加密 24×7 timer 增加显式日历语义；④ 在有权威持仓和衍生品仓位侧语义的 callback/use-case 上评估目标仓位与保护性退出 helper；⑤ 单独评估向量化研究 adapter。策略文件 worker 的订单状态离线投递和 Python `StrategyOutput` 目标仓位/多意图构造器已完成代码切片，但仍需扩大故障恢复验收并完成真实供应商 scope 验收。每一项都应覆盖宿主时序、重复/过期事件和数量精度；不宣称未完成的宿主已支持。

## 10. 2026-10-26 复核：标准函数分组与吸收决策

经典框架里“策略类有哪些函数”其实混合了三种东西：引擎生命周期回调、策略作者实现的信号回调、框架提供的查询/下单工具。牵星应把三者分开，统一事件语义，不要求每个策略都实现一长串空函数。

| 函数组 | 常见经典接口 | 牵星当前状态 | 采用决策 |
|---|---|---|---|
| 生命周期与参数 | `__init__/on_init/on_start/on_stop`、参数声明 | 新实例、`on_init/on_start/on_stop` 已存在；候选隔离靠每次创建新实例。Python Runtime class worker 已有首版持久快照，但暂停/恢复/故障和持久快照仍没有完整的跨宿主合同。 | 保留四个直观生命周期点；用有版本的 lifecycle update 表达 pause/resume/fault，继续扩展独立 `snapshot_state/restore_state` 的 host 覆盖，不把诊断快照当 checkpoint。 |
| 历史与预热 | Freqtrade `startup_candle_count`；Backtrader `prenext/nextstart`；NautilusTrader indicator initialization | `history_requirements` 与逐标的 `on_warmup_complete` 已覆盖 Bar readiness；数据加载和可见性仍归宿主控制，部分非 Bar host 对 Bar 预热明确拒绝。 | 继续以 PIT-safe manifest/数据绑定提供历史；让 helper 简化预热状态，但不开放绕过 as-of 的任意未来数据查询。 |
| 行情与时钟 | `handle_bar/handle_tick`、`on_bar/on_tick`、`on_timer` | 统一 `on_event` 必需入口；Python helper 已分发 Bar/Tick/OrderBook/Timer。 | 核心保留 tagged event；语言 helper 提供 typed hooks。A 股交易日、集合竞价和 session start/end 只有在交易日历明确产生事件后才开放。 |
| 执行反馈 | `notify_order/notify_trade`、CTA `on_order/on_trade/on_position/on_account` | fill 与订单状态已分开；Python Runtime class worker 已接 account/position 完整快照。 | 继续补 Rust/C ABI/C++ 宿主覆盖和规范 fixture；只消费 EventLog 权威事实，不在策略层二次记账。 |
| 查询和执行工具 | `history_bars`、indicator、`buy/sell/close/cancel`、gateway/cache | callback SDK 有 `decision/order_intent`；文件策略 API 有身份绑定的目标仓位和多意图构造器。策略没有应被依赖的通用数据订阅、日历、账户服务或直接交易所下单 API。 | 先提供只读、PIT 约束的数据/账户查询 facade；订单快捷函数只生成带单位的 intent/policy/request，经能力门、Risk、OMS 和执行端处理。 |
| 批量研究 | Freqtrade `populate_indicators/populate_entry_trend/populate_exit_trend`；Qlib/vectorbt 的批量决策/搜索 | 尚未把整表 DataFrame 生命周期作为统一事件策略 API；现有事件策略与候选研究链仍需保持语义区分。 | 单独实现 Vectorized Research adapter，输出信号/候选，再由 Rust 事件回测重算；不把 pandas 回调混入 Live 策略协议。 |

### 10.1 竞品函数设计吸收什么

- **Freqtrade：** 指标计算、入场信号、出场信号和按需交易管理 callback 分层清楚；这适合“快速研究 + 回调运行”。牵星应吸收职责分离、显式 startup warmup、未来数据/递归偏差检查和参数搜索入口。它的策略回调文档特别区分一次性向量函数与运行时高频 callback，且要求高频 callback 保持轻量。参考 [策略定制](https://docs.freqtrade.io/en/stable/strategy-customization/) 和 [策略回调](https://docs.freqtrade.io/en/latest/strategy-callbacks/)。
- **Backtrader：** `prenext/nextstart/next` 把指标未就绪、刚就绪和常规决策分开，`notify_order/notify_trade/notify_cashvalue` 又把市场决策与成交/资金反馈分开。牵星已采用显式 per-instrument warmup 与分离的订单状态/成交更新；不复制 broker 对象和直接副作用。参考 [Strategy API](https://www.backtrader.com/docu/strategy/)。
- **VeighNa CTA：** `on_tick/on_bar/on_order/on_trade/on_position/on_account` 的命名贴近交易员工作流，适合国内期货和事件策略。牵星保留 typed helper 的可读性，但每类事实必须先有稳定来源和 schema；交易快捷方法不能绕过统一执行链。参考 [CTA 策略模板](https://github.com/vnpy/vnpy/blob/master/docs/community/app/cta_strategy.md)。
- **RQAlpha：** `before_trading/open_auction/handle_bar/after_trading` 显式表达 A 股交易日阶段。牵星应把 session 作为交易日历驱动的可选事件，不用墙钟触发，也不强加给 24×7 数字资产。参考 [策略 API](https://github.com/ricequant/rqalpha/blob/master/rqalpha/__init__.py) 与 [入门教程](https://github.com/ricequant/rqalpha/blob/master/docs/source/intro/tutorial.rst)。
- **NautilusTrader：** 生命周期和数据/订单事件以可选 `on_*` handler 组合，启动阶段订阅数据、注册指标、加载历史，停止阶段清理；还区分策略运行状态。牵星可吸收可选 handler、stateful lifecycle 和启动前准备的清晰性，但维持自己的版本化 DTO/worker 信任边界。参考 [Strategies](https://nautilustrader.io/docs/latest/concepts/strategies/)。
- **Qlib：** 以执行结果作为下一轮决策的输入，强化策略目标和执行反馈闭环。牵星应继续把 `target position → order intents → executed facts → next decision` 显式化；目标仓位不是订单，更不是成交事实。参考 [BaseStrategy](https://github.com/microsoft/qlib/blob/main/qlib/strategy/base.py)。

### 10.2 建议面向用户公开的“标准策略类”

普通事件策略只需提供一个决策入口；使用 Python helper 时建议写成：

```python
class MyStrategy(BaseStrategy):
    def history_requirements(self):
        return {"warmup_bars": 30}

    def on_bar(self, context, bar):
        # 只使用 bar.ts 之前可见的数据。
        intents = []
        return self.decision(context, "Bar", bar, intents=intents)

    def on_trade(self, context, trade):
        # trade 是宿主已提交的单笔 fill；只更新策略本地状态。
        pass
```

作者按需覆盖 `on_init/on_start/on_stop`、`history_requirements/on_warmup_complete`、`on_bar/on_tick/on_order_book/on_timer` 和已支持的订单/成交更新。A 股策略只有在 host 提供交易日历事件时再实现 `before_trading/on_session_start/on_session_end/after_trading`。Python Runtime class worker 可选覆盖 `on_account/on_positions_snapshot/on_position`。不要同时要求作者实现 `on_event` 与 `on_bar`；`on_event` 是跨语言 wire contract，`BaseStrategy` 负责 Python 事件分发。

#### 参数声明与基础函数约定

策略文件的 `STRATEGY_MANIFEST.parameters` 已支持类型、必填、默认值、数值范围和 choices；callback `BaseStrategy` 还没有同一份参数元数据接口。策略文件入口现会在预检前将声明默认值绑定到策略配置，并在每个搜索候选实例化前重新绑定。模块可导出可选的 `validate_config(config)`，收到只读的已解析参数映射，必须返回 `None`，用异常拒绝不合法组合；不得查询行情、访问账户或连接交易所。该校验在单次运行预检和每个搜索候选 factory 调用前执行。callback SDK 的 class-level 参数 schema 尚未统一到 manifest；目标是让 CLI、Web、预检和参数搜索继续读取同一份版本化声明，而不是再造第二套参数源。

标准函数分组应保持如下最小面：

| 分组 | 标准函数 | 作者是否必须实现 | 牵星当前状态 |
|---|---|---|---|
| 实例与参数 | `create_strategy(spec)`；schema 驱动的参数校验；可选 `validate_config(config)` | 工厂要返回隔离的新实例；validator 可选 | 文件策略 manifest 的类型/边界校验、默认值绑定和逐候选 validator 已落地；callback SDK 的 class-level 元数据仍待统一。 |
| 生命周期与预热 | `on_init`、`history_requirements`、`on_start`、`on_warmup_complete`、`on_stop` | 都可选 | Rust/Python Bar callback 已支持；C ABI/C++ 动态插件新增可选 warmup 声明、就绪回调和 v2 contextual-stop 导出，旧 vtable 不变。缺失声明默认 0 根预热，缺失就绪回调不阻断运行。版本化 stop context 已存在；终态原因仍未从所有 host 路径映射。 |
| 市场决策 | 核心 `on_event`；Python helper 的 `on_bar/on_tick/on_order_book/on_timer` | Rust 核心只要求 `on_event`；Python 作者只重写实际使用的 typed hook | 已实现事件分派和 intent builder；intent 由 Rust 校验并经过 Risk/OMS。 |
| 执行反馈 | `on_order_status_update/on_order`、`on_fill_update/on_trade`、`on_account/on_positions_snapshot/on_position` | 可选 | Python Runtime class worker、Rust trait 和 C ABI/C++ 动态插件均有版本化订单/成交/账户更新适配及共享 fixture；独立 JSONL worker、其他部署形态和故障恢复矩阵仍需分别验收。 |
| 诊断和恢复 | `diagnostic_state`；独立 `snapshot_state/restore_state/on_restore` | 可选 | Python Runtime class worker 已用 input v4 支持 schema v1、策略身份绑定、64 KiB JSON checkpoint，并与 cursor 原子保存；其他宿主/SDK 不自动继承此能力。 |

不能让所有策略都继承几十个空回调，也不要同时强制 Python 作者实现 `on_event` 和 `on_bar`。如果只做 Bar 策略，用户看到的必要入口就是 `create_strategy(spec)` 和 `on_bar(context, bar)`；其它生命周期与反馈函数按场景覆盖。核心协议仍统一成 tagged `MarketEvent` 和精确 `StrategyDecision`，保证各语言策略能被同一回测/执行链运行。

### 10.3 实施顺序与发布口径

1. **P1 易用层收口：** 发布函数调用顺序、可选性、异常/取消语义和各 host 支持矩阵；保持 `BaseStrategy` 为 Python 可选 helper，Rust trait、C ABI、文件 worker 使用同语义的独立适配器。
2. **P1 事实闭环：** 扩展独立 fill/order/position/account/lifecycle DTO；明确事件来源、顺序、去重、重启游标和幂等投递，再逐 host 接通。
3. **P1 市场时段：** 由交易日历生成 A 股盘前/集合竞价/盘中/盘后事件；加密策略通过 engine timer 使用仿真/引擎时间，不依赖系统墙钟。
4. **P2 数据与工具：** 设计只读 PIT history/indicator/calendar facade 和目标仓位/撤改单意图 builder；所有请求仍经过执行能力和风险检查。
5. **P2 研究体验：** 单独建设 vectorized adapter、参数搜索和交互式研究报告，明确筛选结果必须由事件回测和 OOS 诊断复核。

以上是 API 设计与源码接口核对，不代表全部 host 或供应商已验收。任何新增基础函数必须有确定的调用时点、时间/数据可见边界、返回合同、错误策略和跨语言兼容规则；每个新 hook 都必须有权威来源；Python Runtime 的 account/position hook 已按版本化快照实现，其他宿主应复用同一事件语义。

### 10.4 标准策略类的最小函数面与最终取舍（2026-10-26）

经典策略类的回调很多，但不应把它们全部变成新策略的必填项。推荐把标准函数分成“参数与实例、生命周期与预热、一个市场决策入口、执行事实反馈、可选研究适配器”五组，并通过语言 helper 暴露符合用户习惯的名称。

| 类别 | 建议函数 | 必须实现 | 当前实现/边界 |
|---|---|---:|---|
| 参数与实例 | 构造函数/工厂、`validate_config(config)`、参数 schema | 只要求框架能创建一个参数合法且状态隔离的实例 | 文件策略支持模块级 manifest；显式导出的 `STRATEGY_CLASS` 可把同一版本化 manifest 和 validator 放在类上，inspect/默认值/预检/搜索仍复用同一管线。低层 Python SDK callback API 不自动做 manifest 预检。构造函数只建状态，不应联网或下单。 |
| 生命周期 | `on_init(context)`、`on_start(context)`、`on_stop(...)` | 否 | Rust/Python 已有 init/start/stop；停机原因、失败通知和跨宿主状态语义仍要用兼容的版本化合同补齐。 |
| 预热与就绪 | `history_requirements()`、`on_warmup_complete(context, instrument, observed_bars)` | 否；默认 0 根历史 | Rust/Python Bar 策略已支持声明及就绪通知；C ABI/C++ 动态插件通过可选 `qx_strategy_history_requirements_v1` 与 `qx_strategy_on_warmup_complete_v1` 映射同一 trait，不改旧 vtable。跨语言共享 fixture 已覆盖声明值、标的、观测数和调用顺序。Warmup 输入由 host 按 as-of 提供；未就绪时宿主屏蔽订单意图。不要另加语义重复的 `prenext/nextstart/on_ready` 到核心协议。 |
| 市场决策 | 核心 `on_event(context, event)`；易用层 `on_bar/on_tick/on_order_book/on_timer` | 策略至少选择一种实际使用的决策 hook；语言协议层只保留一个规范入口 | Rust trait 以 `on_event` 为核心；Python BaseStrategy 分派 typed hook。普通 Bar 策略只需覆盖 `on_bar`。Hook 返回 decision/intents，不直接提交订单。 |
| 执行反馈 | `on_order_status_update(...)` / `on_order(...)`、`on_fill_update(...)` / `on_trade(...)`、`on_account(...)`、`on_positions_snapshot(...)` / `on_position(...)` | 否 | Python Runtime class worker 与 Rust/C ABI/C++ 动态插件均接入版本化订单状态、成交和账户/持仓快照；包含 EventLog 序号、账户/venue 绑定、精确数量和空快照 fixture。快照只用于策略观察。独立 JSONL worker 与跨进程恢复/重投故障矩阵仍需单独验收。 |
| Session 与日历 | `before_trading/on_session_start/on_session_end/after_trading` | 否 | 仅由已验证的交易日历事件驱动；适用于 A 股等有 session 的市场。24×7 市场使用引擎时钟/timer，不从本机墙钟推断交易阶段。 |
| 批量研究 | `populate_indicators/populate_entry_trend/populate_exit_trend` | 否，且不属于事件型策略基类 | 作为独立的 Bar 向量研究适配器；输出候选信号后交 Rust 事件引擎重算，不得替代撮合、费用、资金费、保证金、风险和多市场资金核算。 |
| 恢复与诊断 | `diagnostic_state()`；`snapshot_state()/restore_state()/on_restore()` | 否 | 诊断快照只用于偏差检查。Python Runtime class worker 已实现 schema/strategy identity 绑定的 checkpoint 与恢复；仍须扩展多 worker/介质故障矩阵，且不承诺 exactly-once。 |

建议的最小 Python 策略示例：

```python
from qianxing_strategy import BaseStrategy


class SmaCross(BaseStrategy):
    def history_requirements(self):
        return {"warmup_bars": 30}

    def on_bar(self, context, bar):
        # 只读取截至当前事件可见的输入；返回的是意图，不是订单或成交。
```

|---|---|---|---|
| Backtrader | `prenext/nextstart/next` 清楚表达指标未就绪、首次就绪和常规决策；`notify_order/notify_trade` 让执行反馈可见。 | 保留明确 warmup gate 和分离的订单状态/fill 事实；无需策略作者自己模拟这三阶段。 | 不把 `buy/sell/close/cancel` 的 broker 副作用作为跨语言核心 API。Backtrader 也提醒同一时间点可能因 tick 更新重复触发策略逻辑，因此牵星事件需用序号/幂等身份保护。 |

| RQAlpha | `before_trading/handle_bar/after_trading` 明确分开 A 股交易日阶段。 | 增加日历驱动的可选 session 事件，按交易所和市场能力使用。 | 不在 24×7 数字资产上模拟 A 股日历，不按本机时间触发 session hook。 |
| NautilusTrader | 生命周期状态、数据/订单/持仓/计时器 handler 粒度明确；将准备工作放在启动阶段，并区分运行状态。 | 后续完善状态化 lifecycle、定时器与可恢复状态合同；typed helper 允许只实现策略需要的 handler。 | 不把 cache、portfolio 或执行客户端直接暴露给所有语言策略；维持 StrategyContext 只读边界和统一 Risk/OMS。 |

**最终建议：**标准策略类只需一个真实的市场决策函数；其余生命周期、预热、订单/成交反馈都是可选。Python 作者主要使用 `on_bar/on_tick/on_order_book/on_timer`，Rust/C++/worker 使用等价 adapter；共同线协议仍是带 schema 版本、事件身份、as-of 边界的事件/意图 DTO。易用 helper 可以提供 `order_intent/target_position/close_position` 等构造器，但只能构造声明式请求。凡是可能改变账户状态的操作最终都经过相同的产品能力、精度、Risk、OMS 与执行链路。
