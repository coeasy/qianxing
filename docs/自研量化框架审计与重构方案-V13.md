## 1. 项目主要功能（功能地图）

### 1.1 能力面：19 块登记在册

`maturity/capabilities.yaml` 本轮实测 19 个能力块：16 块 `implementation + code_tested = true`；
3 块 `implementation = false` —— `postgres`、`nats`、`broker_gateway`。

每块还带 `limitations` 名单（例如 `local_backtest` 17 条、`paper_execution` 14 条、`multi_leg_execution` 9 条），
这份名单是本轮审计的起点，也是 §7 撤销机制的对象。

### 1.3 读面：17 个 HTTP 端点

`crates/qx-api/src/lib.rs` 本轮实测 17 条路由（16 GET + 1 POST），完整清单见 `s24_measure.txt` §8：

本项目没有独立前端工程：所谓"前后端贯通"在这里等于 **CLI/HTTP 读侧 ↔ 产物写侧**，判定见 §3。

## 2. 架构与实现细节

`prod` = 门禁 `_production_lines` 口径（剔 `#[cfg(test)]` 整项与注释行），并且**额外剔掉 test-scope 文件**

三点判读：
1. **qx-cli 占生产文本 30%，但它的 src 有 35% 行数是测试**（10,385/29,786）。它是命令面 + 装配面 + 内联用例三合一，
   这是刻意选择（单 binary），但它也让"生产 panic 面按 crate 归因"极易读错：
   含 test-scope 的口径下 `.unwrap()` 是 1,078 处，剔掉之后只有 **61 处**（`s24_measure.txt` §2）。
   **口径必须先于结论**，这也是 §7 为什么要给每条挂账配复算命令。
2. 尾部 7 个 crate（qx-risk 510、qx-provider 470、qx-guanxing 442、qx-orchestrator 381、
   qx-control 359、qx-plugin 326、qx-genglu 197、qx-python 150）prod 都在 500 行以下。
   它们中有的已经在 V10 P2a 合过一轮，剩下的边界还能再合 —— 但合 crate 是结构动作，不解决正确性，
   所以排在 §5 的 R4，而不是 R1。
3. `qx-storage` 8,965 行 src（sqlite.rs / postgres.rs / lib.rs 三份都在 1,500+ prod 行）是"两套后端各写一遍"的形状。
   今天的对账口径靠门禁钉"单一写路径"，但两套后端仍是**逐字重复逻辑的温床**（§4 L2-B4）。

## 3. 核心功能是否全部实现 · 主体链路是否全部贯通

| 链路 | 贯通判定 | 依据 | 残留缺口 |
| --- | --- | --- | --- |
| 配置 → 装载 → 生效口径播报 | 通 | `config validate/fingerprint/lock` + 运行时体检；§12/§13 收口 | ~~无代码引用的 13 份模板~~ A6 已给 52 份模板建立按执行计的读覆盖（[§9.8](archive/自研量化框架审计与重构方案-V13-逐轮执行记录.md)）；仍无模板被接进 CI 部署 |

| 账户/持仓/权益读模型 | 通 | `qx-api` 17 端点 + 快照契约版本门禁 | 权益口径 6 个重载 + 2 处异名（§4 L2-B3） |
| Paper 下单 → 成交 → 事实流 → 报告 | 通 | `venue_runtime/`、`reconcile`、`report` | 账户级 unrealized/margin/frozen/realized/funding **无生产者**（快照打印 null，属已声明边界） |
| 长驻编排（supervise / worker 家族） | 通（本机、无外部） | `RuntimeSupervisor::new` 10+ 生产构造点 | 优雅停机的信号投递路径仍无用例（capabilities 自述） |
| A 股规则链（Rust 侧） | 通（R1-A1 后） | `qx-xingban/src/ashare*` | 除权除息锚已从装载的公司行为折算，覆盖表降为第二出口（[§9.1](archive/自研量化框架审计与重构方案-V13-逐轮执行记录.md)）；样例快照仍不带公司行为文件 |
| A 股规则链（Python 侧） | **半接线** | `python/qianxing_ashare` 2,050 行，Rust 无调用点 | 无判据能发现它与 Rust 规则漂移（§4 L1-2） |
| C++ 策略 SDK | 半接线 | `crates/qx-strategy/src/c_api.rs:740` 的 `Library::new` | CI 从不加载插件（工作流里 `plugin` 关键词 0 命中） |
| Postgres / NATS 后端 | 未认证 | 能力块 `implementation=false` | 8 条用例永远躲在 feature 门后（§4 L4-1） |
| 真实柜台（live） | 有意不做 | `sandbox_tested=false` 由门禁钉住 | — |

结论：**核心功能没有"没实现"的黑洞，主体链路是贯通的**；风险集中在两类地方 ——
"结构存在、生效点缺席"（字段/包/端点有一份没人喂数据），以及"同一件事有多个主人"（币种、权益、
对账类型、venue 识别）。这两类恰好都是门禁今天看不见或只看一半的。

## 4. 不合理清单（分级）

### L1 半接线与断链（正确性风险，最高）

1. **除权除息日的锚读不到仓库已经装载好的公司行为**（`§4 L1-1`，**已在 R1-A1 处置，见 [§9.1](archive/自研量化框架审计与重构方案-V13-逐轮执行记录.md)**）。
   取证：`crates/qx-xingban/src/ashare.rs:494`（pub 字段）、`:518`（`BTreeMap::new()`）、
   `:981`（自检只验非正数）、`ashare/trading.rs:49`（读取覆盖推导）。
   **本轮复核更正**：原文写"生产文本里没有第四个写点、唯一赋值来自测试夹具"，这句**不成立** ——
   `ashare_binding.rs:38` 用 `serde_json::from_str::<AshareRuleConfig>` 装载整份规则快照，字段带
   `#[serde(default)]`，`deploy/qianxing.ashare.rules.json:17` 就是那张（空的）覆盖表。所以它是
   **数据侧可达、样例侧无值**的活字段，而不是死字段。真正的断链在别处：`apply_corporate_actions_json`
   有两个非测试写点（`ashare_binding.rs:44`、`runtime_check.rs:393`），红利/送转/配股就这样被装进
   `corporate_actions`，而锚一个字都不读它们 —— 于是代码注释声称"覆盖表才是除权除息的出口"，
   事实是**那条出口没有生产者，而有生产者的一侧没人读**。
   后果（处置前）：除权除息日的涨跌停锚继续用未调整昨收。
2. **`python/qianxing_ashare` 无 Rust 运行时接线**（§1.5）。它让"同一套 A 股口径有两份实现"成为事实，
   且没有任何判据比较两者。
3. **C++ 插件曾只有静态/独立构建证据**。本轮前 CI 只构建插件，没有交给 Rust 宿主加载；现已由
   `crates/qx-strategy/tests/cpp_plugin_host.rs` 与三平台 `cpp-sdk` 作业补上实际动态加载、事件回调和统一策略契约校验，
   并显式导出 Windows `qx_strategy_get_vtable` 符号。
4. **账户级五个金额字段无生产者**：`unrealized_pnl / margin_raw / frozen_raw / realized_pnl / funding_raw`。
   现状是 `Option` + null 播报（V11 Q67/Q70 的诚实化成果），不是造假。风险在于**快照被下游当成完整账务读**。
5. **调度/重试子系统仍有半边**：`Failed` 生产者与 `retry_run_at` 消费者（任务 #129 登记过），
   capabilities 的 `scheduler_run_retry_has_no_production_path` 本轮复算仍成立（52 处 `retry*` 生产文本命中，
   但没有一条把"到点重跑"接进 tick）。
6. **13 份零代码引用的 deploy 模板**（§1.4）。它们是"人跑示例"，但今天没有任何 CI 步骤 validate 它们；
   其中 2 份连文档都不提 —— 那 2 份已属孤儿。

## 8. 风险与推进顺序

* **顺序**：R1 → R2 → R3 → R4。R3（量具）刻意排在正确性修复之后：先让判据接住已经存在的洞，
  再让判据长出新洞，避免"新判据一上线就把本轮自己的改动判红"这种回合浪费。
* **风险 1（改名与删公共面）**：R2 的跨 crate 改名会撞上游分叉。对策：改名前 `git log --all -S` 核一次，
  合流按既有口径（我方架构胜出 + 逐 hunk 移植对方语义修复），并跑 `cargo test --workspace --all-targets`。
* **风险 2（新门禁大面积报红）**：R3-3/R3-4 首轮会点出几十条。对策：允许清单 + 每轮只收紧一类，
  行数棘轮与门槛计数**不放宽**，走 `--snapshot` 记账。
* **风险 3（删模板/删字段破坏示例可跑性）**：A6/A1 的删除动作必须先在本机跑一次
  `build.bat` 九步全过，再把"跟踪产物 0 改写"当验收。
* **回合纪律**：每轮一份新门禁日志、每个新判据一对红绿变异、文档只抄当轮日志（项目记忆

### 9.58 QX-DEV-PLAN M1 · T1-1 运行证据包（阶段 1 最大一件 / 退出门 G1 第一条「同一运行可由 RunManifest 离线复算」）；门禁 977 → 985（floor 919 → 927），未 git add

**两处「先看真产物再写判据」的修正（本轮最贵的两笔）。** ① **指纹是两格，不是一格**：`run.data_fingerprint` 是**合成**身份（`barframe:<内容哈希>` / `dataset-bundle:<bundle 指纹>`），而摘要里的 `input.fingerprint` 是**纯内容哈希**。第一版把 `dataset.fingerprint` 与 `run.data_fingerprint` 直接交叉比对——那样会让**每一份真产物都被自己的校验拒掉**。修法是拆成 `dataset.content_fingerprint`（这份输入文件是什么，如实声明、**不**交叉比对）与 `dataset.composed_fingerprint`（这次运行认哪份数据，**必须**与 `run.data_fingerprint` 逐字相等）。② **质量报告允许缺席、不许空**：回测链今天**不产**数据集质量报告（那是 T1-6 的 `data-validate`），所以字段是 `Option<RunEvidenceQualityReport>`；一份全 0 的假报告读起来是「核过了，没有重复、没有缺口」——比 `null` 更坏。判据在代码里（`usable_tiers.is_empty()` 拒绝臂）与 schema 里（`oneOf [null, object]`）各钉一次，用例另带一条对照组（把 `usable_tiers` 换成 `["bar"]` 必须被接受），免得拒绝臂其实是「只要带报告就拒」。
