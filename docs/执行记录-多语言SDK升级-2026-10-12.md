## 本轮交付

- 将 `qx-provider` 接入 `qx-python` 原生扩展；Python Provider adapter 通过 Rust `ProviderRegistry` 完成 capability 校验、候选排序、failover、来源身份与数据载荷校验。
- 增加 Rust `ProviderResult::from_payloads`，由共享 Rust 代码生成 RawRecord 与结果摘要，语言绑定无需复制指纹算法。
- 新增 `qianxing.data` 的 ProviderQuery、ProviderCapability、ProviderResponse 和 ProviderRegistry；支持将严格 Bar 查询结果标准化成共享 BarFrame。
- 新增 `ProviderAdapterError`、`ProviderManualInterventionError`、`ProviderPermanentError` 三类失败语义，分别映射至 Rust failover、人工介入终止和永久错误。
- 新增 `ProviderRegistry.run_backtest`：只冻结经 Rust 校验的 BarFrame；相同文件可重用，不同内容拒绝覆盖；回测继续调用原 Rust `qx-app` 用例。
- 更新 Python SDK 说明、Rust SDK 迁移指南、Provider 能力矩阵、数据主链调用图与架构门禁名册。

## 增量：Provider 到标准 BarFrame 的共享 Rust 入口

- `ProviderRegistry::fetch_bar_frame(DataRequest)` 统一执行注册表候选筛选、确定性 failover、Provider 身份/结果血缘校验、strict Bar 质量检查与标准 `BarFrame` 投影，并同时返回 `ProviderResult` 和帧，避免调用方重复解析或丢失实际主源/备源血缘。
- Rust SDK 重导出 `ProviderBarFrame`；Rust 仓外消费者测试改用统一入口取得标准帧，再走既有 `qx-app` 回测和 `ReplayVerifier`。Python PyO3 `fetch_bar_frame_json` 与 `fetch_bar_dataset_json` 也改调同一入口，数据集 manifest 构造复用已校验帧，不再对同一 ProviderResult 再做一次标准化。
- 验证：`cargo test --offline -p qx-provider -p qx-sdk -- --test-threads=1` 通过（Provider 14 单测 + 2 provenance 集成测试；SDK 5 单测及所有消费者测试通过）；`cargo check --offline -p qx-python`、`cargo fmt --all -- --check`、`cargo clippy --offline -p qx-provider -p qx-sdk -p qx-python --all-targets -- -D warnings` 通过；架构不变量 1096 项通过。第一次 SDK 测试因 Windows 默认临时目录拒绝访问有 10 项失败；指定 `TEMP/TMP=target/test-temp` 后完整重跑通过。
- 用更新源码重建 Windows `cp310-abi3-win_amd64` wheel，`tools/check_python_wheel.py` 通过；隔离 Python 3.13 安装后运行 `python.tests.test_provider_sdk`，8 项全部通过。SHA-256：`5f4a2993c11686e5c3769d559c3486722f3a41db3d31b04460af5288d4c74ef9`。
- 此增量统一的是 Provider→BarFrame 边界，不等于 Provider 已贯通全部 CLI/HTTP/实时 Paper/Live 数据入口；Rust SDK 自动 DatasetManifest 工作流、真实源分页/订阅、Provider 实际凭据授权、交易所 testnet 认证和跨账户组合执行仍有缺口。
