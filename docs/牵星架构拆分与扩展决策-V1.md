# 牵星架构拆分与扩展决策 V1

> 本文是《牵星终极改造计划 V1》的补充决策稿，回答三个问题：哪些模块必须拆分、哪些能力必须扩展、哪些拆分现在不应该做。目标是让 qianxing 在保持 Rust 原生、确定性和多资产能力的同时，逐步对齐 Barter、NautilusTrader、LEAN、Hummingbot 和 vectorbt 的成熟做法。

## 1. 结论

### 1.1 需要拆分，但不是立即微服务化

牵星需要拆分，拆分顺序应当是：

```text
职责拆分
  → crate 内文件拆分
  → 稳定端口/事件协议
  → 少量高价值 crate 拆分
  → 必要时才做进程/节点隔离
```

当前最危险的不是 crate 数量少，而是同一个职责在多个入口中重复存在：

- `qx-core::Engine` 已经承担确定性事件循环；
- `qx-runtime::LiveEventPipeline` 又承担实时事件、OMS、Ledger 和恢复归约；
- `qx-execution` 同时存在依赖 Runtime 的旧执行服务和独立的端口执行服务；
- `qx-application` 已有执行端口，但事件回报和风险决策模型仍不完整；
- `qx-core::ledger`、`qx-runtime::pipeline`、`qx-execution::lib` 等文件过大，职责边界难以通过代码结构表达。

因此第一阶段不是“再建十个 crate”，而是先让同一职责只有一个权威实现。

### 1.2 事件引擎和交易执行引擎都应当保留，但要从“能力存在”升级为“边界唯一”

牵星已经具备事件驱动、确定性队列、事件日志、重放校验、OMS、Paper 撮合和部分真实 Venue 适配能力；但目前事件引擎、实时 Pipeline、执行服务之间仍有重叠。终态应明确为两个逻辑引擎：

```text
EventEngine
  负责输入、排序、事实归约、EventLog、AuditStream、Snapshot、Replay

ExecutionEngine
  负责 PortfolioTarget、Risk、OMS、ExecutionAlgorithm、VenueRouter、Reconcile
```

两者初期仍在同一进程、同一单写者核心中运行，不要求立刻拆成两个服务。这样既保留确定性，又为未来节点隔离留下稳定协议。

### 1.3 必须扩展，但扩展重点不是因子库

`finkit` 已经是因子与指标计算的责任边界，qianxing 不应重新建设第二套指标库。qianxing 应把资源集中在交易引擎的六个缺口：

1. DataEngine：行情接入、标准化、订阅、质量、缺口和重连；
2. Portfolio/Accounting：多资产持仓、现金、保证金、费用、估值和企业行动；
3. RiskEngine：可组合、可审计、支持 pre-trade 和 runtime guard 的风险决策；
4. ExecutionAlgorithm：TWAP/VWAP/分片/被动/做市等执行算法的生命周期；
5. Reconciliation：未知结果、私有流、REST 对账、重启恢复和人工处置；
6. Control Plane：命令、查询、审计、StateReplica、可视化和运行管理。

## 2. 与顶尖开源项目的对齐结论

| 项目 | 最值得借鉴的结构 | 牵星当前差距 | 牵星应采取的动作 |
|---|---|---|---|
| [Barter](https://github.com/barter-rs/barter-rs) | Rust 原生事件驱动、Indexed State、Mock/Live 复用、AuditStream、Engine Command、State Replica | 已有确定性队列和 EventLog，但 Live Pipeline 与 Engine 尚未完全收敛；索引、命令、审计副本仍需统一 | 以单写者 EventEngine 为核心，补齐 `EngineCommand`、`AuditStream`、`StateReplica`、`InstrumentIndex` 和回测/纸盘/实盘同构 |
| [NautilusTrader](https://nautilustrader.io/docs/latest/concepts/architecture/) | 明确区分 Kernel、MessageBus、Cache、DataEngine、ExecutionEngine、RiskEngine、Portfolio、Trader；Backtest/Sandbox/Live 共用 Kernel；组件有生命周期和恢复策略 | 牵星已有类似零件，但 `qx-runtime`、`qx-application`、`qx-execution` 的组合关系仍不够单一；Risk/Portfolio/Data 的公开边界不完整 | 建立统一 `EngineNode`/`EngineBuilder`，把 Data、Risk、Portfolio、Execution、Lifecycle 变成显式组件，统一 Sandbox/Paper/Live |
| [LEAN](https://github.com/QuantConnect/Lean) | 事件驱动、跨资产模型、Universe/Alpha/Portfolio/Execution/Risk 分层、研究/回测/优化/实盘 CLI 工作流 | qianxing 的内核方向正确，但组合构建、Universe、调度、参数优化、研究到实盘的产品链还不够统一 | 把策略决策、组合目标、风险、执行算法分层；增加 RunSpec、数据版本、参数空间和可复现实验清单 |
| [Hummingbot](https://hummingbot.org/docs/) | Connector 标准化、OrderBook/UserStream/InFlightOrder 责任清晰；Executor 与 Controller 解耦，支持多机器人和控制面 | qx-adapter 仍以供应商实现为主，统一能力矩阵、私有流、订单跟踪和执行算法生命周期不足 | 固化 `MarketDataAdapter`、`ExecutionAdapter`、`ReconcileAdapter`、`CapabilityMatrix`；把执行算法做成可管理的短生命周期组件 |
| [vectorbt](https://vectorbt.dev/) | 向量化研究、批量参数扫描、Python 交互分析、Rust/Numba 加速和丰富图表 | qianxing 不应复制其研究范式，但需要提供研究结果到 Engine Intent 的可追溯交接 | 由 finkit/vectorized research 负责批量分析；qianxing 负责 `DatasetVersion`、`ResearchBinding`、`StrategyDecision` 和可重放执行 |

对齐后的定位是：

```text
finkit/vectorized research 解决“如何研究信号”
qianxing EventEngine      解决“如何可靠地处理事实”
qianxing ExecutionEngine  解决“如何把意图变成可对账的交易”
Control Plane              解决“如何观察、控制和恢复”
```

## 3. 当前模块的拆分决策

### 3.1 总体目标结构

```text
qx-domain / qx-model        稳定的资产、合约、订单、事件、命令、回报和 ID
        ↓
qx-core                     时钟、序列、因果队列、确定性 reducer 原语
        ↓
qx-event-engine             Ingress、Sequencer、Reducer、EventStore、Audit、Replay
        ↓
qx-portfolio / qx-ledger    账户、持仓、现金、保证金、估值、费用、结算
qx-risk                     风控规则、限额、风险决策和运行时保护
qx-oms                      订单状态机、意图、生命周期和幂等
qx-execution                执行算法、路由、提交、撤改单和结果编排
qx-adapter                  行情、交易、私有流、对账和供应商协议适配
        ↓
qx-runtime                  节点装配、生命周期、Worker、恢复和运行模式
qx-storage                  EventLog、Snapshot、Outbox、Query、Lease
        ↓
qx-api / qx-cli / qx-zhenlu / visualization
                             命令、查询、审计副本、图表和运维控制面
```

这里的 `qx-event-engine`、`qx-portfolio`、`qx-ledger` 等是终态职责名称，不表示当前就必须全部新建 crate。新建 crate 必须遵守第 6 节门禁。

### 3.2 当前阶段应该怎么拆

| 当前模块 | 现在的处理方式 | 终态职责 | 决策 |
|---|---|---|---|
| `qx-core` | 事件、队列、Engine、Ledger 等基础能力混在一个核心包中 | Kernel primitives + 稳定领域事实 | 先按文件和模块拆；事件协议稳定后再评估 `qx-domain` 与 `qx-ledger` |
| `qx-runtime` | Pipeline、Supervisor、Worker、恢复和配置集中 | Node composition、生命周期、运行模式 | 先拆 `pipeline/event_engine/supervisor/recovery` 文件；禁止继续向 Pipeline 堆新业务职责 |
| `qx-application` | 已有端口，但事件回报和风险决策语义较少 | 唯一 Ports/Commands/Queries 契约层 | 立即补齐事件、命令、风险、能力、快照和对账端口；不得依赖具体 Adapter/Runtime |
| `qx-execution` | 新旧执行入口并存，部分逻辑依赖 Runtime | ExecutionEngine 的算法、路由、提交和结果编排 | 立即迁移旧入口；最终只保留一条执行入口，拆成 `service/algorithm/router/reconcile` 文件 |
| `qx-oms` | 已有独立订单状态机，职责较清楚 | Order lifecycle 和 idempotency | 保留独立 crate；补齐拒绝、Working、部分成交、撤改单、过期、Unknown 和非法迁移测试 |
| `qx-core::ledger` | 账簿代码量大且与 Kernel 关系紧 | Portfolio/Accounting/Ledger | 先不急于拆 crate；先定义 `PortfolioState`、`AccountingFact` 和 valuation 端口，之后再提取 |
| `qx-xingban` | 已有多种回测撮合模型 | Simulation/Backtest environment | 保留；与 EventEngine 通过同一事实和 VenuePort 接口接入，不能发展成第二套 OMS |
| `qx-adapter` | 供应商协议、行情、交易、私有流和 Runtime 适配并存 | Market/Execution/Reconcile adapters | 先按 adapter 类型拆文件；完成能力矩阵后再按供应商或协议拆 crate |
| `qx-storage` | 持久化、审计、快照、任务等能力较多 | EventStore/Snapshot/Outbox/Query/Lease | 先按存储语义拆模块；Postgres/SQLite/File 只是 backend，不应泄漏到核心协议 |
| `qx-api`、`qx-cli`、`qx-zhenlu` | 控制面与业务入口代码量较大 | Command/Query/Operator/Visualization | 保持只读副本原则；API/CLI 不得直接改 Ledger、OMS 或 Adapter 内部状态 |
| `qx-factor` | 因子能力与 finkit 有边界冲突风险 | ResearchBinding/compatibility only | 不再扩大为第二因子平台；保留迁移兼容层，新增能力优先进入 finkit |

## 4. 哪些必须扩展

### 4.1 EventEngine：从事件循环升级为可恢复的事实总线

当前 `qx-core::Engine` 已有 `(ts, priority, seq)` 的确定性排序和 follow-up event 能力，这是很好的 Kernel 基础；下一步必须补齐：

- `IngressEnvelope`：source、partition、source_seq、receive_ts、event_ts、schema_version；
- `Sequencer`：为多输入建立全局或分区内的稳定序列；
- `Backpressure`：bounded queue、队列水位、拒绝策略、降级策略；
- `EventStore`：append、cursor、snapshot、重放、校验和、schema migration；
- `AuditSink`：把每个命令、决策、回报和状态变更输出给控制面；
- `DeadLetter`/`Gap`：迟到、重复、缺口、解码失败不能静默丢失；
- `Reducer`：唯一状态写入口，禁止 API、Adapter、ExecutionService 直接修改核心状态；
- `ReplayVerifier`：重放后校验 EventLog、Ledger、OMS、Portfolio 的 digest。

事件、命令、查询、事实必须分开：

```text
Command       请求系统采取动作，可能被拒绝
Event/Fact    已发生且可重放的事实
Query         读取 StateReplica 或快照，不改变状态
Audit         面向审计/观察的事实投影，不是第二个真相源
```

### 4.2 ExecutionEngine：从“能下单”升级为“可对账的执行系统”

执行链必须固定为：

```text
StrategyDecision / PortfolioTarget
  → RiskDecision
  → OrderIntent
  → OMS register
  → SubmissionAttempt
  → Venue submit
  → Accepted / Rejected / Working / Unknown
  → PartialFill / Filled / CancelPending / Cancelled / Expired
  → Reconcile
  → EventEngine reduce
```

必须增加：

- `RiskDecision`：不仅返回布尔值，还要包含 rule、limit、observed、projected、reason、correlation；
- `ExecutionPolicy`：价格、数量、时限、被动/主动、重试、取消和路由策略；
- `ExecutionAlgorithm`：每个算法有独立状态、生命周期、父子订单关系和完成条件；
- `VenueCapability`：支持的订单类型、精度、最小名义金额、撤改单、私有流、限频和结算币种；
- `SubmissionAttempt`：外部副作用前固定 idempotency key，超时统一进入 Unknown；
- `ReconcileWorker`：REST open orders、fills、balances、private stream 和本地状态的差异处理；
- `Compensation`：多腿交易只实现补偿/回滚编排，不宣称跨 Venue 原子提交；
- `ExecutionFact`：适配器只产生标准事实，不能直接改 OMS、Ledger 或 EventLog。

### 4.3 Portfolio/Risk/Data 三个缺口必须显式化

这三个职责不能长期隐含在 Runtime、Ledger 或 Adapter 中：

| 能力 | 最小终态 | 关键验收 |
|---|---|---|
| DataEngine | 订阅、标准化、PIT、质量、缺口、重连、回补和统一时钟 | 同一数据输入在 Backtest/Paper/Live 产生同构事实；缺口、迟到和降级可审计 |
| Portfolio | 资产、持仓、现金、保证金、费用、估值、PnL、公司行动和结算 | 多资产、多币种、合约乘数、冻结资金和部分成交下账务重放一致 |
| RiskEngine | pre-trade、运行时限额、熔断、kill switch、风险暴露和可解释拒绝 | 风险拒绝发生在外部副作用之前；规则、输入和结果可重放、可查询、可审计 |

### 4.4 Control Plane 必须是只读副本加命令入口

对照 Barter 的 AuditStream/State Replica、NautilusTrader 的 Cache/MessageBus、LEAN 的 CLI 工作流和 Hummingbot 的 API/Dashboard，qianxing 的控制面应当统一为：

```text
Command API  → EngineCommand → EventEngine → AuditStream
Query API    ← StateReplica / Snapshot / Event cursor
Visualization ← Query API / AuditStream / RunManifest
```

禁止：

- WebSocket 直接持有 `&mut Ledger`；
- CLI 直接调用某个 Adapter 的下单函数绕过 Risk/OMS；
- 图表从数据库旁路拼装出与 EventLog 不一致的订单状态；
- 用监控缓存替代可重放的事实存储。

### 4.5 可视化不是第二条事实链

当前可视化方案必须以 `EventLog → ProjectionReducer → StateReplica/AuditStream → qx-api → Client` 为唯一读取链。`qx-api::ApiState`、实时 EventBus 和账户快照只能作为投影/传输实现，不能独立接受事实或重新生成订单、账簿和持仓状态。

投影协议必须同时携带 `schema_version`、`run_id`、`as_of`、`event_seq`、`cursor`、`state_hash` 和 lineage；游标不连续、快照过期或投影落后时必须进入 `resync_required`，不能把旧数据继续标记为实时。UI 的 Cancel、Close、Reconcile 等动作必须回到 `ControlCommand → Engine → committed fact`，图表和读模型没有交易副作用。

同时，`qx-core::Engine::run()` 需要 `max_events`、取消、deadline、最大因果深度和重复调度保护；否则 Handler 自调度可能让“队列排空”永远无法发生。WebSocket、Scheduler、插件拓扑和外部执行重试也必须分别具备关闭、上限或环检测条件。

## 5. 不应该现在拆分或扩展的部分

### 5.1 暂不拆成微服务

在以下条件满足前，不把 EventEngine、ExecutionEngine、Risk、OMS、Portfolio 拆成网络服务：

- 事件 schema、版本迁移和幂等语义已冻结；
- 单进程回放、恢复、对账和故障注入稳定；
- 已有明确的延迟、吞吐、故障隔离指标证明进程拆分有收益；
- 跨进程传输具备序列、确认、重试、死信和审计；
- 生产环境已经需要独立扩缩容或安全域隔离。

默认部署应是单节点、单写者、异步 I/O；未来再按账户、策略组、Venue 或风险域做节点隔离。

### 5.2 暂不新增第二套因子/指标系统

qianxing 只保留：

- `DatasetVersion`、`FeatureBinding`、`FactorBinding`、`StrategyDecision`；
- finkit 的版本、参数、输入窗口和产出校验；
- 研究结果到交易意图的 lineage。

不在 qianxing 新增均线、技术指标、因子表达式和研究 Notebook 运行时，避免与 finkit 形成双重真相。

### 5.3 暂不为了“看起来完整”增加大量连接器

连接器扩展必须以能力矩阵为准。一个 Venue 至少要说明：

```text
MarketData: quote / trade / bar / book / snapshot / gap-recovery
Execution: submit / cancel / amend / batch / order-types / precision
Private: order / fill / balance / position / reconnect
Reconcile: open-orders / fills / balances / cursor / manual-repair
Operations: rate-limit / clock-skew / credential-rotation / sandbox
```

只实现行情或只实现下单的适配器不能标记为“实盘支持”，只能标记为对应能力级别。

## 6. 拆分门禁与依赖规则

### 6.1 新 crate 门禁

只有同时满足以下条件，才创建新 crate：

1. 有清晰且唯一的职责，能用一句话定义所有权；
2. 至少存在两个实现或两个独立消费者，证明端口不是偶然抽象；
3. 新边界能消除依赖环或减少编译/发布耦合；
4. 事件、错误、feature 和 semver 策略可以独立维护；
5. 有独立单元测试、契约测试和迁移责任人；
6. 新 crate 不只是为了缩短一个文件，而是确实形成架构边界。

### 6.2 进程/节点门禁

进程拆分必须由证据驱动，至少提供：

- 单节点基线和拆分后延迟/吞吐对比；
- 重复投递、断线、超时、进程崩溃和恢复演练；
- 跨节点 EventLog/Event cursor/StateReplica 一致性证明；
- 失败时的所有权、重试和人工处置流程；
- 不会因为网络重试而重复下单的端到端幂等证明。

### 6.3 依赖方向

```text
domain/core
   ↑
application ports
   ↑
event/portfolio/risk/oms/execution
   ↑
runtime composition
   ↑
adapters, storage backends, api, cli, visualization
```

具体约束：

- `qx-application` 不依赖 `qx-runtime`、`qx-adapter` 或具体数据库；
- `qx-execution` 不再以 `LiveEventPipeline` 作为业务依赖；
- `qx-adapter` 只依赖稳定的 domain/application 协议，不反向依赖 API；
- `qx-storage` 提供端口实现，不让 SQLite/Postgres 类型进入 EventEngine；
- `qx-api`、`qx-cli`、可视化只发 Command 或读 Replica；
- `finkit` 是外部研究能力，qianxing 通过 Binding/协议调用，不复制实现。

## 7. 分阶段终极改造计划

### Phase A：边界收敛（现在开始）

- 冻结 Command/Event/Fact/Query/Envelope/schema/version/correlation/causation；
- 以 `qx-application` 为唯一端口层；
- 把 `qx-core`、`qx-runtime`、`qx-execution`、`qx-storage` 按职责拆文件；
- 标记并迁移所有重复 Pipeline/Execution 入口；
- 补齐 OMS 状态迁移表和非法序列属性测试。

**通过标准：** 任何订单都能回答“由哪个命令产生、经过哪些风险规则、在哪次提交尝试中产生了哪个 Venue 回报、最终由哪条事件归约”。

### Phase B：双引擎收敛

- 建立 `EngineBuilder`/`EngineNode`；
- 将 `qx-core::Engine` 收敛为 deterministic reducer/kernel；
- 将 `LiveEventPipeline` 变成 EventStore/Reducer 的 Runtime adapter；
- 将 `PortExecutionService` 提升为唯一执行边界；
- 增加 bounded ingress、AuditStream、StateReplica、Snapshot 和 dead-letter；
- 统一 Iterator、Replay、Paper、Live 的事实链。

**通过标准：** Backtest、Paper、Live 在相同事件输入和模型配置下，核心 EventLog/OMS/Portfolio digest 一致；真实 Venue 的不确定性只出现在 adapter 边界。

### Phase C：交易能力扩展

- 提取或重构 Portfolio/Accounting 与 RiskEngine；
- 增加 ExecutionAlgorithm、VenueCapability、ReconcileWorker；
- 完善多资产、多币种、合约乘数、保证金、费用、公司行动和结算；
- 补齐行情质量、订阅、缺口、重连和统一时钟；
- 形成 Paper/Sim/Live 的统一 VenuePort。

**通过标准：** 至少一个现货、一个永续/期货或其他带保证金语义的资产类别通过相同端到端测试；所有执行异常都有 Unknown/Reconcile 路径。

### Phase D：研究、控制面和插件产品化

- finkit 通过 `ResearchBinding` 提供版本化因子结果；
- 形成 RunSpec、DatasetVersion、ModelVersion、StrategyVersion、ExecutionPolicy 和 RunManifest；
- 控制面统一 Command/Query/Audit/StateReplica；
- 插件 manifest、能力声明、版本兼容、权限和签名校验；
- Rust/Python/其他语言只共享稳定协议，不共享可变内部状态。

**通过标准：** 任意一次回测或实盘运行都可以从 RunManifest 复现输入、策略、因子、风险、执行和图表数据。

### Phase E：性能与可用性收口

- 以单写者基线测量 ingress、reduce、append、audit、risk、submit、reconcile 延迟；
- 对热点状态使用 typed ID、索引和 cache-friendly layout；
- 评估 `qx-domain`、`qx-ledger`、`qx-event-engine` 是否达到独立 crate 门禁；
- 仅在有明确收益时做账户/策略组/Venue 级多节点；
- 通过 sandbox、故障注入、重启、灾备和发布回滚验收。

**通过标准：** 性能、恢复、审计和多语言兼容都有可重复的测试证据，而不是只依据 feature、配置或代码存在。

## 8. 最终判断

牵星需要继续拆分和扩展，但正确路线是：

```text
先拆职责，不先拆进程
先冻结协议，不先扩连接器
先统一 EventEngine/ExecutionEngine，不先堆功能
先显式化 Data/Portfolio/Risk/Reconcile，不重复建设 finkit
先让控制面只读可审计，再追求复杂可视化
```

终态不是“crate 越多越先进”，而是：

```text
一个事实入口
一个状态写者
一个订单生命周期
一个执行边界
一个对账恢复路径
一个可重放审计链
多个可替换的适配器、策略、执行算法和语言入口
```

在此基础上，qianxing 才能同时获得 Barter 的 Rust 性能与事件模型、NautilusTrader 的组件边界、LEAN 的完整量化工作流、Hummingbot 的连接器/执行扩展性，以及 vectorbt/finkit 的研究效率，而不牺牲自身的确定性和可审计性。
