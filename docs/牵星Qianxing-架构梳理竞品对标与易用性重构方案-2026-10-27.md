# 牵星 Qianxing：架构梳理、竞品对标与易用性重构方案

> 日期：2026-10-27  
> 基线：当前工作区可见的 qianxing 源码、Cargo workspace、Python/C++/Web 入口及 `docs/` 中现行方案。  
> 本文是面向决策和实施排序的收敛文档；订单精度、恢复、策略协议及每日代码验收仍以 [10 月 26 日架构与竞品深度复核总方案](牵星Qianxing-项目架构与GitHub竞品深度复核及优化重构总方案-2026-10-26.md) 为事实台账，以[工业化易用性收口指南](工业化易用性收口指南-V1.md)为当前操作手册。

## 1. 结论与架构决策

牵星的合理方向是**Rust 模块化单体 + 可审计的 worker 边界 + 稳定应用合同 + 多语言轻量门面**。现阶段不应改写成微服务，也不应继续横向增添独立产品能力。优先工作是降低用户必须理解的概念数、稳定跨边界事实，并让每种能力通过一条可发现、可复算、可解释的主路径完成。

目前仓库已有 29 个 Cargo workspace 成员，另有 Python SDK、C/C++ SDK、Rust SDK、HTTP/WebSocket API、Web Console 和 CLI。这个数量本身不是架构缺陷；真正的风险是领域状态所有权、wire schema、能力声明、示例和发布证据在多入口间重复表达，造成“代码能走通”与“用户知道怎么使用、该能力已被验证”之间的落差。

**重构原则：**

1. Rust 继续拥有订单、风险、撮合、账本、EventLog、Run 身份和确定性计算事实；Python/C++/CLI/API/UI 负责表达请求、适配与呈现。
2. 保持模块化单体。仅在部署隔离、依赖隔离或独立扩展带来可量化收益时增加进程/服务边界。
3. 把默认用户旅程收敛为“创建项目 → 检查 → 回测 → 诊断/比较 → 复核报告”。高级功能仍保留，但从新手主路径移出。
4. Research、Paper、Live 共用必要的领域合同和状态归约；数据可见性、撮合、外部副作用、凭证与验收等级必须清楚区分。
5. 任何“支持”都要明确范围：资产/产品、Venue、账户模式、订单操作、入口、依赖、平台和证据级别。未外部验收的能力不得显示为已验证实盘能力。
6. 因子计算继续以 finkit 集成为边界，不在 qianxing 内复制因子引擎；行情数据产品、策略商城、托管平台不属于本轮重构范围。

## 2. 项目定位与架构梳理

### 2.1 项目职责边界

Qianxing 是多资产量化交易引擎内核与研究/执行运行基础设施。它负责把数据、策略事件、交易规则、风险准入、订单生命周期、账本和可复核产物连接起来；可以通过多语言 SDK 被第三方调用，但不是行情供应商、完整资管产品或前端策略 IDE。

| 子域 | 主要职责 | 应避免的职责重复 |
|---|---|---|
| 领域和确定性内核 | `qx-core`、`qx-protocol`、`qx-spec`：身份、单位、事件、订单/账本及版本化合同 | SDK、CLI 或 Web 自行推导订单/账本事实 |
| 市场数据与仿真 | `qx-guanxing`、`qx-data`、`qx-provider`、`qx-datastruct`、`qx-xingban`：数据语义、质量、PIT、结构、撮合/费用/延迟模型 | 把 provider 接通等同于数据已认证；把向量化候选结果等同于事件仿真结果 |
| 风险、执行和对账 | `qx-risk`、`qx-zhenlu`、`qx-execution`、`qx-genglu`、`qx-adapter`：准入、OMS、外部端口、协议适配、回报和恢复 | Adapter 直接绕过风险/OMS 写交易所；超时后盲目重发 |
| 应用与运行 | `qx-app`、`qx-service`、`qx-runtime`、`qx-orchestrator`、`qx-scheduler`、`qx-storage`、`qx-control`：用例、装配、worker 生命周期、调度、持久化和权限审计 | CLI/API/Python 各自另造一份业务编排或运行状态 |
| 扩展和接入 | `qx-plugin`、`qx-strategy`、`qx-factor`、`qx-sdk`、`qx-python`、`cpp/`：策略、插件合同、因子边界和稳定语言入口 | 把静态组合注册误称为运行时热加载；把一种语言的继承形式强加给其它语言 |
| 用户界面 | `qx-cli`、`qx-api`、`web/console`、Python/C++ 公共接口 | UI 重算指标、命令和路由各自实现同一业务判断 |

### 2.2 核心调用链

**研究回测：** CLI/Python/HTTP → `qx-sdk` 或 `qx-app` 用例 → Schema/策略/数据/PIT 预检 → `qx-data`/`qx-provider` → `qx-strategy` 事件 → `qx-xingban` 仿真 → `qx-core` 事件与账本 → `qx-app` 产物和核验 reader → CLI/API/Python/Web 报告。

**Paper/Live 执行：** 市场/账户/规则事实 → 策略输出 `OrderIntent` → 精度与 capability 预检 → `qx-zhenlu` 风控/资金预留 → `qx-execution` OMS → `qx-service` 装配的窄 Venue 端口 → `qx-adapter`/交易所 → 回报归约、EventLog、账本 → 对账与重启恢复 → 策略状态更新。

**API/Console：** Web/SDK 请求 → `qx-api` 身份、权限、限流和协议适配 → 同一应用用例或 `ControlPlane` → 领域/服务 → 版本化 DTO 与有界报告投影。读、控制和外部副作用必须使用不同权限范围；浏览器不得持有交易所密钥。

这些链路已经有大量实现和合同测试，重构重点是把它们做成所有入口共同遵循的应用路径，并持续检验事实归属，而不是另造一套调用体系。

**不做竞品功能数量竞赛。** 吸收共同优点：单一核心事实源、可组合 adapter、统一 run identity、项目级新手入口、策略诊断和可复现示例。保持牵星差异：精确多资产交易事实、A 股规则/PIT、订单治理、恢复/对账、跨语言一致性与证据分级。

## 4. 当前设计中值得保留的部分

1. `qx-app` 为 CLI、API、Python 入口共享用例，`qx-sdk` 对第三方提供稳定 Rust 门面；应用层依赖方向已有静态架构约束。
2. 执行链有 `ExchangeGateway` 组合与账户/Venue 路由概念，执行能力与端口边界比一个单体 broker trait 更易演进。
3. EventLog、Run identity、schema version、报告 reader、重放验证和能力证据为恢复及复核打下基础。
4. Python wheel、Rust CLI、C/C++ SDK、HTTP/WebSocket 和 Web Console 让内核有多种宿主；策略类是语言内便利层，不应成为统一 ABI。
5. `quickstart`、`init`、`doctor`、`config explain`、结构化 JSON 诊断、样例运行时与 `README.qianxing.md` 已构成首次使用的基础。应把它们打磨成首选工作流，避免再增加另一套项目初始化器。

## 5. 架构与开发细节问题

| 优先级 | 观察到的问题 | 用户/维护影响 | 改进决策 |
|---|---|---|---|
| P0 | 一份领域事实须通过 Rust、Schema、Python、C ABI/C++、CLI/API DTO、Web 展示多次映射 | 单位、默认值、错误、事件时序和字段版本发生漂移时，用户看到的结果可能不一致 | 对订单、数量/金额、instrument rules、策略生命周期、Run identity、能力矩阵维护 owner+consumer 矩阵；Schema/DTO 有单一生成或双向对拍机制 |
| P0 | 交易和研究能力覆盖面大，`implemented`/本地合同通过/包装可用/外部验收容易被误读为同一状态 | 用户可能将本地回测、Paper 或 fake-provider 验收理解为真实账户可交易 | 所有连接器能力带 `venue × product × account mode × operation × order shape` scope 和证据级别；`doctor/live-check` 逐项报告缺少的权限、凭据或外部验收 |
| P1 | CLI 有许多低层命令，虽已有 `quickstart` 和模板，新手仍可能从 `help` 中面对领域术语和能力矩阵 | 需要记住命令顺序、输入路径、产物位置，首次失败难定位 | `quickstart` 作为首屏路径；按场景引导 Backtest/Research/Paper/Live，复用现有子命令；错误提供字段路径、原因、修正示例和下一条命令 |
| P1 | Python API 面向高级组合能力丰富，但顶层使用者需了解多类 Spec、精确金额编码、provider、manifest、local/remote 约束 | 强大的能力可用，但“最小代码”与“完整控制”之间跨度大 | 提供稳定的 `ResearchProject`/`research(...)` 高层 facade 与 typed builder；JSON/低层 Spec 作为高级接口保留；不得在 facade 复制撮合/风险计算 |
| P1 | 报告入口、产物格式和运行类型持续增长，CLI/API/Web/Python 对 report 的能力可能不完全同构 | 用户常需知道运行目录和文件名；报告含义/分页/可视化不一致 | `RunHandle` 终态统一给出 artifact index 与下一步；单一 reader 产出 versioned report sections；展示层仅渲染且支持有界分页/下载/复算 |
| P1 | 多账户、多 Venue 与多腿运行的领域复杂度直接暴露给初次使用者 | 容易把组合 Saga 理解成跨所原子事务，也不易定位资金/腿失败 | 高层向导展示每腿账户、风险预算、部分成交、补偿和人工介入状态；高级用例必须输出逐腿身份和恢复说明 |
| P2 | crate 细分与大热点并存：workspace 29 成员；`qx-api`、`qx-zhenlu`、`qx-storage`、`qx-execution` 仍有显著大入口文件 | 新 crate 增加接口/构建认知，巨型模块又令日常修改困难 | 先在现有 crate 内按领域 owner、用例、transport、reader、renderer 拆模块；新 crate 要有独立依赖/发布/所有权收益，不按行数机械拆分 |
| P2 | 命令、路由、Schema、能力注册、SDK 文档和示例需要持续同步 | 更新容易只改一层，留下“文档能看、调用不存在”或功能存在但发现不了 | 把 CLI/API/Schema/能力/策略 hook/包导出/示例关联成可生成的目录或双向一致性门禁；错误报告给出具体缺失登记项 |
| P2 | 数据量、L2、参数搜索、报告和多 worker 的性能成本并不等同于微基准数字 | 用户难选运行环境，也无法判断优先优化点 | 发布可重复的 workload 档位和 RSS/时延/吞吐/磁盘画像；只对 profile 的真实热点做 Rust 优化 |

### 5.1 需要明确的非目标

- 不把静态 plugin registry/manifest 组合描述为任意时点热插拔；真正的动态加载必须另立兼容、安全、签名与卸载合同。
- 不增加一套新的 GUI/桌面 IDE 来解决 CLI 学习成本；先让 CLI/Python/现有 Web Console 分享场景模型和 run artifacts。
- 不把每一种语言都做成相同继承 API；各语言 facade 可自然不同，底层事件合同一致即可。
- 不以向量化预筛替代事件回测，不把模拟撮合证据当成交易所订单验收。
- 不为满足“多资产”而无限增添抽象；unsupported instrument/order shape 应可说明、可查询、可 fail-closed。

## 6. 目标用户旅程与接口收敛

### 6.1 新手：本地研究

```text
安装 qx-cli 或 Python wheel
  → quickstart/init 生成独立项目和示例数据
  → doctor 检查输入、依赖和策略
  → backtest 生成可复算 Run
  → diagnose 检查未来数据/预热/数据质量
  → report / compare 展示事实和差异
```

每一步都应在输出中给：运行身份、输入摘要、产物目录、结果等级、失败字段、下一步操作。默认 quickstart 控制在几分钟内，不要求先配置交易所凭据、数据库、远程沙箱或 Web 服务。

### 6.2 研究者：搜索和样本外评估

```text
已有策略与数据 → typed ResearchSpec → 预算约束搜索 → 候选事件引擎复算
→ rolling/walk-forward OOS → 成本/敏感度比较 → 可携带证据包
```

所有候选记录算法/版本、seed、预算、失败淘汰原因、fold、数据与策略指纹。HTML/Web 报告是 Run 的 reader，不产生新的统计语义。`best` 必须标明是样本内排序还是样本外证据。

### 6.3 部署者：Paper 到 Live

```text
部署 profile → doctor/runtime-check → capability scope 预检
→ Paper 订单状态/恢复验证 → live-check → 小额外部验收
→ 持续状态/对账/审计
```

凭证、权限和真实请求必须只在服务端边界使用。检查结果逐项给出 `unconfigured / unavailable / configured / code-tested / sandbox-tested / production-approved` 中对应的级别与证据。任何不支持或未知状态都在送网前停止，并给出可执行的修正项。

### 6.4 统一入口的分层规则

| 使用者 | 首选入口 | 暴露细节 | 必须共用的事实 |
|---|---|---|---|
| 第一次使用者 | `qx-cli quickstart` / Python 一屏示例 | 最少配置、示例数据、默认报告 | Rust 用例、RunSpec、结果校验 |
| 日常研究 | `qx-cli research` 或 Python typed facade | 数据和策略、目标、预算、fold | qx-app 搜索/仿真/reader |
| 高级集成者 | `qx-sdk`、typed `qx-app`/API contracts | Provider、异步句柄、Schema、扩展端口 | 领域状态机与错误合同 |
| 运维者 | `doctor`、`runtime-check`、`live-check`、Web Console | 能力 scope、worker、端口业务健康、证据阶段 | 同一 capability catalog 与 runtime state |

若新增 `research` 命令，应只是已有用例的场景编排与展示；不得另写算法。Python 高阶 facade 也应调用相同的 versioned Spec/use case。

## 7. 重构路线图与开发验收

| 阶段 | 工作包 | 具体开发动作 | 验收标准 |
|---|---|---|---|
| R0（P0）事实合同收口 | Order/Instrument/Run/Strategy/Capability | 建立 owner、schema 版本、跨语言字段、错误和 event order 矩阵；逐入口核对 caller 到 reader；未知能力失败关闭 | 一份 golden input 在 Rust/Python/C++/HTTP 产生同一规范化意图、身份和核心结果；不支持场景错误可定位 |
| R1（P1）首次使用主路径 | CLI/Python onboarding | 打磨 `quickstart` 的安装、生成、检查、运行、报告和失败恢复文案；Python 提供最小示例与 typed builder；对相对路径、Windows、空数据/非法配置给出一致诊断 | 从仓库外干净目录安装后，复制一条流程得到 Run 与报告；示例不读取仓库私有测试文件、不需要密钥 |
| R2（P1）研究闭环 | StrategySpec、diagnostics、experiment、report | 打通策略预检、baseline、lookahead/warmup、限额搜索、候选复算、OOS、compare、bundle | 单入口能从策略/数据到可复算报告；对没有 OOS 的运行明确标注，输入更改可解释身份变化 |
| R3（P1）Run 与报告一致 | `qx-app` reader、CLI/Python/API/Web | 统一 artifact index、分页游标、报告 section、运行状态与取消结果；展示层不得重算交易事实 | 同一 Run 在 CLI/SDK/API/Web 的核心字段相等；大报告受限分页且退出/中断可查 |
| R4（P0/P1）交易验收体验 | Gateway、doctor/live-check、service | 生成 operation scope 清单；区分配置/进程/业务/外部证据；解释余额、规则、凭证、订单状态未满足的项 | 缺少 capability/精度/权限在送网前拒绝；未知 submit 状态只查询/对账，不盲重发；证据状态可导出 |
| R5（P2）结构与目录治理 | 大模块/目录/Schema | 按行为 owner 分割内部模块；机器生成或校验命令、路由、Schema、SDK exports、capability 和示例索引 | 依赖图无反向边；生成可重复；新增能力若漏任一登记会被单项门禁指出 |
| R6（P2）性能与发行可用性 | Rust 热路径、wheel、CLI、C++ SDK | 建立 workload profile；干净环境安装/最短样例；发布说明声明 OS/ABI/功能/限制 | 同输入结果不变；性能报告包含机器和输入；平台安装、导入、示例产物及 capability 文档一致 |

依赖顺序为 **R0 → R4 的交易安全子集 → R1 → R2/R3 → R5/R6**。R1/R2 的便利层不能掩盖 R0 的语义差异；交易外部验收的前提是 R0 和 R4 的写操作边界可靠。任何阶段都先在既有 crate 内做最小垂直切片，保持用户 API 向后兼容或明确升级版本。

### 7.1 重点代码边界

- `crates/qx-app/`：继续负责 use case、输入校验、报告事实和错误分类；避免把网络、UI 或命令解析塞进应用层。
- `crates/qx-sdk/`：给嵌入者稳定、可发现的 Rust facade；避免公开大量内部类型使 SDK 与 workspace 结构锁死。
- `crates/qx-cli/src/cli_args.rs`、`cli.rs`、各命令 handler：参数语法与分发单源；场景命令不得复制领域用例。
- `python/qianxing/`：稳定高层 typed request/result 和用户指南；本地/远端限制作为对象级能力与错误公开。
- `crates/qx-api/`、`web/console/`：API 做授权/有界传输/适配，前端做查询与展示，不在浏览器维护另一份业务状态机。
- `crates/qx-service/`、`qx-runtime/`、`qx-execution/`、`qx-adapter/`：业务事实、生命周期、订单状态与供应商协议保持单向依赖；按账户、Venue 和 operation 做诊断。
- 大文件拆分按责任和调用者变更范围进行；一次拆分一次行为对拍，不把纯搬移包装为业务完成。

## 8. 三轮审查与停止条件

### 第一轮：架构与依赖

逐项检查 crate owner、反向依赖、跨层调用、Schema 权属、配置来源、错误转换和生成目录。发现两处 owner 或同一规则在 facade 重复实现时，先确认唯一事实来源，再进入下一轮。

### 第二轮：核心链路贯通

分别从最短 Bar 回测、研究搜索、Paper 下单、Live 预检追踪调用者 → app use case → domain → artifact/event reader → CLI/API/Python/Web。每个边界标记输入、输出、持久化身份、失败/取消/恢复行为和证据等级；不能用一个“端到端测试通过”替代各边界的说明。

### 第三轮：易用性与发行

在仓库外/干净环境按新手和操作者两类旅程执行：安装、quickstart、修改策略、错误修复、查看比较报告、Paper、Live preflight、跨语言示例。检查指令是否可复制、路径是否独立、无凭据时能否完成离线研究、错误是否给下一步、包内文件与文档是否一致。

每轮修正所有已确认的阻断项后再进入下一轮。架构审查不能声称“已证明无所有潜在问题”；应以覆盖的入口/合同/异常矩阵和未验证项作为可审计结论。Live 发布门在真实 Venue 沙盒、副作用后故障恢复和账户/产品/订单类型 scope 验收之前保持关闭。

## 11. 本地策略运行核心补齐记录（2026-10-28）

本轮从 Python `BaseStrategy` 的多标的运行链修复一个会改变订单目标的上下文错误：`market_bars` 中非主标的 Bar 回调原先收到主标的 `context.instrument`，预热完成回调也有相同问题。现在这两类回调均以当前 Bar 的标的构造上下文；行情数据门户仍按当前事件时间提供可见历史，意图校验与风险/OMS 链保持原有统一入口。

| 核心路径 | 修正 | 影响与边界 |
|---|---|---|
| 多标的 Bar 回调 | `BaseStrategyProcessAdapter._dispatch_bars` 传入当前事件标的 | `context.instrument`、由 context 默认值构造的订单意图与当前 Bar 对齐；显式指定标的的策略不受影响。 |
| 多标的预热回调 | `_complete_warmup` 以正在完成预热的标的创建上下文 | `on_warmup_complete` 可按每个标的分别初始化指标/状态，避免将主标的身份误用于其他标的。 |
| 更新/恢复/其他市场回调 | 维持现有账户/venue、EventLog cursor、warmup 状态和策略 checkpoint 机制 | 本次没有改变 wire schema、checkpoint 版本、事件顺序或执行端授权边界。 |

本轮做了代码静态复核；未运行测试。跨宿主 hook 完整同构、checkpoint 与外部订单命令的全局事务一致性、第三方进程完整符合性仍按总方案的未完成项继续跟踪。
