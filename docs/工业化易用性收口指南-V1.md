# 牵星工业化易用性收口指南 V1

本指南是当前代码的统一使用入口。推荐先完成回测，再完成 Paper 主链路验收，最后在部署机执行实盘前置检查。所有入口都复用同一份运行时配置、策略契约、风险门禁、订单队列和 Ledger，不会因为换成快捷命令而绕过核心链路。Paper、CCXT 和 Binance 通过同一应用层执行事实契约校验订单归属、成交数量/价格和回报类型；异常回报会停止自动推进并转入对账。

## 1. 最短可用路径

本指南全文的命令都写成源码仓库里的 `cargo run -p qx-cli -- …`。按 README「安装」A 那条
（`cargo install --path crates/qx-cli --locked`）装过的人，把前缀换成 `qx-cli ` 即可，参数与行为一致：
`init` / `doctor` / `backtest` / `report` / `status` 在仓库外的任意目录都实测过退出码 0，且 `init` 生成的
项目自包含（配置、样例 BarFrame、品种规格、调度文件与 `README.qianxing.md` 全在项目目录内，不引用 `deploy/`）。
唯一区别是安装后的 binary 没有 `--version` 旗标 —— 它按"未知参数"fail closed 以退出码 2 拒掉并打印入口清单，
所以确认装好的办法是跑 `qx-cli help` 看入口摘要（首行 `牵星 Qianxing — 分级校准，量天定位`，末行指向本文）。

在仓库根目录执行：

```powershell
# 生成本地配置；已有文件默认拒绝覆盖
cargo run -p qx-cli -- init qianxing.runtime.json
# 也可以一步生成绑定 MACD 的可回测项目：
cargo run -p qx-cli -- init qianxing.runtime.json --strategy macd

# 按场景初始化自包含项目：paper / ccxt / ashare / multi-venue / backtest
cargo run -p qx-cli -- init qianxing.runtime.ccxt.json --profile ccxt
cargo run -p qx-cli -- init qianxing.runtime.ashare.json --profile ashare

# 在回测前一次检查配置、路径和策略输入；不会连接交易所或发送订单
cargo run -p qx-cli -- doctor qianxing.runtime.json
# CI/部署脚本使用稳定 JSON 诊断；stdout 只包含 JSON，不读取或输出密钥
cargo run -p qx-cli -- doctor qianxing.runtime.json --json

# 查看最终生效配置；--json 输出可供脚本消费的配置，不包含密钥内容
cargo run -p qx-cli -- config explain qianxing.runtime.json
cargo run -p qx-cli -- config explain qianxing.runtime.json --json
cargo run -p qx-cli -- config fingerprint qianxing.runtime.json
# CI/部署平台使用结构化运行时健康结果；失败时仍返回非零退出码
cargo run -p qx-cli -- runtime-check qianxing.runtime.json --json
cargo run -p qx-cli -- run runtime-check qianxing.runtime.json --json
# 实盘发布前检查也支持同一结构化输出（仍不连接交易所、不发送订单）
cargo run -p qx-cli -- live-check deploy/qianxing.runtime.production.example.json --json
cargo run -p qx-cli -- run live-check deploy/qianxing.runtime.production.example.json --json
# 常用安全入口也可以统一调用：
cargo run -p qx-cli -- backtest
cargo run -p qx-cli -- run paper
# 查看最新回测摘要；也可以把参数换成具体的 *.summary.json
cargo run -p qx-cli -- report qianxing.runtime.json
cargo run -p qx-cli -- report qianxing.runtime.json --json

# 使用默认策略回测配置和 BarFrame
cargo run -p qx-cli -- backtest

# 验收 Scheduler → Strategy → Paper Execution → Ledger
cargo run -p qx-cli -- paper-check deploy/qianxing.runtime.paper-strategy.example.json
```

`init` 会同时生成运行时配置、调度样例、BarFrame、DatasetBundle、品种规格、Paper 目标和
`README.qianxing.md`，所有引用都位于运行时配置同一项目目录下；不包含交易凭据。使用
`--strategy <name>` 时会直接绑定内置策略和样例数据。需要覆盖时必须显式使用 `--force`：

`--profile` 会选择与场景匹配的运行时模板，并自动把模板中的 `deploy/...` 引用改写为
项目内相对路径、复制对应 endpoint/spec/公司行为/日历文件。`ccxt`、`multi-venue` profile
只生成公共连接配置和凭据引用，不会读取密钥或发送订单；切换 sandbox 前仍需配置环境变量并完成
交易所验收。

`run backtest`、`run paper`、`run doctor` 和 `run live-check` 只是统一入口别名，仍复用各自的
安全门禁；其中 `run paper` 只执行本地 Paper 验收，不会连接真实交易所或发送订单。
`doctor --json` 与 `run doctor --json` 返回同一份诊断结构，包含 `ok`、`checks`、`warnings`、
`failures`、`config_fingerprint`、`network_accessed` 和 `orders_sent`，适合 CI 门禁和部署平台采集。
其中拓扑那一项的名字是 `runtime_supervisor_build`，通过时打印
`监督器可构建，启用 worker=<N>（未启动，不代表运行健康）`：`doctor` 只做静态装配判定，一个 worker
都没启动，因此它不能、也不被当作"运行健康"的证据；运行健康看 `runtime-check`。

```powershell
cargo run -p qx-cli -- init qianxing.runtime.json --force
```

## 2. 四类入口的职责

下表只标注**副作用边界**（会不会连交易所、会不会下真实订单）。入口的完整清单与参数以
`cargo run -p qx-cli -- help` 为唯一来源：那份文本由 clap 的 `Command` 定义派生，与 `cli.rs`
的派发分支一一对应（`tools/check_architecture.py` 校验这条不变量），因此它不可能与实现漂移；
未识别的命令或未知参数会打印同一份摘要并以退出码 2 失败。

| 入口 | 作用 | 是否连接交易所 | 是否可能下真实订单 |
|---|---|---:|---:|
| `backtest` | 跨语言策略进入统一 Rust 回测撮合 | 否 | 否 |
| `paper-check` | 验收调度、策略、Paper 执行、Ledger 主链路 | 否 | 否 |
| `doctor` | 面向用户的一次性配置、路径、策略和拓扑诊断 | 否 | 否 |
| `config explain` | 输出有效配置摘要或 JSON 配置 | 否 | 否 |
| `config validate` | 校验配置和本地文件引用 | 否 | 否 |
| `report` | 查看最新或指定回测摘要与结果哈希 | 否 | 否 |
| `runtime-check` | 检查拓扑、配置解析、运行时健康与指纹 | 否 | 否 |
| `live-check` | 实盘启动前静态门禁，检查证书、凭据来源、规格和研究快照 | 否 | 否 |

`live-check` 只是发布前置检查，不等于真实账户验收，也不会替代交易所 sandbox、网络连通性、用户流和对账验收。真实运行仍需显式启动对应 worker。

`runtime-check --json` 与 `run runtime-check --json` 输出统一的 `schema_version`、配置指纹、
健康快照、warnings/failures、`ok`、`network_accessed` 和 `orders_sent` 字段；该入口不连接交易所，
不会因为健康快照处于启动前的 `starting` 状态而误报失败，但会对配置引用错误和 `Failed` 服务返回非零退出码。

`live-check --json` 与 `run live-check --json` 使用相同的机器可读安全边界，额外返回逐项
环境、TLS、凭据、产品规格、风险限额和研究快照检查；检查失败时输出完整 JSON 后返回非零退出码。

CCXT 私有 worker 的密钥可以直接配置在 `endpoint` 指向的 CCXT JSON 文件中：
`credential_env.api_key` 和 `credential_env.secret` 填环境变量名，启动时由公共 CCXT
worker 读取环境变量；RuntimeConfig 不需要重复填写密钥引用。`doctor` 会校验交易所绑定并提示
凭据是否可用，`live-check` 会把该来源纳入生产凭据门禁，但不会输出密钥内容。

A 股 `capital_change` 公司行为必须提供 `issuer_total_shares_raw`（绝对总股本），
可选 `issuer_free_float_shares_raw`（绝对流通股本）；回测报告会保留生效日快照，
但不会把发行人股本变化伪造成账户持仓或现金流水。缺少绝对股本时，配置校验会直接失败。

本地只读状态查看：

```powershell
cargo run -p qx-cli -- status qianxing.runtime.json
cargo run -p qx-cli -- status qianxing.runtime.json --json
```

`status` 展示当前配置、启用 Worker、已保存回测摘要和安全状态；不会连接交易所、读取密钥或发送订单。

运行配置中的 `storage.consistency` 必须与后端一致：单机 Files/SQLite 使用
`local_durable`；PostgreSQL 使用 `transactional`；启用 NATS Outbox Relay 时使用
`distributed_outbox`。该字段会进入配置指纹，并在 `runtime-check`/`status` 的 JSON 中输出，
避免把本地恢复能力误认为跨进程事务能力。

## 3. 回测与 Paper

### 3.1 内置策略

当前提供 17 个不依赖外部 Python 环境的内置 Bar 策略：

```powershell
cargo run -p qx-cli -- builtin-strategies
```

也可以直接从模板生成策略配置并回测：

```powershell
cargo run -p qx-cli -- strategy init macd qianxing.strategy.macd.json
cargo run -p qx-cli -- strategy backtest qianxing.strategy.macd.json deploy/qianxing.bar-frame.example.json
```

`strategy init` 会校验策略名称、生成唯一策略 ID、绑定默认 BarFrame，并在默认数据路径下绑定示例 Bundle；
如果传入自定义 BarFrame，则不会错误绑定不匹配的示例 Bundle。

DatasetBundle 中新增的非行情组件通过 `strategy.dataset_component_paths` 显式绑定，例如
`suspensions`、`limit_rules`、`factors`。组件必须是数组或包含 `rows`/`data` 数组，回测启动时会做
递归 JSON 规范化、fingerprint 和行数校验；没有对应绑定的组件会 fail-closed。`corporate_actions`、
`calendar` 继续兼容 `ashare_actions_path`、`ashare_calendar_path`。

如果组件由 Arrow 生产者输出，可将 Bundle 组件的 `format` 设为 `arrow`，并把
`dataset_component_paths.<kind>` 指向 Arrow Dataset manifest（示例：
`deploy/qianxing.dataset-component.arrow.example.json`）。manifest 必须声明 `kind`、数据指纹、
行数、时间范围和字段 schema；回测会在启动前校验这些信息。Arrow IPC/C Data Interface 的实际读取
仍由数据提供方负责，Qianxing 不会把未验证的二进制文件静默当成 JSON。

策略名单不在本文重复维护：`builtin-strategies` 会打印每个内置策略的中文名与**它被哪条回测链接受**。
当前实测 17 个：13 个单标的策略（`sma_cross`、`ema_cross`、`macd`、`rsi`、`bollinger`、
`donchian_breakout`、`momentum`、`mean_reversion`、`grid`、`atr_trend`、`keltner_trend`、
`vwap_reversion`、`volatility_breakout`）可走 `backtest builtin` / `backtest ccxt-builtin` /
`backtest book`；4 个套利 kind（`pairs_arbitrage`、`basis_arbitrage`、`cross_venue_arbitrage`、
`spot_futures_arbitrage`）只被 `backtest multi-builtin` 接受，`book` 会明确拒绝它们。
单标的策略统一输出目标仓位差额，仍然经过 RiskGate、OMS 和撮合引擎。

直接回测：

```powershell
cargo run --release -p qx-cli -- backtest builtin `
  macd deploy/qianxing.bar-frame.example.json `
  deploy/qianxing.binance.spot.spec.json 1
```

`quantity` 是策略目标仓位的整数单位；合约策略必须提供对应的 market spec。内置策略也可以写入 runtime 配置，并通过统一策略回测入口执行：

```powershell
cargo run --release -p qx-cli -- backtest `
  deploy/qianxing.runtime.builtin-strategy.example.json `
  deploy/qianxing.bar-frame.example.json
```

运行时配置使用 `builtin_strategy` 选择策略，使用 `bars_snapshot_path` 提供 K 线窗口。实时模式额外设置 `live_enabled=true`、`live_timeframe`、`live_history_limit` 和 `live_closed_only=true`；CCXT MarketData worker 会持续维护闭合 BarFrame，Strategy worker 以快照摘要作为幂等键触发策略任务，输出仍进入原有 RiskGate、OMS 和 Execution 链路。配置校验会 fail-closed 检查：主标的和套利对冲腿必须各有包含对应 InstrumentId 的启用 MarketData worker，且主执行账户/交易所必须有匹配的 Execution worker，避免服务“启动成功但没有行情或执行端”。策略还会拒绝未来 Bar 和超过新鲜度窗口的 Bar；`live_max_staleness_ms` 可显式配置，省略时默认允许最近 3 个周期，行情停滞时不会继续生成订单。实时 Job 在执行前和生成订单前都会再次校验 Bar digest，旧 Job 或执行期间发生行情切换时只确认并跳过，不会用错误的 Bar 生成订单。`pairs_arbitrage`、`cross_venue_arbitrage`、`basis_arbitrage` 与 `spot_futures_arbitrage` 需要 `builtin_reference_instrument` 和 `builtin_reference_bars_snapshot_path`；多交易所时两条腿由各自的 CCXT REST worker 更新。

如果不需要保留中间 BarFrame，可直接从公共 CCXT 拉取并回测：

```powershell
cargo run --release -p qx-cli -- backtest ccxt-builtin `
  deploy/qianxing.ccxt.exchange.example.json `
  macd BTC/USDT.OKX 1704067200000 1706745600000 1h `
  deploy/qianxing.ccxt.okx.perpetual.spec.json 1
```

该命令只在获取阶段访问 CCXT，撮合和指标计算仍在本地 Rust 引擎完成；需要长期复现、审计或多人共享时，优先使用三步式快照流程保存 BarFrame。

指定输入文件时：

```powershell
cargo run --release -p qx-cli -- backtest `
  deploy/qianxing.runtime.strategy-backtest.example.json `
  deploy/qianxing.bar-frame.example.json `
  deploy/qianxing.binance.spot.spec.json
```

该命令支持现有 Rust、Python、C++ JSONL 策略契约，以及 `framed_json`、`shared_memory_json` 和 `shared_memory_columnar` 传输模式。成交、费用、保证金、持仓和结果哈希仍由统一回测引擎处理。

Bar 回测链（`backtest` / `strategy backtest` / `backtest builtin` / `backtest ccxt-builtin`，
以及按同一装配跑的 `fast-backtest` 每个 job）会在各自运行时 `storage.data_dir/runs` 下原子保存
三类结果文件；`backtest book` 同样三类，只是落在它的 `--root` 下：

- `*.summary.json`：策略、数据、模型、假设、收益和回放摘要；
- `*.equity.csv`：时间、权益和持仓的定点 raw 曲线；
- `*.fills.csv`：成交、费用、账户、策略和 Venue 归属。

文件与同一回测的 `*.run.json` 使用相同前缀，重复运行必须得到相同内容；内容冲突会拒绝覆盖。
`backtest multi-builtin` 不在这一族里：它不产 RunManifest 与上面三类文件，只在 `--root` 点名时写
1 份 `runs/multi-leg-*.spread-attribution.json`，组级归因数字无论落不落盘都照常印在 stdout。

多标的、多币种和多参数研究可使用并行批量入口：

```powershell
cargo run --release -p qx-cli -- fast-backtest `
  deploy/qianxing.fast-backtest.example.json
```

每个 `jobs[]` 使用独立 runtime、BarFrame 和可选 market spec，账户与结果相互隔离；多个策略实例仍可通过同一 runtime 的 `strategies[]` 配置。

### 3.2 回测入口族与配置落点

回测不是一个入口，而是一族；它们共用 `qx-xingban` 撮合内核与同一条事实流，**区别只在输入形状和
哪些策略段在这条链上有落点**。总原则：**这条链接受不了的策略段一律整轮拒绝，绝不静默忽略**
（V11 Q58–Q65 的收口口径）。

| 入口 | 输入 | 有落点的策略段 | 明确无落点（配了即失败） |
|---|---|---|---|
| `backtest [runtime] [bar-frame] [market-spec]` | 跨语言策略（Rust / Python / C++ JSONL，含 `framed_json` / `shared_memory_json` / `shared_memory_columnar`） | 风控规则、撮合模型、成本规则、market spec、A 股段 | — |
| `strategy backtest <runtime> <bar-frame> [market-spec]` | `strategy init` 生成的内置策略配置 | 同上，另加 `strategy.builtin_*` 四个信号参数（口径印在 `[Strategy · Signal]` 行） | — |
| `backtest builtin <strategy> <bar-frame> [market-spec] [quantity] [--config]` | 单个内置策略 + BarFrame | 风控/撮合/成本/market spec/A 股段 + `builtin_fast_window`/`builtin_slow_window`/`builtin_period`/`builtin_threshold_bps` | 非法取值整轮失败；下单数量只认命令行 `quantity` |
| `backtest multi-builtin <strategy> <primary> <reference> [primary-spec] [reference-spec] [quantity] [--funding-bps] [--quantity] [--root] [--config]` | 两条对齐的 BarFrame，双腿独立账户 | 信号参数（两条腿共用同一份信号，印在 `[Multi · Signal]` 行） | **A 股段**（一份策略段套不住两条腿各自的交易制度）；**`strategy.initial_cash_raw`**（两条腿的本金各按本腿行情定资，一份单账户数字定不了它，配了即 exit 2）；`--funding-bps` 非零时两条腿都必须带 spec |
| `backtest book --fill-tier <l1\|l2> --root <dir> <strategy> <depth-frame> [market-spec] [quantity] [--fee-bps] [--latency-snapshots] [--market-impact-bps] [--config]` | 深度档 frame：`l1` 走 Tick 内核（每档 snapshot 只许一档，多一档即拒）、`l2` 走订单簿内核并按 `DataTier::L2L3` 吃掉帧里带的全部深度，因此没有 `l3` 旗标（产物写明实际内核） | 信号参数（`[Depth · Signal]` 行）、`--fee-bps`（优先级：显式旗标 > `cost_rules_path` 的 `taker_bp` > 内核默认吃单费率） | **A 股段**（盘口引擎没有 T+1/整手/涨跌停的挂钩点）；**`strategy.fill_model`**（这条链的撮合口径是 `--fill-tier` + 两个内核参数那份描述子，没有 `FillModel` 落点，配了即整轮拒绝，V11 R11）；成本规则里的**非零延迟**（深度档无落点，直接报错） |
| `backtest ccxt-builtin <ccxt-config> <strategy> <instrument> <start_ms> <end_ms> [timeframe] [market-spec] [quantity] [--config]` | 一次完成 CCXT 取数 + 内置策略回测 | 取数后交给 `backtest builtin`，因此其口径全部相同 | — |
| `fast-backtest <manifest.json>` | 多个独立回测任务并行 | 每个 `jobs[]` 各自绑定 runtime/BarFrame/可选 spec | — |

保证金与资金费**只向 market spec 声明为衍生品的腿计提**；缺 spec 时不再按 0 记账，而是先拒再跑
（V11 Q58/Q59）。衍生品直连不存在：`fapi`/`dapi` 在 `qx-adapter` 零命中，衍生品只经 CCXT（V11 E5）。

回测压在多少钱上是一格可声明的配置：`strategy.initial_cash_raw` 是**定点整数**（1e9 刻度，
100,000 元写作 `100000000000000`），它同时是收益率的分母与风控门看到的可用现金。三条单腿链
（`strategy backtest` / `backtest builtin` / `backtest book`）在结果行之前各印一行 `[X · Account]`，
写明用了多少、从哪来；落摘要的链把同样的两格写进 `summary.account`。`0` 与负数当场报错而不是回落
默认，`backtest multi-builtin` 则整轮**拒收**那一格 —— 两条腿的本金由本腿行情各自定资
（`2 × quantity × 本腿最高价 + 费用余量`），一份数字定不了两条腿，规模请用 `quantity` 表达（V11 Q72）。

来源标签一共四格，缺哪一种都写不出来：`builtin-default`（没人声明，按仓库里唯一一处默认本金记账）、
`strategy-initial-cash`（只有回测侧声明过）、`strategy-initial-cash+paper-worker-cash`（回测侧那格
同时被 `worker.paper_initial_cash_raw` 原数确认过，V12 R3）、`multi-leg-funding-rule`（多腿链按腿定资）。

同一份 runtime 里账户本金只能有一个口径（V12 R3）：`strategy.initial_cash_raw` 是回测侧那一格，
`worker.paper_initial_cash_raw` 是 Paper 侧每个 worker 入账初始资金的那一格。两侧过去互不知情，
一份配置写 100,000 与 200,000 也能照常启动，使用者却以为"我声明了一份本金"。现在只要回测侧说了
N，就不允许别的格子说 M≠N —— 三条回测链、`paper submit-order`、paper worker 在**任何副作用之前**
一起拒掉，报错里并列点出两处名字与两个数（`strategy.initial_cash_raw=… vs worker[<id>]=…`）。
两个 paper 账户各写各的数不在此列：那本来就是按账户定资，没有任何格子声称它是全局口径。

### 3.3 产物、输入身份与重放结论

四份同前缀文件（`.summary.json`、`.equity.csv`、`.fills.csv`、`.run.json`）由 Bar 链与深度链各自
原子写出：Bar 链落在运行时 `storage.data_dir/runs`，`backtest book` 落在它的 `--root/runs`，
`backtest multi-builtin` 一份都不写（见 §3.1）。重复运行必须得到相同内容，冲突时拒绝覆盖。本轮实测的字段：

- `*.run.json`：`run_id`、`code_commit`、`config_hash`、`data_fingerprint`、`input_components`、
  `clock_start`/`clock_end`、`global_seed`、`determinism_mode`、`result_hash`、`strategy_version`、
  `instrument_spec_version`、`model_fingerprint`、`input_event_hash`、`output_event_hash`、`runtime_version`；
- `*.summary.json` 中与可复核性直接相关的段：`schema_version`（当前 v4）、`account`
  （`initial_cash_raw`/`source`，即真正记账的期初本金与它从哪来）、`input`
  （`dataset_id`/`dataset_version`/`kind`/`fingerprint`）、
  `replay`、`matching_kernel`、`fill_model`、`execution_costs`、`risk_rules`、`rejected_orders`/`rejection_reasons`、
  `model_descriptors`、`assumptions`。

三条纪律值得单独说明：

1. **声明的输入必须能重算**。`summary.input.fingerprint` 与 `run.json.input_components.bars` 是同一个值，
   指向实际读到的 BarFrame，而不是"配置里写着什么"（V11 Q63/Q66）。
2. **重放是真做过的校验**。`replay` 记录的是把事件流逐条过 `append_checked` 重新入账后得到的
   `log_digest`/`ledger_entries`，因此 `replay.log_digest == result_hash` 是一次**结果**而不是恒等式；
   旧口径那个"把同一段事件切片再哈希一遍"的 `replay_hash` 键已经删除，架构门禁禁止它复活
   （V11 Q62）。
3. **帧文档自己声明它按哪一版契约被读**。BarFrame JSON 的第一格是 `schema_version`：写侧印出、两侧读侧
   （`qx-data` 的 provider 与 `qianxing_bridge`）据此选严格模式还是旧格式兼容分支，高于支持版本的直接拒
   （V11 R16）。此前两侧都靠"缺字段=旧格式"推断，Rust 自己写出的帧在自家读侧被降级成宽松分支。

### 3.4 读模型里的 `null` 与 `0`

`status`、`report --json` 与 `qx-api` 的账户快照共用同一份 `AccountSnapshot` 线格式。钱字段与价格字段的
"没有"是两套编码，混用会把"没算"读成"没有"（V11 Q67/Q68/Q70）：

- **钱**：`equity_raw`、`available_raw`、`margin_raw`、`frozen_raw`、`realized_pnl_raw`、`unrealized_pnl_raw`、
  `fees_raw`、`funding_raw`，以及持仓行的 `unrealized_pnl_raw`/`margin_raw`，类型是可选整数。JSON 里 `null` =
  这一层没有算它（或交易所没有报），`0` = 算过且结果为零。消费方不得把 `null` 折算成 0。
- `equity_raw` 是这一族里最晚归队的一个（V11 Q70）：权益要现金账簿**和每一条持仓的标记价**才拼得出来。
  此前它退回纯现金，于是「账户有一条还没读到行情的持仓」与「这个账户只剩现金」印成同一个数；现在缺任何
  一条标记价就报 `null`，行情事实到位后同一个账户重新算得出。
- **价格**：`average_price_raw`/`mark_price_raw` 仍是裸定点整数，用 `0` 表达"没有"—— 0 不是合法价格，
  这个哨兵是有意保留的，不要按钱字段的口径去改。
- 持仓行没有 `unrealized_pnl`/`margin` 的生产者：这两项要按冻结的 market spec 逐标的折算，而读侧没有规格
  来源，所以由本地 Ledger 拼出来的行**恒定报 `null`**。CCXT 持仓回报缺 `side` 时该条事实整条被拒（不再默认
  多头），缺钱的字段落为 `null`。
- **版本号真的认版本**（V12 R2）：`AccountSnapshot` 只认 `schema_version = 1`。顶层那一格是唯一的真值，
  `header.schema_version` 缺席时按顶层补齐、已声明时必须与顶层同号（声明成 `"1"` 这种字符串版本号当场拒，
  不会被补写成合法值）。判定排在字段解析**之前**：一份来自未来版本的文档，即使本构建恰好读得出它的形状，
  也只会得到"schema_version=7 不受支持（本构建只认 1）"，而不是"某个字段缺失"—— 这两句话是两件不同的事实。
- 对账侧两格（`reconcile.last_reconcile_ts`/`discrepancy_count`）由磁盘上本账户身份的对账报告投影而来
  （V11 R7），并且同一个 `Option` 编码：**没有报告 = 两格 `null`，对过且无差异 = `Some(0)`**（V11 R10）。
  此前它们是不可区分的整数，"从未对账"与"对账很干净"在 JSON、`state_hash` 与 diff 上是同一份状态。
  换哈希形状是一次有意的 fail-closed：升级前落盘的账户快照会在 `from_json` 的 `state_hash` 核对处被拒，
  由 EventLog 重投影即可恢复（`data/` 下的账本才是真相，快照只是读模型）。
- 四张键表（`positions`/`orders`/`fills`/`transfers`）的键**一律是带引号的字符串**：订单/成交/划转用十进制
  字符串（`"orders":{"77":{…}}`），持仓用 `标的代码.交易所`（`"positions":{"BTCUSDT.BINANCE":{…}}`），
  与 `from_json` 认的那一份 serde 编码同源（V11 R14/R15）。`Side`/`OrderStatus` 印变体名而不是数字码。
  这份文档 Python 侧读得到读不到，两侧钉在同一份夹具上：`python/tests/fixtures/account-snapshot-v1.sample.json`
  由 `to_json` 原样产出，改编码就要重产，手抄一份近似形状过不了（V11 R18）。

Paper 主链路使用：

```powershell
cargo run --release -p qx-cli -- paper-check deploy/qianxing.runtime.paper-strategy.example.json
```

需要单独验证 Paper Venue 的接受、报价成交、断线转对账和恢复契约时，仍使用兼容入口：

```powershell
cargo run --release -p qx-cli -- paper
```

### 3.5 摘要读侧：`absent`、世代与复核结论

`report <summary.json>` 与 `status` 的 `[Latest Backtest]` 共用同一个排版模块，因此同一格在两个命令里
的字面量必然一致（V12 R1）：

- **缺席不落在数值域里**：摘要里没有这个键，就印 `absent`；印了 `0` 才真的是 0。读侧不做"缺就补 0"，
  架构门禁禁止 `report` 出口把缺席渲染成任何域内合法值。
- **`schema_version=… input=… account=… replay=…` 一行说清世代**：每块 either `declared`、
  `not_declared_before_vN`（这一代根本没有这块）、或 `MISSING_IN_THIS_GENERATION`（这一代该有却没有，
  是产物坏了）。少了这一行，读者无法区分"老摘要没这块"与"新摘要丢了这块"。
- **`input_verified=`**：整份报告里唯一回答"这份产物的输入有没有按声明重算过"的一格。复核失败向上抛，
  不静默降级；没有 `input` 块的旧摘要在这里显式写 `not_declared（该摘要没有 input 块，输入身份未经核对）`。
- 多腿归因的 `cost_bps` 同一条纪律：换手为 0 时**没有分母**，报"算不出"而不是 `0`（0 会被读成"零成本"）。

## 4. 实盘发布前

先复制并按部署环境修改 production 配置，再计算并写入配置锁。`config_fingerprint` 必须来自最终发布文件，不能使用模板中的 `null`：

```powershell
cargo run --release -p qx-cli -- config lock `
  deploy/qianxing.runtime.production.example.json `
  deploy/qianxing.runtime.production.locked.json
cargo run --release -p qx-cli -- runtime-check deploy/qianxing.runtime.production.example.json
cargo run --release -p qx-cli -- live-check deploy/qianxing.runtime.production.example.json
```

`config lock` 默认生成 `<原文件名>.locked.json`，也可以显式指定输出路径；已有输出文件必须显式添加
`--force` 才会覆盖。生成后会重新读取并验证指纹锁，避免手工复制指纹时产生错误。

`live-check` 会拒绝或提示以下问题：

- environment 不是 `production`，或没有有效的 `config_fingerprint`；
- TLS 证书链、私钥、客户端 CA 不存在；
- Execution 缺少交易品种规格、订单/持仓名义额上限，或错误配置为 Paper；
- UserStream、Execution、Reconciler 的凭据环境变量/凭据文件不可用；
- 生产策略的研究快照文件不存在；
- API 只绑定本机地址时给出部署提醒。

凭据检查只验证引用是否可用，不输出 key、secret、余额或订单内容。实盘 worker 启动前仍应先执行公共探测、私有余额探测、用户流连接、单轮对账和 sandbox 小额矩阵。

### 4.1 会提交订单的入口一律先过两道闸门

Paper 与实盘不接受 A 股策略段：Paper Venue 没有 T+1 交收状态、整手数量与板块涨跌停锚点，配了这段
又没有闸门可用时，半截接线比直接失败更危险。因此凡是**会把订单送进出价/排队路径**的入口，都在读到
任何副作用之前先拒掉它 —— 当前七个：`serve`、`strategy-worker`、`paper-worker`、
`binance-worker`、`ccxt-worker`、`paper submit-order`、`binance-submit-order`
（V11 Q65 覆盖其中五个；`serve` 与 `strategy-worker` 是 V12 R1 补上的两个排队入口，它们收下
`Trading` 命令却从未问过这道闸门）。报错文案点出入口名，架构门禁按调用点逐个清点，新增提交入口
不接闸门即红。

同一批入口还共用第二道闸门：一份 runtime 的账户本金口径（见 §3.2，V12 R3）。Paper 侧
`worker.paper_initial_cash_raw` 马上要按它入账初始资金，所以入账前先确认它没有和回测侧那一格各说一套。

## 5. 故障处理约定

- 配置解析失败：先修复 JSON 和 `RuntimeConfig` 校验错误，不要通过删除字段绕过门禁。
- `config_fingerprint` 不匹配：重新审核最终配置后重新计算发布指纹，不能直接复制旧指纹。
- 凭据不可用：检查 Secret Manager/CSI 投影或环境变量名称；策略子进程不会继承交易凭据。
- 品种规格不可用：补齐 precision、最小数量、最小名义额、乘数、杠杆和保证金档位后再启动 Execution。
- Paper 有订单但没有 Ledger：保留 `data/qianxing-paper` 和 EventLog，先检查队列终态与执行 worker，不要重复提交相同控制命令。
- 真实账户出现未知状态：停止继续下单，进入 ReconcileRequired，对账确认后再恢复。
