## 1. 终极目标

牵星最终不是策略脚本集合、指标库或交易所连接器集合，而是：

> **以 Rust 为核心、面向多资产和多 Venue、统一 Backtest/Paper/Live、可重放可审计、支持多语言与插件的量化交易引擎。**

终极形态必须同时满足四个条件：

1. 研究结果可以被可靠地带入交易，但研究计算本身由 finkit 负责；
2. 同一套交易事实和风控/订单语义覆盖回测、纸面和实盘；
3. 实时系统的每一次决策、拒绝、成交、状态变化和恢复都可以追溯；
4. 用户可以通过 CLI、Python、C/C++、Web/API 和可视化报告完成从数据到运行的完整闭环。

## 2. 开源项目对比后的架构取舍

本计划只吸收已经被对应项目公开验证的结构性经验，不复制其语言、业务范围或未经验证的生产承诺。

| 项目 | 最值得借鉴 | qianxing 的吸收方式 | 明确不照搬 |
| --- | --- | --- | --- |
| [Barter](https://github.com/barter-rs/barter-rs) | 轻量 Engine、Instrument 索引、可替换 MarketStream/Execution、AuditStream、外部控制命令 | `qx-application::EngineBuilder`、Registry/Index、统一 Feed、AuditStream、EngineCommand | 不复制其 crate 结构、数值语义或交易所覆盖范围 |
| [NautilusTrader](https://nautilustrader.io/docs/latest/concepts/architecture/) | Rust Kernel、MessageBus、Cache、Data/Execution/Risk/Portfolio 分层、Backtest/Sandbox/Live 共用 Kernel、单写者事件核心与异步 IO | 固化 Engine/Application/Ports、确定性 reducer、状态副本、生命周期 FSM、事件溯源和恢复 | 不把复杂 Actor/unsafe 运行时直接引入 qianxing；先保持安全的单写者模型 |
| [LEAN](https://github.com/QuantConnect/Lean) | 研究、项目初始化、回测、优化、实盘的产品工作流；模块可插拔 | 建立 `init/doctor/backtest/optimize/paper/live/report` 统一 CLI 和 RunManifest | 不引入云平台耦合，也不让 CLI 代替核心交易内核 |
| [Hummingbot](https://hummingbot.org/docs/) | 连接器标准化、Strategy V2 的 Controller/Executor 分离、Dashboard/API 控制和多 Bot 管理 | Connector Capability Matrix、Strategy/Execution Algorithm 分离、统一控制面和运行实例 | 不采用 Python 作为热路径主语言，不让脚本直接拥有交易副作用 |
| [vectorbt](https://vectorbt.dev/) | 向量化研究、快速参数扫描、Portfolio/Trade/Drawdown 分析 | 由 finkit 和研究层承接向量化计算，产物以 artifact 进入 qianxing | 不把向量化研究引擎当作真实订单生命周期或实盘执行引擎 |

### 2.1 综合判断

最终组合应当是：

```text
NautilusTrader 的 Kernel / MessageBus / Cache / 生命周期
          + Barter 的轻量 Engine / Indexed State / AuditStream
          + LEAN 的 Research → Backtest → Optimize → Live 工作流
          + Hummingbot 的 Connector / Controller / Executor 产品化
          + vectorbt 的研究吞吐和结果分析
          + qianxing 的确定性、多资产 Ledger、PIT、finkit 和跨语言
```

其中 `qx-core` 仍是交易事实唯一来源；任何外部项目的优势都必须通过 qianxing 的事件、账簿、重放和安全边界落地。

## 3. 当前基线与主要缺口

当前仓库已经有确定性 Kernel、数据与 PIT 模型、回测撮合、OMS/Ledger、Paper、CCXT/Binance、跨语言策略、运行时、存储、控制面和 `qx-application` 端口层。V8 已经识别并部分修复了配置闭环、Paper 行情事实、执行端口、统一风险和单机恢复等问题。

终极改造仍需解决以下结构性缺口：

1. **Engine 仍未成为唯一组合根**：部分 CLI、Worker 和 Runtime helper 仍然自行编排业务；
2. **热路径状态还没有形成明确的 Cache/Index/Reducer 契约**：外部 ID、查询模型和内部状态边界需要固定；
3. **Backtest/Paper/Live 的共用语义需要 golden vectors 和同一生命周期 FSM 证明**；
4. **Research → Strategy → Portfolio → Risk → Execution 的 artifact lineage 需要完全由 finkit 契约驱动**；
5. **可视化目前缺少仓库内已确认的统一场景 schema、实时快照、报告和图层注册体系**；
6. **连接器、策略、执行算法、风控规则和可视化扩展的版本/能力/验收矩阵还需产品化**；
7. **真实外部环境、跨节点 HA、备份恢复、动态插件隔离和跨平台发布仍未达到终态门禁**。

### 4.1 四条不可分叉的主链

```text
Data / Artifact
  → StrategyContext
  → StrategyDecision
  → PortfolioTarget / OrderIntent
  → RiskDecision
  → OMS
  → Venue / Matcher
  → ExecutionFact
  → Ledger
  → Audit / Report / Visualization
```

这条链只有一个版本。Backtest、Paper、Live、Replay 和 Visualization 都是它的不同输入或输出环境，不得再各自建立第二条业务链。

### 4.2 单写者核心与异步边界

采用以下并发模型：

```text
网络 / 文件 / 数据库 / Python / C++ Worker
             │ async tasks / bounded channels
             ▼
      Engine Input Queue
             │ ordered reducer, single writer
             ▼
      EngineState + EventLog + AuditStream
             │ async projections / replicas
             ▼
      API / UI / reports / metrics / storage backends
```

- 热路径中只允许一个有序 reducer 修改订单、持仓、风险和账簿状态；
- IO、解析、压缩、查询、可视化和持久化可以异步并行；
- 队列必须有容量、背压、丢弃/降级和恢复策略；
- 任何并行优化都必须与单写者基线比较 EventLog digest 和 Ledger 结果。

## 5. 核心模块终态

### 5.1 `qx-core`：不可替代的交易事实层

只负责：

- Clock、Event、Sequence、CausalPriority；
- 定点价格/数量/金额和精度规则；
- InstrumentSpec、Order、Fill、Position、Cash、Margin、Ledger；
- EventLog、ReplayVerifier、RunManifest；
- 可序列化、可比较、可重放的核心事实。

禁止依赖 Runtime、网络、数据库、Python、UI 或任何具体 Venue。

### 5.2 `qx-application`：唯一组合根

终态 API：

```text
EngineBuilder
  → validate configuration / lineage / capabilities
  → freeze Registry + IndexLayout
  → build Engine
  → init components
  → run Feed
  → snapshot / reconcile / drain / shutdown
```

负责装配：

- `MarketDataPort`；
- `VenuePort`；
- `RiskPort`；
- `EventAppender` / `EventReader`；
- `OrderStore` / `SnapshotStore`；
- `ReconcilePort`；
- `StrategyHost` / `PortfolioAllocator`；
- `AuditSink` / `StateReplicaSink`。

CLI、API 和 Worker 只能调用 Application Service，不能自己拼接上述端口。

### 5.3 Registry、Index 与 Cache

```text
外部稳定 ID
InstrumentId / AccountId / VenueId / StrategyId
                │ resolve once at build time
                ▼
IndexLayout
                │ direct access in hot path
                ▼
Vec/arena based EngineState
```

要求：

- Registry 冻结后 index 不变；
- EventLog 记录稳定 ID，不记录不可跨运行复用的数组位置；
- symbol、JSON、数据库主键只在边界解析；
- Account、Venue、Instrument、Strategy 按 index 分区；
- Cache 是可丢失的内存投影，EventLog/Ledger 事实才是恢复依据；
- 状态副本只能读，不能成为交易事实写入口。

### 5.4 Engine 生命周期与 Component 状态

所有 Worker、Strategy、Connector、Storage 和 Report task 都遵守有限状态机：

```text
Created → Validating → Ready → Starting → Running
                                  │          │
                                  ▼          ▼
                              Degraded    Draining
                                  │          │
                                  ▼          ▼
                              Faulted → Stopped → Disposed
```

终态规则：

- `Ready` 才可以启动；
- `Degraded` 必须定义是否允许继续交易，默认 fail-closed；
- `Faulted` 不允许静默恢复到 `Running`，必须经过 reconcile/recovery；
- 外部 supervisor 可以重启进程，但不能跳过启动恢复和配置校验；
- `TradingEnabled` 是 Engine 级状态，不由单个策略自行决定。

## 6. 数据、研究与 finkit

### 6.1 数据契约

```text
RawRecord
  → Canonical Dataset
  → Quality Gate
  → DatasetManifest / fingerprint
  → PIT DataView
  → finkit Artifact
  → qianxing ResearchBinding
```

每个交易运行必须绑定：

- Dataset fingerprint；
- Provider、原始来源和时间范围；
- Instrument universe 和 symbol mapping 版本；
- finkit artifact id/version/schema/digest；
- `as_of`、训练/验证区间；
- Strategy version、RiskRuleSet version、配置 fingerprint；
- RunManifest 和最终 EventLog digest。

### 6.2 finkit 边界

finkit 负责：

- 因子、指标、特征和复合计算；
- DAG、缓存、PIT 研究视图；
- 研究报告、候选策略和 artifact 发布；
- 研究侧向量化计算和参数扫描。

qianxing 负责：

- 验证 artifact 的版本、签名、PIT 和 fingerprint；
- 将 artifact 绑定到 StrategyContext；
- 将研究结果转为 Signal/Target/OrderIntent；
- 记录研究产物到订单、成交和 Ledger 的完整 lineage。

禁止 qianxing 和 finkit 维护两套同名因子、指标、DAG、报告或 PIT 语义。`qx-factor` 进入迁移期兼容模式，最终收敛为契约包或移出 workspace。

## 7. 交易与连接器产品化

### 7.1 Connector Capability Matrix

每个 Provider/Venue 必须声明并逐项验收：

```text
market_data: trades / quotes / bars / order_book
execution: submit / cancel / amend / batch
account: balances / positions / orders / fills
stream: public / private / reconnect / sequence
reconcile: open_orders / history / balances / positions
rules: precision / lot / tick / margin / funding / calendar
```

状态分为：

```text
implemented → unit-tested → contract-tested → sandbox-tested → production-approved
```

没有达到 `sandbox-tested` 的适配器不能作为生产模板；没有达到 `production-approved` 的适配器不能在文档中写成实盘完成。

### 7.2 统一执行链

```text
Strategy / EngineCommand
  → Portfolio
  → RiskEngine
  → OMS
  → VenuePort
  → Accepted / Rejected / Unknown
  → external response or reconcile
  → ExecutionFact
  → Ledger
```

未知结果不得盲目重试。必须进入 `ReconcileRequired`，由 `ReconcilePort` 通过订单历史、开放订单、成交和账户快照确认后才能继续。

### 7.3 Strategy 与 Execution Algorithm 分离

- Strategy 负责观察数据和提出意图；
- Portfolio 负责目标、净额和组合约束；
- Execution Algorithm 负责拆单、TWAP、VWAP、做市、套利腿和超时策略；
- RiskEngine 负责拒绝或放行，不静默改变策略语义；
- VenueAdapter 负责协议和传输，不负责策略和组合决策。

这吸收 Hummingbot Controller/Executor 的职责分离，同时保留 qianxing 的 Rust 风险和账簿边界。

## 8. 可视化与控制面终态

### 8.1 可视化原则

可视化不是另一个计算引擎，而是 Engine 事实、研究产物和报告的只读消费层：

```text
EngineStateReplica / AuditStream / EventLog / RunManifest
                         │
                         ▼
                  Visualization View Model
                         │
                         ├── HTML / SVG / Canvas
                         ├── Web Console / WebSocket
                         ├── Python / Notebook
                         ├── Static PNG / PDF
                         └── JSON / Arrow / Parquet
```

实时控制仍走 `EngineCommand`；图表、表格和报告没有交易副作用。

### 8.2 统一 `ChartScene` 契约

新增可视化规范时，优先冻结与具体前端无关的场景 schema：

```text
ChartScene
├── schema_version
├── run_id / strategy_id / account_id
├── instrument / venue / timeframe
├── time_range / timezone / calendar
├── source_fingerprint / artifact_refs / event_cursor
├── panes[]
│   ├── scale / axis / viewport
│   ├── series[]
│   ├── overlays[]
│   └── annotations[]
├── tables[]
├── metrics[]
├── actions[]  (read-only metadata; real action uses EngineCommand)
└── theme / layout / locale
```

每个点、线、标记和表格行都应保留：

- 原始数据索引或事件序号；
- `instrument_id`、时间戳和时区；
- source/artifact/event lineage；
- confirmed/unconfirmed 状态；
- 计算版本和 schema 版本。

这样可以实现“图上一个成交点 → 订单 → RiskDecision → StrategyDecision → finkit artifact → 原始数据”的反向追踪。

### 8.3 Chart Registry、Theme 和报告

参考 Nautilus 的 Chart Registry、Theme 和 declarative configuration，把可视化拆为：

- `ChartRegistry`：注册 equity、drawdown、returns、fills、orders、positions、risk、latency、data-quality、factor-exposure 等图表；
- `ThemeRegistry`：颜色、字体、正负方向、风险等级、暗色/亮色和无障碍对比度；
- `LayoutConfig`：声明图表、面板、尺寸、数据源和筛选，不把布局写死在前端；
- `Tearsheet`：离线回测报告，可独立归档、分享和复现；
- `LiveDashboard`：订阅状态副本和 AuditStream，不直接读写热路径；
- `Notebook/JSON`：向 Python、Node、WASM 和外部分析工具提供相同 schema。

### 8.4 实时数据与大数据可视化

- WebSocket/SSE 只传递增量、快照指针和 cursor，不重复发送完整历史；
- 客户端落后时返回 `SnapshotRequired`，从一致性快照重新同步；
- K 线、指标和 Overlay 使用 viewport、LOD、MinMax/LTTB 或聚合级别控制点数；
- 抽样只减少绘制点，不改变原始索引和事件 lineage；
- 多周期结构使用基础周期坐标映射，高周期标注保留 source range；
- 缓存必须绑定 dataset/revision/viewport/theme/schema fingerprint；
- 对极大数据集优先返回 Parquet/Arrow/分页块，不生成单个无限膨胀 HTML。

### 8.5 可视化验收

- JSON、HTML、SVG、Canvas、Python 输出同一输入的语义对象一致；
- 缩放/平移不丢失成交、订单、风险和结构的原始索引；
- 任何图表指标都能定位到 RunManifest 和数据 fingerprint；
- 实时断线重连后通过 snapshot + cursor 恢复，不重复或跳过事件；
- 未确认结构、模拟成交、真实成交、风险拒绝使用明确状态和颜色；
- 可视化测试不访问可变 Ledger，不发送订单，不修改 EngineState；
- 生成的 HTML/PNG/PDF 可以在无服务端环境中读取并显示运行元数据。

## 9. 产品工作流终态

参考 LEAN 的项目化工作流，统一为：

```text
qx init
  → qx doctor
  → qx dataset inspect/build
  → qx research bind
  → qx backtest
  → qx optimize
  → qx report / qx visualize
  → qx paper
  → qx live-check
  → qx live
  → qx reconcile / qx replay
```

每次命令都生成或验证：

- 配置 fingerprint；
- 输入 Dataset/Artifact fingerprint；
- Strategy/Risk/Execution 版本；
- RunManifest；
- 输出目录和文件清单；
- EventLog/Audit digest；
- 运行状态和失败原因。

CLI 是产品入口，不是业务真相。所有命令最终调用同一个 Application/Engine API。

## 10. 插件与多语言终态

### 10.1 插件扩展点

```text
DataProvider
VenueAdapter
RiskRule
PortfolioAllocator
ExecutionAlgorithm
StrategyHost
StorageBackend
ReportChart
```

插件 manifest 必须包含能力、版本、依赖、冲突、配置 schema、ABI/schema 版本、artifact digest 和信任状态。

分级策略：

1. 受信任、签名、同版本插件：可以进程内加载；
2. 外部策略和实验组件：独立进程、资源限制、超时和崩溃恢复；
3. 非受信任动态库：默认禁止进程内加载，必须完成 sandbox、签名信任根轮换和回滚后才可开放。

### 10.2 多语言协议

统一为：

```text
StrategyContext + MarketEvent
       ↓
StrategyDecision { intents[] }
       ↓
Portfolio / Risk / OMS / Execution
```

- Rust：同进程核心策略和低延迟路径；
- Python：研究、机器学习和中低频策略，默认进程外；
- C/C++：稳定 C ABI 或进程外协议，必须有 ABI golden vectors；
- Node/WASM：研究/可视化和受限策略场景，不能直接修改交易事实。

## 11. 终极实施路线

### Phase 0：基线和契约冻结

交付：

- 将本计划、V2、V8 和可视化契约列为文档基线；
- 补回或确认 `docs/Qianxing-Visualization-Architecture-V1.md`；
- 建立 `maturity/capabilities.yaml` 和每个连接器的证据等级；
- 固定 Event、Order、Fill、Ledger、RunManifest、ResearchBinding、ChartScene schema 版本；
- 清理生成物、修复文档入口和路径。

完成条件：文档之间没有互相冲突的定位、模块归属和状态描述。

### Phase 1：Engine/Application 收敛

交付：

- `qx-application::EngineBuilder`、EngineFeed、EngineCommand、TradingState；
- CLI、API、Worker 全部从 Builder 装配；
- 迁移旧 Runtime helper，禁止新增旁路；
- Backtest、Replay、Paper、Live 的生命周期统一。

完成条件：一条 golden vector 可以通过 Iterator、Replay 和 Paper 路径得到相同核心 Ledger digest。

### Phase 2：State/Cache/Index 收敛

## 14. 事件引擎与交易执行引擎专项收敛

### 14.1 当前是否已经具备

**具备，但完成度不同。** 当前实现可以证明 qianxing 已有事件引擎和交易执行引擎的基础，不应再把它们写成“待从零建设”；下一步是统一边界、事件状态机、实时输入和恢复语义。

| 能力 | 当前实现 | 当前判断 |
| --- | --- | --- |
| 因果事件循环 | `qx-core::Engine`、`EngineCtx`、`CausalQueue`、`Handler`，按 `(ts, priority, seq)` 出队，支持 handler 产生后续事件 | 内核基础已具备，A- |
| 事件事实与重放 | `qx-core::Event`、`EventLog`、`ReplayVerifier`、`RunManifest` | 确定性/重放基础较强，A-/B+ |
| 实时事件归约 | `qx-runtime::LiveEventPipeline` 归约 EventLog、OMS、Ledger、报价、账户观察和恢复 | 已有运行时事件管线，但还不是独立的统一 Engine 产品边界，B+ |
| 订单生命周期 | `qx-oms::Oms` 负责订单登记、接收、成交、部分成交和终态约束 | 单一 OMS 方向正确，A-/B+ |
| 执行副作用边界 | `qx-application` 的 `VenuePort`、`ExecutionEventPort`，`qx-execution::PortExecutionService` 统一注册、提交、回报和待对账 | 本地/契约链已具备，B+ |
| Paper/回测撮合 | `qx-xingban` 的 Bar/L1/L2、成本、延迟、订单簿和保证金模型 | 仿真执行能力较完整，A-/B+ |
| 外部实盘执行 | CCXT/Binance、用户流、重连、对账和未知结果保护 | 代码已接线，真实外部闭环仍为 B |

证据入口：[qx-core 事件引擎](../crates/qx-core/src/engine.rs)、[qx-runtime 实时事件管线](../crates/qx-runtime/src/pipeline.rs)、[qx-application 执行端口](../crates/qx-application/src/lib.rs)、[qx-execution 执行服务](../crates/qx-execution/src/lib.rs) 和 [qx-oms 订单状态机](../crates/qx-oms/src/lib.rs)。

### 14.2 当前最重要的结构问题

#### 事件引擎问题

1. `qx-core::Engine` 目前是同步的 `Vec<Box<dyn Handler>>` 循环，适合确定性内核测试，但还没有统一的外部 Feed、Command、Audit、Snapshot、Backpressure 和运行生命周期。
2. `qx-core::Engine` 与 `qx-runtime::LiveEventPipeline` 存在两种 Engine 语义：前者是通用队列循环，后者是实时 EventLog/OMS/Ledger 归约器；终态必须由一个 Application/Engine 组合根装配，不能继续双轨扩张。
3. 多个异步 Worker 可以向共享 EventLog 写入，但“接收顺序 → 全局序列 → 因果队列 → 归约”的正式 Sequencer 边界还需冻结；重试不能由线程调度顺序决定结果。
4. 当前 EventLog 已有来源、去重、因果和规则字段，但还需要明确事件 schema registry、版本迁移、分区/租户边界、输入背压、缺口和死信策略。
5. `EventLog`、内存状态、Outbox、AuditStream 和 StateReplica 的提交顺序、失败恢复和观察延迟必须形成统一事务/一致性矩阵，避免“日志成功但副作用未落地”被不同运行模式解释成不同结果。

#### 交易执行引擎问题

1. `qx-execution::PortExecutionService` 已经不依赖具体 Runtime，仍有历史 `ExecutionService`、CLI helper 和部分事件函数直接依赖 `LiveEventPipeline`；必须完成迁移后删除兼容路径。
2. `VenuePort` 当前以同步 `submit/cancel → Vec<ExecutionEvent>` 为主，尚未完整表达异步私有回报、`Rejected`、`Working`、`Expired`、`CancelPending`、部分撤单、修改订单和批量订单等统一执行事实。
3. Strategy/Portfolio/Risk/OMS/Execution Algorithm/Venue Adapter 的责任已开始拆分，但执行算法层还没有成为正式扩展点；TWAP、VWAP、做市、冰山和多腿套利不能继续堆进单腿提交服务。
4. 风控端口的最小返回值仍偏弱。终态 `RiskDecision` 必须携带 violations、投影持仓/保证金、规则版本、参考价时间、snapshot id 和 reject-before-side-effect 证据，而不是只返回布尔值或字符串错误。
5. 多腿执行已经具备组身份、补偿和恢复基础，但不能宣称跨 Venue 原子性；组级状态、腿级事实、对冲策略、超时、人工介入和 reconcile 必须由同一 Execution Engine 管理。
6. “提交请求已写入”和“外部 Venue 已接受”之间的未知窗口必须具有持久化 `SubmissionAttempt`、幂等键、重启恢复和 `ReconcileRequired` 语义，任何执行器都禁止通过自动重试掩盖未知结果。

### 14.3 双引擎终态分工

终态不是两个互相写状态的引擎，而是“事件引擎拥有事实归约，执行引擎拥有外部副作用编排”：

```text
                         ┌──────────────────────────┐
Market / Command / Fill ─►      Event Engine           │
                         │ Ingress → Sequencer        │
                         │ Causal Queue → Reducer     │
                         │ EventLog → Audit/Replica   │
                         └─────────────┬────────────┘
                                       │ StrategyContext / OrderIntent
                                       ▼
                         ┌──────────────────────────┐
                         │    Execution Engine        │
                         │ Portfolio → Risk → OMS     │
                         │ Algo → Router → Venue      │
                         │ Unknown → Reconcile       │
                         └─────────────┬────────────┘
                                       │ normalized ExecutionFact
                                       └───────────────► Event Engine
```

事件引擎负责：

- 接收并校验 MarketEvent、EngineCommand 和 VenueEvent；
- 分配稳定全局序列，按业务时间、因果优先级和序号排序；
- 驱动确定性 reducer，更新 EngineState、OMS、Portfolio 和 Ledger；
- 追加 EventLog，派生 AuditStream 和 StateReplica；
- 处理 Replay、Snapshot、恢复、缺口、重复和死信；
- 向策略、执行引擎、报告和可视化发布只读事实。

交易执行引擎负责：

- 接收经过策略/组合生成的 OrderIntent 或 EngineCommand；
- 调用统一 RiskEngine，生成可审计 RiskDecision；
- 通过 OMS 建立唯一订单生命周期和 SubmissionAttempt；
- 按 ExecutionPolicy/Algorithm 拆单、限频、超时和多腿补偿；
- 通过 VenueRouter/Adapter 执行外部副作用；
- 将同步回报、异步用户流和对账结果归一化为 ExecutionFact；
- 对 Unknown/Timeout/断线只进入 Reconcile，不直接补单。

执行引擎**不能直接修改 Ledger 或 EventLog 内部状态**；它只能把执行事实送回事件引擎，由事件引擎在统一提交边界完成归约。

### 14.4 统一事件与订单状态机

事件状态最小集合：

```text
MarketEvent / Timer / EngineCommand
  → StrategyDecision / PortfolioTarget / OrderIntent
  → RiskAccepted | RiskRejected
  → OrderSubmitted
  → SubmissionAttempted
  → Accepted | Rejected | Working
  → PartiallyFilled | Filled
  → CancelRequested | CancelPending | Cancelled | Expired
  → Unknown / ReconcileRequired
  → Reconciled
```

约束：

- `OrderSubmitted` 是 qianxing 已接受的内部事实；`Accepted` 才是 Venue 接受事实；
- `SubmissionAttempted` 必须带 attempt id、idempotency key、adapter、receive time 和 correlation；
- `Unknown` 是保护态，不是失败态；未对账前不得再次产生外部副作用；
- Fill 只能由 Venue/Matcher/明确结算事实产生，不能由状态查询差额推导；
- OMS 只归约合法状态迁移，Ledger 只归约已确认 Fill/Cashflow/Settlement；
- 每个事件带 causation、correlation、source、source_seq、observed/effective/engine time 和 rule/schema version；
- 任何非法、迟到、重复或跨账户事实进入拒绝/死信/对账流，不能静默丢弃。

### 14.5 必须新增的 Engine 端口

以下是目标边界，不要求立即创建同名类型；应优先复用现有 `qx-application` 和 `qx-core` 类型，避免重复契约：

```text
EventIngress       raw input → validated envelope
EventSequencer     envelope → global ordered event
EventReducer       event → state transition / derived facts
EventStore         append / read / replay / snapshot
AuditSink          event result → audit consumers
StateReplicaSink   committed state → read-only projections
EngineCommandPort  operator/API → ordered command

ExecutionPort      OrderIntent → normalized ExecutionFact
RiskPort           intent/order → rich RiskDecision
OrderStore         OMS registration and lifecycle query
VenuePort          submit/cancel/amend and private stream binding
ReconcilePort      unknown → confirmed external state
ExecutionPolicy    intent → one or more child orders
```

### 14.6 分阶段加强顺序

#### E0：事实和状态机冻结

- 补齐 ExecutionEvent 的拒绝、工作中、过期、修改、撤单中和对账完成语义；
- 冻结 `OrderSubmitted → SubmissionAttempted → Accepted/Unknown → Reconcile` 状态图；
- 将 `RiskDecision` 从布尔结果升级为可审计结构；
- 为所有事件、命令和回报增加 schema/version/correlation/causation/gap 规则；
- 用状态迁移表和非法序列属性测试取代分散的例外判断。

#### E1：统一 EventEngine

- 在 `qx-application` 建立 `EngineBuilder`/`EngineNode`，装配 Feed、Clock、Reducer、EventStore、Audit 和 Replica；
- 将 `qx-core::Engine` 作为确定性 reducer/Iterator 内核复用，不再与 Runtime 形成第二个公开 Engine；
- 将 `LiveEventPipeline` 变成 EventStore/Reducer 的 Runtime adapter；
- 增加 bounded ingress、backpressure、SnapshotRequired、cursor、dead-letter 和 graceful shutdown；
- 通过 Iterator、Replay、Paper、Live 四种输入模式验证同一 reducer。

#### E2：统一 ExecutionEngine

- 将 `PortExecutionService` 提升为唯一单腿执行边界；
- 将旧 `ExecutionService`、CLI 直连 Pipeline helper 和重复归约入口迁移后删除；
- 把 ExecutionPolicy/Algorithm、VenueRouter、ReconcileWorker、RecoveryWorker 变成显式组件；
- Paper、CCXT、Binance 和未来券商只实现 Venue/Stream/Reconcile adapter；
- 多腿套利以组级 FSM 编排单腿，不宣称跨 Venue 原子提交。

#### E3：恢复与一致性

- 外部副作用前持久化 intent/attempt/idempotency key；
- 发生超时、空回报、连接断开或进程崩溃时一律恢复到 Unknown/Reconcile；
- 启动顺序固定为加载配置 → 校验能力 → 恢复 Snapshot/EventLog → 对账 → 才允许交易；
- 建立 EventLog、Outbox、OMS、Ledger、Audit 和 StateReplica 的提交/失败矩阵；
- 对每个 adapter 注入迟到、重复、乱序、断线和错误回报。

#### E4：性能与可观察性

- 测量 EventEngine 的 ingress→reduce→append→audit 延迟和队列水位；
- 测量 ExecutionEngine 的 risk→OMS→adapter→fact 延迟和未知窗口时长；
- 所有指标带 run/account/venue/strategy/order correlation，不能只输出全局计数；
- Visualization 只消费 AuditStream/StateReplica/RunManifest，提供订单、风险和成交的端到端追踪；
- 任何并行 reducer 都必须与单写者基线比较 EventLog/Ledger digest。

### 14.7 双引擎验收门禁

```text
EventEngine
  - causal ordering / same-timestamp priority
  - follow-up event and timer scheduling
  - bounded queue / backpressure / gap / dead-letter
  - append failure / crash recovery / snapshot restore
  - replay digest and state equivalence

ExecutionEngine
  - risk reject-before-side-effect
  - OMS legal/illegal transition matrix
  - accepted/rejected/partial/full/cancel/expire
  - duplicate / timeout / unknown / reconcile
  - venue private stream out-of-order and reconnect
  - multi-leg compensation and restart recovery

Parity
  - Iterator Backtest == Replay == Paper == Live core facts
  - Rust/Python/C++ same intent vectors
  - AuditStream/StateReplica/ChartScene trace back to EventLog
```

未通过 E0–E3 之前，qianxing 可以称为“具有事件引擎和交易执行引擎能力”，但只能称为“代码级/单机级可用”；完成 E4 和外部 sandbox/production 证据后，才可以把对应能力标记为生产批准。

## 15. 最终判断

牵星的终极改造方向应当是：

```text
确定性 Rust Kernel
  → 唯一 Engine/Application 组合根
  → 单写者状态 + EventLog + AuditStream
  → 统一 Backtest/Paper/Live
  → finkit ResearchBinding
  → 标准化 Connector / Strategy / Execution
  → 只读 StateReplica + ChartScene + Web/Report/Notebook
  → 可验证的多语言、插件、恢复和发布体系
```

最重要的执行纪律是：先收敛事实、生命周期、端口、状态和 schema，再扩展交易所、策略、图表和插件。只有所有输入、决策、执行、可视化和恢复结果都能由同一条可重放链路解释，qianxing 才真正成为可长期演进的 Rust 原生量化交易引擎。

## 16. 可视化与端到端主链三轮审计结论

本节是对 `Qianxing-Visualization-Architecture-V1.md` 的三轮交叉审计结果。可视化文档中的原始“Review Pass”不能直接作为实现完成声明；以下结论覆盖模块、数据、命令、实时、恢复和终止条件。

### 16.1 第一轮：模块所有权和依赖链

发现的问题：

1. 原可视化方案把 `qx-schema`、`qx-viz`、`qx-server`、`qx-backtest` 作为目标模块，但当前工作区实际已有 `qx-protocol`、`qx-api`、`qx-xingban` 和 `qx-cli serve`，继续照原方案新增会形成平行入口。
2. 原方案把 `Runtime → Result Schema → API` 作为主链，忽略了 EventLog、Reducer、StateReplica、AuditStream 和 RunManifest，无法解释结果的事实来源与恢复方式。
3. 原方案的 `/api/v1/*` 与 `/ws` 并非当前 API 的稳定路由；当前稳定边界是账户快照/订单/持仓/账簿、事件游标、控制命令、健康/指标和 `/stream` WebSocket。
4. `qx-portfolio` 当前主要生成目标仓位到调仓计划，尚未自动进入统一 Risk → OMS → Execution 主链；它不能被文档描述为已经完成 Portfolio Engine。

收敛决策：

```text
qx-protocol 负责版本化线协议和快照
qx-api       负责 QueryPort / CommandPort / 认证 / 限流
qx-runtime   负责组合根、Worker 和 Pipeline adapter
qx-xingban   负责模拟 Venue/撮合，而不是第二套 OMS
前端         作为外部只读客户端，不创建 Rust Runtime 依赖
```

### 16.2 第二轮：事件、状态、执行、恢复和可视化闭环

发现的关键断链：

```text
LiveEventPipeline → EventLog / OMS / Ledger

ApiService         → 独立 ApiState / EventLog / EventBus
```

当前仓库缺少正式的：

```text
Committed EventLog Fact
  → ProjectionReducer
  → StateReplica / AuditStream
  → Snapshot + event_seq + cursor + state_hash
  → qx-api QueryPort / WebSocket
  → UI
```

因此必须执行：

- 将 API 的事件总线降级为传输缓存，不能成为第二个 EventLog；
- 增加 EventLog/Outbox 到 StateReplica 的投影桥，保持 committed seq 不变；
- 快照和实时事件必须共享 `state_hash`、`event_seq` 和可恢复 cursor；
- cursor 过旧、超前、跨状态或投影落后时统一返回 `resync_required`；
- 投影失败要进入 stale/replay 状态，不得静默返回旧数据并标记正常；
- 控制面动作必须走 `ControlCommand → queue → Engine → committed fact`，UI 只读投影；
- WebSocket 必须有认证过滤、有界发送缓冲、心跳、关闭、重连和快照重同步；
- API listener 不能被单个长连接占用，生产实现需按连接隔离或使用异步并发边界。

最终的双向闭环是：

```text
数据/研究
  → Data Quality / ResearchBinding
  → EventEngine / EventLog
  → StrategyDecision / PortfolioTarget
  → RiskDecision
  → OrderIntent / OMS
  → ExecutionAlgorithm / Venue
  → Accepted / Rejected / Fill / Unknown / Reconcile fact
  → EventLog / Ledger / Portfolio / StateReplica
  → Query API / AuditStream / ChartScene

UI action
  → Auth + Permission
  → ControlCommand
  → CommandQueue / EventEngine
  → 同一 ExecutionEngine
  → 同一投影链
  → UI 状态更新
```

### 16.3 第三轮：孤儿逻辑、循环依赖和死循环

已确认具备保护的部分：

- `qx-plugin` 对插件依赖有拓扑排序和环检测；
- `qx-scheduler` 对任务缺失依赖和依赖环有校验；
- Pipeline 并发写入重试有固定上限；
- 控制命令、订单请求和执行回报已有部分幂等键与终态校验。

仍需补齐的潜在问题：

1. `qx-core::Engine::run()` 只以队列为空为终止条件。Handler 可以持续产生同一时刻或未来事件，形成无界自调度。必须增加 `max_events`、取消 token、运行时 deadline、最大同一因果链深度和重复调度保护；触发保护时写入可审计的 `RunAborted`/`DeadLetter` 结果。
2. WebSocket 循环在长连接期间持续占用当前服务调用栈；没有连接级最大寿命、心跳和发送队列上限时，慢客户端可能造成资源泄漏或阻塞其他连接。
3. `qx-portfolio` 的调仓计划、`qx-risk` 的风险决策和策略输出需要统一转成 `PortfolioTarget → OrderIntent`，否则会出现“计算完成但没有订单事实”的孤儿逻辑。
4. `qx-protocol::AccountSnapshot` 与可视化 `ChartScene/BacktestResult/FactorResult` 不是同一套 schema；必须由统一 Envelope/lineage 关联，而不是再建一个无所有者的 `qx-schema`。
5. 原可视化插件中的 broker/factor 插件会越过 qx-plugin 与 finkit 边界；必须拆成 Rust 启动期插件和前端只读渲染插件。

终止条件必须显式化：

| 组件 | 正常终止 | 异常终止/恢复 |
|---|---|---|
| EventEngine | 队列为空且无待处理 Timer | 超预算、取消、deadline、schema/dead-letter 后写入 RunAborted |
| ExecutionAlgorithm | Filled、Cancelled、Rejected、Expired 或明确失败 | Unknown → ReconcileRequired，不自动无限重试 |
| Scheduler | Succeeded/Failed/Cancelled 且 retry 次数达到上限 | 超时、租约丢失、人工介入 |
| Projection | cursor 连续追平 committed EventLog | gap/stale → snapshot replay，不继续伪装实时 |
| WebSocket | 客户端关闭、服务关闭、idle timeout 或 resync | 写入断开原因，客户端按 cursor 重连 |
| Plugin bootstrap | 拓扑顺序完成或启动失败 | 依赖环、冲突、签名失败立即拒绝启动 |

### 16.4 端到端验收门禁

以下测试全部通过后，才可以把可视化链路标记为已贯通：

1. **单源事实**：同一 Fill/Order/Balance 只能由 EventLog 产生一次，API、报告和图表都能反查 `event_seq/correlation_id`。
2. **快照连续性**：客户端从 snapshot cursor 接收增量，遇到过旧、缺口、断线后可恢复，最终 `state_hash` 与服务端一致。
3. **命令闭环**：UI Cancel/Close/Reconcile 等动作经过权限、幂等、CommandQueue、Engine、Execution/Recovery 后在 UI 看到最终事实。
4. **研究闭环**：finkit 的数据版本、因子版本、策略版本和 RunManifest 能关联到回测报告和策略决策。
5. **模式一致性**：Iterator Backtest、Replay、Paper、Live 使用同一事实/状态协议；模式差异只存在于 Feed、Venue 和延迟模型并写入 Manifest。
6. **无死循环**：自调度事件、重试、WebSocket、任务和插件拓扑均有预算、终止或环检测测试。
7. **慢消费者安全**：WebSocket/StateReplica 出现慢客户端、满队列和投影落后时只降级读模型，不阻塞交易热路径。

可视化专项修订稿见：[Qianxing Visualization Architecture V1](../Qianxing-Visualization-Architecture-V1.md)。
