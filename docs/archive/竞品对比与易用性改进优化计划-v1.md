## 1. 一页结论

**我们现在的位置**：一个把"可复核"做到极少项目做到的框架 —— 515 条架构判据、997 条 Rust 用例、52 份模板全量被真实读取者覆盖、回测/Paper/Live 风控同源且有契约测试咬住、产物带输入指纹。它已经越过了"能跑"和"经得起审计"两道门。

**它还不是一个"别人愿意用"的产品**。三个词概括差距：

1. **看不见** —— 没有图表、没有 HTML 报告、没有任何 GUI。竞品默认交付一张标注买卖点的 K 线图或一份交互式 HTML（freqUI、Jesse 的本地 Web GUI、LEAN 的云端 HTML 报告、Hummingbot 的 Streamlit Dashboard）。我们交付 `*.equity.csv` / `*.fills.csv` / `summary.json`，把"读结果"这件事留给了用户自己。
2. **跑不起来第二遍** —— 没有参数寻优、没有 walk-forward、没有样本外切分。`walk_forward|hyperopt|optuna` 在 `crates` 与 `python` 下 **0 命中**，只在一份归档方案文档里作为计划存在。竞品把"回测→调参→再回测"做成一条 CLI 旗标。
3. **没被真实市场验证过** —— `sandbox_tested: true` **0 颗**，21 条能力全部停在 `code_tested`。Freqtrade 官方核验 21 家交易所、Hummingbot 声称接入 140+ 交易场所并有 paper_trade 柜台。我们的测试网验收脚本 `tools/binance_testnet_acceptance.py` 是 fail-closed 设计（无凭据退 3），执行方案也已成文（`docs/外部链路验收执行方案-V1.md`：三段链路 + `--send-orders` 分档 + `sandbox_tested` 翻转规则，87 行）。**闸门与方案都是对的，缺的只有"过一次"，而那一步的前置条件是一个可用的测试网凭据。**

**易用性的最大单点**：一个新用户拿到 exe 之后，第一件事是问"我跑的是哪个构建" —— `--version` 与 `version` 双双退 2。第二件事是"我这条命令写对了吗" —— `doctor` 吃位置参数、`backtest builtin` 吃 `--config`，两种参数形状在同一命令面并存，而"未知命令"的回显是 161 行整篇摘要，新手要在一面墙里找自己那半行错。

**计划**：P0 合流（前置，需用户先提交）→ P1 版本与诊断出口 + 错误回显分级 → P2 十分钟首跑路径固化 → P3 结果可读性（无依赖 SVG + HTML 报告）→ P4 参数研究与样本外 → P5 数据自助 → P6 通知与部署配方 → P7 测试网真验收。P1–P3 是高收益低成本，P4/P7 是决定"能不能被当成研究工具用"的分水岭。

**明确不做**：Web GUI、云端服务、多语言文档站、指标库（TA-Lib 级 200+）。理由见 §7。

### 4.3 我们真实更强的 5 项（避免单向愿望清单）

1. **三态同源有门禁背书**：回测/Paper/Live 风控同源且被共用契约测试咬住；竞品普遍只在文档口头承诺 parity，Nautilus 官方文档亦承认延迟/对账差异。

3. **可复现产物**：输入指纹 + 产物哈希 + 来源声明进报告（#66/Q1b）。六家竞品均未见等价机制。
4. **运行期零依赖单文件分发**：11.9 MB exe、39–48 ms 冷启动、无 pip/conda/Docker 环境地狱（本轮实测）。竞品除 vn.py 发布包外都要求先解决 Python 环境。
5. **文档即门禁**：端点表、输出字面量、模板份数、词表与代码逐轮核对，515 条判据钉住；成熟竞品文档漂移是常态。

## 5. 改进优先级怎么定

三个轴打分：**首晚可感知**（新用户第一小时是否撞得上）、**不可复核风险**（做错会不会污染结论）、**与单 binary 契约定位的一致性**。

- 高首晚可感知 + 低风险 → 立即做（P1、P2、F1、F10）。
- 高首晚可感知 + 高不可复核风险 → 做，但**先定口径再写代码**（P4 参数寻优：若不把"寻优过程"本身纳入输入指纹，就是给"同一份输入只能有一个结果"这条既有纪律开倒车）。
- 依赖外部条件（凭据/网络/商业协议）→ 登记为阻塞项而非任务（P7 需用户提供 Binance 测试网凭据；F8 需厂商协议）。
- 与定位冲突 → 明确不做并写下理由（§7）。

## 6. 详细改进计划

统一收口链沿用本仓既定 15 步：取证 → 改前实测 → 修复 → 行为判据 + 模块挂载 → 变异反向验证 → 门禁 → 整树测试 → fmt/clippy → 九步构建 → 发布物载荷复核 → `/metrics` 发布面实测 → 干净 venv 冒烟 → 文档（CHANGELOG + V13 §9.x + capabilities + 接口文档）→ 终树复跑总账 → 列出可暂存路径并停止。下文每个阶段只列**该阶段特有的验收判据**。

### P1｜版本与诊断出口（最小成本，最先做）

任务

## 7. 明确不做，以及为什么

| 不做 | 理由 |
|---|---|
| 自研 Web GUI / 交易面板 | GUI 是持续维护承诺（freqUI、Jesse GUI 背后是专职前端与长期 issue 流）。我们的 HTTP 读面 + `/metrics` 已是机器可读出口，正确做法是把 JSON 契约做稳（P3/P6）而不是养一个 UI。 |
| 云端托管 / 账户体系 | 与"本地可审计单 binary"的定位冲突，且引入凭据与合规面。 |
| TA-Lib 级指标库（200+） | 指标数量不是采用率瓶颈；瓶颈是"结果可不可看、参数可不可搜、市场可不可验"。要做也只做研究常用的 20–30 支，且每支都要有对拍用例。 |
| 多语言文档站（i18n） | 中文主场是有意的产品选择（vn.py 45.7k stars 证明中文不缺市场）。代价认了。 |
| 贝叶斯/并行寻优（第一版） | 先把样本外诚实做对；算法先进但结论不可复现是更坏的结果。 |
| A 股柜台接口（CTP/XTP 等） | 无厂商协议（`unavailable_without_vendor_protocol`），非代码问题，等商业条件。 |

## 8. 风险登记

1. **合流是最大风险，不是本文的改进项**。27 颗冲突 + 两套门禁实现 + 两个互斥的用例地板；若处理顺序错了（例如先把上游门禁整篇取过来），会得到一棵"全红但不是判据不咬"的树，那种树按本仓纪律只能作废重跑。
2. **可复现性与新功能面的冲突是结构性的**。P3 的图形产物、P4 的寻优结果都进了"产物"却没进"指纹"的话，等于给既有纪律开洞；每一步都要先回答"这个东西的身份由什么决定"。
3. **易用性改造会引入新的静默失败面**。全局 `--config` 别名、quickstart 的多步编排、通知的异步出站，三处都是"错了也退 0"的高危形状，必须每处配一条"摘掉即红"的变异。
4. **文档面继续变胖而不解决采用率**。V13 已经写到 §9.32（第二十六遍）、规模在十万字节量级以上；本文之后的改进应以"命令级教程 + 参考手册分层"补 README 侧，不再扩审计文档。
5. **P7 是唯一能把"诚实登记"变成"已验证"的一步，也是唯一可能推翻既有分类的一步**。在拿到凭据之前，本文所有关于"实盘可用"的表述都必须保持 `code_tested` 措辞。
