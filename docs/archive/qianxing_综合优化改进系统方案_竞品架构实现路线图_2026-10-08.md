
# 牵星 Qianxing 综合优化改进系统方案
## 多轮审计汇总 · GitHub 竞品对比 · 目标架构 · 详细实现 · 发布体系 · 未来路线图

**项目：** `coeasy/qianxing`  
**文档性质：** 综合架构与工程落地方案  
**基线：** 2026-10-08 公开仓库状态 + 前序多轮审计结论  
**目标：** 将牵星从“高确定性回测 / Paper 内核”进一步收敛为可长期演进的多市场量化交易平台

# 1. 执行摘要

牵星当前最有价值的方向不是继续无边界增加功能，而是把已有能力收敛成一套稳定、可验证、可扩展的统一交易平台。

当前仓库已经形成以下重要基础：

- Rust 确定性内核
- Bar / L1 / L2 多档位回测
- Paper 闭环
- 多交易所 / 多数据源 / 多账户 / 多策略建模
- 账户、订单、成交、Ledger、对账、EventLog
- Runtime / Supervisor / Scheduler / Outbox
- HTTP / WebSocket API
- Python / C++ 策略边界
- SQLite / PostgreSQL / NATS 的可选基础设施
- schema / maturity / architecture gate
- 安装、quickstart、wheel、模板契约与发布物验证

公开仓库当前已经将“主体链路是否贯通”从单纯人工判断推进到了机器可验证阶段；最新 V13 记录已经覆盖 600+ 架构门禁、1000+ Rust 测试和多轮终止性、浏览器准入、协议一致性、发布物验证。

因此下一阶段的核心目标应从：

> “继续修一个问题”

升级为：

> “建立一个不会轻易重新产生问题的系统”。

最终目标建议定义为：

> **Deterministic Trading Kernel + Unified Market Domain + Unified Execution/Reconciliation + Schema-first Control Plane + Optional Web Console + Evidence-driven Release System**

# 2. 现状判断

## 2.1 当前定位

牵星目前最适合的产品定位：

> **确定性量化研究、回测、Paper 与交易执行基础设施。**

而不是立即把项目包装成“已经完成所有券商实盘接入的生产交易终端”。

当前 README 已明确：

- 真实账户生产能力仍需要逐家 sandbox / production evidence；
- plugin 是静态装配，而不是运行时热插拔；
- Backtest 与 Paper 共享规则语义，但不是完全相同的撮合机；
- 当前不包含跨节点 HA、WASM、券商柜台协议和逐家生产签名实现。

这类边界声明应该保留，因为它实际上提高了项目可信度。

## 2.2 当前最大的优势

### A. 正确性意识强

当前设计坚持：

- 金额 / 价格 / 数量使用确定性定点；
- 回测不依赖系统墙钟；
- 顺序敏感路径避免无序容器；
- 不使用不稳定的 DefaultHasher；
- 固定 RNG 语义；
- 同时间戳按因果优先级处理；
- 防止 cheat-on-close；
- EventLog 是事实源；
- Projection 不反写交易状态；
- null 与 0 语义分离。

这套原则应继续作为项目的“不可侵犯层”。

### B. 证据链意识强

当前已经形成：

`代码 → 测试 → architecture gate → capability matrix → 文档 → release artifact`

这比大量量化项目只维护“能运行的 demo”成熟得多。

### C. 多语言能力已经具备基础

Rust / Python / C++ 都有策略边界。

下一阶段不应该继续增加语言数量，而应该：

> **统一策略协议，减少语言之间的语义漂移。**

# 3. GitHub 优秀竞品对比

## 3.1 NautilusTrader

项目：

https://github.com/nautechsystems/nautilus_trader

NautilusTrader 是最值得牵星重点研究的竞品之一。

它采用：

- Domain Driven Design
- Event-driven architecture
- Ports & Adapters
- Crash-only design
- DataEngine
- RiskEngine
- ExecutionEngine
- Portfolio
- Trader
- MessageBus
- Cache
- Backtest / Sandbox / Live 环境

其架构特别值得借鉴的是：

> Backtest / Sandbox / Live 共享核心系统，但环境差异通过 data / execution / persistence / timing / reconciliation 等边界表达。

同时它把 live reconciliation 当成一等公民，而不是异常补丁。

### 对牵星的启示

应该进一步强化：

```text
Environment
 ├── BACKTEST
 ├── PAPER
 ├── SANDBOX
 ├── LIVE
 ├── REPLAY
 └── RECOVERY
```

环境不应该复制 Order / Risk / Ledger / Strategy 逻辑，而应该只替换：

```text
Clock
MarketDataSource
ExecutionVenue
PersistencePolicy
ExternalSideEffectPolicy
ReconciliationPolicy
```

## 3.2 HftBacktest

项目：

https://github.com/nkaz001/hftbacktest

它的强项是：

- L2 / L3
- Queue Position
- Feed latency
- Order entry latency
- Order response latency
- 多资产
- 多交易所
- Live bot

尤其值得吸收的是三段延迟模型：

```text
feed latency
    ↓
order entry latency
    ↓
exchange matching
    ↓
order response latency
```

### 对牵星的启示

不要只使用一个：

```text
latency = N snapshots
```

长期应抽象：

```rust
trait LatencyModel {
    fn feed_latency(&self, event: &MarketEvent) -> Duration;
    fn order_entry_latency(&self, order: &OrderIntent) -> Duration;
    fn order_response_latency(&self, report: &ExecutionReport) -> Duration;
}
```

并允许：

- constant
- empirical
- distribution
- venue-specific
- region-specific
- strategy-specific

# 6. 核心 Domain Model

## 6.1 MarketContext

所有交易域对象必须能够定位自己的市场环境：

```rust
struct MarketContext {
    market_id: MarketId,
    venue_id: VenueId,
    calendar_id: CalendarId,
    timezone: TimeZone,
    quote_currency: Currency,
    settlement_currency: Currency,
    margin_currency: Option<Currency>,
    rule_set: RuleSetId,

```

禁止：

```rust

```

这种单字段解决全部问题。

因为：

- quote currency
- settlement currency
- margin currency
- fee currency

可能完全不同。

# 12. Execution State Machine

统一订单状态：

```text
CREATED
 ↓
VALIDATING
 ↓
RISK_ACCEPTED
 ↓
SUBMITTING
 ↓
ACKED
 ↓
PARTIALLY_FILLED
 ↓
FILLED
```

异常：

```text
REJECTED
CANCEL_REQUESTED
CANCELLED
EXPIRED
UNKNOWN
```

特别增加：

```text
UNKNOWN
```

原因：

网络超时不等于订单没有成交。

因此：

```text
Submit timeout
       ↓
UNKNOWN
       ↓
Venue query / UserStream / Reconciliation
       ↓
ACKED / FILLED / CANCELLED / REJECTED
```

绝不能：

```text
timeout → retry submit
```

否则可能产生重复订单。

# 14. Reconciliation

对账应该是持续机制，而不是启动时的一次命令。

建议：

```text

       ↓

       ↓

       ↓

       ├── MATCH
       ├── MISSING_INTERNAL
       ├── MISSING_VENUE
       ├── QUANTITY_MISMATCH
```

其中：

```text

```

```text

```

# 68. 最重要的战略结论

牵星真正应该建立的护城河不是：

> “比别人多几个指标 / 多几个交易所 / 多一个策略。”

而是：

> **任何一笔交易、任何一次回测、任何一个数据结论，都能够说明：它从哪里来、经过了什么规则、为什么产生、如何复现、发生差异时在哪里出现。**

因此建议将牵星的核心品牌能力定义为：

```text
Deterministic
Traceable
Reproducible
Auditable
Multi-Market
Extensible
```

最终产品形态：

> **牵星 = 面向多市场、多资产、多账户、多策略的确定性量化研究与交易基础设施。**

# 70. 本方案与当前仓库的关系

本方案是“下一阶段系统级目标设计”，不是声称当前仓库已经完成全部目标。

当前仓库已经完成大量工程化收口，但以下项目应继续作为显式路线：

- Web Console
- 完整浏览器级 API → UI E2E
- 更完整的多市场 / 多账户 / 多策略组合矩阵
- Production venue evidence
- Sandbox acceptance
- PostgreSQL / NATS 的真实环境验证
- Broker gateway
- 分布式 HA / DR
- 完整 Research / Experiment 平台

尤其需要保持：

> **代码已实现 ≠ 生产已验证 ≠ production approved**

这三层证据必须继续分开。

# 71. 建议建立的最终工程管理机制

每一个新功能建立一张：

```text
Capability Card
```

字段：

```yaml
id:
name:
owner:
status:
producer:
consumer:
schema:
runtime_effect:
observability:
tests:
mutation_tests:
replay_safe:
recovery_safe:
security_review:
sandbox_evidence:
production_evidence:
docs:
```

这样未来即使项目从 6 万行扩大到几十万行，也不会重新退化成“靠人工 grep 找断链”。

# 72. 结论

综合多轮审计与竞品对比，牵星不需要推倒重写。

最佳路线是：

```text
保留 Rust Deterministic Kernel
        ↓
统一 Domain / Identity
        ↓
统一 Event / Schema / Execution / Reconciliation
        ↓
加强 Data / PIT / Calendar / Multi-currency
        ↓
建立 Research Workflow
        ↓
建立 Web Console
        ↓
完善 Sandbox / Production Evidence
        ↓
最后再做 HA / Ecosystem
```

最重要的工程策略：

> **不追求一次性“功能大全”，而追求每增加一个能力，都能被 Domain、Schema、Runtime、Test、Evidence 五个层次同时接住。**

这会比继续堆功能更有长期价值。
