## 4. 不合理清单（按影响分级）

### P0 —— 数字或断言会骗人

1. **两个读模型把"产物根本没声明的块"印成 0**
   `report` 的读侧助手是 `integer(pointer) = summary.pointer(pointer).and_then(as_i64).unwrap_or(0)`
   （`crates/qx-cli/src/config_commands.rs:295-299`）；`status` 的 `[Latest Backtest]` 行同形
   （`:419-431`，`fills` / `/metrics/return_bps` / `/metrics/max_drawdown_bps` 三处 `unwrap_or(0)`）。
   键不存在与"真值为 0"渲染成同一个 `0`。而 16 份 git 跟踪的 blessed 产物停在 `schema_version: 1`
   （本轮实测：`git ls-files | grep summary.json` → 16 份，`schema_version` 计数 `{1: 16}`），
   代码写到 `4` —— 用 `report` 读那 16 份时，`input` / `account` / `replay` 全部按 0 或 `-` 印出。
   这与 Q67/Q68/Q70 建立的"absent ≠ zero"纪律直接冲突，且是它唯一还没覆盖的读侧。
2. **协议版本门禁只防"前后不一致"，不防"两边一起编"**
   `crates/qx-protocol/src/lib.rs:493-513` 只把顶层 `schema_version` 与 `header.schema_version` 比对，
   缺失时**还会用顶层值补写 header**；而 `schemas/account-snapshot-v1.json:9` 声明 `"const": 1`。
   于是一份自洽的 `schema_version: 7` 快照会被 `from_json` 接受，"契约校验"这句话在这条路径上不含任何真校验。
   （本轮为静态证据；行为探针留到 R1 那轮做，避免文档写没跑过的东西。）
3. **多腿 `cost_bps` 的可表示性上限取 `i64::MAX`，零成交时又取 0**
   `crates/qx-cli/src/backtests/multi_builtin.rs:380-385`：
   `i64::try_from(...).unwrap_or(i64::MAX)` 与 `else { 0 }`。前者把一个诊断量推到天文数字，
   后者把"没有成交额"与"成交额非零但费用为零"合成同一个 `cost_bps=0`。
4. **本金两个入口不交叉校验**
   `strategy.initial_cash_raw`（回测侧，Q72）与 `worker.paper_initial_cash_raw`（paper 侧，
   `venue_runtime/paper_submit.rs:10`）互不知情：同一份 runtime 配了两者也不报错，
   使用者会以为"我声明了一份本金"。
5. **多腿链没有 summary 产物**（§3）：归因数字只在 stdout，无法被别人重算/bless/复核 ——
   单腿四件套有的东西它一样都没有。

### 13.3 两颗曾经"绿得对但没意义"的变异，本轮才真的咬住（本轮最实质的收获）

轮 5 日志里 M4 与 M6 的行为口径是 `ok`（`4 passed; 0 failed`、`8 passed; 0 failed`）—— 静态判据亮了，

1. **M4 是覆盖缺口**。`input_verified=` 是整份报告里唯一回答"这份产物的输入有没有按声明重算过"的一格，
   而全仓（含新增的读侧用例集）没有任何断言提到它：本轮补用例之前，
   `grep -rn "input_verified" crates/` 只命中生产代码的 6 处（`config_commands.rs:290/295/297`、
   `report_readout.rs:89/91/115`），一处断言也没有。

   → 补两条：`report_prints_the_recompute_verdict_as_its_own_field`（真子进程，断言
   `input_verified=not_declared` 与"输入身份未经核对"）与
   `readout_gives_the_recompute_verdict_its_own_field_verbatim`（排版层，断言调用方结论串原样入格）。
   轮 6 里 M4 两口径 `1 failed` / `1 failed`，轮 7 复跑同一格逐字不变。
2. **M6 是纵深，但纵深在能被证伪之前不等于纵深**。`from_json` 的 header 版本号由顶层归一：

   所以旧用例无论怎么断言都分不出是哪道闸门拦的。这就是轮 5 那个 `ok` 的全部原因，它不是漏洞。
   顶层闸门真正独有的职责只有一件：**在字段解析之前**把一份未来契约叫住。于是补的那条就往这一件下手 ——

### 14.4 第三遍当场抓出的存储断链（TX5）

`AccountSnapshot::to_json()` 是手写的稳定编码器，而 `orders` / `fills` / `transfers` 三张表按 `u64` 建键：
键原样拼进 `{}` 时**产出的不是合法 JSON**；订单行的 `instrument` 落显示串、`side`/`status` 落数字码，
而 `OrderSnapshot` 的派生反序列化认的是内核身份对象与枚举名 —— 折算层根本不存在。合起来的后果是：
**账户一旦真下过单**，`SqliteSnapshotStore` / `FileSnapshotStore` / `GET /account/snapshot` 三条读法
都会在这份快照上当场失败。仓库里原有的往返用例只放 `cash_raw` 与 `positions`，所以这三张表

- 读侧：`wire.rs::fold_stable_order_row`（`:244`）+ 唯一一份方向码/状态码表（`:201`–`:237`），
  未知码一律 `ProtocolError::Invalid`，不兜底猜方向。
- 用例：`rows_keyed_by_integer_still_produce_and_recover_valid_json`（写出→读回→篡改 `side=9`/`status=99` 必须被拒）
  与 `crates/qx-storage/tests/snapshot_rows_persist.rs`（文件与 SQLite 两个后端各跑一次带行快照）。

  门禁 1 红 + 协议用例 `FAILED` + 两个存储用例 `FAILED`；**T2** 摘掉折算调用点 → 同样三处红；

### 14.5 #102：四个信号旋钮按 kind 部分失效（本轮最实质的口径修正）

`fast_window` / `slow_window` / `period` / `threshold_bps` 此前无条件接受配置，但只有部分 kind 真读它们：
`macd` 一个都不读（写死 `MACD_WINDOWS (12,26,9)`、`MACD_REQUIRED_BARS 35`），`rsi` 只读 `period`。
于是"改了参数没反应"是设计内的，而**播报和产物却把它说成生效了**。修法是把准入收成一张表：
`BuiltinStrategyKind::signal_knobs()`（Macd 为 `&[]`）+ `uses_signal_knob()` / `signal_knob_list()`，
内核历史上限、运行时体检、`builtin-strategies` 的生效列、stdout 的 `knobs=… declared_unused=…`、
摘要的 `signal{}` 块全部问这一张表。

**一条对 §6 原方案的偏离必须写清楚**：清单外的旋钮**不 fail-closed**（不报错、不拒跑），而是照常跑并
把它列进 `declared_unused`。理由是这些键同时是历史配置里的兼容项，拒跑会让既有 runtime 全部起不来；
代价是"配了但不生效"这件事只在播报与产物里可见，读者要看的那一列由门禁钉住。

变异（`mutation-r4l*.log`，#102 共 7 颗）：M1（历史上限重新偷读清单外的 `period`）→ 门禁 + 内核用例红；
M2a（把摘要那一格**注释掉**）→ 门禁红 —— 这条判据原先用 `'"declared_unused"' in artifacts` 计数，
被注释行蒙过，改成"块内非注释行按 `key":` 计数"（`emitted_key`）；M2b（整格不写，可编译形态）→
门禁 + 两条 CLI 用例红；M3（运行时体检重新不看清单）→ 门禁 + 2 条红；M4（清单把四个旋钮全说成 macd 读的）
→ 只红内核用例 `macd_has_no_tunable_signal_knob_and_still_signals`，**刻意不给它加文本判据**（再加一条
抄表内容的正则就是自证空转，行为用例才是真闸门）；M5（少印 knobs 列）第一版删格式串列让编译都过不去，
换成 M5b 列与实参一起删 → 门禁 3 条红 + 新加的行为断言（"生效列必须逐项等于内核清单"）红；
M6（深度链多出一处读点）→ 门禁红。

## 16. 三遍连通性清点收口（2026-09-25，日志在 `%TEMP%/qx_v12p2/logs/`）

§15.6 第 4 条把"三遍清点"排给了这一轮。三遍都在**合流之后的代码**上重跑，一遍一个口径：
第一遍找孤儿（有定义没有读者），第二遍找无退出（有循环没有停机条件），第三遍找断链（三端各自

本节值得单独记的不是那 4 个缺陷，而是**量具的第三类瞎法**（前两类在 §14/§15）：契约判据只覆盖

### 16.1 第一遍：孤儿逻辑（#120 / #121 / #122）

三颗都是"代码在跑，但它产出的值没有任何人读"：

### 16.2 第二遍：死循环与无退出条件

一条真断链：API 两条 accept 循环（明文 `serve` 与 mTLS `serve_tls_mtls_with_stores`）都在
`incoming()` 上阻塞，监督器的 `ShutdownToken` 递不进去 —— 停机时进程能退出，但**是在连接上退出的**，
没有连接就一直等。修法是两条循环共用 `await_connection`：先 `stopped()` 判定，再 `set_nonblocking(false)`
取连接。门禁按名字钉住两条循环 + 两个出口 + 闭包接线 + 用例在位（本轮实跑点名 6 条 `[PASS]`，

### 16.3 第三遍：三语言契约贯通（#123）

审计代理报回 1 真 1 小，两条都收：

- **真 BROKEN**：Rust 的 `StrategyContractIntent` 会写 `margin_mode` / `position_mode` / `leverage`
  三个衍生品字段，schema 也认，`python/qianxing_bridge/strategy.py` 的 `StrategyIntent` **根本没有这三格**。
  后果不是报错而是静默：Python 策略作者写不出这三字段，而 Rust 侧 `deny_unknown_fields` 会让带这三键的
  输入整体被拒 —— 多腿衍生品在 Python SDK 上不可表达。补的口径与 `contract.rs:295-304` 逐项对齐

  断"Rust 写得出的，Python 读得回"，`test_intent_rejects_derivative_fields_rust_would_reject` 断"Rust 会拒的取值，Python 也拒"。
- **minor**：`ecosystem` / `paper` / `verify` / `all` 四条命令在文档里不存在。补进 `deploy/README.md`

### 16.4 本轮的通用教训

三遍里唯一值得复用的是这句：**判据覆盖几种语言，就等于只存在几种语言。** 前两类的瞎法（`#[cfg(test)]`
截断、一行注释满足判据）都会在"红"这一侧暴露自己；第三类不会 —— 它连红都不红，Python 侧漂移时门禁
全绿。所以补的是"字段集逐项相等"这种**结构性**判据，而不是"Python 里应该出现 leverage 这个词"。

### 17.1 `build.bat` 的三步失败，每一步都是独立缺陷

1. **解释器口径**：`[5/7] python -m unittest discover …` 与 `[6/7] python tools/validate_core.py`
   直接信任 `PATH` 上的 `python`。本机那个是 WindowsApps 存根
   （`C:\Users\Administrator\AppData\Local\Microsoft\WindowsApps\python.exe`），实测
   `python -c "print(1)"` **退出码 0、什么都不打印** —— 所以"跑一下看退出码"式探测会放它过关，
   真正跑到 `[5/7]` 才失败，失败信息是一句 `python312.dll: cannot open shared object file`
   或空输出，不提该用谁，而且是在 **4 分钟 Rust 门禁之后**。
2. **步骤编号说谎**：标签写到 `[7/7]`，而第 7 步里塞了三条 `cargo run`（`all` / `ecosystem` /
   `runtime-check`）—— 数着标签复核门禁的人会漏掉 `runtime-check` 这道。`build.sh` 是同一个形状。
3. **cmd.exe 根本读不懂这个文件**：这是实测出来的，不在原计划里。四象限矩阵（把命令行逐行 `rem`
   掉、保留全部中文与行尾，跑 dry-run 变体，看退出码与打印出的步骤标记行数）：

   | 变体 | 换行 | `chcp 65001` | 退出码 | 步骤标记行数 |
   |---|---|---|---|---|
   | `W1_lf_chcp.bat` | LF | 有 | **1** | 0（崩在第 5 行 REM） |
   | `W2_crlf_chcp.bat` | CRLF | 有 | 0 | 9（`[0/8]`…`[8/8]` 全出） |
   | `W3_lf_nochcp.bat` | LF | 无 | **1** | 0 |
   | `W4_crlf_nochcp.bat` | CRLF | 无 | 0 | 9 |

   结论：**决定能不能解析的是换行符，不是代码页**（`chcp` 只修显示）。机制是 GBK 前导字节把下一行的
   行首字符吃掉，于是 `REM` 变成可执行语句，命令行打印一串"不是内部或外部命令"后 `exit 1`。
   HEAD 版 `build.bat` 在 LF 下同样崩（`'?REM' 不是内部或外部命令`），只是本机 `core.autocrlf=true`
   让检出恰好是 CRLF，所以这个雷一直没人踩到 —— `autocrlf=false/input` 的克隆会立刻踩。

### 17.2 修到什么程度

- `build.bat` / `build.sh` 同一口径重写：`[0/8]` 先按 **`QX_PYTHON` → 仓库 venv → `PATH` 上的 `python`**

  为什么不只看退出码：本机 `PATH` 上的存根与 `QX_PYTHON=C:\Windows\System32\cmd.exe` 都在
  `-c "import sys"` 上返回 0（前者空输出、后者忽略参数），旧式探测会把它俩都当 Python 放行 ——
  实测换成"必须打印出版本号"之后，两者都在 `[0/8]` 被拒。

### 19.1 #133：构建脚本探测出的解释器，从没交给 Rust 侧

`build.bat` / `build.sh` 的 `[0/8]` 会按 `QX_PYTHON` → 仓库 venv → PATH 的顺序挑一个"能真打印出
版本号"的解释器，但挑完之后只把它存进脚本自己的变量。Rust 侧读的是**另一个**名字：
`crates/qx-cli/src/main.rs:273 python_interpreter_origin()` 只认 `QX_PYTHON`，而 `[3/8]` 的两条 Python
桥契约用例和 `[7/8]` 的策略 worker 都是由 Rust 去起 Python 的。于是本机（裸 `python` 是 WindowsApps
占位桩）实跑：

```
[3/8] ... test result: FAILED. 202 passed; 2 failed
  rust_invokes_python_strategy_jsonl_worker_through_versioned_contract ... FAILED
  rust_invokes_python_multi_intent_strategy_contract ... FAILED
BUILD_BAT_EXIT=1        （s20r_build_bat_full.txt）
```

也就是说 `[0/8]` 那一步自 §17 加进来之后**从来没有真正生效过**：脚本自己找到了能用的解释器，
cargo 却拿不到，第 3 步照旧回落到桩。修法只有一句交接：

- `build.bat`：探测成功后、`[1/8]` 之前，用 `for %%I in ("%QX_PY%") do set "QX_PYTHON=%%~fI"`
  把仓库 venv 那一档**绝对化**后导出（`QX_PY` 是 cmd 变量，永远进不了 cargo 的环境；用户已设
  `QX_PYTHON` 时原样保留，PATH 上的裸 `python` 不改写成一个不存在的路径，留给它自己的占位桩诊断）；
- `build.sh`：同一口径的 `export QX_PYTHON`。

修后实测 `s19_build_bat_fix.txt`：`[0/8]` 多印一行 `QX_PYTHON 已交给 Rust 侧 = P:\github_public\qianxing\python\.venv\Scripts\python.exe`，
`[3/8]` 变成 **92 个 `test result: ok.` 段 / 843 passed / 0 failed**，八步全过，`BUILD_BAT_EXIT=0`。
编辑过程中还踩实了一条 Windows 侧硬约束：用 `sed -i` 改 `.bat` 会把 CRLF 抹成 LF，门禁当场红在
"有 98 个孤立 LF"；归一化只能用按字节的 `raw.replace(b"\r\n", b"\n").replace(b"\n", b"\r\n")`。

### 19.3 本轮新增判据里的两颗"假绿"（#136 / #138）

这两颗都不是产品缺陷，是**量具缺陷**，而且都只可能在变异反向验证里现形：

1. **#136**：M2（把 `build.sh` 的 `export QX_PYTHON` 换成 `QX_PYTHON_READY=1`）跑完门禁 **exit=0、红 0 条**。

   `echo "       或: export QX_PYTHON=/完整路径/python3.12"`。判据把"脚本告诉用户怎么做"读成了
   "脚本自己做了"。修：`interpreter_handoff()` 跳过 `echo` 开头的行（与 §19 早前那个 `#\b` 永不匹配

   对列表用 `in` 判的是"存在一整行正好等于 `CrossedBook`"，因此 `revived` 恒为空、判据恒绿。

两颗合起来是 §17.4「判据可以整段消失而门禁全绿」的第 3、4 个实例，形状也不同：那次是**没人调用**判据函数，

### 19.6 本轮把"零生产者变体"这条判据形状推到全仓，又收了回来

`#135` 的形状（定义之外零出现）用一次性脚本 `t_scan_variants.py` 扫了全仓 `pub enum` 变体、`pub trait`
与顶层 `pub struct`，报出四颗候选，逐颗判定后**本轮一颗都不动**：

- `qx-risk::RiskDecision::Rebalance` —— 内核 `evaluate()` 只返回 Allow/Reject/Reduce，全仓没有一条
  `match` 臂认它，看着是纯孤儿；但 `RiskDecision` 带 `Deserialize`，删变体会让 `"rebalance"` 从
  "静默降级"变成"反序列化失败"，这是对外行为改动，不能夹在收口轮里做。
- `qx-zhenlu::ConnectorState::Connecting` —— `crates/qx-adapter/src/binance.rs` 只赋过
  Live/Snapshotting/ReconcileRequired，`schemas/` 与 `python/` 里也搜不到 `connecting`，是最像真孤儿的一颗。
- `qx-provider::ProviderErrorClass::Retryable` —— 全仓只构造 Permanent/SwitchProvider/ManualIntervention，
  `crates/qx-provider/src/lib.rs:466` 的读者只认两种。注意 CCXT worker 的 `error.class` 字符串在
  `crates/qx-adapter/src/ccxt.rs:181` 只被拼进错误消息，**没有**映射进这个枚举，所以它不是"数据侧生产者"。
- `qx-data::CorporateActionType::{Split, Merge}` —— 看着最像假阳性：该枚举带
  `#[serde(rename_all = "snake_case")]`，线格式 `"split"` 是合法生产者。**这颗正是扫描器本身量不出来的
  东西**（按裸名字数出现，读不到 serde 的隐式映射），也因此不能拿扫描结论当删除依据。

判定口径记下来：**扫描器报"零出现"只够立案，不够动手**；动手前必须单独证明它没有 serde 隐式入口、
没有对外矩阵/文档引用。`quality_issue_producer_check` 因此仍只对 `QualityIssue` 生效 —— 那个枚举
没有 `Deserialize` 的隐式入口，判据才咬得住。这条已作为 #137 挂在下一轮。
