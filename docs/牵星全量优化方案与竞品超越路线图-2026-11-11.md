# 牵星全量优化方案与竞品超越路线图

日期：2026-11-11
适用范围：研究、回测、Paper、实盘交易、数据、可视化、观测、发行和运维
状态：实施计划；文中的性能目标是待测目标，不是当前实测结论。

本文将现有架构方案、数字资产实盘审计、能力目录与最新代码变化合并为一份可执行路线图。它不替代各模块设计文档；实施时以代码、版本化协议、能力矩阵和验收证据为准。

## 1. 目标与原则

目标是让用户从安装到“取真实历史数据、选择常见策略、运行可信回测、查看交互结果、切到 Paper、按交易所能力进入 Demo”有一条短而可靠的路径；同时让专业用户获得高吞吐、可复算、多账户隔离、可追踪和可恢复的工程能力。

“超越竞品”按各类可量化能力分别验证，不用一句总评掩盖取舍：

- **执行效率：** 对同输入、同撮合语义、同硬件和同结果正确性，测回测吞吐、批量参数实验耗时、数据导入速度、峰值内存和实时信号到提交的本地耗时。
- **核心流程：** 安装、取数、策略选择、回测、诊断、报告、Paper、Demo 各阶段有贯通入口和可恢复状态；步骤失败时定位到具体数据、参数、账户、订单或运行 ID。
- **易用性：** 新用户可以一条 quickstart 得到可视化报告；从样例数据切换到真实数据、从回测切换到 Paper、从 Paper 切换到 Demo 都能明确看到新增前置条件。
- **可视化：** 回测、策略比较、数据质量、订单生命周期、账户持仓和运行健康共用同一套可核对的事实模型。
- **可观性：** 每个运行、策略、账户、交易所、订单组、订单和成交可通过稳定 ID 串起日志、指标、事件与报告；故障可从 Unknown/部分成交继续对账。

安全与事实原则：无凭据不访问私有接口；没有交易所证据不标为已验收；没有 OOS 证据不称策略有效；本地模拟不称实盘成交；不支持的订单形态必须在提交前拒绝。

## 2. 当前代码基线

截至 `61e74452`：

- `qx-strategy` 已有 17 种内置 Bar 策略：13 种单标的策略及 4 种双腿策略。单标的包括 SMA/EMA 交叉、MACD、RSI、布林带、Donchian、动量、均值回归、网格、ATR、Keltner、VWAP 和波动突破。双腿策略包括配对、基差、跨所和现货期货套利。
- 单标的策略输出目标仓位意图，已有不同仓位 sizing、风险门禁、回测和实时策略 worker；现有 `quickstart --strategy` 能为单标的策略建立样例回测项目。策略库存不是当前的主要缺口，缺口是策略配方、真实数据选择、成本/风险/保护设置和研究到运行的更短工作流。
- Binance Spot 原生执行及 Binance/OKX/Bitget 的 CCXT Market/Limit 主链、杠杆/持仓模式核对、部分市场过滤器、订单查询/撤单/恢复已有本地实现；能力矩阵仍标记为 `implemented-unverified`，不代表沙盒验收。
- 本路线图之后，单笔 trigger/stop-loss/take-profit/trailing 意图已进入 Rust 精确订单请求、SubmitOrder 幂等身份、CCXT worker 路由与 Python 按市场 feature 的拒绝式预检；Paper/Binance Direct 未声明这些能力时会在通用门禁拒绝。其 OKX/Binance/Bitget CCXT 产品形态现已列入逐产品 execution-scope，但仍标为 `implemented-unverified`，无 Sandbox 证据，生产预检不会因此放行。CCXT Python 适配器的原生 `edit_order` 已明确 `amount_exact` 为改单后总量，并在发出改单前读取活动订单，拒绝新总量不高于累计成交、终态订单及方向/市价限价类型变更；此入口尚未接入 Rust Venue/OMS/账本/恢复，也没有交易所验收证据。链路核查确认改单仍未进入执行端口和交易所能力门禁，因此不可对外标为端到端可用。
- 2026-11-11 单改单意图已通过持久 `OrderAmendmentPending` / `OrderAmended` 进入执行端口、CCXT Venue、CCXT Execution worker、Control API、Python SDK 和网页控制台。改单前做订单快照、路由、风险、余额、市场规格及原生 editOrder 预检；写 pending 后才触达交易所；确认结果须经过权威 `fetch_order` 核对。条件单与 quote-budget 单、Paper 和 Binance Direct 仍 fail-closed。未知结果持久化后禁止重复改单。
- 2026-11-11 继续将 pending 恢复接入 CCXT Reconciler：重启后只读取原远端订单；只有远端总量/限价精确匹配持久请求，才追加改单确认并归约随后取得的成交/取消事实；条款仍不匹配或查询异常则保持 pending，不会补发 editOrder。CCXT adapter 恢复测试 2/2 通过，服务 reconciler 编译通过。逐交易所 sandbox、已发生并发成交时的恢复语义、远端仍为旧条款时的最终解除方式及人工审批操作面仍未完成，因此改单能力依旧是 `implemented-unverified`，不能称为交易所验收。
- 订单组、附属保护腿 ID/生命周期、独立 OCO、统一改单/撤单重挂语义仍未全部进入 OMS、账本和恢复链路；现有改单只覆盖普通 Market/Limit 单。
- OHLCV 分页已修复 OKX 短页导致的历史截断；仍需将时间轴连续性、重复/缺失 bar、未收盘 bar、源切换和数据新鲜度作为统一 Dataset Quality Contract。
- 核心金额、数量、价格仍有 `1e9 raw` 与精确十进制 sidecar 并存。账簿和部分协议支持精确金额，不代表所有风险、Paper 撮合、订单 wire、策略 sizing 和报表均支持任意精度。
- HTML/SVG/JSON/XLSX 报告、账户活动 API、CLI 健康检查和 maturity 能力目录已存在；尚缺统一实时操作台视图、统一 trace/metrics、性能容量基线，以及所有声明能力的逐交易所沙盒证据。

实现前每个任务先更新 `maturity/capability-matrix.yaml`、相关 schema/fixture 和成熟度状态；实现后再生成目录，不允许先把能力状态改为 verified。

## 4. 目标架构和核心对象

### 4.1 一条研究链、一条交易链

```text
研究：数据源 → 校验/冻结 → 策略与参数 → 回测/搜索/OOS → 结果身份 → 报告/比较/复算

交易：策略意图 → 能力/单位/规则检查 → 账户预留与风控 → OMS/幂等提交
     → 交易所原始回报 → 订单组/子订单归约 → 账本 → 对账/恢复 → 操作台
```

两条链共享 Instrument、费用/成本模型、策略意图、运行 ID 和报告事实；订单提交不能绕过 Runtime/Risk/OMS 直接从 Python worker 调交易所。

### 4.2 版本化的领域订单意图

扩展领域订单模型，不把交易所私有参数字典作为稳定 API：

1. **基础单：** Market、Limit、PostOnly、IOC、FOK；显式价格/数量单位、有效期和 client ID。
2. **条件单：** Trigger、StopLoss、TakeProfit；触发价、触发价来源（last/mark/index）、触发后执行方式（market/limit）、执行限价。
3. **追踪单：** activation price/type、callback ratio/spread、触发后执行方式；精度和范围受市场能力规则约束。
4. **保护组：** 订单附属止损/止盈、持仓保护组、独立 OCO 两腿组。记录 group ID、parent/child IDs、数量来源、部分成交后的保护数量和一腿成交时另一腿的原子取消语义。
5. **改单/撤单：** 新总量与已成交累计量的语义明确；区分 native amend、cancel-replace 与普通 cancel/new。不能把撤单重挂称为原子改单。

新增 `OrderGroup` / `OrderLeg` 生命周期事实：创建意图、提交中、部分受理、活动、部分成交、一腿触发、对端取消中、终结、Unknown/需对账。进程超时后的提交结果、改单结果和 OCO 对端取消结果均进入对账，禁止盲目重发。

精度和数量必须在领域边界带单位：BaseQty、ContractQty、QuoteBudget；Money/fee 带币种；价格、触发价格和比例明确 scale/rounding。兼容旧 raw schema，新增字段进入新的 schema/hash 版本，并提供旧产物只读解析与迁移工具。

### 4.3 Venue Capability Profile

能力键至少由 `venue × product × account_model × position_mode × order_intent × operation` 组成。能力状态分 `implemented`、`code_tested`、`packaged`、`sandbox_tested`、`production_approved`。静态矩阵、CCXT 能力表和市场规则快照共同门控运行；只有具备对应成熟度证据才对 UI 显示可用。

## 5. 交易所实现方案

交易所适配保持窄端口：行情/规则、账户查询、订单提交、订单组/改单/撤单、回报和对账各自独立；CCXT 是一条适配路径，不覆盖供应商账户模式差异。

| Venue / 产品 | 规则与领域映射重点 | 实施顺序 |
|---|---|---|
| OKX Spot / Swap | 每笔普通单传正确 `tdMode`；Hedge 使用 `posSide`；合约量以 contracts；附加 `attachAlgoOrds` 与独立 `/trade/order-algo` 区分；独立 algo 的查询、撤销、修改及 child IDs 要进同一订单组。保护单仅在父单成交时激活等状态事实要保存。 | Spot 普通单 → Swap OneWay/Hedge → parent-attached TP/SL → independent algo/OCO/trailing → amend/recovery |
| Binance Spot | OCO 是 order-list 资源而非普通单；保存 orderListId 和两个 order IDs，成交后核对另一腿取消。普通 amend 与 cancel-replace 是不同操作，明确 `cancelReplaceMode` 语义。完整读取过滤器及账户级限制。 | 过滤器补齐 → Spot OCO/order list → cancel-replace → user stream 恢复 |
| Binance USDⓈ-M / COIN-M | 普通单与 conditional/algo 单区分；核对当前 API 的 New Algo Order/Modify/Cancel Algo Order；Hedge 的 `positionSide` 与 `reduceOnly` 互斥限制；不同产品条件单规则及 trailing activation/callback 范围独立登记。 | USDⓈ-M OneWay → Hedge → algo stop/TP/trailing → amend/cancel/reconcile → COIN-M 单独验收 |
| Bitget Classic | 合约开平按 `side + tradeSide`；保证金/币种字段使用 Classic 契约；追踪、计划单、改单和 OCO 按 Classic endpoint 单独能力登记。 | Spot → USDT-Futures Classic OneWay/Hedge → conditional/protective → amend/reconcile |
| Bitget UTA | 不混用 Classic `marginMode/marginCoin` 请求形状；按 UTA `category/qty/posSide` 与 account settings 处理。UTA strategy endpoints 的 OCO 和 trailing 支持随产品线不同：官方矩阵中 OCO 对 Spot/Margin 可用但对 USDT/COIN Futures 不可用，trailing 也有产品差异。锁定 CCXT 版本未暴露能力时，先评估升级并跑请求契约；必要时增加独立 UTA adapter，不伪装成通用 CCXT 支持。 | UTA 普通单 → `tpsl/trigger` → 按产品支持的 `oco/trailing_stop` → sub-order 查询/恢复 |

来源合同须随实现复核：[OKX V5](https://my.okx.com/docs-v5/en/)、[Binance USDⓈ-M trade API](https://developers.binance.com/docs/derivatives/usds-margined-futures/trade/rest-api/New-Order)、[Bitget UTA Strategy Order](https://www.bitget.com/legacy-docs/uta/strategy/Place-Strategy-Order)、[CCXT createOrder capabilities](https://github.com/ccxt/ccxt/wiki/Manual)。官方接口支持只说明可实现，不说明当前牵星或当前 CCXT 版本已经支持。

## 6. 内置策略和开箱即用体验

不重复实现已有 17 种信号。将其整理成版本化 **Strategy Recipe**，每条包含策略目的、适用产品/时间周期、可调参数、预热长度、目标仓位规则、允许做空条件、成本模型、退出/保护意图、示例数据要求、风险说明和已验证入口。

第一批交付：

- 单标的模板：趋势（SMA/EMA/MACD/Donchian/ATR/Keltner/波动突破）、反转（RSI/Bollinger/mean reversion/VWAP）、网格和 momentum。
- 双腿模板：pairs、spot/perpetual basis、spot/futures、cross-venue；必须声明两腿数据、数量/对冲比例、资金费/借贷成本、腿不同步和部分成交风险。
- 默认 short policy：Spot Cash 不做空；Spot Margin 须显式开通/借币规则；Perpetual/Future 只有产品规格、账户权限、持仓模式、杠杆和 RiskGate 验证通过后才能开空。
- `quickstart --strategy` 生成配方、样例配置与报告；真实数据 quickstart 显式指定数据源/市场/时间范围，不用合成数据冒充行情。
- 策略结果必须分开报告 long/short 贡献、仓位暴露、换手、资金费、手续费、滑点、回撤、时间区间和基准。默认参数是可运行起点，不保证收益。

## 7. 行情、回测和效率

### 7.1 数据入口闭环

Provider registry 统一历史 OHLCV、实时 Bar、trades、L1/L2 的 market/timeframe/interval、since/end、分页、rate limit、retry、cursor、source version。每次导入输出 QualityReport：覆盖区间、缺失/重复/乱序、空量、异常价格、交易时段、未闭合 Bar、时区和采样间隔；任何自动补值必须是显式的研究选择，且进入 Run identity。

长期缓存按内容寻址；下载与交易所执行配置分开。真实数据快照包含 provider/version、市场规格版本、source hash、获取时间与许可元数据。支持增量拉取、断点续取与按限频预算做并发；数据源无法覆盖时明确失败，不静默切源。

### 7.2 回测正确性

统一表达 next-bar-open、tick/order-book 撮合、成交优先级、部分成交、队列位置、费用层级、资金费、借贷、滑点、冲击成本、价格限制和延迟。回测报告标出使用数据粒度能证明的内容；15m bar 不声称还原盘口成交。

Common test corpus 覆盖未来数据、warmup、重复信号、long/short、做空限制、手续费、多币种费用、funding、止损触发 gap、OCO 同时触发/部分成交、精度边界、时区和断档。每个撮合模型附可读假设和参数。

### 7.3 可复现的竞品性能测试

建立 `qx-bench` 标准数据集和固定容器/机器：

| 工作负载 | 固定条件 | 主要指标 |
|---|---|---|
| 单策略 Bar 回测 | BTC/USDT 15m、180 天、同费用/滑点/仓位/策略参数；另用权益数据作独立组 | bars/s、运行时间、峰值 RSS、结果一致性 |
| 多策略参数批次 | 固定 50/500/5000 配置、同样本/OOS split、相同随机种子 | runs/s、总耗时、CPU 利用率、峰值 RSS、失败候选比例 |
| 多标的回测 | 固定 20/100 个标的及 Bar 数、确定性并行度 | bars/s、p95 单标的完成时间、内存、结果 hash 稳定性 |
| 数据导入 | 相同来源文件、时间窗、列和质量规则 | rows/s、解码/验证/持久化耗时、压缩比、峰值 RSS |
| 执行处理本地成本 | fake transport，不计公网 RTT；固定 order/fill 事件序列 | intent→adapter p50/p95、事件处理吞吐、队列积压、内存 |

与 Freqtrade、NautilusTrader 或 vectorbt 对比时必须先对齐指标定义、成本、数据、信号、撮合粒度和输出正确性；不能对不等价的事件撮合与向量化研究直接比一个吞吐数字。目标是 Rust 核心在等价 workload 上建立领先：发布前先形成基线，优化期目标至少比当前版本快 2 倍、峰值内存降低 25%；同行对比作为单独竞品报告，不能在未实测前宣称领先。任何优化不得改变 canonical result hash 或解释成交结果差异。

## 8. 可视化与可观性

### 8.1 研究与报告视图

- 单次回测：权益/回撤、benchmark、价格/信号/进出场/保护价、成交标记、费用/资金费、仓位和可用保证金时间序列。
- 多策略对比：同资产/同数据/同成本下叠加权益、滚动收益、回撤曲线、月度/年度归因、long/short 分项、换手、交易分布、滑点敏感性和参数/OOS 差异。
- 数据质量：K 线缺口时间线、数据源切换、未闭合 bar、时区、数据快照指纹、规则/手续费版本。
- 保持 HTML 离线报告可分享/可复算，同时提供 Console 的交互筛选、缩放、hover 细节和 run comparison；图表数据由版本化报告 DTO 提供。

### 8.2 运行与交易操作台

首页显示服务健康/数据延迟/最后闭合 Bar、worker 和交易所状态、账户净值按币种分列、持仓/保证金/强平距离、open order、conditional group、未匹配事件、unknown order、对账延迟和最近错误。点击任一订单组可看 parent/children、每次请求与原始响应摘要、成交费用、取消竞态和恢复动作。

### 8.3 Observability 契约

所有日志和 span 带 `run_id, strategy_id, account_id, venue_id, instrument, client_order_id, exchange_order_id, order_group_id, event_id`（敏感信息不进入字段）。指标至少包括 feed freshness/gaps、bar lag、strategy duration/errors/skips、risk rejects、submit/ack/cancel/amend latency、rate limit/retry、unknown orders、unreconciled fills、ledger lag、worker restarts、queue depth、RSS 和 storage growth。

定义 dashboards 与 alert thresholds、健康探针和 operator runbooks；告警需区分市场停滞、凭据失效、交易所限频、能力不支持、订单结果未知和账本不一致。Telemetry 默认本地/可选导出，不上传 API key、地址或账户明细；每个指标声明标签基数上限和保留期。

## 9. 分阶段实施顺序

| 阶段 | 优先级 | 交付范围 | 退出门 |
|---|---|---|---|
| A. Baseline 与能力真相源 | P0 | 更新 capabilities matrix；订单 shape/status 精确到 venue/product/account；完整清点当前分支、Schema、Worker API、缺陷和性能 workload | 每项能力有代码入口、测试、sandbox evidence 字段；无“支持但不知道覆盖范围” |
| B. 强类型订单/订单组领域模型 | P0 | Quantity 单位、conditional/bracket/OCO/trailing/amend 类型；OrderGroup/Leg 状态；canonical ID/hash/schema 迁移；Rust Risk/OMS/Ledger 消费 | 模拟与 live 共用 intent；状态迁移、部分成交、重复、Unknown/restart 有确定行为；旧快照兼容 |
| C. 交易所适配和恢复 | P0 | OKX Spot/Swap、Binance Spot/USDⓈ-M、Bitget Classic/UTA 的 mapper、能力查询、过滤器、金额规则、查询/撤改/撤组、用户流 | 每一 scope 先离线请求契约，再 Sandbox 下单/查询/成交/部分成交/撤改/OCO 竞态/断线重启，全事件可对账 |
| D. 数据与策略配方 | P1 | OHLCV/Depth quality report、断点/补数、13 个单标的 recipe、4 个双腿 recipe、做空/持仓 sizing/成本/保护默认模板 | 一命令从真实数据准备到报告；非交易时段/缺数/权限/做空不支持都明确拒绝 |
| E. 性能和容量 | P1 | criterion/bench corpus、并行 Run、内存与队列画像、限流/背压/缓存优化 | 与基线比对；结果 hash 不变；目标负载内存/耗时达标；超限有预估或拒绝 |
| F. 可视化和可观性 | P1 | 研究比较 UI、订单组详情、实时健康/账户页、structured logs/metrics/traces/告警/runbook | 一次 run/订单从入口到报告/账本可追踪；缺事实显示 Unknown/Unavailable 而非 0 |
| G. 发行和成熟度提升 | P0 发布门 | Linux/Windows/macOS 支持矩阵、Rust/Python/C++ 包、干净安装、SBOM/签名/构件 attest、版本/回滚文档 | Research 与 Live 分别验收；未 sandbox-tested 的能力不能标 production-ready |

## 10. 验收门与发布状态

### 10.1 Research Release

- 干净环境安装后，默认策略 quickstart 一条命令生成报告；真实数据路径不使用合成样例。
- 所有策略/数据/参数/手续费/滑点/撮合/随机种子进入行为身份；不同入口对同一输入结果一致。
- 策略参数搜索有预热/未来数据诊断，至少有 validation/OOS；没配 OOS 的报告显示“仅样本内”。
- 主流基础策略全部有示例、recipe 元数据、单元/回归和报告案例；报告可搬迁复算。
- 固定 benchmark 达到发布 SLO，并提供等价竞品测量报告、机器规格和完整 workload。

### 10.2 Exchange Sandbox Release

每个 `venue × product × account_model × position_mode × order_intent` 独立验收：市场规则、权限/模式、下单、参数精度、接收回报、部分成交、撤单/改单、条件触发、OCO 对端取消、资金费/费用、超时 Unknown、重启恢复和账本金额一致。sandbox 证据包括 CCXT/原生 adapter 版本、请求/响应脱敏样本、市场规格指纹和运行 commit。

### 10.3 Live Production Release

要求指定账户授权、sandbox 门通过、风控上限、限额/熔断、kill switch、人工恢复手册、审计日志保留、版本回滚、低额运行观察和明确责任人。Live 发布范围只包括已有 sandbox 证据的产品/账户/订单形态；一个交易所的通过不能推导另一个交易所通过。

## 11. 主要风险与明确不做

- 不以模拟结果或假 exchange 回复冒充沙盒/实盘证据；不自动注册交易所账户。
- 不以本地 OCO 双单加“触发后再撤另一单”冒充交易所原子 OCO；除非明确名为 synthetic OCO、其超额成交风险有上限且用户显式启用，否则不开放。
- 不因向量化回测更快而用它替代订单队列/部分成交/多币种账本仿真；向量筛选与事件回测分开报告。
- 不宣称“任何交易所、所有产品、全部账户模式通用”；能力必须细化到产品线和账户模式。
- 不把 9 位 raw 局部改成 18 位；精度升级包含 schema/hash/持久化/跨语言/订单与账本迁移。
- 不把策略默认值称为投资建议或收益保证；所有 recipe 要揭示费用、杠杆、资金费和做空条件。
