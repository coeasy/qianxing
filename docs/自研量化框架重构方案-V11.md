## 2. 架构现状与依赖事实

- **分层是"内核 → 领域 → 基础设施 → 编排 → 门面"，但向上边普遍存在**：
  `qx-adapter`(基础设施) → `qx-zhenlu`(编排)、`qx-execution` → `qx-zhenlu` + `qx-risk`、
  `qx-xingban` → `qx-zhenlu`/`qx-risk`/`qx-strategy`/`qx-data`、`qx-api`(门面) → `qx-storage` + `qx-scheduler`
  （跳过整个编排层）。后果：撮合与仿真的可替换性被编排层类型钉死。
- **dev 依赖环两处**：`qx-risk` ⇄ `qx-zhenlu`（已在 `crates/qx-risk/Cargo.toml:13` 说明理由）、
  `qx-execution` ⇄ `qx-runtime`（**未登记说明**）。
- **`qx-cli` 依赖全部 19 个可依赖 crate，且是唯一 `qx-api` 消费者**：门面层没有充当 CLI 的收口边界。
- **体量集中**：最大 crate `qx-cli` 19,014 行（占 src 约 24%）；最大文件 `qx-xingban/src/backtest.rs` 3,313、
  `qx-api/src/lib.rs` 3,137、`qx-storage/src/sqlite.rs` 2,579、`qx-storage/src/lib.rs` 2,405、
  `qx-adapter/src/binance.rs` 2,291、`qx-zhenlu/src/lib.rs` 2,270、`qx-runtime/src/pipeline.rs` 2,237。
  登记集 37 条只降不升（测试目录是已知例外，`qx-core/tests/ledger.rs` 1,031 行不受棘轮约束）。
- **`qx-zhenlu::lib.rs` 是垃圾抽屉**：风控门、`Signal/SignalMerger`、`RateLimiter:266`、`Venue` trait:326、
  `PaperVenue:1200`、spread 组:338-936、策略运行时:1535 同居一文件，与 `qx-execution` / `qx-adapter` 职责重叠。
- **`qx-orchestrator` 与 `qx-runtime` 边界近乎不存在**：前者只做 worker 计划与子进程看护，
  后者在 `lib.rs:32` 再导出监督类型。
- **V10 之后仍残留的兼容层**：`qx-xingban/src/lib.rs:52` 纯 re-export `qx_core` 费用模型、
  `qx-zhenlu/src/lib.rs:91-100` 的 `legacy_gate_context`（标 deprecated）、
  `qx-execution/src/lib.rs:26,49` 的 `RiskContextPort` / `BorrowedVenuePort`（**全仓零消费者，已 grep 证实**）。

## 3. 主体链路走查（逐条贯通判定，带证据）

### A. 行情 → 信号 → 风控 → 提交 → 成交 → 账本 → 持久化

- Binance 现货：代码路径完整——提交 `venue_runtime/binance_submit.rs:53-89` → 网关
  `qx-execution/src/lib.rs:441-545` → 用户流回报 `venue_runtime/binance_stream_worker.rs:76-120` →

- CCXT 通用 venue：`ccxt_execution.rs:28-259` + 断线重连 `:264-436` + 对账 worker，链完整；
  精度 / 沙盒矩阵是已知空白。
- Paper：队列 `paper_worker.rs:73-270`，无市场事实即拒成交（`:169-176`）。
- Binance 合约：**无直连实现**（`qx-adapter/src/binance.rs` 只有 `/api/v3`，`fapi|dapi` 零命中）；
  合约唯一通路是 CCXT 端点带 swap 参数（`ccxt.rs:569-579`），示例配置指向 OKX。

  **没有重启策略、没有重启预算、没有退避**；REST 歧义响应只转 `ReconcileRequired`、不自动重投
  （`binance.rs:1434-1457` + 网关硬拦 `execution/src/lib.rs:471-486`，这是正确的保守，但意味着
  "崩溃后远端未知态"完全依赖人工对账）。
- 文件后端 EventLog 与 outbox **不在同一事务**（`pipeline.rs:407-413`：先追加再投 outbox）。

  `DataTier::Bar` 等撮合与档位项 —— 那些仍属 Q1a 的不可达面。）
- **实现存在但 CLI 选不到**（引擎测试之外无生产调用点）：`BestPrice` / `OneTickSlippage` /

  零生产消费者、CI 与门禁也不引用该模板 —— 见 §0 E3。（✅ 本轮 Q0c 已关闭，见 §12：

      **Q0e 轮的进度**：多腿链（`backtest multi-builtin`）已经落了拒单与"计划 vs 成交"差距的
      产物事实（每腿 `unfilled_planned_qty_raw` / `rejected_orders` / `rejection_reasons` 与
      `pending_reconcile`，§14.1），单腿的 `strategy backtest` / `backtest builtin` 两条链仍只有
      内存 EventLog 里的 `append_rejection`，`fills=0` 依旧无法与"全被拒"区分 —— 那两段的接线
      随 Q1a 的示例修复一起做（示例必须真成交，成交不了就必须看得见为什么）。

## 5. 核心功能是否全部实现 / 主体链路是否全部贯通

| 能力 | 实现 | 被测 | CLI 可达 | 真实外部验证 |
|---|---|---|---|---|
| 内核 / 账本 / 规则集风控 | 是 | 是 | 间接 | 不适用 |
| 数据帧 / 数据集指纹 | 是 | 部分 | 是 | 不适用 |
| Bar 回测（默认口径） | 是 | 是 | 是 | 不适用 |
| 替代撮合 / 资金费率 / 强平 / 多档保证金 | 是 | 仅引擎单测 | **否** | 不适用 |
| L1/L2 深度回测 | 是（队列位置与冲击为简化模型） | 是 | 是（仅扁平 fee_bps） | 不适用 |
| 多腿归因 | 是 | **只有 pairs** | 是 | 否 |
| 跨语言策略（Python / C++） | 是 | 是（cpp 在 CI 编译并 smoke） | 是 | macOS wheel 本机不可证明 |
| Paper 全链 | 是（**撮合是首档 touch，不是回测的簿内核**，§13） | 是 | 是 | 注入合成报价；费用已与回测同源（§10）且口径来自成本文件（§12） |
| 实盘 Binance 现货 | 是 | 仅进程内 | 是 | **从未** |
| 实盘 Binance 合约（直连） | **无实现** | — | — | — |
| 实盘 CCXT | 是 | 进程内 + 契约 | 是 | **从未** |
| SQLite / Postgres / NATS | 是 | 契约用例存在 | 是（feature 门） | CI 绿灯本机不可证明 |
| 崩溃恢复 / 远端未知态对账 | 部分（**无重启策略**，文件后端 outbox 非原子） | 进程内 | 部分 | **从未** |

**判定**：

- **主体链路（行情 → 信号 → 风控 → 提交 → 成交 → 账本 → 持久化 → 对账）在现货 / paper / CCXT 三条上
  结构贯通**，并有租约、幂等、EventLog 重建与审计链支撑。
- **"核心功能全部实现"要打折**：撮合与虚拟交易的高保真能力只存在于引擎，命令面接不到（§3B、§4.3），
  因此实际"可用功能集"远小于"已实现功能集"；Binance 合约无直连适配器。
- **示例配置在空转**（Q0c 轮实测并定位根因，见 §4.18）：随仓库发布的三条 Bar 策略回测示例
  产物全部 `fills: 0 / turnover_raw: 0`，另一条只有 1 笔且名义额小到费用归零。
  链路"可达"不等于链路"跑得出结果"，e2e 断言目前走在零成交路径上。
- **两处正确性缺陷会直接污染结论**：~~paper 零手续费（§4.1）~~ 已由 Q0a 关闭、成本配置悬空
  （§3B 末条）已由 Q0c 关闭（§12）；**仍未处理的是多腿乐观记账 / 无跨腿否决（§4.5）**。
- **可复现性不足以支撑"研究结论"**：运行时不绑定数据集指纹、指纹不覆盖日历与公司行为、
  数据根目录可变（§3D）。
- 结论口径：**链路贯通、核心有缺口、数值面两处偏乐观、外部未证**。

## 7. 门禁与验收设计（本轮新增项）

1. 沿用 V10 §7 五条（一轮一脚本一新日志、`--snapshot` 在变异段前、反向验证成对红/绿、数字纪律、
   `sandbox_tested` 只由结果包翻转、棘轮例外显式声明）。
2. 新增不变量（每项都要用注入违规证明会红）：
   - clap 旗标不得在 `cli.rs` 分支中被 `_` 丢弃；
   - "共用内核 / 同一口径"类表述必须引用真实共享符号（✅ Q0d 落地：费用与风控同源由
     `paper_fee_same_source_check()` 承载，撮合内核由 `kernel_claim_check()` 的 6 条判据承载，见 §13.1）；

### 14.2 与计划的偏离与本轮踩到的坑

1. **§6 的"每腿费用按各自 venue spec"没做**，改成立即可查的偏离声明。原因：
   `TradingInstrumentSpec` 没有任何费率字段，唯一生效的费率来源 `ExecutionCostRules` 只有
   全局 `maker_bp` / `taker_bp`（Q0c 接的就是它），所以"按 venue 分档"无处落地。
   仓库里确实有一套分档费率——`crates/qx-core/src/fenye.rs`（464 行，带 `maker_bp` / `taker_bp`），
   但 `fenye::` 在其自身文件之外**零消费者**（全仓只有 `qx-core/src/lib.rs:16` 的挂载声明），
   是 V10 P2a 合并留下的死码。与其把它"接上"冒充真实口径，不如把偏离写进产物 assumptions
   （`fees=one explicit cost binding shared by both legs; market spec carries no maker/taker field,
   so per-venue fee tiers are not applied`）与 `capabilities.yaml` 的
   `backtest_multi_leg_fees_share_one_cost_binding_because_market_spec_has_no_tier_fields`。
2. **门禁判据假绿过一次**：G3 最初写的是"函数体内有 `i64::try_from(required)`"，
   而 `i64::try_from(required).unwrap_or(i64::MAX)` 照样命中这个子串——变异注入后门禁仍绿。
   改成"`i64::MAX` 在函数体内只出现 1 次"后，任何写法（`.min` / `.unwrap_or` / `.or`）的
   静默截断都会多出一处字面量而变红。
3. **行为变异假红过两次**（同一个坑的镜像）：R3 的第一版 `.unwrap_or(i64::MAX)` 与第二版
   `.or(Ok(i64::MAX))` 都**编译不过**（E0308 / E0283），日志里的"红"来自编译器而不是用例。
   换成可编译的 `i64::try_from(required).or(Ok::<i64, std::num::TryFromIntError>(i64::MAX))`
   之后才是真红（`multi_leg_funding_bound_fails_loudly_instead_of_capping_cash ... FAILED`）。
   记给 Q4：**变异段必须区分"编译失败"与"用例失败"**，前者只能算注入未生效。
4. **锚点与行尾**：源码是 CRLF（`core.autocrlf=true`），多行 python 锚点在字节层面找不到，
   全部改单行锚点；门禁读文件走 `read_text`（CRLF 归一为 `\n`），所以门禁里的匹配串要写
   `"\n}"`，写成真实换行会把 python 字符串截断成语法错误（本轮就踩了一次）。
5. **破坏性 splice 误删过函数**：改 `multi_leg.rs` 时锚点取的是"文档注释前缀 + 换行"，
   边界写错导致 `multi_leg_bar_close_raw` 整块被删。发现方式不是编译错误而是
   `git diff | grep "^-"`；按备份逐字还原。规则：删除型改动必须看 diff 的减行，不能只跑编译。
6. **行数棘轮的盲区**（本轮暴露，交给 §14.4）：`source_line_counts()` 只扫
   `crates/*/src/**/*.rs`，所以 `crates/qx-cli/tests/multi_leg_attribution.rs` 从 256 行写到
   **507 行**（已越过 `OVERSIZED = 500`）而不触棘轮、也不需要 `--snapshot`。
   本轮没有把它塞进 `src`（那会立刻变红），但"用例文件不受棘轮管"这个事实要么在 Q4 扩范围，
   要么显式承认——不能既享受豁免又声称棘轮覆盖全仓。

### 14.4 交给 Q1a / Q1b / Q4 的事实

1. **策略侧仍是"意图仓位"口径**。本轮改的是归因与产物，`StrategyContext::positions`
   （`crates/qx-xingban/src/lib.rs:172-187`）是策略自持的 `BTreeMap`，引擎只往里读、
   成交回报不回填。要消灭"策略以为建了仓、账上其实没有"，得让内置策略看到实际成交——
   那需要动 `qx-xingban` 的策略上下文契约，与 Q1b 的输入指纹改动会撞同一批回测哈希，
   所以按 §6 的依赖序留在 Q1a 之后一次做。本轮已经把入口留在产物里：
   `legs[].vetoed_signal_ts` 就是"策略以为有仓"的时点清单。
2. **单腿两条链还没有拒单事实**：`strategy backtest` / `backtest builtin` 的
   `append_rejection` 仍只写内存 EventLog（§4.18）。Q1a 修示例夹具时必须顺手把
   `[Multi-leg · Integrity]` 的 token 约定推过去，否则"示例零成交"仍然分不清是没信号还是全被拒。
3. **每腿 venue 费率的前置条件是字段承载**：给 `TradingInstrumentSpec` 加 maker/taker，
   或把 `qx-core/src/fenye.rs` 真正接线并删掉重复的全局 `ExecutionCostRules` 语义。
   在那之前任何"按 venue 分档计费"的说法都只能写成偏离声明（§14.2 第 1 条）。
4. **门禁与被检物的两处结构性缺口**，建议 Q4 一并裁决：① `source_line_counts()` 不覆盖
   `crates/*/tests/`（§14.2 第 6 条）；② 变异段要能把"编译失败"判为注入未生效而不是红（§14.2 第 3 条）。
   另加 §13.4 第 3 条仍未裁决的 `deploy/data/**/runs/` 产物增长。
