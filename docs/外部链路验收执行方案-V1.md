## 1. 前置条件

```bash
cargo build -p qx-cli --features sqlite,postgres           # 验收脚本要求 target/debug 下有 binary
export QX_BINANCE_TESTNET_API_KEY=...                     # 只读探测之外的全部步骤需要
export QX_BINANCE_TESTNET_API_SECRET=...
```

凭据只从环境变量读取：验收配置 `deploy/qianxing.runtime.binance-testnet.example.json`
按名字引用它们，命令行与结果包里都不出现值。缺凭据时脚本以 **退出码 3** 结束（skip），
不会把"没跑"报成"跑过"；CI 的未验收分支用 `--allow-skip` 折叠成 0。

## 2. 三段链路（同一条命令，按凭据与 `--send-orders` 分档）

| 段 | 命令 | 产出 | 失败即 |
|---|---|---|---|
| 离线安全门禁 | `runtime-check <acc.json> --json` → `live-check <acc.json> --json` | 配置可用；`network_accessed=false`、`orders_sent=false` 两条契约被断言 | 中止，不进入任何触网步骤 |
| 只读探测 | `binance-public-probe testnet <instrument>`、`binance-private-probe <acc.json> <worker>` | 交易所侧产品规格与账户可达 | 中止（退出码 2） |
| 单次受控下单 | `binance-submit-order <acc.json> <worker> submit-order.json` | 幂等下单一次；**同一 `request_id` 再提交必须被拒**（输出含"幂等"） | 中止；未知结果不得自动重发 |
| 断线恢复 | `binance-worker <acc.json> <worker> --once` | 重启后从 EventLog 收敛 | 中止 |
| 对账与终态 | `reconcile <acc.json> reconciler-main` → `status <acc.json> --json` | `status.json` 落在结果包里 | 中止 |

```bash
# 第一/二段（无 --send-orders 时全程 dry_run，不发真单）
python tools/binance_testnet_acceptance.py --binary target/debug/qx-cli.exe
# 第三段（真正的单次受控下单，需要凭据与显式开关）
python tools/binance_testnet_acceptance.py --binary target/debug/qx-cli.exe --send-orders
```

`--send-orders` 是唯一把命令 `dry_run` 置为 false 的开关，且只作用于**一笔**小额测试单
（数量与限价写在脚本的 `build_command` 里，改它等于改验收口径，需要一并更新本文件）。

## 3. 崩溃后远端未知态（第三段的延伸，需人工配合）

1. 用 `--send-orders` 跑通一次，记下结果包里的 `client_id`。
2. 在 `binance-submit-order` 返回前杀掉进程（或断网），使本地停在 `Submitted/Unknown`。
3. 重跑 `binance-worker <acc.json> <worker> --once`：网关必须先给出 `ReconcileRequired`
   事实而不是自动补单——`qx-execution` 的提交路径对已有 `Submitted/Unknown` 客户单号
   直接返回"必须先对账，禁止自动补单"。
4. `reconcile <acc.json> reconciler-main` 用交易所回报收敛该单，`status --json` 里
   该 `client_id` 必须进入终态且 Ledger 无重复成交。

## 4. 结果包与 `sandbox_tested` 翻转规则

每次运行都在 `maturity/evidence/testnet/<UTC时间戳>-{dryrun|orders}/` 留下：

* `result.json` —— `outcome`（`pass` / `skipped` / `fail`）、起止 UTC、每阶段退出码与
  耗时末行输出、`send_orders`、`credentials_present`，以及
  `sandbox_tested_flip.allowed`；
* 本次实际使用的验收配置与 `status.json`（若跑到终态）。

翻转条件（脚本与登记表同口径）：**`outcome=pass`、`credentials_present=true` 且 `send_orders=true`；全部必需阶段成功；live-check 必须满足只读安全断言；唯一允许的非零阶段是带幂等拒绝证据的重复提交**。dry-run、无凭据运行即使离线步骤通过，也不能翻转 `sandbox_tested`。验收脚本会将该重复提交阶段显式标记为 `expected_idempotent_rejection`，并要求请求幂等拒绝事实已确认。
`live-check` 允许非零（它按定义在缺凭据/缺前置条件时报 2，脚本另行断言它没有触网、没发单）。
满足后手工把 `capabilities.yaml` 对应条目置 `sandbox_tested: true`，并把该结果包目录一起
提交——**没有结果包的路径不得翻转**；`skipped`/`fail` 一律保持 `false`。目录不自动删除。

## 5. 第二交易所（CCXT 沙盒）同形复跑：当前缺口

`deploy/qianxing.ccxt.exchange.example.json` 已有 `"sandbox": true` 与
`QX_CCXT_OKX_API_KEY/SECRET/PASSWORD` 引用，`ccxt-worker <acc.json> <worker> <ccxt.json> --once`、
`ccxt-market-spec`、`ccxt-fetch-ohlcv` 三条链路可用。**但下单一步目前没有对应入口**：
命令面上只有 `binance-submit-order` 与 `paper-submit-order`，CCXT 侧的
`deploy/qianxing.submit-order.ccxt-derivatives.example.json` 只是载荷样例，没有执行它的

* 现在可跑：只读探测（market spec + OHLCV）与 worker 单轮，全部不含发单；

  `ccxt-submit-order <runtime.json> <worker-id> <ccxt-config.json> <command.json>`，
  复用同一个执行网关与幂等口径；补齐时应连带把验收脚本参数化成 `--venue` 而不是复制一份脚本。

## 6. wheel 腿（跨平台产物）

`.github/workflows/ci.yml` 的 python-wheel 矩阵已覆盖 ubuntu / macos / windows
（`tools/build_python_wheel.sh` 对 `Linux*|Darwin*` 统一取 `.so` 后缀）。macOS 腿的证据
形态与 §4 同规格：CI artifact 目录名带 run id 与时间戳，产物含 wheel 文件名与
`qx_python` 冒烟输出。本机验证方式见 `crates/qx-python`（需 `QX_PYTHON` 指向真实解释器，
裸 `python` 在 Windows 上是坏桩）。口径统一在一处：`build.bat` / `build.sh` 的 `[0/9]` 探测出可用解释器后会
**把它导出成 `QX_PYTHON`**，`[4/9]`/`[8/9]` 由 Rust 起的子进程因此看得见它（V12 §19 #133，编号按 §22 之后的九步）；手工跑单条命令时
仍需自己带上一个能打印版本号、且 `import tzdata` 通过的绝对解释器路径，wheel 脚本走 `-Python` / `PYTHON=` 参数。
