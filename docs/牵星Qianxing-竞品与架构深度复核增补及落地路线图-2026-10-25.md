> - 复核日期：2026-10-25
> - 范围：当前工作树的 Rust workspace、Python SDK/策略包、C++ SDK、CLI/API/Web、Schema、能力登记与发行脚本；竞品依据官方仓库和文档。
> - 性质：对[GitHub 竞品对标与架构优化重构执行方案](牵星Qianxing-GitHub竞品对标与架构优化重构执行方案-2026-10-25.md)的复核增补，记录本轮重新核对的事实、尚未闭合的风险和落地顺序。本文件是方案，不代表所有工作包已完成或已发布。
> - 标准策略接口（生命周期、行情/时钟回调、成交通知、意图 helper 与经典框架对照）见[标准策略接口经典框架对比与改进方案](牵星Qianxing-标准策略接口经典框架对比与改进方案-2026-10-25.md)。

## 1. 结论

牵星已经拥有较完整的研究与执行基础：Rust 确定性领域内核、多层数据质量与 PIT 语义、Bar/Tick/订单簿回测、应用用例、风险/OMS/执行端口、多交易所适配入口，以及 Python/C++/CLI/API/Web 用户面。架构方向合理，无需推倒重写。

主要问题是跨入口和跨运行类型的“同一事实”尚未完全统一，产品能力面明显宽于可证明的发布面。当前最值得先解决的是：

1. 给每一种 RunType 建立唯一输入身份、产物引用、验证与报告事实，避免 CLI、Python、API 各自重新解释文件。
2. 把“导入策略到诊断、样本外评估、比较、报告和复算”收成一条短旅程，并让未来数据/预热诊断落实到每个搜索候选。
3. 让价格、基础数量、合约张数、报价预算、手续费和结算币种有跨 Rust/Python/C++ 一致的单位合同，覆盖小币种与合约乘数。
4. 为超时未知结果、多账户和跨交易所组合建立持久化恢复状态；进程内重试不能代替组级 Saga。
5. 建立固定容量画像与多平台发行验收。当前本机 wheel 验收只覆盖 Windows x64 的 CPython stable ABI 构件，不代表 Linux/macOS、sdist 或交易所沙盒验收。

`ExchangeGateway` 可以作为用户侧连接门面；内部继续采用按职责拆分的行情、规则、账户、订单和对账端口。`BaseStrategy` 可以作为 Python 便利基类；协议应由生命周期合同和版本化事件/意图定义，不应强制跨语言继承。

## 2. 本轮代码画像与证据边界

### 2.1 仓库结构

本次 `cargo metadata --no-deps` 得到 **29 个 workspace 成员：28 个 `qx-*` crate 和 `contract-tests`**。公开交付面还包括 `python/`、`cpp/`、`web/console/`、`schemas/`、`maturity/`、`deploy/` 与 `tools/`。

| 责任域 | 当前主要模块 | 应拥有的事实 |
|---|---|---|
| 领域、身份与协议 | `qx-core`、`qx-spec`、`qx-protocol`、`qx-guanxing` | 标的/市场身份、事件因果、数值语义、PIT 可见性和跨边界版本合同 |
| 数据与存储 | `qx-data`、`qx-provider`、`qx-datastruct`、`qx-storage` | 数据摄取、来源与质量、列式数据、EventLog/快照和存储实现 |
| 仿真与研究 | `qx-xingban`、`qx-app`、`qx-factor`、`qx-risk` | 撮合/成本/保证金、研究用例、实验搜索、风险和经过核验的研究事实 |
| 策略与执行 | `qx-strategy`、`qx-execution`、`qx-zhenlu`、`qx-genglu`、`qx-adapter` | 策略生命周期、订单意图、风控/OMS/路由、Venue 映射、回报与对账 |
| 运行与编排 | `qx-runtime`、`qx-orchestrator`、`qx-service`、`qx-scheduler`、`qx-control` | worker 生命周期、任务状态、调度、控制面和恢复协调 |
| 用户入口 | `qx-cli`、`qx-api`、`qx-sdk`、`qx-python`、`python/`、`cpp/`、`web/console/` | 命令/API/语言绑定、授权、交互、导出；不重复计算领域事实 |

目标主链路应保持单向：

```text
研究：策略/配置 → 输入校验与 PIT → qx-app RunSpec → qx-xingban → EventLog/账本
     → qx-app Artifact/Report Reader → CLI/Python/API/Web 投影

交易：市场事件 → Strategy intent → 能力/精度预检 → Risk/OMS/Gateway
     → Venue command/response → 账本归约 → 对账/持久恢复 → 账户报告
```

`qx-app` 持有应用用例和核验后的研究事实；CLI、Python、HTTP 是入口/适配器；运行时组合根负责装配；Venue adapter 负责供应商语义转换。若同一指标、订单事实或输入身份必须在多个入口再次计算，应视为边界漂移。

### 2.2 本轮实际验证

- Windows 本地构建出 `qianxing-0.2.2-cp310-abi3-win_amd64.whl`，约 4.97 MB；wheel 检查确认原生 `.pyd` 与 stable ABI 标签。
- 将该 wheel 安装到新建虚拟环境，运行公开 wheel smoke 流程通过：策略目录 17 项、A 股 Bar 回测、实验参数网格、13 种单腿策略选择、多账户回测、资金溢出预检、多腿/深度回测、自定义 Python 策略和异步运行句柄均完成。
- 这是单机、单平台、离线/本地数据验收。没有验证 sdist、Linux/macOS、Python 全版本矩阵，也没有发起交易所私有 API 调用或订单；不得据此标记 `sandbox_tested`。
- 工作树包含大量未提交变更。本文件记录的是本地源码快照，不等于当前 Git 提交、已发布 wheel 或经过生产批准的版本。

### 3.1 牵星相对优势

- 以 Rust 作为确定性核心，策略/回测事实可进入事件日志、哈希和复算流程；安全地把 Python/C++ 当策略和集成入口。
- A 股制度、数字资产、深度撮合、保证金和多账户研究纳入同一应用与产物体系，范围比单一 crypto bot 更广。
- 认真区分 `implemented`、`code_tested`、`sandbox_tested`、`production_approved`，有条件做到“源码在”不等于“已经验收”。
- 能力门禁覆盖命令分派、死入口、风险门、回测归属等架构不变量，适合防止大仓库退化。

### 3.2 牵星当前短板

- 概念和入口较多，第一次研究策略需要了解 CLI、Python facade、实验配置、诊断和报告多套边界；高层一条龙体验需要收敛。
- 29 个 crate、跨语言 schema 和大模块增加理解成本；少量事实源被 manifest、schema、文档、示例、CLI/API DTO 重复描述。
- 所有 RunType 的 artifact identity、writer/reader/report/verify/recompute 覆盖未完全对齐；旧路径和新逻辑 ArtifactId 并存带来迁移负担。
- 基础数值精度与合约单位模型需要覆盖低价小币种、不同 lot/tick、合约乘数、币本位/币种结算及不同舍入规则；统一 raw 数字不足以说明单位。
- Backtest、Paper、Live 在撮合、异步时序、交易所规则、超时未知提交与状态持久化上天然不同；“同一策略代码”不能表述成“相同成交结果”。
- 多账户/多交易所联合不是原子事务；组级状态与补偿/人工接管必须持久化，不能只依靠内存路由、局部重试和单腿生命周期。
- 未来数据/预热诊断已有能力路径，但候选级证据、报告交互和容量画像仍需补齐；自适应搜索也必须防止重复使用 OOS。
- 当前真实供应商沙盒证据不足以覆盖私有账户和完整下单恢复。离线 fixture 只能证明代码形状，不证明交易所真实行为。

## 4. 架构设计问题和开发细节

| ID / 优先级 | 具体问题 | 主要改进 | 关闭条件 |
|---|---|---|---|
| A1 / P0 | Run 输入身份、manifest、产物引用、报告核验在不同 RunType/入口覆盖不一致 | 为 Bar、Depth、Tick、provider、多市场、多账户、多腿、实验建立 `RunType × writer × manifest × reader × report × portable × recompute` 矩阵；行为输入 canonicalize，路径只当来源信息 | 每种 RunType 有 writer/reader/verify/recompute 证据；改变行为输入 fingerprint 必变，搬移同内容工件 identity 不变；跨 Run/损坏输入一致拒绝 |
| A2 / P0 | 多入口重复构造 DTO/计算报告，API 与 CLI/Python 对同一产物可能出现语义漂移 | `qx-app` 持有版本化 Report DTO 与验证事实；`qx-api` 只做授权、rooted resolver、限流/分页与 HTTP 语义；CLI/Python/Web 只渲染 | 同一工件经过 CLI、Python、API 的状态、指标、错误和身份相同；reader 对尺寸、分页、格式和引用有界 |
| A3 / P0 | 数值合同混合 fixed-point raw、十进制和 `f64`；合同张数、基础数量和 quote budget 容易混用 | 先完成 ADR：wire decimal、scale、舍入、溢出、哈希和 schema 迁移；新增带维度的 Price/BaseQty/ContractQty/QuoteBudget/Fee/Money 类型，保留显式 legacy adapter | 小币种、小数边界、逆向/线性合约、乘数、费用币种、min notional 和 rounding 的 Rust/Python/C++/JSON golden vectors 一致；订单权威值不经 `f64`/JS Number 丢精度 |
| A4 / P0 Research | Quick Research 多命令拼接，诊断不一定证明每个被选中的参数候选 | 提供 `inspect → preflight → run/search → diagnose → split/OOS → compare → report → verify` 高层入口；基于候选实际参数重跑 future-leak/warmup 诊断 | 仓库外策略从安装包一条命令到完整报告；每个排名候选附诊断状态/范围；没有 OOS 就明确标为样本内 |
| A5 / P1 | `ExchangeGateway` 若成为万能接口会把交易所能力差异抹平；BaseStrategy 若是强制继承会使 Rust/C++/Python 语义分裂 | 用户 API 可提供 Gateway facade；内部组合 `MarketDataSource`、`InstrumentRulesProvider`、`AccountQueryPort`、`OrderExecutionPort`、`ReconciliationPort`；策略对齐 lifecycle protocol，BaseStrategy 只是 Python 可选 helper | `venue × product × account mode × position mode × order shape × operation` 能力在下单前校验；Rust/Python/C++ 对 init/warmup/ready/event/order/fill/stop 与 PIT 的 golden cases 一致 |
| A6 / P1 Live | 超时后提交结果可能未知，多腿/多账户无原子提交；只靠进程内重试会重复下单 | 持久化 `OrderGroup/LegState` Saga：预留、幂等 key、submit attempt、venue order ID、外部回报、补偿、人工终态、重启恢复与 reconcile；先 query 未知结果，再决定补偿 | 在请求、写库、回报、撤单、进程重启各故障点做重复/乱序注入；无重复订单和重复记账；不能自动恢复时进入可查询人工状态 |
| A7 / P1 | 搜索候选/报告/事件数据量增大后缺少峰值资源与背压边界 | 固定 Bar/Tick/L2、候选数、标的数、账户数、并行度，测吞吐、p50/p95、峰值 RSS、磁盘、冷启动；加任务预算、取消、限流、背压/落盘策略 | 文档注明机器、commit、数据集、配置和测量方式；超限运行前估算或明确拒绝；容量回归有阈值 |
| A8 / P1/P2 | CLI/API、adapter、搜索和 storage 的少数模块过大，架构门禁也逐渐变成维护对象 | 按身份、风险、报告、单一 adapter responsibility 拆小；门禁每项拥有稳定 rule ID、owner、被守护的风险、替代规则和耗时；减少跨 crate 的 `pub` 暴露 | 拆分保持契约和行为不变；每条规则有 owner 和风险依据；架构门禁运行时间可追踪，不删除有效规则来换取全绿 |
| A9 / P2 | Schema、capability、CLI/API 路由、示例、README 和 maturity 多点维护 | 将 Cargo/Schema registry/CLI 路由/capability matrix/包平台作为源数据生成文档和覆盖检查；示例配置由生产解析器校验 | 发布时 `--check` 无漂移；用户看到的支持范围能追溯到唯一事实源和证据 |

## 5. 分阶段改进与交付物

### R0 — 版本基线与事实目录（先行）

- 冻结本轮 commit、dirty diff 清单、Rust/Python/C++ 工具链和 OS/Python 支持矩阵；区分工作树能力和已发布能力。
- 建立所有 RunType/capability 的 writer、读者、schema、验证器、CLI/Python/API/Web 入口、测试及外部证据索引。
- 产出：`release-baseline.json`、RunType 覆盖表、证据档位表、迁移兼容表。
- 验收：源码存在不能直接翻转 maturity；所有未知项明确写 `unknown/not exercised`。

### R1 — Run 身份和共享报告事实（P0）

- 先单市场 Bar/Depth，再 provider、多市场、实验、多账户、多腿/Tick；引入逻辑 `ArtifactId`，不将宿主绝对路径作为身份。
- 报告 reader 核验 manifest、sidecar、EventLog、hash、行数、边界和损坏状态；API 做文件授权映射，不自己重算指标。
- 产出：RunType 覆盖矩阵、共享版本 DTO、V1 只读兼容与分批 V2 writer。
- 验收：CLI/Python/API 对同一 run 得到同一验证事实；搬迁不改变 identity；路径越界、伪造引用和超限内容拒绝。

### R2 — 安装后 Quick Research 与诊断闭环（P0 Research）

- 给 Python 用户提供 `qianxing research <strategy.py> --data ...` 一条龙入口，底层复用现有 app/engine，不复制交易逻辑。
- 统一策略导入预检、数据 PIT/质量、搜索预算与种子、候选级 future-leak/warmup、时间折、一次性 OOS、报告和 verify。
- 报告提供候选排名、收益/风险/交易分布、回撤、成本敏感性、标的/市场归因、失败候选、训练/验证/OOS 标记；交互图表引用同一已验证 DTO。
- 验收：干净 venv 可安装后运行仓库外策略；可在命令输出定位输入/策略/候选；没有 OOS 明确禁止称为“最佳有效策略”。

### R3 — 精度单位与交易所能力合同（P0 Live blocker）

- 先写金额和单位迁移 ADR；按 Binance、OKX、Bitget 分现货、线性/反向合约、单向/双向模式、保证金模式和每类订单登记能力。
- market metadata/过滤器作为有时间戳和版本的规则快照；转换使用 Decimal/定点和显式舍入；合约张数与币数量不混淆。
- 验收：小数位极端值、最小名义、tick/lot、step、乘数、杠杆、settlement currency、reduce-only、双向 side、手续费币种和拒单语义在多语言 fixture 一致。

### R4 — 多账户/多交易所持久订单组（P1 Live）

- 按单一订单 lifecycle 统一提交、确认、部分成交、撤单、未知结果、重启、对账与补偿；组合状态放入 storage，而不是 CLI 临时对象。
- 单账户/单交易所先可恢复，再扩展多账户联动；记录每腿独立余额、风险限额、抵押品、成交和费用，拒绝隐式净额。
- 验收：用 fake venue 对每个持久化边界故障注入；代码验收通过后才按用户提供的沙盒凭据验收具体交易所，不将离线通过升级为 sandbox。

### R5 — 容量、安装和工程可维护性（贯穿各阶段）

- 建立固定 benchmark matrix：Bar、Tick、L2；1/10/100 标的；多账户；1/10/1000 candidates；并行度和数据跨度分别记录。
- 验证 Windows/Linux/macOS、Python 最低/当前版本、wheel/sdist、C++ SDK 安装和 CLI 产物；Windows wheel 单平台 smoke 已有本轮记录，其他维度待验。
- 按模块责任拆大文件；将可机读元数据作为 CLI/schema/route/capability/docs 的生成事实源。
- 验收：报告吞吐、p50/p95、RSS、磁盘、冷启动、工具链与机器；资源边界有取消、上限或清晰错误；发布文档生成无漂移。

### R6 — 供应商验收与发布准入（独立 Live 发布轨）

- 每个验收范围必须具体到 venue、产品、账户模式、持仓模式、下单类型和 API 环境；账户 key 通过环境变量输入，禁止写入仓库与日志。
- 完成只读市场/账户、规则同步、开仓、回报、部分成交、撤单、平仓、杠杆/双向模式、超时未知订单、进程重启与对账；如用户没有提供 key，只运行 fail-closed 离线验收并明确缺口。
- Research 发布与 Live 发布互不替代；能力矩阵按证据逐格升级。

阶段依赖：`R0 → R1 → R2 → Research release`；`R0 + 数值 ADR → R3 → R4 → R6 → Live release`；`R5` 贯穿所有阶段。R6 只能在用户提供可用 sandbox 环境或密钥之后完成外部验收。

## 6. ExchangeGateway 与 BaseStrategy 最终建议

### ExchangeGateway

**抽象用户概念，分拆内部端口。** Python/Rust SDK 可以暴露易发现的 `ExchangeGateway` facade，将行情、规则、账户、订单和对账客户端组合起来；业务内核通过最窄需要的 port 注入能力。不要新增一个必须实现全部供应商功能的万能 trait，也不要让策略直接操作交易所原始 JSON。

### BaseStrategy

**统一生命周期协议，按语言提供 optional helper。** 推荐顺序：创建策略并绑定 `history_requirements` → `on_init → on_start` → 市场事件；N>0 时每个标的前 N−1 根 Bar 更新状态但抑制订单意图，第 N 根 Bar 可见时先调用 `on_warmup_complete`，再调用该 Bar 的策略事件 hook；其决策最早在后续撮合 Bar 成交。零预热在 `on_start` 后收到 `on_warmup_complete(None, 0)`。之后按已提交事实投递订单/成交更新，最终调用 `on_stop`。所有宿主必须维持相同的 ready、PIT、账户/标的身份、订单意图单位、异常和停止语义。

Python 可提供 `BaseStrategy` no-op hooks、类型化事件、参数读取、日志和常用 intent helper；Python duck typing、Rust trait、C++ ABI 均可直接满足协议。`populate_indicators`/`populate_entry_trend`/`populate_exit_trend` 属于独立向量化 Bar 研究 adapter，不要求 live 策略实现。撮合、风控、账本和订单回报归约始终属于 Rust 核心。

## 7. 发布准入与不可声称事项

### Research release

- 声明平台的安装产物在 clean environment 可用；策略文件一条龙完成预检、回测/搜索、候选级诊断、OOS、比较、HTML/JSON 报告和复算。
- 主要 RunType writer/reader/schema/portable/recompute 覆盖表完整；报告显示数据、Run identity、费用/滑点/撮合假设、训练/验证/OOS 和不完整原因。
- 固定 benchmark 报告资源消耗和运行限制。

### Live release

- capability 与证据按 venue/product/account/position/order scope 登记；精度和订单单位多语言合同一致。
- 指定范围通过沙盒完整下单、回报、撤单、恢复、对账和异常处理；多账户组具有持久恢复证据。
- 没有对应外部账户证据时，保持实现/本地代码验收档位，不能宣称“该交易路径已实盘验证”。

## 8. 不采用的做法

- 不因 crate 数量或单个文件体量直接推倒重写；不以行数目标机械拆分。
- 不新增重复的回测引擎、报告指标计算、风险门或交易所归约实现。
- 不将 `ExchangeGateway` 设计成所有 venue 都必须支持所有操作的宽接口；不强制继承 `BaseStrategy`。
- 不让向量化研究筛选代替事件撮合验证；不重复使用 OOS 调参后仍称其为独立样本外结果。
- 不把离线夹具、公开行情、编译、wheel smoke 或模拟交易描述成真实私有 API 下单验收。
- 不删除仍有风险覆盖价值的历史门禁；调整门禁必须同时给出覆盖同一风险的替代证据。
