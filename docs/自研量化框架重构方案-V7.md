# 牵星（Qianxing）项目架构审计与重构方案 V7

更新时间：2026-09-12  
审计基线：`main@c48f20b1bfdb8a7e5a8c39d9fe263d1c64657063`  
定位：基于**当前主分支真实代码**重新审计，不以 README、V5/V6 规划中的“已完成”描述替代代码事实。

---

## 0. 本次审计方法与结论口径

本次审计重点回答四个问题：

1. 当前项目到底实现了哪些主要功能，真实架构和实现边界是什么；
2. 功能、架构和实现中有哪些不合理、重复、耦合、断链或仅完成接口的部分；
3. 核心功能是否全部实现，主体链路是否真正端到端贯通；
4. 下一阶段如何在不推翻现有确定性内核的前提下，把项目收敛成可验证、可运行、可发布的产品架构。

本次采用四级状态，而不是简单的“有代码/没代码”：

- **A：已实现且代码链路闭合** —— 关键领域逻辑与调用路径存在，具备单元/局部测试；
- **B：代码已接线但缺完整验收** —— 有主要实现和入口，但缺 CI、进程级、外部环境或故障恢复证明；
- **C：部分实现/契约先行** —— 接口、协议、注册表或兼容路径存在，但不能视为产品能力完成；
- **D：未形成可交付能力** —— 缺关键实现、部署闭环或发布门禁。

> 重要限制：当前仓库只有一个初始提交，主分支没有 `.github/workflows`，该提交没有 CI status。因此本文可以证明“代码中存在什么、调用链如何连接”，**不能把 `cargo test --workspace`、跨平台 wheel、PostgreSQL/NATS、真实交易所等能力写成已经由主分支 CI 证明通过**。V7 将“代码闭环”和“发布闭环”分开评级。

# 1. 总体结论

## 1.1 一句话结论

牵星已经不是概念项目：确定性事件内核、回测、OMS/Ledger、Paper、控制面、CCXT/Binance 适配、存储、调度、多语言策略等都存在大量真实实现；但是当前工程仍处于**“大规模功能堆叠后的第一次架构收敛期”**，还不能定义为“核心功能全部完成、所有主体链路全部生产级贯通”。

## 1.2 当前最准确的产品状态

| 能力 | 状态 | 结论 |
|---|---:|---|
| 确定性 Core / Event / Ledger / Replay | A- | 领域基础较扎实，模块也相对清晰 |
| Bar/L1/L2 回测与撮合 | A- | 本地代码链路完整，仍需正式性能/回归门禁 |
| PIT 数据 / Provider / Factor Research | B | 有真实模型和快照契约，但研究产物仍保留旧 target 兼容路径 |
| Strategy → Portfolio → Risk → Intent | B | 已存在，但策略、风险与兼容模型仍有双轨语义 |
| OMS / Order Lifecycle | A-/B+ | 独立 `qx-oms` 已建立，仍被旧模块 re-export/兼容 |
| Paper E2E | B+ | 有 `paper-e2e` 明确入口，代码链可闭合；但发布级恢复/进程矩阵未证明 |
| CCXT 多交易所 REST | B | MarketData/Execution/Reconcile 已有实现，真实多交易所语义验收未闭合 |
| Binance Direct | B | 协议实现较多，真实 private sandbox/实盘矩阵未在仓库证明 |
| API / Control / mTLS | B | 代码能力存在，缺持续集成与真实证书/部署验收证据 |
| Files / SQLite / PostgreSQL | B | 多后端实现存在，但不同后端事务能力并不等价 |
| NATS / Outbox / Consumer | B-/C+ | 代码存在且 feature 化，但默认构建关闭、无集成 CI 证明 |
| Rust/Python/C++ Strategy | B | 契约、动态 C ABI/进程协议、共享内存均有实现，SDK/ABI 发布门禁不足 |
| 通用 Plugin System | C | manifest、签名、依赖/冲突解析已实现；尚不是完整通用插件装载/隔离平台 |
| 跨节点 HA / 读写分离 / 灾备 | D | 当前不应标记为完成 |
| CI / Release / Feature Matrix | D | 主分支当前没有 GitHub Actions，无法形成发布证明 |

## 1.3 “核心功能是否全部实现？”

**否。**

如果把核心定义为“确定性量化内核 + 本地回测 + Paper 闭环”，核心已经基本成型；如果把项目 README 当前定位理解为“多交易所、多账户、多策略、多语言、研究到实盘、可生产部署”，则仍有以下未完成项：

- 真实交易所的 sandbox/private 网络验收与差异矩阵；
- 生产风险配置的统一 fail-closed 门禁；
- 研究发布物完全替代旧目标仓位兼容路径；
- 通用插件真正的装载、实例化、生命周期、隔离和运行时贡献绑定；
- PostgreSQL/NATS 的发布级集成与故障恢复门禁；
- 跨节点 HA、读写分离、灾备；
- Python wheel/C++ ABI/共享内存协议的跨平台持续发布证明；
- CI、feature matrix、release gate、升级/迁移 gate。

## 1.4 “主体链路是否全部贯通？”

不能用一个“是/否”回答，应该拆成四条链：

### 链路 A：回测

```text
BarFrame / DataView
  → Strategy
  → Signal / Target / Intent
  → Risk
  → Xingban Matcher
  → Fill
  → Ledger
  → Report / Replay
```

**结论：代码级贯通，A-/B+。**

### 链路 B：Paper

```text
Scheduler
  → JobQueue
  → Strategy Worker
  → Signal / Risk / OrderIntent
  → ControlCommand
  → CommandQueue
  → Paper Execution Worker
  → PaperVenue
  → VenueEvent
  → LiveEventPipeline
  → EventLog / OMS / Ledger
  → Reconcile / Query
```

**结论：代码级有明确 E2E 入口，B+；发布级尚未证明。**

需要特别注意：独立 `paper-submit-order` helper 会人为构造报价推动成交，它适合 smoke/契约验收，不能等价为真实持续 Paper MarketData 驱动。

### 链路 C：CCXT / Binance 实盘

```text
Strategy / API Control
  → SubmitOrder Command
  → Execution Worker
  → Risk preflight（配置完整时）
  → CCXT / Binance Venue
  → Accepted / Fill / Cancel
  → EventLog / OMS / Ledger
  → UserStream wake-up
  → REST Reconcile 补偿
```

**结论：代码已接线，B；真实外部闭环未证明。**

未知提交结果的保护、ReconcileRequired、幂等和 fencing 思路是正确的；但真实交易所的认证、断线、订单状态差异、手续费/资金费/强平、精度和杠杆档位必须用外部环境验收，不能由本地单测替代。

### 链路 D：生产部署与消息化

```text
RuntimeConfig
  → Supervisor
  → API / Scheduler / Strategy / Execution / Reconcile Workers
  → Storage
  → EventLog + Outbox
  → NATS
  → Consumer / Projection / DLQ
  → Metrics / Health / Recovery
```

**结论：局部实现很多，但整体仍是 B-/C+。**

主要原因不是“没有代码”，而是：默认 feature 关闭、没有 CI feature matrix、文件/SQLite/PostgreSQL 事务语义不同、生产示例配置当前还存在路径断链，且跨节点 HA 尚未实现。

# 2. 当前主要功能与真实实现

## 2.1 `qx-core`：确定性交易领域内核

主要职责：

- 128-bit 定点金额/价格/数量；
- Clock、Event、Priority、EventLog；
- Instrument/Account 等身份；
- Order/Fill/OrderStatus；
- Ledger 与衍生品记账；
- Event sourcing / replay / RunManifest；
- TradingInstrumentSpec、OrderPolicy、Margin/Position mode。

评价：这是当前最值得保留的核心。它较少依赖外部系统，确定性原则明确，应继续作为最内层。

## 2.2 `qx-fenye` / `qx-guanxing` / `qx-provider`

形成身份、数据质量、PIT 可见性、Provider capability/failover 等数据平面基础。

合理方向：

- Instrument 与数据源身份分离；
- `as_of` / PIT 语义；
- Provider 主备与能力矩阵；
- 不让回测从未来数据读取信息。

仍需补强：

- Provider 数据血缘、质量策略和存储接口目前分散在多个 crate；
- 多供应商真实一致性/回填/复权并没有形成一套统一产品化流水线。

## 2.3 `qx-factor`

已经不是纯接口：有 FeatureDefinition、Artifact、FactorReport、Candidate、StrategyResearchSnapshot 等真实模型。

问题是研究层到交易层仍存在双轨：

```text
正式方向：ResearchSnapshot → StrategyContext
兼容方向：target_snapshot / target_qty
```

生产环境应该最终只允许第一条。

## 2.4 `qx-xingban`

承担 Bar/L1/L2 仿真、费用、延迟、容量、保证金和确定性随机。

这是“同规则内核”的重要组成部分，但需要进一步明确：

- Matcher / Fee / Latency / Margin 是模型接口；
- BacktestEngine 是事件驱动器；
- PaperVenue 是执行适配器；
- Live Venue 是外部副作用边界。

当前这些概念分布在 `qx-xingban`、`qx-zhenlu`、`qx-execution`、`qx-adapter`，职责仍有交叉。

## 2.5 `qx-zhenlu`

当前同时包含：

- RiskContext / RiskRule / RiskGate；
- Signal / SignalMerger / TargetPosition；
- OrderIntent；
- Router / VenueQuote；
- Venue trait；
- PaperVenue；
- Strategy lifecycle；
- 对 `qx-oms::Oms` 的兼容 re-export。

这已经超过一个 crate 应承担的责任，是下一轮优先拆分对象。

## 2.6 `qx-oms`

OMS 已独立出来，这是 V6 以来正确的方向。

后续应彻底移除 `qx-zhenlu` 对 OMS 的历史兼容语义，让订单生命周期只有一个权威实现。

## 2.7 `qx-execution`

已经抽出了 `ExecutionService`，统一：

```text
ControlCommand
  → register OrderSubmitted
  → Venue.submit
  → VenueEvent
  → RuntimeExternalEvent
  → LiveEventPipeline
```

并处理：

- 重复订单；
- Unknown/Submitted 的未知结果保护；
- `ReconcileRequired`；
- 风险预检；
- 带 TradingInstrumentSpec 的衍生品成交归约。

方向正确，但依赖方向仍不理想：`qx-execution` 直接依赖具体 `qx-runtime::LiveEventPipeline`，导致“应用服务”反向依赖“运行时实现”。

## 2.8 `qx-runtime`

承担：

- RuntimeConfig；
- WorkerConfig / role；
- Strategy contract；
- supervisor/health/shutdown；
- LiveEventPipeline；
- EventLog/OMS/Ledger 恢复；
- Python/C++/shared-memory strategy protocol glue。

问题：职责过多且 `lib.rs`、`pipeline.rs` 都已经非常大。运行时配置、策略协议、进程生命周期、事件归约本应是不同子模块。

## 2.9 `qx-storage`

已实现：

- flat/segmented file EventLog；
- control state / command queue；
- JobQueue；
- Outbox/relay；
- consumer checkpoint / projection / DLQ；
- SQLite；
- PostgreSQL；
- NATS JetStream adapter。

这部分能力很丰富，但必须承认**不同 backend 的一致性保证并不相同**。

文件 EventLog 路径中，EventLog 先完成文件提交，再逐条写 FileOutbox；这不是单一原子事务。PostgreSQL 才适合作为“事件 + outbox 原子提交”的生产基线。

## 2.10 `qx-adapter`

当前包含 Binance direct 与 CCXT process adapter，协议代码量很大。

推荐继续保留“两级连接层”：

```text
首选：公共 CCXT adapter
特殊场景：Direct venue adapter
```

但二者必须共享同一 Venue contract 和 contract test，而不是在 CLI 中各自拼执行流程。

## 2.11 `qx-api` / `qx-control`

有权限、operator、Accepted→terminal、审计、WebSocket、mTLS、TLS reload 等实现。

需要把 API 明确定义为“控制/查询适配器”，禁止成为业务编排器；所有交易副作用必须落到统一 CommandExecutor/Execution pipeline。

## 2.12 `qx-strategy` / `qx-python` / `python/` / `cpp/`

已具备较丰富的跨语言边界：

- Rust native Strategy；
- Python JSONL worker；
- external executable；
- C ABI；
- framed JSON；
- shared memory JSON；
- shared memory columnar；
- PyO3 / Arrow C Data Interface 基础。

因此不能说“多语言策略没有实现”；更准确是：**第一阶段已实现，但尚未达到稳定 SDK + ABI compatibility + 跨平台发布门禁的产品完成度。**

## 2.13 `qx-plugin`

已经实现：

- Manifest；
- Provides/Requires/Replaces；
- deterministic topological order；
- exclusive conflict；
- FNV/Ed25519 manifest signature；
- startup phase plan。

但目前它主要是**插件元数据与装配计划系统**。没有看到与所有扩展点一一对应的通用运行时实例创建、动态代码装载、隔离、能力注入和统一生命周期容器，因此不应把它描述成完整成熟的通用插件平台。

# 3. 当前架构中最不合理的地方

## P0-1：`deploy/` 示例配置与“相对 runtime 文件解析”契约发生真实断链

当前代码已经明确：相对路径按 runtime 配置文件目录解析。

例如：

```text
runtime file = deploy/qianxing.runtime.production.example.json
configured   = qianxing.binance.spot.spec.json
result       = deploy/qianxing.binance.spot.spec.json
```

但当前 production 示例仍写：

```json
"instrument_spec_path": "deploy/qianxing.binance.spot.spec.json"
```

结果会变成：

```text
deploy/deploy/qianxing.binance.spot.spec.json
```

Paper 示例同样存在：

```json
"jobs_path": "deploy/qianxing.scheduler.paper-order-smoke.json"
"target_snapshot_path": "deploy/qianxing.strategy-target.paper.json"
```

这是当前最明确的**主体链路配置断点**之一。

### 修复原则

`deploy/*.runtime*.json` 内所有同目录资源统一写裸相对路径：

```text
qianxing.binance.spot.spec.json
qianxing.scheduler.paper-order-smoke.json
qianxing.strategy-target.paper.json
```

禁止一部分“相对 CWD”、另一部分“相对 config dir”。

CI 必须新增 `runtime-check` 遍历所有 deploy runtime 示例。

## P0-2：主分支没有 CI，所有“已通过”都缺发布证据

当前仓库：

- 只有一个初始提交；
- 无 `.github/workflows`；

因此当前最严重的问题不是某个函数，而是**没有持续验证系统**。

需要立即建立：

```text
fmt

→ cargo test workspace/default
→ cargo test feature matrix
→ paper-e2e
→ runtime-check(all configs)
→ process recovery
→ Python wheel matrix
→ C/C++ ABI smoke
→ optional PostgreSQL/NATS integration
```

没有这些 gate，V6/V7 中任何“已完成”的状态都很容易下一次提交退化。

## P0-3：生产 Risk 仍保留“无 InstrumentSpec 时走兼容基础执行”语义

当前执行路径中，只有 worker 能构造出完整 `RiskContext + PositionSnapshot` 时才调用 `execute_submit_order_with_risk`；否则会进入基础 `execute_submit_order`。

兼容性对开发环境有价值，但**生产环境不应该依赖调用点自己决定是否启用风险**。

目标必须改成：

```text
ProductionTradingProfile
  ├─ account binding
  ├─ venue binding
  ├─ instrument spec
  ├─ settlement currency
  ├─ risk limits
  ├─ credentials reference
  ├─ reconcile policy
  └─ execution policy
        ↓
启动时一次性 validate
        ↓
任何交易 worker 缺一项 → 不启动
```

`environment=production` 下禁止兼容 bypass。

## P0-4：文件后端不能与 PostgreSQL 宣称同等级的 EventLog + Outbox 原子性

当前 file runtime store 的大致顺序是：

```text
1. write EventLog file
2. project whole log to outbox events
3. append outbox events one by one
```

进程如果在 1 与 3 之间退出，可能出现“交易事实已经持久化，但消息还没进入 outbox”。下一次写入可能通过重新投影补齐，但如果没有下一次写入，就不能称为原子事务。

建议明确分级：

- Files：local/dev/replay；
- SQLite：single-node durable；
- PostgreSQL：production transactional baseline；
- PostgreSQL + NATS：distributed delivery baseline。

不要用一个 `StorageBackend` 枚举掩盖不同 backend 的一致性等级。

`qx-cli/src/main.rs` 当前超过 300KB，直接依赖几乎所有业务 crate，并在一个手写 `std::env::args()` if-chain 里承担：

- demo/backtest；
- API serve；
- supervisor；
- scheduler worker；
- strategy worker；
- paper worker；
- Binance market/user/execution/reconcile；
- CCXT worker；
- private/public probe；
- order submit；
- outbox relay；
- event consumer；
- DLQ replay；
- research/data tools；
- 大量 tests。

V6 已要求“禁止继续往单一 main.rs 堆功能”，当前实际代码仍未完成该收敛。

### 目标

拆成三个产品入口：

```text
qx-node   # 服务节点 / workers / supervisor
qxctl     # operator / diagnostics / submit / reconcile / dlq
qx-lab    # research / fetch / backtest / benchmark / smoke
```

内部再共享 `qx-app`/application services，而不是复制业务流程。

## P1-4：风险系统存在两套语义

`qx-zhenlu` 同时有：

```text
RiskRule + RiskGate
RiskContext::validate_order
```

前者是规则链，后者又独立实现保证金、规格、名义额判定。

长期会出现：回测调用 A、Paper 调用 B、Live 只调用其中一部分。

目标应统一为：

```text
RiskEngine
  ├─ InstrumentRules
  ├─ OrderRules
  ├─ PositionRules
  ├─ AccountMarginRules
  ├─ PortfolioRules
  └─ VenueRules

RiskDecision {
  allowed,
  violations[],
  snapshot_id,
  rule_set_version
}
```

回测/Paper/Live 只允许调用这一入口。

## P1-5：兼容路径过多，正在变成永久双轨系统

当前同时存在：

- research snapshot vs target snapshot / target_qty；
- `qx-oms` vs `qx-zhenlu` re-export；
- Rust native vs JSONL vs framed vs SHM 多条 transport glue；
- CCXT preferred vs Binance direct compatibility；
- file / segmented / sqlite / postgres；
- RiskContext optional vs no-risk basic path。

兼容不是问题，**没有退场日期/门禁才是问题**。

每条兼容路径必须标记：

```text
compat_since
replacement
production_allowed
removal_gate
```

## P1-6：Paper helper 的合成行情语义容易被误用为 Paper 产品能力

`execute_paper_submit_effect_*` 为了 smoke，会按订单限价或固定 100 生成 bid/ask，然后直接驱动 `PaperVenue.on_quote()`。

这是一个很好的确定性测试 helper，但必须改名/隔离，例如：

```text
PaperSmokeExecutor
SyntheticQuoteFixture
```

真正的 Paper Runtime 必须只消费 MarketDataPort 输入，不能在执行服务内部制造行情。

---

## P1-7：RuntimeConfig 仍是“字符串 + optional 字段 + role 分支”模型

当前 WorkerConfig 同时承载不同角色的大量 optional 字段，实际约束散落在：

- RuntimeConfig.validate；
- CLI worker 入口；
- production readiness；
- adapter-specific validation；
- deploy 文档。

推荐使用 tagged config：

```rust
WorkerConfig {
    common: WorkerCommon,
    kind: WorkerKindConfig,
}

enum WorkerKindConfig {
    Api(ApiWorkerConfig),
    Scheduler(SchedulerWorkerConfig),
    Strategy(StrategyWorkerConfig),
    Execution(ExecutionWorkerConfig),
    MarketData(MarketDataWorkerConfig),
    UserStream(UserStreamWorkerConfig),
    Reconciler(ReconcilerWorkerConfig),
    OutboxRelay(OutboxRelayWorkerConfig),
    Consumer(ConsumerWorkerConfig),
}
```

让非法拓扑尽量在反序列化/启动前失败。

## P1-8：默认 feature 与 README/部署能力有认知差异

`qx-cli` 默认 feature 为空：

```text
default = []
sqlite = ...
postgres = ...
nats = ...
```

因此“普通 `cargo run -p qx-cli`”与“生产 SQLite/Postgres/NATS”不是同一个二进制能力集合。

应提供显式产品 feature：

```text
minimal
node-sqlite
node-postgres
node-postgres-nats
all-integrations
```

并由 CI 全部编译/测试。

# 4. 推荐目标架构 V7

## 4.1 目标分层

```text
┌──────────────────────────────────────────────────────────────┐
│ Interfaces                                                   │
│ qx-api / qxctl / qx-lab / Python SDK / C++ SDK              │
└───────────────────────┬──────────────────────────────────────┘
                        │ commands / queries
┌───────────────────────▼──────────────────────────────────────┐
│ Application                                                  │
│ StrategyService / PortfolioService / RiskService             │
│ OrderService / ExecutionService / ReconcileService           │
│ SchedulerService / ControlService                            │
└───────────────────────┬──────────────────────────────────────┘
                        │ domain ports
┌───────────────────────▼──────────────────────────────────────┐
│ Domain Kernel                                                 │
│ identity / clock / event / order / oms / ledger / risk       │
│ trading spec / deterministic replay                          │
└───────────────────────┬──────────────────────────────────────┘
                        │ ports
┌───────────────────────▼──────────────────────────────────────┐
│ Adapters                                                      │
│ Paper / CCXT / Binance / File / SQLite / PostgreSQL / NATS   │
│ HTTP / WS / mTLS / Python process / C ABI / SHM              │
└───────────────────────┬──────────────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────────────┐
│ Runtime                                                       │
│ topology / worker lifecycle / supervisor / health / shutdown │
└──────────────────────────────────────────────────────────────┘
```

## 4.2 核心依赖规则

必须固化为架构测试：

1. `qx-core` 不依赖 runtime/storage/api/adapters；
2. domain 不依赖 concrete storage；
3. application service 依赖 Port，不依赖 concrete `LiveEventPipeline`；
4. adapters 依赖 domain/application contracts；
5. runtime 只装配，不拥有业务规则；
6. CLI/API 只做输入解析、鉴权、调用 application service；
7. 任何 Venue-specific 类型不得进入 core event；
8. Paper/CCXT/Binance 必须通过同一个 Execution contract test。

## 4.3 推荐模块重组

不要求一次性大量改 crate 名，但目标职责如下：

| 目标模块 | 职责 |
|---|---|
| `qx-core` | Fixed numeric、Identity、Clock、Domain Event、TradingSpec |
| `qx-ledger` 或 core/ledger | Ledger / accounting / valuation |
| `qx-oms` | Order aggregate / transition / idempotency |
| `qx-risk` | 统一 RiskEngine / RiskDecision |
| `qx-portfolio` | Signal merge / target / allocation / netting |
| `qx-application` | Use cases：submit/cancel/reconcile/strategy run |
| `qx-execution` | Venue-neutral execution orchestration，只依赖 Ports |
| `qx-market` | MarketData/PIT/Provider contracts |
| `qx-adapter-paper` | PaperVenue + market-driven simulator |
| `qx-adapter-ccxt` | CCXT process/client mapping |
| `qx-adapter-binance` | Direct Binance compatibility |
| `qx-storage` | Port implementations；内部按 event/control/job/outbox 分模块 |
| `qx-runtime` | typed config / workers / supervisor / health |
| `qx-strategy` | Strategy SDK + protocol contracts |
| `qx-plugin` | startup plugin registry；若要通用插件则补 instance factory/runtime |
| `qx-api` | HTTP/WS/mTLS adapter |
| `qx-node` | production service entry |
| `qxctl` | operator CLI |
| `qx-lab` | research/backtest/data/probe |

# 5. 统一主体链路

V7 不再允许 Paper、CCXT、Binance 各维护一套业务流程。

唯一主链：

```text
Trigger / Market Event
        ↓
StrategyContext
        ↓
StrategyDecision
        ↓
Portfolio / Netting
        ↓
OrderIntent
        ↓
RiskEngine.evaluate()
        ↓
RiskDecision(allowed + evidence)
        ↓
ControlCommand / OrderCommand
        ↓
OMS register
        ↓
ExecutionService
        ↓
VenuePort(Paper / CCXT / Binance)
        ↓
ExecutionFact
        ↓
EventAppender
        ↓
Reducer
   ┌────┼──────────┐
   ↓    ↓          ↓
 OMS  Ledger   Read Models
        ↓
ReconcileService
```

区别只能存在于 Port Adapter，不能存在于业务规则。

# 6. 分阶段重构方案

## Phase 0：先建立“可信基线”

### 必做

- 建立 GitHub Actions；
- 对所有 runtime JSON 执行 `runtime-check`；

## Phase 1：拆 God CLI，但不改变业务语义

# 7. 验收门禁

以后“功能已实现”必须同时满足实现与 gate。

## G0：代码质量

- fmt；
- clippy；
- dependency audit；
- forbidden dependency/layer test。

## G1：确定性

- same input → same event hash；
- parameter/data change → hash changes；
- no future data；
- fixed seed；
- stable replay across restart。

## G2：领域契约

- Order state transitions；
- Ledger conservation；
- derivative accounting；
- margin/funding；
- risk reject-before-side-effect。

## G3：Paper E2E

同一 CI run 必须真实执行：

```text
Scheduler
→ Strategy
→ Queue
→ Execution
→ Market Event
→ Fill
→ EventLog
→ Ledger
→ Restart
→ Reconcile
```

不允许用一个函数直接跳过中间组件。

## G4：Persistence

Files / SQLite / PostgreSQL 分开测试，不共享“绿色即等价”的结论。

必须包含：

- crash during append；
- lease takeover；
- stale fencing rejection；
- duplicate delivery；
- event/outbox atomicity；
- snapshot/replay equivalence。

## G5：Connector Contract

每个 Venue adapter 运行同一套 contract tests。

外部 sandbox 结果独立标记：

```text
code-tested
sandbox-tested
production-approved
```

三者禁止混用。

## G6：Release

一个 Release SHA 必须同时满足：

- Rust default + all feature matrix；
- Linux/macOS/Windows；
- Python wheel；
- C++ smoke；
- Paper E2E；
- process recovery；
- runtime config validation；
- Postgres/NATS integration（对应 release profile）；
- artifact SBOM/checksum/signature。

# 9. 推荐立即执行顺序

按风险和收益排序，不建议再继续横向加功能：

5. **拆 qx-cli God Binary**；

9. **PostgreSQL Event+Outbox 作为生产事务基线**；
10. **研究快照彻底替代生产 target 兼容路径**；

# 10. 本轮不建议做的事情

- 不继续新增更多交易所直连协议，先统一已有执行链；
- 不把所有 crate 再拆成更多小 crate，先解决依赖方向；
- 不为了“架构漂亮”重写已稳定的 qx-core；
- 不把 file backend 包装成分布式生产能力；
- 不因为已有接口就把功能状态改成 complete；
- 不在没有 CI 之前继续扩大“当前状态已完成”清单；
- 不同时大改领域模型、存储和适配器，必须分阶段保持可回归。

# 11. 最终判断

## 哪些已经做得比较好

- 确定性和可重放是从底层模型开始设计，而不是后补；
- `TradingInstrumentSpec`、事件事实、未知下单结果、ReconcileRequired 等设计方向正确；
- OMS/Ledger/Execution/Paper/CCXT/Binance 都不是空接口；
- 已意识到 PIT、研究血缘、账户隔离、fencing、Outbox、DLQ、mTLS 等生产问题；
- 多语言策略已经有可执行边界，不只是 SDK 设想。

## 当前最主要的问题

不是“缺少更多功能”，而是：

> **功能增长速度已经超过架构收敛、持续验证和发布证明的速度。**

因此 V7 的核心策略是：

```text
停止横向扩功能
→ 修真实断链
→ 建 CI
→ 收敛唯一主链
→ 统一风险/执行
→ 反转依赖
→ 分级存储语义
→ 建立正式验收
→ 再扩展生产能力
```

只有完成上述收敛，才能把当前的“代码量很大、能力很多”升级为“主体链路可证明贯通、核心能力可持续发布”。
