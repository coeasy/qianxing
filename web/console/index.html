这一页是静态件，本身不带凭据：它没有自己的 CSRF token、服务端会话或权限代理， 因此单独打开时连接入口只允许 127.0.0.1 / localhost，不能连接远端 API。 要同源形态（服务端会话 + CSRF 双提交 + 身份注入，浏览器只跟一个源说话）就用 qx-cli console <runtime.json>——它在回环地址上同时发这一页并代理 API， 凭据全留在服务端。 写面只有一条：本页的读面板全部只做查询，唯一的写操作是 POST /control/commands（控制面受理入口）。它不直接下单—— 下单要走这条命令，由控制面受理 → 判定执行者 → 走到终态退场。 身份边界：operator_id 是审计字段，启用访问策略的部署里由 mTLS 认证边界覆盖， 页面不能自声明身份（那时会回 403 authenticated_operator_required）。 跨源读取必须在部署配置的 api.cors_allowed_origins 里逐字符登记本源 （如 http://127.0.0.1:8080），否则浏览器会在 CORS 处拦下—— 这不是服务端故障。API 服务用 qx-cli serve <runtime.json> 启动。 同源 BFF 形态（qx-cli console）另有两条差异：写面要按双提交带 X-QX-CSRF（那一枚 cookie 刻意不是 HttpOnly，页面读它就是为了回填请求头）， 且 Origin 必须等于 Host；BFF 只代理 HTTP 请求， 不转发 WebSocket 升级，因此该形态下实时面退化为 5 秒轮询，页面会如实标成 「不适用」而不是「已连接」。
